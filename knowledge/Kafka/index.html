Kafka知识地图

来源

基于 Kafka 4.x 官方文档与源码整理。文中所有配置默认值均标注适用版本，跨版本请以你所用版本的官方文档为准。 本页是全库唯一入口，不引入正文之外的结论——每条结论都能沿双链回到出处。

本页覆盖 Kafka 4.x 的架构、存储、生产、消费、可靠性、高可用运维与面试应答七个主题，共 20 篇笔记（1 张根地图 + 7 张索引页 + 12 篇正文）。基线是「KRaft 已是唯一元数据协调模式」的 4.x；ZooKeeper 时代做法只作为存量系统对照，保留在正文的 warning callout 中，不作为主线叙述。

版本口径与阅读约定

本库所有结论按三档标注可信度，写作时不允许把 B/C 档的具体数字写成确定值。

档位含义允许的写法
A有官方文档明文，或版本变更记录明文可写具体数值，并标注适用版本
B官方文档给了语义但未给数值，或数值随版本漂移只写语义，注明「默认值随版本变化，以你所用版本的官方文档为准」
C来自社区实践、源码阅读或推断只写结论方向，不写数值，并说明这是实践口径

旧机制的统一处理：Kafka 3.x 的 ZooKeeper 协调不删减，但一律放进 > [!warning] 旧版做法（ZooKeeper 时代） callout，且新版做法在前、旧版在后。存量系统仍需维护，面试也可能问到，但它不作为 4.x 的主线叙述。

配置默认值必须标注适用版本，例如 linger.ms 默认 5ms（Kafka ≥ 4.0；4.0 之前为 0）。凡未标注版本的数字，视为误写。

概念在两版间发生实质变化时，正文必须写出「此机制为旧版，新版由 ⟨具体替代物名称⟩ 替代」，不留抽象占位词——例如 ZooKeeper 协调在 4.x 由 KRaft 替代。

全库主线

主线的因果是单向的：写入端的 幂等、acks 与事务 决定 Broker 端 复制模型与 ISR 的容错上界，而消费端「处理与提交的先后」又把副本保证翻译成端到端的 投递语义与消息去重。运维层不引入新概念，只把前面每一环的失败模式变成可观测指标与处置动作。

推荐学习路线

阶段读什么为什么是这个顺序
第 1 轮 · 地基Kafka 架构全景与角色分工先立坐标系。分区为什么是并行最小单位、为什么单 Leader 追加写，这两条不立住，后面所有参数都没有挂靠点
第 2 轮 · 存储分区日志与稀疏索引 → 零拷贝、页缓存与保留策略架构讲数据模型，存储讲这份数据怎么变成文件。顺序写与零拷贝是吞吐的结构性来源，不是调优出来的
第 3 轮 · 两端分区选择、批量与压缩 → 幂等、acks 与事务 → 消费组、位点提交与 Rebalance → 顺序消费与积压处理生产与消费是一对约束。分区数同时限制生产与消费的并行度，acks 与提交时机共同决定语义，必须对照读
第 4 轮 · 可靠性收口复制模型与 ISR → 投递语义与消息去重前三轮的机制在这里合成可对外承诺的语义。「副本够不够」与「语义给什么」是两个问题，混答就答不完整
第 5 轮 · 运维落地KRaft 协调与选主 → Kafka 监控与排障只会原理不会定位等于不会。把每个机制对应到指标与命令
第 6 轮 · 冲刺Kafka 面试速查总表不重新通读，按主题回扫，用答题结构查漏

第 3 轮刻意画成分叉：生产侧与消费侧不分先后读完，因为 分区选择、批量与压缩 里的分区数假设，要靠 消费组、位点提交与 Rebalance 里的分区独占分配才能验证。

默认值口径

写具体数字前先确认它是不是 A 级事实。以下四类必须查你所用版本的官方文档：Broker 端 log.retention.* 与 num.partitions、Producer 的 linger.ms（4.0 起由 0 改为 5）、Consumer 的 session.timeout.ms 与 max.partition.fetch.bytes、以及任何与 acks 相关的集群级搭配。本页不给这些数字兜底，正是为了避免把某一版本的取值写死成「标准答案」。

与 RocketMQ 对照速查

两者都常被归为「消息中间件」，但在最根本的三件事上相反：元数据协调、存储单元、消费模型。被追问「这两个有什么区别」时，下面这张表是骨架。

维度Kafka 4.xRocketMQ 5.x
元数据协调KRaft（Controller Quorum，RAFT 共识）NameServer（无状态，双 master 互备）
存储单元每个分区一个独立日志段全部 Topic 共用单一 CommitLog
消费模型消费者组 + 分区独占集群 / 广播消费模式 + 队列
事务事务生产者（read_committed 读）事务消息（half 消息 + 回查）
延时消息不原生支持原生支持（5.x 定时器）
消息过滤不支持（需应用侧或 Kafka Streams）Tag + SQL92，Broker 端过滤
顺序保证分区内有序队列内有序
消息堆积靠消费者扩容靠消费者扩容
