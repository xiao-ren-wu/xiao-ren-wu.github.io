投递语义与消息去重

来源

基于 Kafka 4.x 官方文档（producer-configs、consumer-configs、operations/monitoring）与源码（ProducerConfig.java、ConsumerConfig.java）整理。文中未标注 ⚠️ 的结论可直接用于面试应答。

本篇解决一个具体问题：一条消息从生产到消费完成，会在哪些环节被丢、被重，以及哪些重复是 Kafka 原理上必然产生、必须由业务兜底的。凡涉及默认值但官方页面未给出干净对照值的配置，本文只写语义与影响。

一、三种投递语义的准确含义与判定标准

判定投递语义只需要问两个问题：会丢吗？会重吗？

语义会丢吗会重吗判定口径靠什么实现
at-most-once（至多一次）会不会位点提交早于业务处理完成提交位点后再处理，或生产端不等待任何确认
at-least-once（至少一次）不会会位点提交晚于业务处理完成先处理后提交位点，生产端允许重试
exactly-once（恰好一次）不会不会重复与丢失都被机制挡住幂等生产者 + 事务 + read_committed；跨出 Kafka 需业务去重

必须先说一句容易被跳过的话：「exactly-once」永远是「在某个边界内」的 exactly-once。 谈语义不谈边界，等于没谈。Kafka 官方对 exactly-once 的表述本身就是「Kafka 内部链路上的有效 exactly-once」，一旦消息要写进 MySQL、调第三方 HTTP 接口、或进入另一套 MQ，这个承诺就失效了。边界在哪，是本篇第二节和第六节要展开的核心。

二、语义是组合出来的：生产端 × 消费端

Kafka 不提供一个总开关决定「我的语义是 at-least-once」。实际语义是生产端动作与消费端动作的组合结果。

生产端侧：

生产端配置Broker 侧持久性重试时会不会产生重复备注
最低档 acks（不等待任何确认就返回）只在 Leader 缓冲，失败对客户端不可知不会（因为它不重试）会丢，而且丢了你也不知道
只等 Leader 确认Leader 写成功即返回会客户端超时重试 = 同一逻辑消息两条记录
等全部 ISR 确认（acks=all / -1）Leader + 多数派副本会持久性最强，但重试重复依然存在
开启幂等 + 等全部 ISR 确认同上不会Broker 端按 PID + 序列号去重
事务生产者同上不会（Kafka 内部链路）多个分区的写入成为原子操作

补充

acks 的默认值口径 acks 的默认值随版本变化，本库不给数字，以你所用版本的官方文档为准。上表的「三档」只表达可靠性与吞吐的方向性阶梯：档位越高越持久、吞吐越低。

消费端侧：

消费端行为位点提交时机崩溃或重启的后果综合语义
先提交位点，后处理处理之前位点已过，消息不再投递at-most-once
先处理，后提交位点处理之后位点未过，重启后重复投递at-least-once
处理与提交位点放进同一事务与输出消息同一事务事务回滚则两者都不生效exactly-once（仅 Kafka 内）
先处理后提交，另有业务去重兜底处理之后重复投递但业务无感端到端 effectively-once

组合矩阵（这张表才是回答「我的系统是什么语义」的正确方式）：

生产端消费端综合语义典型用途
不等待确认任意at-most-once，且失败对端不可知埋点、指标，允许丢
等 ISR + 重试，无幂等先处理后提交at-least-once绝大多数传统业务场景
等 ISR + 幂等 + 重试先处理后提交at-least-once（重复只可能来自消费端）推荐的默认起点
幂等 + 事务read_committed + 位点与处理同一事务exactly-once（Kafka 到 Kafka）Kafka 内部流处理
任意业务幂等键或去重表端到端 effectively-once写数据库、调外部 API

三、为什么 Kafka 的默认路径是 at-least-once

根因是：位点提交与业务处理是两次落在不同系统上的操作。 位点提交写进 Broker 的 __consumer_offsets，业务处理写进用户代码或数据库，这两者之间没有共同的原子性保证。

Kafka 官方 consumer-configs 中 enable.auto.commit 的默认值是 true。在这种模式下，位点由客户端按周期自动提交，提交点与业务处理进度没有任何绑定关系。无论提交点落在处理进度之前还是之后，客户端都无法保证「已提交位点 == 业务已完成位置」。

Kafka 选择 at-least-once 这个方向是一次有意的工程取舍：重复可以在业务侧去重，丢失无法恢复。 一个能被幂等键挡住的重复，和一笔凭空消失的订单，代价完全不对等。

面试追问：为什么 Kafka 不做端到端 exactly-once 而默认 at-least-once？

因为它做不到。事务协调器只能协调「同一个 Kafka 集群内、由同一个事务发起的写入」，协调不到外部数据库的提交，也协调不到第三方接口的调用结果。要做端到端 exactly-once，就得引入两阶段提交或外挂一套幂等设施，两者都带来 Kafka 之外的新成本和新的失败模式。Kafka 的选择是把边界划清楚：集群内给 exactly-once，集群外交给使用者。

四、重复从哪来：五个具体场景

场景一：生产端重试。 网络超时或 Leader 切换让生产者无法判断上次写入是否成功，于是重投，同一逻辑消息落了两条。这是唯一被幂等生产者覆盖的重复来源。

场景二：处理完成、提交位点之前崩溃。 业务逻辑已经执行（订单已扣款），但位点还没提交，进程重启后从上次位点重新消费。这是 at-least-once 的主要重复来源，也是 enable.auto.commit=true 时最容易被忽略的风险。

场景三：Rebalance 中途被踢出组。 max.poll.interval.ms（客户端两次 poll() 之间的最大间隔）在官方 consumer-configs 中核对值为 300000（5 分钟）。如果一批消息处理超过这个间隔（典型触发：单批消息量大叠加下游 RPC 慢），成员会被判定为失效并移出消费组，分区转交给新成员，新成员从上次已提交位点重新开始，于是重复。这不是 bug，是防止「僵尸消费者」卡住整个分区的正常机制。

*脚注：max.poll.interval.ms 的核对来源为 Kafka 3.4 文档页。本库基线为 Kafka 4.x，跨小版本使用前请以所用版本官方文档为准。

场景四：unclean 选举导致的状态跳变。 这里要精确一点：unclean 选举造成的是丢失而不是重复。落后副本当上 Leader 后，它没有的那些消息永久消失；业务侧看到的现象是「上一条还是状态 A，下一条直接跳到状态 C」，很容易被误判为重复处理的副作用。它出现在重复排查清单里，是因为排查时需要先排除它，否则会一直在消费端找不存在的问题。

场景五：日志 compact 的边界。 日志压缩是按消息 key 保留最新值的清理策略，它删除旧记录而不产生重复。真正让人误以为「有重复」的是两种情况：同一条业务事件用了不同的 key（压缩无法折叠，于是看起来像重复），以及压缩是段级、后台异步执行的，删除有延迟，短时间内旧值仍在日志里。

五、幂等生产者解决了什么、没解决什么

机制：Broker 为每个生产者分配一个 PID（producer ID），生产者对每个分区维护单调递增的序列号。Broker 侧按「PID + 分区」记住已见的最大序列号：重复的序列号被丢弃，出现更大的序列号则接受。由此，重试产生的重复写入在 Broker 侧被自动去重。

  • enable.idempotence 在 Kafka 3.0 起默认值改为 true（ProducerConfig.java 的 ConfigDef），本库基线 4.x 沿用这一默认行为。
  • 幂等开启时 max.in.flight.requests.per.connection 被硬校验为不超过 5，超出直接抛 ConfigException（ProducerConfig.java 校验逻辑）。
  • 幂等开启要求 retries 大于 0；配置互相冲突时幂等会被静默禁用（Kafka 4.0 官方 producer-configs）。这是一个很坑的细节：排查「为什么没去重」时，要先确认幂等确实处于启用状态。
重复来源幂等生产者是否覆盖
生产端重试导致同一逻辑消息落两条覆盖
消费者处理完、提交位点前崩溃不覆盖
Rebalance 中途被踢出组不覆盖
unclean 选举导致的状态跳变不覆盖（且它是丢失不是重复）
业务自己发了两条语义相同的消息不覆盖

另外两个作用域限制必须记住：

  1. 只覆盖同一个生产者会话。 PID 会随生产者进程重启、显式 close()、或超过 delivery.timeout.ms（Kafka 4.0 官方 producer-configs 核对值 120000，即 2 分钟）而变化，Broker 侧的去重状态随之重置。
  2. 只覆盖单分区内。 序列号是每个分区独立的，所以幂等提供的是「同一分区内，幂等重试不会重复也不会乱序」，而不是跨分区的全局有序。

面试追问：幂等生产者开启后，消费端还会重复吗？

会。幂等只在生产端生效，它保证「同一条逻辑消息不会因为重试在 Broker 里存两份」。但消费端「业务处理完成、位点提交之前崩溃」这个窗口产生的重复，与生产端完全无关，仍然存在。这也是为什么生产系统的标准做法是「幂等生产者 + 业务幂等键」双保险，而不是只开幂等。

六、exactly-once 的三件套与作用域边界

三件套，缺一不可：

  1. 幂等生产者：消除生产端重试产生的重复。
  2. 事务生产者（配置 transactional.id）：把「写入多个分区」变成原子操作；未提交的事务消息对消费者不可见。transactional.id 与 transaction.timeout.ms 的默认值随版本变化，以你所用版本官方文档为准。
  3. 消费端 isolation.level=read_committed：Kafka 官方 consumer-configs 中该配置默认值是 read_uncommitted，合法值为 read_committed 与 read_uncommitted。只有显式设为 read_committed 才启用。

read_committed 有一个必须知道的代价。 官方文档明确：它的读取上界是 LSO（Last Stable Offset，第一个未完成事务的 offset 减一），而不是 HW。有在途事务时，read_committed 消费者读不到 high watermark，事务后面的消息会被扣住。所以一个长事务会直接压低消费可见度，这是 exactly-once 的吞吐代价。官方同时说明：非事务消息在两种隔离级别下都无条件返回，只有事务消息才受提交状态约束。

原子性如何跨到消费端：客户端提供把「消费位点提交」与「本批输出消息」放进同一事务的接口（sendOffsetsToTransaction）。这样崩溃时要么两者都成功，要么一起回滚，消费后再生产的链路不会重复。

边界exactly-once 是否成立
Kafka → Kafka（同一事务内）成立，这是官方承诺的范围
Kafka → 外部数据库不成立，事务协调器管不到数据库提交
Kafka → 第三方 HTTP API不成立
Kafka → 另一套 MQ不成立

七、端到端去重的三种模式对比

模式做法覆盖范围性能代价复杂度适合
业务幂等键 + 唯一约束用业务唯一键（订单号）做唯一索引，重复插入被数据库拒绝全部重复来源一次唯一索引开销低写数据库场景几乎必选
inbox / 去重表独立表存「已处理消息标识」，配合 TTL 定期清理全部重复来源，含跨系统一次插入 + 一次清理中需要跨系统判定、消息量大
read_committed + 事务生产者Kafka 内部链路去重仅 Kafka 到 Kafka事务协调开销 + LSO 阻塞中高Kafka 内部流处理

三者不互斥。生产上常见的组合是「幂等/事务生产者 + read_committed」消掉 Kafka 内的重复，再用「业务幂等键」兜住跨系统边界。

inbox 表设计的三个要点：

  1. 去重键的粒度。 优先用业务唯一键（订单号），而不是消息字节的哈希值。哈希值会随序列化格式、字段顺序、版本升级而变化，一旦变化，去重就静默失效，而且很难发现。
  2. TTL 必须有。 去重表无限增长会变成新的故障源。保留窗口要大于系统可能的最大重放时长，包含消息保留期加上最长故障恢复时间。
  3. 去重表与业务写入必须同一事务。 否则会制造出「去重记录写了、业务没写」这种新的不一致，重复消息被吃掉但业务没生效。

八、面试高频追问

  1. Kafka 能保证 exactly-once 吗？ 只能说「在 Kafka 边界内可以」。三件套是幂等生产者 + 事务生产者 + 消费端 read_committed，这样 Kafka 到 Kafka 的消费后再生产链路不重不丢。但只要下一跳是数据库、第三方接口或另一套 MQ，这个承诺就终止，需要业务幂等兜底。答题时先说边界再说机制，否则会被追问打穿。

  2. at-least-once 到底是谁决定的，是 Kafka 还是我的应用？ 由应用决定。Kafka 只提供动作原语，语义取决于两个选择：消费端是「先处理后提交位点」还是「先提交后处理」，生产端是否允许重试。前者决定会不会重，后者决定会不会丢。enable.auto.commit 默认 true 时提交点与处理进度无绑定，语义尤其不可控。

  3. 幂等生产者能保证顺序吗？ 只保证单分区内有序。序列号是每个分区独立的，跨分区仍是并行写入，没有全局顺序保证。max.in.flight.requests.per.connection 在幂等开启时被硬校验为不超过 5，正是为了保证在途请求乱序到达时 Broker 能按序列号还原顺序。

  4. read_committed 有什么副作用？ 吞吐与可见度双重代价。读取上界从 HW 降为 LSO，有在途事务时消费者读不到 HW，长事务会直接压低消费可见度；事务协调本身也带来额外开销。所以它适合 Kafka 内部流处理，不适合对吞吐敏感的大流量场景。

  5. 消费端自动提交为什么危险？ 因为提交点与业务处理进度没有绑定。自动提交按周期推进，可能把尚未处理完的消息标记为已消费（丢），也可能在处理完成后尚未提交时崩溃（重）。需要严格语义时必须关闭自动提交，改为处理完成后手动提交。

  6. Rebalance 期间的消息会重复吗？ 会。成员被移出组后分区转交他人，新成员从上次已提交位点开始消费，所以已经处理但未提交的那批消息会被重新投递。触发原因最常见的是单批消息处理时间超过 max.poll.interval.ms。缓解手段是控制单批处理耗时、把耗时工作异步化，或改用协作式分配减少停机范围。

  7. 幂等加事务能不能替代业务去重？ 不能。两者覆盖的重复来源不同。幂等只管生产端重试，事务只管 Kafka 内部链路，位点提交窗口的重复和跨系统重复都在它们的覆盖范围之外。写外部数据库的场景，业务幂等键是必需项而不是可选项。
