分区日志与稀疏索引

来源

基于 Kafka 4.x 官方文档整理。文中所有默认值均已标注适用版本 Kafka 4.x，跨版本请以你所用版本的官方文档为准。 本篇文件名以「索引」结尾，但它是正文而不是索引页（MOC）；本库的 MOC 统一为 Kafka <主题>索引.md，MOC 负责导航与学习顺序，细节全部留给正文。

一句话回答「Kafka 怎么把消息存下来、消费者又怎么按 offset 找回来」：Broker 把每个分区的数据写成一串以 offset 命名的段文件，每个段文件旁边配一个按固定字节间隔采样的稀疏索引。写入永远只有追加，查询则分三步：先二分定位到段文件，再二分定位到段内物理位置，最后顺序扫一小段字节流。

一、为什么用追加写日志

Kafka 的存储层只提供一种写操作：往分区的末尾追加。它不支持原地更新，也不支持随机插入。这个限制换来的是三样东西。

维度追加写随机更新
磁盘访问模式顺序随机寻道
吞吐上限由带宽决定由 IOPS 决定
索引维护索引可批量追加每次更新都要改索引
崩溃恢复扫文件尾部即可需要日志式回滚

第一，顺序写是磁盘最便宜的工作模式。机械磁盘寻道的代价是随机访问比顺序访问慢一到两个数量级；SSD 没有寻道，但内部仍有通道、缓存和 wear leveling，顺序写仍然是延迟最稳定、最可预测的模式。Kafka 把消息大小交由生产者批量控制，落到磁盘就是一串大块的顺序写，正好踩在磁盘最舒服的区间上。

第二，顺序写让 offset 变成「自描述」的位置。官方 Log 文档对 offset 的定义是：64 位整数，表示消息在「该 topic 该分区历史全部消息流」中的字节位置。也就是说 offset 本身就是位置，不需要再查一张映射表把 ID 翻成地址。这是一次非常划算的简化，早期设计里曾考虑用 GUID 加一张需要与磁盘同步的随机访问索引，最终放弃了，原因就是维护那张表的成本远高于用一个单调递增计数器。

第三，单调递增天然等于有序。消费者按 offset 递增拉取，就自动得到了分区内的全序。Kafka 不需要额外维护排序结构，顺序是追加这个动作的副产品。

关键点

「不修改已有消息」这条约束是后面所有机制的根因。因为不能改，删除只能是追加墓碑或整段删文件（见 零拷贝、页缓存与保留策略），因为不能改，定位只能靠采样索引而不能靠稠密索引，因为不能改，复制协议要防的也只有尾部截断这一种破坏。

面试追问：为什么 Kafka 用追加写，而不是像数据库那样原地更新？

答题骨架：数据库的更新是随机写，代价在寻道和索引维护；Kafka 的场景是日志流，读多写少且按顺序消费，因此把写入优化成纯追加、把所有复杂度挪到「追加流 + 后台整理」上。追加写换来顺序吞吐、offset 自描述、天然有序三个好处，代价是删除变粗粒度、不能改单条消息。

二、分区目录与段文件的物理结构

一个 topic 的每个分区在磁盘上就是一个独立目录，目录名是 topicName-分区号，例如 topic my-topic 的两个分区对应 my-topic-0 和 my-topic-1。目录里的文件是段：

文件内容说明
*.log段数据以该段首条消息的 offset 命名，首个文件恒为 00000000000000000000.log
*.index稀疏位置索引每隔固定字节数记一条「offset 到物理位置」
*.timeindex稀疏时间索引每隔固定字节数记一条「最大时间戳到 offset」
*.snapshot领导者纪元检查点用于截断后阻止旧领导者继续写入

段文件名是 offset，不是行号、不是序号、不是时间戳。第二个文件的数字是「这个段里第一条消息的 offset」，所以从一个段文件名就能立刻算出这段覆盖的 offset 区间起点，这也是按 offset 定位时能直接跳过整个文件的原因。

段文件在三种情况下滚动，Kafka 4.x 的默认值都写在 topic 级配置里：

触发条件Kafka 4.x 默认值含义
segment.bytes1073741824（1 GiB）活跃段写满就切新段
segment.ms604800000（7 天）即使没写满，到期也切
segment.jitter.ms0默认不人为抖动切分时间

segment.ms 存在的理由常被忽略。官方 topic 级文档的解释是：即使段没写满也强制滚动，这样保留策略才能删到或压到旧数据。如果只有大小触发条件，一个迟迟写不满的段会把最老的一条消息无限期地吊住，保留策略对段内所有消息都失效。

为什么一个分区不是一个文件，而是很多段？ 四个原因，每一条都指向清理：

  1. 清理只能整文件做。官方 Log 文档明确「数据一次删一个段」。删除是 unlink，是 O(1) 的元数据操作；如果整个分区一个文件，删一条过期消息就得重写整个文件。
  2. 压实需要能跳过的单位。compact 时可以直接跳过已经压实干净、且不再承载新写入的段，段是压实调度的天然工作单元。
  3. 文件描述符和元数据有上限。一个分区几万个段是可接受的，一个分区一个几 TB 的文件则会让恢复时间不可控。
  4. 段的滚动与 acks 无关。切段是纯粹的元数据事件，不会打断正在写的前后文件。

关键点

段的滚动与删除都不是「立刻」发生的事。可删判断由 cleaner 定期轮询（Kafka 4.x 下log.retention.check.interval.ms 为 300000，即 5 分钟，且是 read-only），从判定为可删到真正 unlink 之间还有 file.delete.delay.ms（Kafka 4.x 为 60000，即 1 分钟）的缓冲。这两个延迟合起来解释了为什么磁盘水位会先于配置值升高。

面试追问：为什么不是每个分区一个文件？

答题骨架：因为删除的最小单位是文件，保留策略必须以文件为粒度生效；分小段把「按时间删」变成几次 unlink，把「压实」变成可增量推进的单元，同时让恢复和文件句柄规模可控。代价是文件数量变多，元数据操作变多。

三、消息在段文件中的物理布局

段文件里不是一行一条消息，而是一串 record batch。每个 batch 有 61 字节左右的固定头部（不含 8 字节 baseOffset 之外的变长部分），头部全部采用定长定序字段，因此可以在不解析业务内容的情况下快速读出定位所需的信息。

字段类型定位与校验中的作用
baseOffsetint64本批第一条消息的 offset
batchLengthint32从该字段之后到批末尾的字节数
partitionLeaderEpochint32领导者纪元，不参与 CRC
magicint8消息格式版本，当前为 2
crcuint32CRC-32C，覆盖 attributes 到批尾
attributesint16bit 0~2 压缩算法；bit 3 时间戳类型；bit 4 事务标记；bit 5 控制批次；bit 6 压实删除视界
lastOffsetDeltaint32本批最后一条消息相对 baseOffset 的增量
baseTimestampint64批内第一条消息的时间戳
maxTimestampint64批内最大时间戳，压实与时间保留都看它
producerIdint64幂等生产者标识
producerEpochint16幂等生产者的纪元
baseSequenceint32幂等序列号
recordsCountint32批内消息条数

由此可以直接推出三条高频面试结论。

第一，lastOffsetDelta 给出批的 offset 区间。 一批覆盖的 offset 是闭区间 [baseOffset, baseOffset + lastOffsetDelta]。只要读到这个字段，就已经知道目标 offset 在不在这一批里，不需要解压批内的任何数据。

第二，整批磁盘大小等于 batchLength + 12 字节。 加的 12 字节是 baseOffset 的 8 字节加 batchLength 自身的 4 字节，因为 batchLength 计数起点在它后面。读到长度就能直接跳到下一批，不需要扫描填充。

第三，压缩数据在批头之后，批头本身不压缩。 attributes 里的 bit 0~2 指明压缩算法，0 无、1 gzip、2 snappy、3 lz4、4 zstd。记录区的字节是整块压缩的，但批头是明文。这意味着即使一个段里的数据全是压缩的，索引依然可读，定位依然不需要解压。这是压缩与稀疏索引能共存的技术前提。

批内单条记录的格式则全是变长编码，这也是为什么无法按 offset 直接算地址：

字段类型
lengthvarint
attributesint8
timestampDeltavarlong
offsetDeltavarint
keyLength / keyvarint / byte[]
valueLength / valuevarint / byte[]
headersCount / headersvarint / [Header]

length 是相对长度而不是「到文件某处的绝对偏移」，所以记录是不可原地寻址的。给定 offset 无法反推出文件位置，必须借助索引。

关键点

批头在压缩区之外这件事还有一个连带影响：Broker 校验一个 batch 时会先解压记录区，确认recordsCount 与实际条数一致，然后以压缩形式原样落盘。批在整个生命周期里保持压缩状态，跨网络传输时也不需要解压重压。

面试追问：批头里 partitionLeaderEpoch 为什么不计入 CRC？

答题骨架：Broker 收到 Produce 请求后要给每个 batch 填上当前的领导者纪元，这个字段是被 Broker 改写的。如果它计入 CRC，Broker 每改一次就得整批重算校验和，抵消了批量校验的意义。官方 message-format 文档明确说明这一取舍。CRC 只覆盖 attributes 及其之后的部分，也就是除 baseOffset、batchLength、partitionLeaderEpoch、magic 之外的批内数据。

四、稀疏索引与二分查找

.index 文件里的每一条记录只有两个定长字段：

字段类型含义
relativeOffsetint64索引采样点的 offset，相对段起点
physicalPositionint32该采样点在段文件内的字节偏移

关键在于它不是每条消息一条，而是每 index.interval.bytes 字节才记一条。Kafka 4.x 下这个值是 4096，即 4 KiB；官方 topic 级文档的原话是「大约每 4096 字节索引一条消息」。段索引文件的预分配上限是 segment.index.bytes，Kafka 4.x 下为 10485760（10 MiB）。

为什么要故意做稀疏？ 三个理由，都是权衡而不是缺陷：

  1. 索引可以整段常驻内存。10 MiB 上限意味着一个段的索引可以全部 mmap 进内存并长期驻留，而不需要在磁盘上做随机读。如果每条消息一条索引，索引体积会逼近数据体积，内存就装不下了。
  2. 写路径不被索引打断。稠密索引意味着每写一条消息就要更新一条索引，索引文件变成第二个随机写热点，顺序写就退化成了两次顺序写交织的随机写。稀疏索引的写入被摊薄到批次粒度，可以和日志一起顺序追加。
  3. 顺序扫的代价有上界。定位误差最多是一次采样间隔的字节数，而采样间隔是配置项，可以按磁盘和内存情况调。

权衡表：

调整方向顺序扫字节数索引体积写路径干扰内存占用
间隔调小变小变大变大变大
间隔调大变大变小变小变小

timeindex 是同一套思路的时间维版本，字段是「maxTimestamp + offset」，采样间隔比位置索引更稀疏，因此体积更小。它服务的是「给我某个时间点之后的第一个 offset」这类查询，比如消费者要跳到最近一小时的数据。它和位置索引的关键差别在于，段的时间保留时间由段内最大时间戳决定，与记录顺序无关，所以时间索引天然是稀疏的。

五、offset 到物理位置的定位流程

这是本篇的核心，值得拆成可复述的四步。

第一步：全局 offset 定位段文件。 每个段的 .index 里第一个 relativeOffset 就是该段的首 offset，且段文件名本身就是这个值。维护一份「段首 offset 有序列表」，对目标 offset 做二分，找到段首 offset 小于等于目标的最大那个段。如果目标小于最小的段首 offset，就是越界，消费者会收到 OutOfRangeException；如果目标大于当前日志末尾的 offset，就是还没写入。

第二步：段内 offset 定位物理位置。 把目标 offset 转成相对值，在该段的 .index 里二分，找 relativeOffset 小于等于目标的最大那条，得到 physicalPosition。

第三步：顺序扫描小段字节流。 从 physicalPosition 顺序读，每次读 12 字节拿到 baseOffset 和 batchLength，再用 batchLength 跳到下一批，逐批检查 baseOffset 是否小于等于目标且 baseOffset + lastOffsetDelta 大于等于目标。命中即停。

第四步：批内定位。 命中批后，算 offsetDelta = 目标 - baseOffset，解压该批，在记录序列里按 offsetDelta 找到目标记录。

用具体数字走一遍。 段文件 00000000000000000000.log，段首 offset 为 0。假设每批 8 条记录、每条 1 KiB，即每批 8 KiB。批间隔 8 KiB 大于采样间隔 4 KiB，所以每个批起点都会产生一条索引项：

索引项覆盖字节区间对应批的 offset 区间
(0, 0)0 ~ 81910 ~ 7
(8, 8192)8192 ~ 163838 ~ 15
(16, 16384)16384 ~ 2457516 ~ 23
(24, 24576)24576 ~ 3276724 ~ 31
(32, 32768)32768 ~ 4095932 ~ 39

要读 offset 20：

  • 第一步：段首 offset 列表里最大的小于等于 20 的值是 0，命中第一个段。
  • 第二步：目标相对值 20，.index 里最大的 relativeOffset 小于等于 20 的是 16，物理位置 16384。
  • 第三步：读 16384 处的批头，得到 baseOffset = 16、lastOffsetDelta = 7，覆盖 16 ~ 23，20 落在区间内，额外顺序扫描 0 字节。
  • 第四步：offsetDelta = 20 - 16 = 4，即批内第 5 条记录，物理位置是段文件内偏移 16384 加上该批内偏移。

现在把采样间隔改成 64 KiB 试一次。索引项变成 (0, 0)、(64, 65536)、(128, 131072)，中间没有别的项。要读 offset 20，第二步会命中 (0, 0)，物理位置 0，然后必须顺序扫过 16384 字节才能读到 baseOffset = 16 的批头。定位代价从 0 字节变成 16 KiB，恰好是索引稀疏程度的三倍左右。

索引不是 O(1)。 完整代价是 O(log(索引项数)) 的内存二分，加上 O(采样间隔 / 平均批大小) 个批头的顺序读。上面第一个例子里顺序扫 0 字节，不是因为定位是常数时间，而是因为批大小 8 KiB 大于采样间隔 4 KiB，索引必然落在批边界上。真正的扫描上界是 min(采样间隔, 平均批大小)，想让定位稳定在一个批以内，就把采样间隔设得不大于平均批大小。

客户端从不接触物理位置。 Fetch 请求里带的是逻辑 offset 和最大拉取字节数，段定位、索引二分、批头扫描、解压定位全部在 Broker 侧完成，客户端拿到的已经是按序排好的字节流。所以换句话说，offset 是逻辑坐标，物理位置是 Broker 的内部实现细节，两者不要混为一谈。

时间维查询走同一套思路。 「给我某个时间点之后的第一条消息」的做法是：先在 timeindex 里二分找到 maxTimestamp 小于等于目标时间的最大采样点，得到一个 offset 下界，再把这个 offset 当作逻辑坐标走上面四步。两个索引解决两个维度，机制一致。

关键点

稀疏索引解决的是「给定 offset 快速找到字节位置」，它不解决消费顺序问题。多个消费者线程各自持有不同位点去拉取同一分区时，位点之间没有任何约束，谁先处理完谁就往后推进，处理完成的先后顺序与 offset 顺序无关。同理，压实和清理会改变分区的物理形态，但也不会让多线程处理变得有序。分区级别的顺序只在单一顺序处理的消费路径上成立，积压与并发消费的处理方式见 顺序消费与积压处理。

面试追问：能不能做到 O(1) 按 offset 定位？

答题骨架：理论上要，代价是稠密索引，每条消息一条索引项。但这带来两个问题。第一，内存：压缩消息长度可变，索引体积会接近数据体积，一个大分区装不进内存。第二，写放大：每条消息都要更新索引，索引文件变成随机写热点，顺序写退化。所以 Kafka 选了稀疏索引加小段扫描，官方 Log 文档对读取的描述就是「先定位所在段文件，算出段内偏移，再对该文件的内存区间做二分查找的一个变体」。O(1) 的代价在实践中不划算。

六、校验与损坏检测

日志文件可能被写坏，坏法不止一种。官方 Log 文档区分了两类，这个区分很关键，因为它决定了 CRC 的必要性。

第一类是截断。 崩溃时已分配但未落盘的数据块丢失，文件比预期短。表现为尾部残缺。

第二类是追加垃圾。 操作系统不保证 inode 元数据与实际数据块的写入顺序。如果 inode 已经把文件大小更新成新值，而崩溃发生在数据块真正落盘之前，文件长度就是对的、内容却是垃圾。这类损坏比截断危险得多，因为按长度读取会读到完全无意义的数据，而且没有任何格式校验会报错。

CRC 正是为第二类而存在。启动时日志恢复会遍历最新的段，逐条检查：

  1. 条目自身的长度加偏移必须小于文件长度；
  2. 条目 payload 的 CRC 必须与存储的 CRC 匹配（RecordBatch 使用 CRC-32C，即 Castagnoli 多项式）。

任何一条不满足，该段就被截断到最后一个有效 offset，把损坏部分直接丢掉。官方文档对此的措辞是：CRC 检出这个边角情况，避免它污染日志，尽管那些未写入的消息本身仍然是丢失的。

表头与段文件两侧的机制各管一件事：

机制覆盖什么不覆盖什么
顺序写并发写同一位置的冲突掉电时的数据完整性
partitionLeaderEpoch领导者变更后旧领导者继续写入进程崩溃时的部分写入
记录级 CRC-32C静默位翻转、追加垃圾消息本身的业务正确性
unclean.leader.election.enable 默认 false落后副本被选为领导者多副本同时截断导致的丢失
幂等生产者（producerId / producerEpoch / baseSequence）网络重发造成的重复与乱序消费者位点回退造成的重复
acks=all 配合 min.insync.replicas单节点、单盘故障整机断电时页缓存中未刷盘的数据

CRC 不能防丢失，只能防污染。 这一条要记牢：所有副本都断电、所有 fsync 都没来得及执行时，CRC 一条也救不回来。CRC 的作用是让「读到一个格式完整但内容是随机字节的场景」永远不会发生。

为什么需要 *.snapshot。 截断会让分区的日志末端发生变化。如果一个被撤销的旧领导者带着过期的日志视图回来继续写，就会把新日志覆盖成不一致的状态。领导者纪元检查点记录了每个分区的领导者变更历史，新写入的批里都带 partitionLeaderEpoch，Broker 会拒绝来自旧纪元的写入。

面试追问：Kafka 怎么保证日志文件不被写坏？

答题骨架：分三层。写入侧用顺序写避免并发冲突，用 record batch 自带 CRC-32C 覆盖追加垃圾这种静默损坏，启动恢复时逐条校验并在发现损坏时截断到最后一个有效 offset。再往上，跨节点的一致性靠复制和领导者纪元保证。需要强调 CRC 的边界：它保证不会读到垃圾，不保证不会丢数据。

七、面试高频追问

  1. offset 是什么？为什么不用全局唯一 ID？ offset 是 64 位整数，表示消息在该分区历史消息流中的字节位置。早期设计考虑过 GUID 加一张「ID 到位置」的映射表，但那张表需要与磁盘同步，本质是一套完整的持久化随机访问结构，代价远高于收益。offset 隐藏于消费者 API 之外，是实现细节而不是对外契约。

  2. 段文件为什么以 offset 命名？ 因为 offset 就是位置。按 offset 定位时可以先对段首 offset 有序列表二分，直接跳过整个不相关的文件，连 .index 都不用打开。这也让「哪些段可能包含 offset 20」在一次二分后就确定下来。

  3. 稀疏索引的扫描上界是多少？怎么估算？ 上界是 min(采样间隔, 平均批大小) 个批头。Kafka 4.x 下采样间隔是 index.interval.bytes 的 4096 字节，而批大小由生产者的 batch.size 与 broker 的 message.max.bytes 共同约束，前者是主要调节手段。批比间隔大时索引必然落在批边界，扫描为零；批比间隔小时扫描要跨多个批。

  4. 压实会破坏 offset 吗？ 不会。压实是整段重写并把存活记录的批重新写入同构的段，offset 保持不变，所以位点提交、消费者进度都不受压实影响。变的只是物理位置，所以「用文件偏移当业务主键」这种做法在压实后会全部失效。

  5. 删除数据时，正在读这个段的消费者会怎样？ 段列表用写时复制实现：删除动作在新的列表上进行，读侧继续在不可变的旧快照上二分。读请求会先在段列表上登记引用，删除要等引用释放才真正 unlink 文件，因此不会出现「文件已删但还有人在读」的窗口。

  6. .timeindex 和 .index 有什么区别？为什么要两个？ 位置索引的键是 offset，值是字节位置；时间索引的键是 maxTimestamp，值是 offset。前者服务「按位点消费」，后者服务「按时间跳转」。位置索引必须更密（否则每次定位都要多扫），时间索引可以更疏（时间本身就是粗粒度筛选条件），两个索引的采样密度天然不同。

  7. Kafka 怎么做到既顺序写又支持随机读？ 顺序写只发生在追加路径，随机读只发生在查询路径，两者不共享瓶颈。写入时除了日志数据，索引也是顺序追加的。查询时只读不写，所以索引可以整段常驻内存。二者唯一的耦合是都摸同一个段文件，而读多写少让这个耦合不成为问题。

  8. 数据在磁盘上是压缩的，索引怎么定位到具体某条消息？ 批头在压缩区之外，且是定长定序字段。baseOffset、batchLength、lastOffsetDelta 全部可以不解压读出，先用它们判断目标是否落在这一批的 offset 区间内，命中之后才解压这一批。绝大多数定位根本不需要解压任何数据。

  9. Kafka 支持按 key 查询吗？ 不支持。存储层只有按 offset 的位置索引和时间索引，没有按键的二级索引。broker 拿到 offsetsForTimes 或 ListOffsets 这类请求时，先把请求转成 offset 区间；真正按键过滤发生在客户端读出数据之后。跨分区的按键分发由生产者按 key 的哈希决定落到哪个分区，不由 broker 查询。

  10. 一个段里最后那条未写满的批，文件大小怎么算？ 按 batchLength + 12 字节算。batchLength 覆盖从它自己之后到批末尾的字节数，加上 8 字节 baseOffset 和 4 字节 batchLength 自身就是整批磁盘占用。读取时按这个长度跳到下一批，不需要依赖任何填充或对齐。
