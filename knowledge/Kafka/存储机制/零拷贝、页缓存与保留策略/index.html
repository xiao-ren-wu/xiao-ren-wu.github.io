零拷贝、页缓存与保留策略

来源

基于 Kafka 4.x 官方文档整理。文中所有默认值均已标注适用版本 Kafka 4.x，跨版本请以你所用版本的官方文档为准。 本篇接续 分区日志与稀疏索引：那一篇讲数据怎么写进去、怎么按 offset 找回来；本篇讲数据在写出时如何避开用户态拷贝，以及它什么时候被删掉。

一句话回答「Kafka 为什么快」：不是靠把数据塞进 JVM 堆内存，而是靠把搬运次数压到最少、把内存管理外包给操作系统页缓存、把删除交给后台按整段处理。三个决策互相支撑，拆开任何单点都不成立。

一、Broker 写路径：为什么可以零拷贝

传统消息中间件转发一条消息，字节要经过这样一条路：磁盘、内核缓冲区、用户空间缓冲区、内核 socket 缓冲区、网卡。落盘时先从磁盘读进内核再拷到用户态，发送时再从用户态拷回 socket，两次系统调用、四次拷贝、两轮用户态与内核态的切换。CPU 大量时间花在搬字节，而不是解析消息。

Kafka 能跳过用户态，依赖一个别人不一定具备的性质：Broker 不修改消息的字节内容。

  • 消息格式是生产者、Broker、消费者共享的统一二进制格式，跨节点传输时不需要转换。官方设计文档的原话是：消息日志本身就是一个目录，里面装的都是与生产者和消费者所用格式相同的消息集合，因此网络传输持久化日志块时可以做优化。
  • Broker 对批做的校验是解压后数一遍条数、比对 CRC，校验完成后以压缩形式原样落盘。批在整个生命周期保持压缩，跨网络也不解压重压。
  • 批头是明文定长字段（详见 分区日志与稀疏索引），消费端能自己定位，不需要 Broker 逐条展开。

既然字节不需要变换，「磁盘到网卡」这一步就不必经过用户空间缓冲。内核可以在页缓存和 socket 之间直接搬运，应用层的 read / write 与随之而来的两次上下文切换就此消失。

前提条件是一条链，缺一环就退化。 顺序写让数据落在页缓存里而不是散落在磁盘各处；统一格式让字节不需要变换；批头明文让消费端能自己解析定位。三者同时成立才存在「页缓存到 socket 不经用户态」这条路。

关键点

零拷贝的适用边界是「字节不需要变换」。一旦某条路径需要对数据做转换，比如必须先解压才能读出内容、或者要做旧版消息格式的兼容转换，这一步就必然回到用户态。零拷贝不是一条覆盖所有读取路径的规则，而是对「原样转发」这一类路径的优化。

页缓存意味着 Broker 的堆内存很小。 写入落进的是操作系统页缓存，不是 JVM 堆。Broker 自己的堆主要装请求对象、批元数据和索引结构，几十 GB 堆的机器上堆内存也可能只配几 GB，剩下的全给页缓存。这与「用大堆做缓冲」的传统思路完全相反，代价和收益见第三节。

面试追问：零拷贝是不是真的「零次拷贝」？

答题骨架：不是，DMA 拷贝依然存在，省掉的是用户态缓冲区这一跳和随之而来的上下文切换。严格说常规路径是四次拷贝两次切换，sendfile 是三次拷贝一次切换。准确的说法是「在用户态不参与数据搬运」，不是「一个字节都不动」。

二、sendfile 与常规 IO 路径对比

维度read + writesendfile
拷贝次数4 次3 次
用户态与内核态切换2 次1 次
申请与释放的缓冲需要不需要
数据是否进 JVM 堆会进不进
对大块数据的效果一般明显更好
消息变小或格式需转换照常工作不可用，需回退

sendfile 的价值在页缓存命中时更明显。如果刚写入的数据还在页缓存里，那么从页缓存送 socket 这一步根本不触发磁盘读。这让「刚写完马上被别的消费者读到」这种常见模式代价极低，也是 Kafka 能在同一台机器上被多个消费组反复读取而不压垮磁盘的原因。

反过来，页缓存不命中时，零拷贝省下的仍然只是用户态那一跳，磁盘读的成本一分不少。所以 Kafka 的零拷贝优化与页缓存的内存预算是绑在一起的：内存越充裕，命中率越高，收益越大。

这是「消息传输」路径的优化，不等于「所有 IO」都被优化。 索引写入、段滚动、清理、复制副本之间的同步都属于别的路径，不在这条链上。把「Kafka 有零拷贝」推成「Kafka 所有磁盘操作都是零拷贝」是常见的过度引申。

面试追问：零拷贝省下的到底是哪一部分？

答题骨架：省掉的是「内核页缓存到用户空间缓冲」和「用户空间缓冲到内核 socket 缓冲」这两次 CPU 拷贝，以及两次系统调用导致的两轮上下文切换。DMA 在磁盘到内存、内存到网卡这两段始终存在。答题时把拷贝次数和切换次数都报出来，比只说「少一次拷贝」更扎实。

三、依赖操作系统页缓存的后果

这是本篇最容易被答错的一节。写请求返回成功，不等于数据落盘。

acks=all 保证的是所有同步副本都收到了这条消息，收到意味着数据进了这些副本各自的页缓存，不意味着已经 fsync 到磁盘。Kafka 4.x 下有两个直接控制主动刷盘的 topic 级配置：

配置Kafka 4.x 默认值含义
flush.messages9223372036854775807累计到这么多条才主动刷，等价于不设
flush.ms9223372036854775807距上次刷盘这么久才主动刷，等价于不设

两个默认值都是 Long.MAX_VALUE，也就是默认不主动刷盘。官方 topic 级文档对此给出的建议措辞是：不要设置这两项，持久性由复制来保证，交给操作系统在后台刷盘效率更高。逻辑是自洽的：主动 fsync 会把随机写变成同步等待，而副本机制已经提供了持久性保证，两者是冗余的。

故障类型页缓存里的数据结果
Broker 进程崩溃或被 kill内核仍在，页缓存完好数据不丢，重启后读得到
内核 panic 或整机断电随内存一起消失未刷盘的数据丢失
单盘损坏且无副本已刷盘部分可读依赖复制，见 复制模型与 ISR
多副本全部断电全部丢失CRC 只能防污染，防不了丢失

读路径的收益同样来自页缓存。 Broker 重启后不需要预热数据，直接开始服务。日志格式的另一个必要条件是「顺序写、文件头简单、可被操作系统直接理解」，操作系统不需要解析业务结构就能管理这些页，这正是 Kafka 不自研内存缓冲的底气。

内存预算是不可预测的。 页缓存会自动占满所有可用内存，操作系统在内存紧张时按自己的策略回收，脏页优先写回。这对使用者意味着两件事：

  1. 不需要估算「Broker 要留多少内存给缓冲」，这个变量不存在了。
  2. 监控内存占用时不能把页缓存算成问题，页缓存大通常是好事，它意味着读命中率高。真正需要关注的是脏页积压和由此产生的写回延迟。

这条推论很实用：排 Kafka 内存问题时，不要在 Broker 进程里找「哪个 buffer 配置能调小」，那个配置不存在；要看的是操作系统的脏页比例与刷盘策略。

消息大小也有上限。 topic 级 max.message.bytes 在 Kafka 4.x 下是 1048588 字节。注意这是压缩之后仍然要满足的上限，因为 Broker 校验批时需要解压记录区，而解压后的中间结果需要能放进单批的处理缓冲。这是「压缩可以放大单批容量」但不是无限的边界。

面试追问：Kafka 到底有没有把数据写盘？

答题骨架：分清三层确认。客户端到 Broker 是网络确认；Broker 之间的 acks 是副本间的网络与页缓存确认；真正的 fsync 是操作系统的后台行为，Kafka 4.x 默认不主动触发。所以在多副本配置下，acks=all 的可靠性依据是「任意单节点故障都不丢」，而不是「已落盘」。如果业务要求单机掉电也不丢，必须自己调低 flush.ms 并接受吞吐损失，或者依赖多副本加跨故障域分布。

四、段文件切分策略

段的切分触发条件在 Kafka 4.x 下的默认值：

配置默认值作用
segment.bytes1073741824（1 GiB）写满即切
segment.ms604800000（7 天）到期即切，不论是否写满
segment.jitter.ms0对切分时间加随机抖动，默认不加

官方 topic 级文档把段的取舍讲得很直接：保留与清理永远是逐文件进行的，所以更大的段意味着更少的文件，但对保留的控制就更粗；segment.ms 存在的意义是即使段没写满也强制滚动，这样保留策略才能真的删到或压到旧数据。

三向权衡：

段大小清理粒度文件数与元数据顺序写效率与恢复时间
偏小细，可精确到接近消息边界多，文件描述符与目录项压力大滚动频繁，但每个文件小，崩溃恢复快
偏大粗，一条过期消息可能拖住整个段少滚动少，但单文件大，恢复要扫更多数据
匹配消息大小浪费最少视消息分布而定最优

段的删除算法（官方 Log 文档的措辞）：

  • 一次删一个段。
  • 时间策略看的是段内最大时间戳，由它决定整段的保留时间，与记录顺序无关。这意味着一个段里只要有一条消息很新，整个段都不会被时间策略删掉。
  • 大小策略默认关闭，启用后持续删除最老的段，直到分区总大小回到限额以内。
  • 两个策略同时启用时，任一命中即删。

段列表用写时复制。 删除在新的段列表上进行，读侧继续在不可变的旧快照上二分，因此删除进行中不需要给读请求加锁。读请求会先在段列表上登记引用，删除要等引用释放才真正删文件。

面试追问：段开多大合适？

答题骨架：先确定硬约束。第一，段必须大于典型消息的批大小，否则小消息会把段切得过碎。第二，保留策略的精度上限就是一个段，segment.ms 设得比保留周期短很多会显著提升删除及时性。第三，压实效率与段数相关，段太多会让 cleaner 的调度开销上升。给结论时给方向（消息平均大小、保留周期、延迟要求、磁盘规格）而不是背一个固定数字，因为默认值随版本变化且与部署规模强相关。

五、delete 与 compact 两种清理方式

cleanup.policy 在 Kafka 4.x 下默认是 delete，也可以设为 compact 或两者组合。

维度deletecompact
删除依据保留时间与保留大小相同 key 的历史版本
保留什么时间或大小内的全部消息每个 key 的最新一条
磁盘特征整段释放，波动大稳定，但有重复数据上限
对顺序消费的影响无有，详见下方警告
典型用途事件流、日志、审计状态快照、事件去重

delete 策略下，超期消息以整段为单位释放。 结合上一节：段的保留时间由段内最大时间戳决定，所以实际释放时刻比单条消息的到期时刻晚，延迟量级是「一个段的跨度」。段越大，这个延迟越明显。

compact 策略的核心语义是「同 key 只留最新值」。 但它的实现方式是被广泛误解的地方：

  • 压实由后台 cleaner 定期扫描，把存活记录重写成同构的新段。offset 保持不变，所以消费者位点和提交进度完全不受影响，变的是物理位置。
  • 记录 key 为 null 的消息叫墓碑。墓碑标记「这个 key 的旧值在保留期内已全部过期」，但墓碑本身必须再保留一段时间，Kafka 4.x 下 delete.retention.ms 的默认值是 86400000（1 天）。
  • 墓碑保留时长还有一个约束：它必须不小于任何消费者从最早位点扫到日志末尾所需的时间，否则墓碑先被删掉，新启动的消费者从早期位点开始读时，会读到本应已被删除的旧值。

压实什么时候触发。 Kafka 4.x 下 min.cleanable.dirty.ratio 为 0.5，官方文档的原话是「避免清理一个已被压实超过一半的日志」。这个比例直接决定磁盘浪费的上限：一个分区中已被压实（重复）的内容最多占约一半。这也解释了压实为什么不是「压得越干净越好」。

相关阈值：

配置Kafka 4.x 默认值作用
min.cleanable.dirty.ratio0.5重复占比超过它就不再触发清理
min.compaction.lag.ms0允许压实多旧的数据
max.compaction.lag.ms9223372036854775807保留多旧的数据不压
delete.retention.ms86400000（1 天）墓碑保留时长

关键点

compact 不保证「任意时刻分区里同一个 key 只有一条消息」。同一个段内可能仍有多条同 key 记录，清理是后台周期性的，min.cleanable.dirty.ratio 甚至允许一半空间是重复内容。只有当策略是纯 delete 时，压实根本不会发生。所以「compact 之后一个 key 只有一条」是错的说法，正确说法是「压实会把每个 key 的历史版本收敛到最新值，代价是磁盘上仍可能残留一段时间的重复」。

六、文件删除与磁盘回收的时机

从「配置上已过期」到「磁盘空间真正回来」中间有四段延迟，串起来才能解释水位线为什么比预期高：

阶段相关配置Kafka 4.x 默认值说明
保留期届满retention.ms（topic）604800000（7 天）消息层面已过期
cleaner 轮询发现log.retention.check.interval.ms300000（5 分钟，read-only）周期检查，不是到期即删
判定到执行删除file.delete.delay.ms60000（1 分钟）缓冲窗口，防止误删
空间真正回收无配置取决于文件引用删除目录项，块在最后引用消失后释放

两点容易踩坑：

第一，retention.bytes 在 Kafka 4.x 下默认是 -1，即不设大小上限。 官方文档明确写的是「默认只有时间限制」，并且这一限制是按分区生效的。也就是说一个 topic 的总容量上限是单分区限额乘以分区数。生产环境里 retention.ms 一旦被误配成 -1 或被意外改大，而写入速率又超过清理速率，磁盘会一路涨到满。

第二，log.retention.check.interval.ms 是 read-only。 它只能在 broker 启动时通过配置或环境变量设定，运行期通过 AdminClient 改会失败。很多「改了配置不生效」的问题出在这里。

磁盘打满的直接后果是 Broker 无法继续接收写入。真正的风险是连锁反应：写入阻塞导致上游生产者重试，重试又放大写入压力，积压继续增长。集群级的连锁是分区无法选出可用 leaders，触发 OfflinePartitionCount 类告警，可靠性相关的排查路径见 Kafka 可靠性与投递语义索引。

多副本下每份副本独立清理。 副本因子大于 1 时，每个副本的数据量、写入时刻都不完全相同，所以各自的 cleaner 在不同时刻删除不同段。所有副本的段都被删掉，磁盘空间才真正回收。 只盯着 leader 所在节点的磁盘水位会低估整体压力。

紧急处置顺序。 磁盘将满时的处置优先级：

  1. 确认是「保留配置过大」还是「写入速率超过清理速率」。前者是配置问题，后者是容量规划问题，处置方式不同。
  2. 调小 retention.ms 或给 retention.bytes 设一个明确上限。这两项都是 topic 级可动态修改的配置，改动对现有数据立即生效，cleaner 会在下一个轮询周期开始删除。
  3. 扩分区。扩分区会改变分区间的数据分布，但不会自动把一个分区的数据拆到多个分区上，已有数据不会自动再平衡。
  4. 扩磁盘或加节点。属于容量侧的兜底，不是止血手段。

清理跟不上写入的判断方法：看 log.dirs 各盘水位与保留期乘以写入速率的估算值是否匹配。如果「保留期内的数据量」本身就超过盘容量，那么无论清理多快都会涨满，正确解法是缩短保留期或加容量。

七、面试高频追问

  1. Kafka 的零拷贝省的是什么？ 省掉「内核页缓存到用户空间缓冲」和「用户空间缓冲到内核 socket 缓冲」这两次 CPU 拷贝，以及随之而来的两次系统调用与两轮上下文切换。DMA 拷贝始终存在。准确说法是「用户态不参与搬运」，不是「零次拷贝」。

  2. 零拷贝对压缩数据有效吗？ 零拷贝的前提是字节不需要变换。压缩段如果能按原样交付给能自行解压的消费者，理论上仍可走原样路径；但任何需要先展开才能读取或需要格式转换的读取都必须回退到用户态。答题时把「前提是字节不变」讲清楚，比背结论更稳。

  3. 为什么 Broker 堆内存很小？ 因为数据走页缓存而不是 JVM 堆。堆只装请求对象、批元数据和索引结构。好处是堆不会引起长尾 GC，坏处是可用内存不可预测，且操作系统回收策略对用户不可见。

  4. acks=all 等于数据落盘了吗？ 不等于。acks=all 保证同步副本都收到了，也就是都进了各自的页缓存。Kafka 4.x 下 flush.messages 和 flush.ms 默认都是 9223372036854775807，等于默认不主动刷盘，官方建议靠复制保证持久性。因此多副本下的可靠性依据是抗单节点故障，不是已落盘。

  5. segment.ms 为什么存在？不是有 segment.bytes 就够了吗？ 只靠大小触发会导致一个迟迟写不满的段把最老的消息无限期吊住，因为清理是逐段做的，整段的时间由段内最大时间戳决定。segment.ms 保证段不会无限期存活，官方文档明确说明它就是为了让保留策略能作用到旧数据。

  6. 压实会改变 offset 吗？会破坏顺序消费吗？ 不改 offset，因为压实重写时保持原 offset，只改物理位置和内容。会影响「每条事件都要处理」这类假设：如果多条不同事件用了同一个 key，压实后只剩最新一条，其余事件被永久丢弃。把每条事件都当独立消息消费时，key 应当唯一或为 null，并且理解 null key 在 delete,compact 组合下会被当作墓碑处理。

  7. 墓碑为什么不能立刻删？ 因为压实从头扫描，墓碑的作用是告诉 cleaner「这个 key 在我之前的值都已经过期」，删太早会让逻辑倒退。约束条件是：墓碑保留时间必须不小于任何消费者从最早位点扫到日志末尾的时间，否则重启后的新消费者会读到本应已删除的旧值。

  8. 磁盘被写满会发生什么？ Broker 无法继续接收写入，表现为写入报错或长时间挂起。连锁反应是上游生产者超时重试、积压增长、分区无可用 leaders。根本原因通常是 retention.bytes 默认 -1（无上限）叠加写入速率超过清理速率，或者保留期内的数据量本身就超过盘容量。

  9. 怎么判断磁盘是「配置问题」还是「容量问题」？ 用「保留期 × 写入速率」估算应有数据量，与盘容量对比。估算值本身就超过容量的是容量问题，必须扩分区或扩盘；估算值远小于容量却涨满的是配置或清理问题，先查 retention.ms 是否被改大，再查 cleaner 轮询与各副本的删除进度。

  10. 单副本和多副本在清理上有什么差别？ 清理由各副本独立执行，副本因子大于 1 时每份副本的段删除进度不同，磁盘空间要等所有副本都删完才回收。只看 leader 所在节点的水位会低估压力。副本数还直接放大磁盘占用，容量规划要按「单份数据量 × 副本因子 × 富余系数」算。

  11. preallocate 为什么默认关闭？ Kafka 4.x 下 preallocate 为 false。预分配能避免段写到一半时磁盘突然找不到连续空间，但会因为文件一创建就占满空间，而在「数据已过期但文件尚未删除」的窗口里造成额外浪费；再叠加分区数多、元数据操作频繁的场景，预分配的收益不如它的空间代价。
