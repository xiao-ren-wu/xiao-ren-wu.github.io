Kafka 架构全景与角色分工

来源

基于 Kafka 4.x 官方文档整理。文中未标注 ⚠️ 的结论可直接用于面试应答。 本篇只讲结构性事实（角色职责、数据流向、选主机制），不涉及具体配置默认值；默认值类陈述集中在生产、消费者、可靠性各篇，并逐条标注适用版本。

Kafka 是什么、由哪些角色组成、一条消息从产生到被消费要经过哪些环节、为什么 4.x 换掉了 ZooKeeper——这是读后续所有篇目的前提。如果分不清 Controller 与 Broker 的职责边界，后面的复制、选主、排障都会变成背概念。

一、消息系统的两类定位

Kafka 常被笼统归为「消息队列」，但它同时满足两类诉求，而这两类诉求决定了它几乎所有的设计取舍。

定位核心诉求典型指标Kafka 的取舍
消息队列（MQ）解耦、削峰、异步化单条投递延迟、投递成功率为降低延迟，允许每条消息只落少数副本、只等 Leader 确认
事件流处理（ESF）高吞吐、可重放、可回溯吞吐量、保留时长为保证可重放，消息不能被「消费即删除」，必须按保留策略留存

关键认知：Kafka 的设计重心偏向后者。

一条消息被成功消费后，它并不会消失，而是继续留在日志里直到超过保留策略（retention）被清理。这意味着：

  • 同一个消费组可以把位点（offset）往回拨，重新消费历史数据
  • 多个互不相关的消费组可以各自独立消费同一份数据
  • 消费者短暂宕机不会丢消息——只要位点没被推进，重启后从上次位点继续

这就是 Kafka 与传统 MQ 最容易被误解的地方：「消费」在 Kafka 里不是「删除」，而是「记录你读到了哪里」。

面试追问：Kafka 和传统 MQ（比如 RabbitMQ）在「消息被消费后」最本质的区别是什么？

答：Kafka 是拉取式 + 保留式，消费不删除数据，只推进位点，因此可重放、可多消费组独立消费，代价是必须显式管理保留策略与磁盘容量。传统 MQ 多为推送式 + 消费即删除（或按 ack 决定），单条投递延迟更低、队列语义更直观，但历史消息不可重放。

补充加分点：Kafka 官方现在把自己定位为 distributed event streaming platform，这个措辞本身就是在强调第二类定位。

二、Kafka 的核心角色与职责边界

集群里有三类核心角色，职责互不重叠。

角色负责什么不负责什么典型故障影响
Broker存储消息、副本同步、响应读写请求不做元数据决策（谁当 Leader）单 Broker 故障 → 该 Broker 上的 Leader 分区需重新选主
Controller（KRaft）维护集群元数据、决定分区 Leader、创建分区不存消息数据、不参与消息读写Controller 不可用 → 已挂载的分区仍能读写，但新分区创建/扩容等变更操作受阻
Producer决定消息去哪个分区、批量压缩、可靠性配置不感知集群拓扑细节，靠拉取元数据获知生产端故障 → 消息发不出去，但不影响已有数据
Consumer按位点拉取、处理消息、提交位点不直接读磁盘消费端故障 → 分区被重新分配给组内其他成员

最容易搞混的一点：Controller 不是 Broker 的「超集」，两者是并列的进程角色。

一个 Broker 进程同时做两件事：

  1. 作为 Controller 参与元数据共识（通常由少数几个 Broker 承担，构成 Controller Quorum）
  2. 作为 Broker 存储与收发消息（通常所有 Broker 都做）

所以「某台 Broker 挂了」要分两种情况看：

  • 它只是普通 Broker → 挂掉时它上面的 Leader 分区重新选主，数据由 Follower 顶上
  • 它同时是 Controller 成员 → 如果 Quorum 里挂掉的成员过半，Controller 也失效；但集群已有的数据读写通常仍可继续（元数据已被提交到日志，未提交的操作暂时不能推进）

面试追问：Controller 挂了，Kafka 集群就完全不可用了吗？

答：不一定，要区分「Controller 全部不可用」和「部分不可用」。已有的分区读写不依赖 Controller 在线——数据面路径上 Controller 只在元数据变更时参与。Controller 不可用时，已经在服务的数据可以继续生产和消费，但会失去动态能力：无法自动创建新分区、无法完成 Leader 重选（如果恰好同时有 Broker 故障）、无法执行需要元数据变更的管理操作。

进一步加分：正因为数据面与元数据面解耦，Controller 的恢复是可回放的——它启动后重放元数据日志即可重建全量状态，不需要 Broker 逐个汇报。

三、Topic 与 Partition：数据如何切分

这是整个系统里最该先想明白的数据模型，它直接决定了后面几乎所有能力与限制。

3.1 逻辑与物理的两层结构

  • Topic：逻辑上的消息分类名，比如 orders、user-events。它本身不存数据
  • Partition：Topic 的物理分片。数据只存在于分区里

一个 Topic 可以有 1 个、3 个、100 个分区。分区数一旦只能增不能减（可以加分区，不能删），且直接影响消费并行度上限。

3.2 分区是最小有序单位

Kafka 只保证分区内有序，不保证跨分区有序，也不保证全局有序。

原因很直白：不同分区由不同的 Leader 独立追加写入，写入顺序由各自的到达时间决定。要实现全局有序，就得让所有写入排队走同一条路径，等于放弃并行——这与 Kafka 的设计目标冲突。

面试追问：业务要求「同一订单的事件必须按顺序处理」，Kafka 怎么保证？

答：靠 key 绑定分区。把订单号作为消息的 key，Partitioner 会用 key 的哈希值决定目标分区（默认对 key 取 murmur2 哈希再对分区数取模）。同一订单号 → 同一分区 → 由该分区的单一 Leader 顺序追加 → 顺序天然得到保证。

必须补充的边界：

  • 顺序性以分区为粒度，跨分区无序
  • 如果目标分区数发生变化（扩分区），取模基数变了，同一个 key 可能被映射到新分区，扩容瞬间会破坏原有顺序
  • 消费侧必须保证该分区单线程按序消费；多线程并发消费同一分区，顺序照样被破坏
  • 失败重试也会破坏顺序：第 1 条重试未完成、第 2 条已成功，业务看到的就是乱序

3.3 分区、副本与可用性的三角

每个分区有多个副本（replica），其中：

  • 恰好一个是 Leader，承担全部读写
  • 其余是 Follower，只从 Leader 拉数据
  • Follower 永不直接服务客户端请求

这个「单 Leader」约束是 Kafka 高效的前提：无需副本间协商读请求，读写都走一条路径。

代价是每个分区都存在单点：Leader 所在 Broker 宕机时，该分区的写入要中断到重新选主完成；消费侧通常能继续（从 Follower 读），但严格一致性语义下会先暂停等新 Leader 就位。

面试追问：Kafka 为什么是「每分区单 Leader」而不是像数据库那样多副本同时可读？

答：为了读写路径无协商。如果多个副本同时可读，客户端要选一个副本、读到不同位置还得处理副本间位点差异（类似读修复），复杂度与一致性成本都高。Kafka 的选择是：写走 Leader，读也走 Leader（read_uncommitted 语义下），用副本数换可用性而非换读扩展性。

顺带说清代价与收益：代价是 Leader 切换期间该分区短暂不可用；收益是读写路径极简，吞吐上限更高。对「日志流」类负载，这个取舍是划算的。

四、一次完整的 produce → consume 生命周期

按时间顺序走一遍。示例中的分区数、副本数都是为了讲解假设的数值，不是 Kafka 默认值。

假设：Topic orders 有 3 个分区，副本因子 3；消息 key 为 order-9527。

4.1 生产端

  1. 取路由：Producer 从元数据缓存里查 Topic → 分区 → Leader 的映射。缓存为空或过期时向任意 Broker 索要元数据
  2. 选分区：由 Partitioner 决定。指定了分区就用指定值；指定 key 就用 key 的哈希；都没有就按轮询选，保证同一 Producer 的多条消息能均匀打到各分区
  3. 发请求：连到该分区的 Leader Broker，追加写入
  4. 确认：按 acks 配置等待不同级别的确认——只等 Leader、还是等全部 ISR 副本、还是不等（详见 [[幂等、acks 与事务]]）

4.2 Broker 侧

  1. 消息被分配一个递增的 offset（该分区内单调递增）
  2. 追加写入分区日志文件
  3. 按 acks 语义决定何时给生产者返回
  4. 异步复制给 Follower；Follower 落后超阈值会被移出 ISR（详见 [[复制模型与 ISR]]）

4.3 消费端

  1. 消费者加入消费组，与协调者完成分配（详见 [[消费组、位点提交与 Rebalance]]）
  2. 从 Leader（或配置允许的 Follower）拉取消息批次
  3. 处理消息
  4. 提交位点

第 3 步和第 4 步的顺序，决定了投递语义。先提交位点再处理 → 崩溃时丢消息（at-most-once）；先处理再提交位点 → 崩溃时重复处理（at-least-once）。Kafka 默认语义是 at-least-once，要拿到更强的保证需要额外的机制，详见 [[投递语义与消息去重]]。

面试追问：offset 是全局唯一的吗？多个分区会重号吗？

答：不唯一。 offset 是分区内唯一且单调递增的，跨分区会重号。所以位点必须成对表示：(partition, offset)，常见编码就是 ${partition}-${offset}。这正是消费组提交位点时提交的是「一组分区的位点集合」而不是单个数字的原因。

五、KRaft 架构全貌

KRaft 是 Kafka 自带的元数据协调机制，基于 RAFT 共识，把元数据本身也变成一条可复制的日志。

5.1 元数据日志

集群的分区分配、Leader 指向、Broker 注册、配置变更等，全部写进一条元数据日志，由 Controller Quorum 内的多个 Controller 成员通过 RAFT 复制。

关键性质：

  • 只有一个 Leader 成员负责追加日志项
  • 其他成员作为 Follower 复制，并可在 Leader 故障时通过选举接替
  • 通过**任期（term）**防止旧 Leader 在网络恢复后继续写入（脑裂保护）
  • 日志项会周期性压缩为快照，加速重启后的状态恢复

5.2 三个阶段（双保险）

KRaft 的成员变更用**联合共识（joint consensus）**分阶段推进，避免单次切换导致脑裂：

  1. 旧配置与新配置同时生效，达成双重多数派
  2. 只用新配置达成多数派
  3. 新配置正式生效

这套机制的好处是成员变更也是被共识保护的操作，而不是一个「谁能联系上就生效」的弱规则。

面试追问：KRaft 相比 ZooKeeper 方案，核心改进是什么？

答：把外部的一致性存储换成内置的共识日志。三点收益：

  1. 运维简化：不再需要单独部署和维护一套 ZooKeeper 集群，Broker 数量可以减半
  2. 一致性更强：元数据变更走 RAFT 共识，有明确的任期和多数派保证；而 ZooKeeper 是最终一致的，写完可能短暂不可见
  3. 可回放恢复：元数据是日志，Controller 重启后重放即可重建全量状态，不依赖向各 Broker 逐一询问

反过来说也要讲代价：ZooKeeper 时代运维团队对这套模型已经形成了肌肉记忆，KRaft 的工具链、监控指标、排障思路都换了，属于有明确收益但有迁移成本的改动。

六、与 ZooKeeper 时代架构的差异

旧版做法

本节描述的是Kafka 4.0 之前的架构。本库版本基线为 Kafka 4.x，其中 ZooKeeper 协调模式已被移除；下述内容保留，是因为存量系统仍可能运行在旧版本上，且面试中常被问到。在新版本上不要再按 ZooKeeper 的方式排查问题。

维度ZooKeeper 时代（< 4.0）KRaft（4.x）
元数据存放外部 ZooKeeper 集群的 znodeBroker 内部的元数据日志
一致性机制ZooKeeper 的最终一致性 + watch 通知RAFT 强一致 + 任期
通知方式推模式：ZK 变更 → watch 回调 → 通知各 Broker拉模式：各节点主动拉取元数据
Broker 角色需靠 ZooKeeper 完成 Leader 选举Leader 由 Controller 统一分配，Broker 不参与投票
组件依赖需额外部署 ZK 集群（含奇数节点、单独监控）无外部依赖
恢复方式Broker 启动后连 ZK 注册、拉取元数据重放元数据日志或加载快照

架构上的本质差异是「谁做决策」：

  • ZooKeeper 时代：Broker 自己参与 Leader 选举，ZK 只提供数据和通知
  • KRaft 时代：Controller 统一决策并下发，Broker 老实执行

这直接改变了排障的思考方式：ZooKeeper 时代要查「ZK 是否抖动、watch 是否丢失」；KRaft 时代要查「Controller Quorum 是否健康、元数据日志是否可读写、当前 term 是多少」。

面试追问：为什么 KRaft 放弃了 watch 推送，改成拉取？

答：watch 推送是易丢事件的——注册了 watch 之后到收到通知之间存在窗口，事件在此期间发生就可能丢失，必须靠客户端自建重连与全量对账来补。而拉取是状态驱动的：不管错过多少次，只要拉到的状态是最新的就一定正确，天然幂等。代价是引入了元数据延迟与一定的重复拉取。

这是分布式系统里一个很典型的取舍：推的延迟低但要求送达保证，拉的延迟略高但状态一定收敛。 Kafka 选择后者，因为元数据变更的频率远低于消息流量，能接受这点延迟换取正确性。

七、面试高频追问

按面试出现频率排序，每条给出答题要点。

1. Kafka 为什么快？能背出哪几条优化？

答题骨架：顺序写磁盘（顺序 IO 吞吐远高于随机）、零拷贝（省用户态与内核态切换）、批量与压缩、页缓存（依赖 OS 而非 JVM 堆）、分区并行。详见 [[Kafka 存储机制索引]]。

2. Kafka 为什么能保证顺序？什么情况下不保证？

答题骨架：顺序性以分区为粒度；用 key 把相关消息固定到同一分区；消费侧必须单线程按序消费；失败重试、扩分区、并发消费都会破坏顺序。

3. 一个分区可以有多个 Leader 吗？为什么？

答题骨架：不能，恰好一个 Leader。这是读写路径无协商的前提。Leader 故障时由 Controller 重新指派，期间该分区短暂不可写。

4. 消费组之间会互相影响吗？

答题骨架：不会。每个消费组独立维护自己的位点，互相看不到对方的进度。同一消费组内的成员分摊分区，一个分区同一时刻只被组内一个成员消费。

5. 消费组里的消费者数量超过分区数会怎样？

答题骨架：多出来的消费者拿不到任何分区，处于空闲状态。所以消费并行度上限 = 分区数，增加消费者前要先确认分区数是否够。详见 [[顺序消费与积压处理]]。

6. Kafka 的 Leader 一定同步完副本才返回客户端吗？

答题骨架：不一定，由 acks 决定。acks 有三档，语义与可靠性/吞吐成反比；而 min.insync.replicas 决定了「至少多少副本同步了才算有效确认」。两者要一起看。详见 [[幂等、acks 与事务]] 与 [[复制模型与 ISR]]。

7. 元数据管理为什么不用现成的 ZooKeeper？

答题骨架：不是不能用，而是内置共识的收益大于成本——去掉一个外部强一致中间件，换来更低运维复杂度、更强一致性保证与可回放恢复。详见第五、六节。

8. Broker 挂了会发生什么？数据丢吗？

答题骨架：分三种情况——普通 Broker 挂则该 Broker 上的 Leader 分区重新选主，Follower 顶上；副本同步策略与 acks 组合决定丢失窗口；Controller 成员挂过半分则元数据操作暂停，但已有数据读写通常继续。详见 [[复制模型与 ISR]]。
