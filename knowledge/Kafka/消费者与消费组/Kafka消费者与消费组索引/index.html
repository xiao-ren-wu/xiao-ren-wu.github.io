Kafka 消费者与消费组索引

本页用途

本主题回答「怎么把消息读出去、读到哪了、多个消费者怎么分工、跟不上怎么办」四组问题。它是整个消费端的地基：分区分配与位点提交决定正确性，顺序与积压决定能否扛住流量。面试里「消费组」「Rebalance」「auto commit 丢消息」「加消费者为什么不解决积压」四类问题全部落在本主题。

关键结论

  1. 一个分区在同一消费组内同一时刻只分配给一个成员。 这一条同时买来「分区内顺序不被并发破坏」和「单条消息不被组内重复处理」，也是消费并行度上限等于分区数的根源。
  2. 位点记录的是「读到哪了」，不是「处理到哪了」。 Kafka 客户端无法知道业务执行到哪一步，所以 enable.auto.commit（Kafka 4.x 默认为 true）按 auto.commit.interval.ms（A 级值 5000 毫秒，多版本文档页一致）推进 poll 返回位置，未处理的那一段被永久跳过。这是消费端第一大丢消息来源。
  3. Rebalance 的代价由协议决定。 eager 先撤销全部分区再重新分配，单成员进出即全组停顿；cooperative 只撤销本轮要移走的分区，但要求分配器为 CooperativeStickyAssignor（range 与 roundrobin 只能 eager），且剧烈变动时轮次可能更多。
  4. 心跳正常不代表成员还在组内。 协调者同时按 session.timeout.ms（失联）与 max.poll.interval.ms（A 级值 300000 毫秒）两个窗口判定。「进程活着、心跳正常、消费却毫无进展」通常是 poll 循环耗时超时的「consumer 假死」，会进入加入、被踢、再加入的循环。
  5. Kafka 只保证分区内有序。 保序要在生产侧用 key 绑定、在消费侧用「每分区串行 + 位点按已处理连续前缀提交」守住；重试插队、扩分区重映射 key、无 key 并发生产、多线程并发消费同一分区都会破坏顺序。Kafka 自身没有死信队列，跳过坏消息必须由应用实现重试上限与旁路。
  6. 消费积压是位点不再前进的结果，不是连接阻塞的结果。 Broker 只把消息留在日志里，代价是磁盘与保留期：log.retention.hours 的 A 级值 168 小时，追不上就会真的丢数据。处置前先算「消费速率 × 追赶时间」是否小于剩余保留期。
  7. 扩消费者对单分区无效，扩分区对已有积压无效。 前者受分区独占约束，后者只提高未来并行度且会因 key 重新映射破坏顺序。任何会制造数据缺口的手段（重置位点）都必须先确认业务可丢并留下记录。

三条最容易踩的事故链

三条链的共同特征是：系统没有任何报错，只有数据不对。

三条链的处置分属不同机制：链一与链二由 auto.offset.reset 的取值决定，属于配置选型；链三由处理耗时分布决定，属于代码与批量参数选型。排障时先判断属于哪一类，再动手，否则很容易在扩消费者和调超时之间空转。

面试高频追问速记

问题一句话答案出处
消费组之间会互相影响吗？机制上三层独立（位点、分配、读取）；例外是同一 topic 被多组读会放大读 IO，以及 group.id 被错误复用会抢分区消费组、位点提交与 Rebalance
消费者数量超过分区数会怎样？多余成员拿不到分区、只发心跳不消费；消费并行度上限等于分区数消费组、位点提交与 Rebalance
为什么 auto commit 会丢消息？位点代表「读到哪了」而非「处理到哪了」，提交快于处理的那一段被永久跳过消费组、位点提交与 Rebalance
eager 和 cooperative 怎么选？看成员变动频率与组规模；cooperative 需 CooperativeStickyAssignor，range 与 roundrobin 只能 eager消费组、位点提交与 Rebalance
Kafka 能保证全局有序吗？不能，只保证分区内有序；全局有序要么单分区降吞吐，要么应用层排序补缺口顺序消费与积压处理
积压了加消费者行不行？先看分区级 lag：均匀涨才能加，个别涨加了也无效顺序消费与积压处理
顺序消费被毒消息卡住怎么办？阻塞式重试静默卡住整个分区且不触发 Rebalance；需重试上限与旁路存储顺序消费与积压处理

学习顺序

  1. 消费组、位点提交与 Rebalance —— 先读「消费者组与分区分配」和「位点存在哪以什么粒度提交」。理由：分区独占与位点归属是顺序与积压的共同前提，不先钉住这两条，后面所有结论都会悬空。
  2. 同篇的「自动提交的陷阱」 —— 理由：这是消费端最容易在生产上造成不可逆损失的一节，且面试提问率最高，值得在读机制之前先建立正确顺序的直觉。
  3. 同篇的「Rebalance 的触发时机」「eager 协议的代价」「协作式 rebalance 协议」「max.poll.interval.ms 与消费线程的生死」 —— 理由：这四节是一条因果链：触发源决定何时发生，协议决定停多久，两个超时窗口决定为什么会被踢出组。拆开读会记不住。
  4. 顺序消费与积压处理 —— 理由：拿到「一个分区只给一个消费者」这条约束后，才能理解为什么顺序粒度必然是分区、为什么加消费者解决不了单分区瓶颈。两篇的顺序不能颠倒。
  5. 同篇的「消费积压的判定指标」与「应急处理手段与取舍」 —— 理由：顺序是设计期决策，积压是运行期决策；先会设计再会排障，遇到线上问题时才知道该改代码还是该改参数。
  6. Kafka 架构全景与角色分工 第 3.2 与 4.3 节 —— 回读分区有序的架构原因与「处理与提交的先后决定投递语义」，把两篇的结论钉回整体数据流。
