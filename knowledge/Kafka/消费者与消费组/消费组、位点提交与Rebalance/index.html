消费组、位点提交与 Rebalance

来源

基于 Kafka 4.x 官方文档（consumer-configs、design/protocol、operations）整理。本文出现的配置默认值均取置信度 A 项并标注了适用版本；session.timeout.ms、max.partition.fetch.bytes、group.initial.rebalance.delay.ms 只讲语义、不写数字，默认值随版本变化，以你所用版本的官方文档为准。本文的 A 级值仅在该版本有官方文档页或源码常量支撑时标注具体版本；标注「多版本文档页一致」表示该取值在多个版本的 consumer-configs 页面上相同，具体版本见 /Users/erik/tools/kafka-facts/sources.md。

消费组是 Kafka 里唯一同时解决「消费并行」和「进度隔离」的机制。它把两个正交的需求塞进一个概念：同一个组内把分区拆开给多个成员并行消费，不同组之间彼此看不见对方的进度。并行度上限、位点归属、Rebalance 代价三个问题全部由消费组定义，答不清这三件事就没法处理生产上的消费问题。

一、消费者组与分区分配

1.1 组的边界

维度结论
组的唯一标识group.id，相同 group.id 的消费者属于同一组
分配范围组内所有成员订阅的 topic 的分区并集
分区独占性一个分区在同一组内同一时刻只分配给一个成员
消费并行度上限组内订阅的分区总数
组间关系位点、分配、Rebalance 完全独立，互相不可见

「一个分区只给一个成员」这条约束是硬约束，它同时买来了两样东西：分区内顺序不被并发破坏，以及单条消息不会被组内重复处理。

1.2 协调者与组内 leader 的分工

消费组的协调者是集群里的某一台 Broker。客户端启动或重连时先发 FindCoordinator 询问「我这个组的协调者在哪」，Broker 端按 group.id 算出归属分区（__consumer_offsets 的某个分区），该分区的 Leader 就是协调者。消费组协调完全是 Broker 侧的事，不经过 KRaft Controller，这一点与集群元数据协调是两套独立机制。

在 group.protocol=classic 下，协调者与组内 leader 分工明确：

  • 协调者：收集成员、选出 leader、把 leader 算出的分配结果同步给全员
  • 组内 leader：执行分配算法（RangeAssignor / RoundRobinAssignor / StickyAssignor / CooperativeStickyAssignor），把「成员 → 分区」列表发给协调者

面试追问：消费组之间会互相影响吗？

答：机制上三层完全独立，是 Kafka 最值得答清楚的一点。

  1. 位点独立：位点以 group.id + topic + partition 为键存储，两个组写的是不同键
  2. 分配独立：各组有各自的成员集合与各自的 Rebalance 节奏，一个组 rebalance 不通知其他组
  3. 读取独立：每个组独立发 FETCH，请求的是各自的位点，互不共享消费状态

但要主动说出两个例外，否则答案不完整：

  • 资源竞争：同一 topic 被 N 个组消费，Broker 侧的读 IO 与网络开销近似放大 N 倍。这是共享资源层面的影响，不是正确性影响
  • group.id 被错误复用：两个语义不同的程序配了同一个 group.id，它们会抢同一批分区。因为分配范围是「成员订阅的分区并集」，一个程序会被分到它根本没订阅的分区去。这类问题表现为「某个消费者莫名其妙收不到消息」或「处理了不该处理的数据」，根因是配置而非机制

另外容易被追问的是：group.id 相同但订阅的 topic 不同，是否会互相影响？答：会。分配基于订阅并集，订阅差异会导致分区被分给不该处理的成员。

二、位点存在哪、以什么粒度提交

2.1 存储形态

位点存在内部 topic __consumer_offsets 里，是一条条「消费进度」记录，不是消息。它是每个组、每个分区一条记录：

所以提交的不是单个数字，而是 (topic, partition) → offset 的映射集合。offset 只在分区内唯一，跨分区会重号，这正是必须成对提交的原因（详见 [[Kafka 架构全景与角色分工]]）。

提交的是「下一条要读的位置」，不是「已处理的最后一条」。 消费了 offset 100 到 149 这 50 条后，提交的位点是 150。

2.2 三种提交方式

方式提交时机崩溃时的后果适用场景
自动提交客户端按 auto.commit.interval.ms 周期提交 poll 返回位置丢消息（未处理的部分被跳过）允许少量丢失的日志、埋点
手动 commitSync处理完一批后同步提交重复处理（at-least-once）绝大多数业务场景
手动 commitAsync处理完一批后异步提交重复处理，且回调失败默认不重试高吞吐场景，必须自己实现重试与重排序

自动提交与手动提交的本质差别不是「谁来发请求」，而是「位点代表读到哪了还是处理到哪了」。 这一句是本节的核心。

2.3 位点会被过期

__consumer_offsets 有保留策略。消费组在保留期内没有任何活动，位点记录会被清理。此时该组再次启动时找不到已提交位点，行为由 auto.offset.reset 决定（见第八节）。一个停机很久的消费者组重新上线时会静默跳过停机期间的全部数据，这是 latest 默认值下最隐蔽的一种数据缺口。

三、自动提交的陷阱

3.1 默认行为

  • enable.auto.commit 在 Kafka 4.x 下默认为 true
  • 自动提交时，客户端按 auto.commit.interval.ms（A 级值 5000 毫秒，多版本文档页一致）周期，把「上次 poll 返回的最后一条记录的下一条 offset」提交给协调者
  • 提交线程在 poll 循环里运行，与业务处理是否完成毫无关系

3.2 丢失窗口

窗口的大小 = 「已提交位点」减去「业务实际处理到的位点」。三条常见的打开方式：

  1. 批内处理慢，而自动提交不看处理进度
  2. 业务逻辑抛异常但没让进程退出，位点照旧前进
  3. 下游依赖超时重试拉长单批耗时，而提交照旧

3.3 正确写法

关掉自动提交，把提交位置与处理完成位置对齐：

commitSync 的超时未显式指定时，走客户端 API 调用的默认超时 default.api.timeout.ms（Kafka 4.x 默认 60000 毫秒）。

面试追问：为什么 auto commit 会丢消息？

答：因为自动提交的位点来自「poll 返回的位置」，而不是「处理完成的位置」。Kafka 客户端能知道的只有「消息已经拉回到本地缓冲区」，无法知道你的业务逻辑执行到哪一步、是否抛了异常、是否已经落库。所以它按自己的节奏把位点往前推。

一旦位点推过了实际处理进度，这段消息就被跳过了，重启也不会回来，因为 Kafka 认为它们「已被消费」。

追问加分：为什么手动提交就一定不丢？答：也不一定。手动提交只是把提交点对齐到处理完成点，代价变成重复消费（崩溃在处理完与提交成功之间，重启会重放这批）。这就是 at-least-once。要做到既不丢又不重，需要业务侧幂等，见 [[Kafka 可靠性与投递语义索引]]。

追问再深一层：能不能既自动提交又不丢？答：可以用「手动提交 + 严格的批次边界」，但前提是你自己把 poll 循环与处理循环的进度绑定。Kafka 侧没有第三种答案，因为位点的语义只有一条：它记录客户端读到哪里，不知道也不关心业务处理到哪里。

四、Rebalance 的触发时机

Rebalance = 重新计算「成员 → 分区」映射并让所有成员停到新映射上。触发源是穷举的：

触发源具体场景备注
成员加入扩容新实例、新订阅关系接入滚动重启期间每个实例上线都会触发一次
成员正常离开调用 close、优雅下线触发一次全组 rebalance
心跳失联超过 session.timeout.ms 未收到心跳该成员的分区被回收并重新分配
心跳正常但 poll 超时超过 max.poll.interval.ms 未调用 poll最隐蔽的一类，见第七节
进程崩溃kill、OOM、宿主机故障无预告地触发
分区数变化扩分区、新 topic 加入订阅范围与业务代码无关，纯运维动作
订阅集合变化成员改订阅、topic 被删除触发重新计算并集
组内 leader 失效classic 协议下 leader 掉线需重新选 leader，因此要全员重新加入
内部状态重建位点数据丢失、组状态被清空从头开始分配

组的宏观状态是四段循环：Empty（无成员）→ PreparingRebalance（收集中止续约，等待成员重新加入）→ CompletingRebalance（leader 算完，等全员同步）→ Stable（正常消费）。kafka-consumer-groups.sh --describe 能直接看到组当前停在哪一段。

Rebalance 期间的共同后果是停止拉取与停止处理，lag 开始累积。 eager 与 cooperative 的差别就在于「停多少」（见第五、六节）。

五、eager 协议：stop-the-world 的代价

5.1 两阶段语义

eager（也被称为 stop-the-world）把一次 rebalance 拆成两段：

  1. 撤销阶段：全组成员交回（revoke）所有分区
  2. 重新分配阶段：leader 算出新映射，全员拿到各自的新分区

只要有一个成员加入或离开，全组所有分区都要经历一次交回与重拿。这段时间里整个组的消费完全停止，lag 持续累积。

5.2 分配器与协议的绑定

分配器支持 eager支持 cooperative特点
RangeAssignor是否按 topic 顺序分连续区间，简单但可能不均
RoundRobinAssignor是否跨 topic 轮转分片，分布更均
StickyAssignor是否尽量少移动分区，但撤销阶段仍要交回全部
CooperativeStickyAssignor是是sticky + 只撤销本轮要移走的分区

这张表里最容易被忽略的一行是 StickyAssignor：sticky 只优化「分配结果少移动」，它不能优化「撤销范围」。只配 sticky 不改协议，Rebalance 的停顿依然覆盖全组。

六、协作式 rebalance 协议

6.1 语义与前提

cooperative（增量式）只撤销本轮确实要移走的分区，成员手里其余分区不中断。前提是分配器必须支持：RangeAssignor 与 RoundRobinAssignor 只能做 eager，要用 cooperative 必须选 CooperativeStickyAssignor。

6.2 收益与代价

维度eagercooperative
单成员加入/退出时的停顿全组停只有被移动的分区停
稳态下的顺序性重新分配后仍按 offset 递增不变
分配算法复杂度低，一次算完高，依赖上一轮分配状态，成员需在元数据里携带自己的既有分配
心跳体积小更大（携带分配信息）
连续增减员时一次算完，收敛快每次只移一部分，可能需要多轮才收敛
适用前提任意分配器分配器必须支持

「cooperative 一定更快」是错的：稳态下它更好，剧烈变动时 rebalance 次数可能更多。真正该看的是「一次成员变动造成的未消费时长」，而不是「rebalance 次数」。

6.3 group.protocol：classic 与 4.x 的 consumer

  • group.protocol 在 Kafka 4.x 下默认为 classic，4.x 新增可选值 consumer（新消费者组协议）
  • classic：本文前六节描述的形态——组内 leader 侧计算分配、JoinGroup 与 SyncGroup 两步同步、eager 或 cooperative 二选一
  • consumer：分配改由协调者（Broker）侧计算，不再有「组内 leader 算分配」这一步，也不需要独立的 SyncGroup 同步阶段；成员常态驻留，只有目标分区真正变化时才调整
  • 迁移代价：两种协议的分配时机、心跳内容、可观测指标都不一样，切换前要重新验证 lag 曲线与 rebalance 频率，不能沿用 classic 的排障经验

旧版做法（ZooKeeper 时代）

早期 Kafka 的消费组成员注册曾依赖 ZooKeeper 的/consumers 路径，0.9 起改为 Broker 侧的 GroupCoordinator 协议（本文描述的 JoinGroup / SyncGroup / 心跳）。ZooKeeper 从 4.0 起已从集群中移除，本篇所有内容都属于现行机制，不存在「旧版协调方式」。

七、max.poll.interval.ms 与消费线程的生死

7.1 两个计时器，各管一件事

计时器由谁发心跳语义超时后果
session.timeout.ms心跳线程协调者判定「成员是否还活着」的失联窗口成员被移出组
max.poll.interval.mspoll 调用协调者判定「成员是否还在正常消费」的窗口成员被移出组

Kafka 4.x 下 max.poll.interval.ms 的 A 级值为 300000 毫秒（5 分钟）（多版本文档页一致，含 3.4 文档页）。session.timeout.ms 只讲上述语义，默认值随版本变化，以你所用版本的官方文档为准。

最反直觉的一点：心跳线程是独立线程，心跳正常也不代表成员还在组内。 协调者同时在按 max.poll.interval.ms 计时，poll 不被调用就照样踢人。

7.2 「consumer 假死」

典型现象：进程活着、心跳正常、网络正常，但协调者不断把这个成员踢出去。

第 J 步是循环形成的真正原因：重新加入后的成员在完成首轮 poll 与处理之前就可能再次超时，于是陷入「加入 → 被踢 → 再加入」。

排查顺序：

  1. 先量批内处理耗时分布（不是平均值，要看 p99 与最大值）
  2. 检查是否有单条消息或单个分区长期卡住整个 poll 循环
  3. 检查 poll 循环是否被工作线程池饿死（例如线程池被占满，poll 迟迟排不上）
  4. 再考虑调大 max.poll.interval.ms 或调小 max.poll.records

7.3 一个必须会算的换算

max.poll.records 的 A 级值为 500（源码常量 DEFAULT_MAX_POLL_RECORDS），与 max.poll.interval.ms 的 300000 毫秒相乘得到一个关键约束：

一次 poll 拿 500 条，整批必须在 5 分钟内处理完，平均每条约 600 毫秒。批内只要出现一条慢消息或一次下游抖动，预算就被击穿，整批连带超时。

所以调大 max.poll.interval.ms 是治标，调小 max.poll.records 或按分区拆批处理才是治本。判断依据见 [[顺序消费与积压处理]]。

八、面试高频追问

按面试出现频率排序。

1. 消费组之间会互相影响吗？

答题骨架：机制上三层独立（位点、分配、读取），是 Kafka 少有的「天然隔离」设计。要主动补两个例外：同一 topic 被多组读会放大 Broker 读 IO；group.id 被不同程序错误复用会导致抢分区，因为分配范围是成员订阅的分区并集。

2. 消费者数量超过分区数会怎样？

答题骨架：多出来的成员拿不到任何分区，处于空闲状态。它们仍然是组内正式成员：仍然发心跳、仍然参与 rebalance 投票、仍然给协调者增加开销，但一条消息也拉不到。因此消费并行度上限等于分区数，扩消费者前必须先确认分区数。参见 [[顺序消费与积压处理]] 第五节。

3. 为什么 auto commit 会丢消息？

答题骨架：位点代表「读到哪了」，不代表「处理到哪了」。自动提交按 auto.commit.interval.ms 周期推进 poll 返回位置，业务处理落后于提交进度的那一段就被永久跳过。手动提交把丢失换成重复，即 at-least-once；两者都不丢则要靠业务幂等。

4. eager 和 cooperative 怎么选？

答题骨架：看成员变动频率与分组规模。成员稳定、规模小，eager 够用且逻辑简单；滚动发布频繁、组内成员多、分区数大，cooperative 值得开，因为单次成员变动只影响被移动的分区。前提是分配器必须选 CooperativeStickyAssignor，range 与 roundrobin 只能 eager。注意 cooperative 在剧烈变动时轮次可能变多。

5. 消费组一直 Rebalance 怎么排查？

答题骨架：先确认是「真频繁」还是「一次长停顿」——看 kafka-consumer-groups.sh --describe 的组状态与客户端的 rebalance 计数。频繁的话按可能性排序：max.poll.interval.ms 超时（看 poll 循环耗时分布，最常见）、session.timeout.ms 相对网络抖动过短、成员反复重启、下游依赖超时把批内耗时拉长。定位置后优先改处理耗时分布，而不是先调大超时。

6. auto.offset.reset 选错了会怎样？

答题骨架：它在没有已提交位点时（新组、位点被清理）决定起点。latest 跳过全部历史，earliest 从最早可用位点读。选 latest 的典型事故是新消费组上线后看不到任何历史数据；选 earliest 的典型事故是回放期把下游打垮。Kafka 4.x 还新增了 by_duration 形式的取值（例如 by_duration:P7D），用于表达「回看一段时长」。它不会覆盖已有位点，只填空白。

7. 位点是怎么存的？为什么重启能续上？

答题骨架：存在内部 topic __consumer_offsets，键是 group + topic + partition，值是下一条要读的 offset。所以重启只要拿到组名就能查到各分区位点继续拉。提交的是「一组分区的位点集合」，不是单个数字，因为 offset 只在分区内唯一。

8. 为什么不能把耗时处理逻辑直接放进 poll 循环？

答题骨架：可以，但整批耗时受 max.poll.interval.ms 约束，超时即被踢出组并触发全组 rebalance，还会拖慢心跳检测与新消息获取。正确做法是主循环持续 poll 维持成员身份，把记录按分区投给有界队列，位点由每个分区的队列消费进度决定，而不是由 poll 位置决定。具体实现见 [[顺序消费与积压处理]] 第四、五节。
