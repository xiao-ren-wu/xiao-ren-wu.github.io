Kafka 生产者索引

本页用途

生产者这一层回答三个问题：消息进哪个分区、怎么在可接受的延迟下把吞吐顶上去、可靠性阶梯怎么选。读完这两篇，能独立讲清「一条消息从send() 到被确认，中间究竟发生了什么」。

本篇笔记

笔记一句话说明何时读
分区选择、批量与压缩Partitioner 的三级判定链、key 与顺序性的绑定、batch.size 与 linger.ms 的攒批权衡、四种压缩算法的取舍排查吞吐上不去或延迟太高、压缩开了没收益；或要向别人解释「Kafka 为什么快」
幂等、acks 与事务acks 三档阶梯、ProducerId 加序列号的去重原理、max.in.flight 为何硬校验 5、事务两阶段提交与只读已提交隔离级别遇到重复消息、要配可靠性参数、或被问「幂等能不能等于 exactly-once」

关键结论

  1. 顺序保证的唯一客户端入口是 key。 同 key 哈希落同一分区，由单 Leader 追加写入兑现顺序。破坏它的有四类操作：扩分区、并发消费同一分区、失败重试、多实例发同一实体。代价是同一实体的消息被压在单个分区，有效并行度下降。
  2. 批量与压缩是同一条流水线上的前后两段。 batch.size 决定批次封口粒度（默认 16384 字节即 16 KiB，Kafka 4.x），linger.ms 决定批次不满时最多等多久（默认 5 毫秒，Kafka 4.x）。批次越小压缩率越差，所以只调压缩不调批量通常是白做。
  3. linger.ms 的默认值在 Kafka 4.0 由 0 改为 5。 开箱即攒批是 4.x 的行为，linger.ms=0 的即时发送语义只适用于 4.0 之前的版本。这是本主题最容易说错版本口径的一处。
  4. acks 与 min.insync.replicas 必须联动看。 后者的 Default 是 1、Recommended 是 2；若为 1，「等全部 ISR 确认」在副本数为 1 的分区上退化为「只等 Leader」，可靠性并未提升。副本因子为 1 时谈这个配置没有意义。
  5. 幂等解决的是「重试导致的写重复」。 它只覆盖单生产者会话、单分区内；消费侧重放、业务重复生产、跨分区原子性都不在范围内。批量越大，一次重复的量级越大，这是攒批与幂等之间的隐藏耦合。
  6. max.in.flight.requests.per.connection 在幂等开启时硬校验不超过 5，超出即启动失败。 上限来自重试与在途并发的乱序风险，而 5 换来的是单分区吞吐。配置约束，不是性能默认值。
  7. 事务只解决幂等解决不了的那部分。 跨分区、跨 topic 的原子可见性，以及把消费位点与生产动作放进同一次提交。端到端 exactly-once 是幂等加事务加消费侧只读已提交加位点入事务的四件套。多数业务不需要事务，先确认自己是不是在用事务解决幂等能解决的事。

一条消息的路程

学习顺序

  1. 先读 分区选择、批量与压缩，因为它是整条链路的前半段：消息进哪个分区、以什么形态发出去。后面 acks 与幂等的讨论都是在某个批量下发生的，重试一次的重复量级也由它决定，先读可靠性会缺少这一层前提。
  2. 再读 幂等、acks 与事务，因为「为什么会重复」这个问题只有在理解攒批与重试之后才成立。反过来先讲幂等，容易讲成一句背下来的口号。
  3. 读完后回到 Kafka 架构全景与角色分工 第四节的 produce 生命周期，把每一步对回架构里的位置。生产者配置的意义只有挂在「单 Leader 追加写入」这个结构事实上才讲得通。
  4. 接着读 Kafka 存储机制索引，补上吞吐的另一半来源（顺序写与零拷贝），并理解为什么「批量加压缩」必须配合零拷贝才构成完整答案。
  5. 最后读 Kafka 可靠性与投递语义索引 与 Kafka 消费者与消费组索引，把生产侧的保证与消费侧的语义接上。只讲生产者的 acks 而不讲消费侧位点提交时机，等于没讲投递语义。

配置项值适用版本一句话说明

linger.ms5 毫秒Kafka 4.x（4.0 起由 0 改为 5）批次不满时的等待上限

delivery.timeout.ms120000 毫秒（2 分钟）Kafka 4.xsend() 到收到确认的总时长上限，含重试

min.insync.replicas1（Streams 文档推荐 2）Broker 侧只对「等 ISR」那一档 acks 有意义

常见误区

  • 把 linger.ms=0 说成默认值。Kafka 4.x 的默认值是 5 毫秒（4.0 起由 0 改为 5）。
  • 以为压缩能单独提升吞吐。压缩作用在批次上，批次太小几乎等于没压。
  • 只把 acks 调到「等全部 ISR」而不动 min.insync.replicas，副本数为 1 时可靠性一点没变。
  • 以为幂等等于 exactly-once。幂等只管写侧重试，管不了消费侧重放。
  • 为了顺序把分区数压到 1。可靠性没提升，吞吐直接砍掉一个数量级。
  • 批量没调就报「Kafka 慢」。开箱的 batch.size 只有 16 KiB，多数场景需要按消息体大小单独调。
  • 声称「开了幂等就配好了」，不核对 retries 与 acks 是否冲突，因为这类降级不抛异常。
