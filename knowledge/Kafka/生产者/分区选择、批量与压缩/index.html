分区选择、批量与压缩

来源

基于 Kafka 4.x 官方文档与ProducerConfig 的配置校验逻辑整理。所有配置默认值均标注适用版本；随版本变化的项目单独用 callout 说明。 文中出现的消息大小、分区数、网络 RTT、请求速率等数值，一律是为讲解假设的示例值，不是 Kafka 的默认值。

生产者这一层只干三件事：决定消息进哪个分区、把它压成尽可能少的中单位、在延迟与可靠性之间选一个点。Kafka「快」的常见归因里有两条落在本篇（批量与压缩），另两条（顺序写、零拷贝）在 Kafka 存储机制索引；可靠性那一侧的阶梯在 幂等、acks 与事务。

一、Partitioner 如何决定目标分区

分区选择是一条有优先级的判定链，不是「一个算法」。

优先级调用方是否指定判定依据结果
1指定了 partition 参数该参数值直接写入该分区，key 被完全忽略
2未指定 partition，指定了 keykey 字节的哈希值同一 key 恒定落到同一分区
3两者都未指定内置分区器的粘性策略尽量往同一个分区攒，凑满一批或等待到期后再换分区

第 1 条是高频陷阱：显式指定 partition 的优先级高于 key。业务代码里如果「有时传 partition、有时传 key」，同一实体的消息会被打散到不同分区，顺序性直接失效。面试若被问「怎么强制写某个分区」，正确答法是传 partition，但必须同时说明这会放弃 key 带来的保序。

第 2 条是 Kafka 顺序保证的唯一客户端入口：默认对 key 取 murmur2 哈希再对分区数取模。

第 3 条是 Kafka 4.x 内置分区器的重要行为：对无 key 的消息采用粘性分区。这样一批消息（而不是一条）对应一个请求，请求数显著下降；代价是短时负载倾斜，在一个批次周期内新增的消息几乎全落在同一个分区。Kafka 4.x 另提供按 Broker 上报的分区负载做分配的自适应分区选项，属早期访问特性，启用前请查你所用版本的官方文档。

面试追问：key 相同的消息一定严格有序吗？

答：分区层面成立，客户端层面不绝对。四点必须说清：

  1. 哈希取模决定了同一 key 落同一分区，而分区由单个 Leader 追加写入，因此服务端写入顺序等于客户端的 append 顺序
  2. 扩分区会改变取模基数，同一 key 会被重新映射，扩容瞬间的顺序就断了
  3. 失败重试会破坏顺序：前面的消息重试未成功、后面的已成功，业务看到的就是乱序（重试的单位是整个批次，批量化会放大这一点，见第四节）
  4. 消费侧还必须单线程按序消费同一分区，并发消费或重试都会打乱（详见 顺序消费与积压处理）

二、自定义分区器的代价

实现 Partitioner 接口很容易，但它是一次用维护成本换灵活性的交易。内置分区器已经替你做完的事，自定义后全部回到你身上：

能力内置分区器自定义后由谁负责
key 哈希与取模已实现自己实现，且必须与历史分区映射保持兼容
无 key 时的负载均衡粘性策略自己实现，否则容易退化成单分区热点
批次粘滞与请求合并已实现自己实现，否则吞吐明显下降
顺序性前提（同 key 同分区）天然满足业务代码负责，写错无人报错
分区扩容后的行为取模自然重分布需要显式处理迁移期行为
客户端 API 演进官方跟随需要自己跟进并回归验证

最常见的翻车写法是「key 为空时返回固定分区」。 这条路径把「无 key 的消息」全部打到同一分区，结果是：单分区成为写入热点，buffer.memory 迅速耗尽，吞吐被钉死在一个分区上。排查时往往误以为是 Broker 侧问题。

第二条常见翻车是只按 key 哈希、不考虑分区数变化。分区数可以在不重建 Topic 的前提下增加（只能增不能减），一旦变化，同一 key 的落点随之改变，扩容前后的顺序性无法衔接。

面试追问：什么时候真的需要自定义分区器？

答题骨架（先给判断标准，再给代价）：只有当内置的哈希策略表达不了业务语义时才值得写。正当理由通常有两个：

  1. 需要按业务维度做亲和，例如同一租户的消息必须进同一分区以满足配额或限流，而 key 承载不了这个语义（可以用复合 key 解决，但会牵动上游）
  2. 需要热点感知或显式规避某些分区

代价必须一并说：放弃官方对请求合并与负载均衡的优化、放弃版本兼容性保证、顺序性的正确性从「框架保证」变成「你的代码保证」。答不到代价这一层，这个回答是不完整的。

三、消息 key 与顺序性的绑定关系

把这一节单独拎出来，因为「顺序保证」是本篇最容易被过度承诺的能力。

3.1 顺序保证来自单 Leader，不来自客户端

Kafka 的分区内有序是一个结构性事实：每个分区恰好一个 Leader，全部写入走这一条路径，天然串行。客户端做的只是「把需要有序的消息都送到同一个分区」。因此：

  • 保序粒度是分区，不是 topic，更不是集群
  • 跨 key 不保序，因为不同 key 会落到不同分区
  • key 为空时（走粘性策略）只保证同一批次内的顺序，批次切换即换分区

3.2 key 该选什么

选 key 的唯一标准是：它必须恰好等于「需要有序的那组实体的标识」。

场景合适的 key常见的错误选择
订单状态变更需有序订单号用户名（一个用户多个订单会互相阻塞）
同一实体的库存扣减商品 SKU订单号（会把不同商品强行串行）
日志类，无需顺序不设 key时间戳（会让相邻时间的消息挤进同一分区）
追求最大吞吐不设 key随机数（均匀打散了，但请求数不合并）

最后一行值得展开：不设 key 走粘性策略，吞吐往往优于设一个高基数 key。设 key 的代价是同一实体的所有消息挤在同一个分区，分区数不够时其余分区闲置，有效并行度下降。这是「保序」与「吞吐」的直接对赌。

3.3 四个会破坏顺序的操作

  1. 扩分区：取模基数变化，同 key 重新映射
  2. 并发消费同一分区：多线程处理等于放弃了消费侧顺序
  3. 失败重试：第 N 条重试未完成、第 N+1 条已成功，业务看到乱序
  4. 多个 Producer 实例发同一实体：不同实例各自持有自己的批次状态，没有任何机制让它们排队

第 4 条经常被忽略：保序的前提是「同一个实体始终由同一个 Producer 实例发送」。

四、批量发送：batch.size 与 linger.ms 的权衡

4.1 先分清两个「batch」

Kafka 里有两层常被混为一谈的批量：

层是什么受什么控制
客户端 RecordAccumulator按分区组织的内存缓冲区，攒住尚未发送的消息buffer.memory
协议层 RecordBatch一次请求实际携带的一段消息，压缩也作用在它身上batch.size

batch.size 默认 16384 字节（16 KiB，Kafka 4.x），含义是：同一个分区上，单个 RecordBatch 攒到 16 KiB 就封口。它不是「一次最多发 16 KiB」的上限约束，而是「多久封口一次」的切分粒度。

linger.ms 默认 5 毫秒（Kafka 4.x），含义是：批次没满时，最多等 5 毫秒就把它发出去。它管的是不满时的等待上限；批次一满立刻发，不等。

版本变化

linger.ms 的默认值在 Kafka 4.0 由 0 改为 5。本库基线是 Kafka 4.x，因此「攒批」是客户端的开箱行为；linger.ms=0 的「来一条发一条」语义只适用于 Kafka 4.0 之前的版本。在 4.x 上要立即发送必须显式配置，面试时把 linger.ms=0 说成默认值是版本口径错误。

4.2 用具体数字说明差别

以下全部是假设值。设：单条消息 1 KiB，稳态写入 1000 条/秒（约 1 MiB/秒），到 Leader 的 RTT 假设 5 毫秒。

配置每秒请求数（估算）单请求有效载荷消息可见延迟上界说明
linger.ms=0（< 4.0 语义）约 1000约 1 KiB约 1 个 RTT（5 ms）几乎每条一个请求，协议头与网络栈开销占比极高
linger.ms=5（Kafka 4.x 开箱值）约 200约 5 KiB约 linger.ms 加发送耗时请求数降到约五分之一
linger.ms=50约 20约 50 KiB约 50 ms 加发送耗时吞吐进一步提升，延迟上界抬到 50 ms
linger.ms=1000约 1约 1 MiB约 1 s 加发送耗时延迟不可接受，见下方与 delivery.timeout.ms 的关系

关键观察：linger.ms 从 5 调到 50，请求数少了一个数量级，代价是延迟上界从几毫秒抬到几十毫秒。 这就是全部权衡的形状：延迟换请求数与压缩率。

4.3 参数之间的相互约束

关系约束
linger.ms vs delivery.timeout.msdelivery.timeout.ms 默认 120000 毫秒（2 分钟，Kafka 4.x），约束的是从 send() 到收到响应（含重试）的总时长。linger.ms 若被设得接近或超过它，消息还在缓冲里就已被判定失败
batch.size vs 消息大小单条消息大于 batch.size 时，该条独占一个批次，batch.size 失效且每请求只带一条，批量收益归零
connections.max.idle.ms默认 540000 毫秒（Kafka 4.x），控制连接空闲回收。它是连接级参数，与批量快慢不直接耦合，但在 linger.ms 很大、连接长时间无流量的场景下会被触发

4.4 缓冲池满了会发生什么

buffer.memory 默认 33554432 字节（32 MiB，Kafka 4.x），这是整个 Producer 实例（不是每个分区）可用的发送缓冲总量。可用空间不足时有三种截然不同的状态，处理方式完全不同：

状态触发条件客户端行为可恢复性
等待分配缓冲池有空间但暂时被其他分区批次占用生产者线程等待分配，等待有上限（由 max.block.ms 一类参数约束，其默认值未在事实清单中取得官方对照，以你所用版本官方文档为准）超时后抛超时类异常，业务侧可重试
单批超限单条消息或单个批次大于整个 buffer.memory分配永远无法满足，抛内存耗尽类异常不可通过等待恢复，必须调大 buffer.memory 或调小消息体
静默丢弃缓冲在等待期间已超过总时长上限，批次被判定超时批次被丢弃，但它可能已经写进了 Broker 的日志调用方收到超时；若随后重试就会产生重复（幂等机制正是为解决这一点，见 幂等、acks 与事务）

第三行是本篇与幂等那一篇的接缝：批量越大，缓冲停留时间越长，超时与重试的耦合越强。调大 batch.size 之前要意识到你在同时放大这个风险。

面试追问：把 linger.ms 调大一定能提高吞吐吗？

答：不一定，分三种情况。

  1. 消息量已经远超网络能力时调大有用：请求数按 linger.ms 反比下降，协议头与系统调用开销被摊薄，吞吐上去了，代价是延迟上界同步抬升
  2. 消息量很小时调大几乎没用：可能一个 linger.ms 周期内只攒到一条消息，攒批根本没有发生，只是白等
  3. linger.ms 已大于可接受的延迟上界时，问题从「吞吐不足」变成「延迟不可用」，此时正确的做法是加分区而不是加 linger.ms

版本口径必须带上：Kafka 4.x 的 linger.ms 开箱值已经是 5 毫秒（4.0 起由 0 改为 5），所以「调大 linger.ms」是针对已经攒批的版本再调，不能把「linger.ms=0 立刻发」说成默认行为。

五、压缩算法选择

compression.type 默认 none（Kafka 4.x），即开箱不压缩。可选值：gzip、snappy、lz4、zstd。

压缩发生在客户端，且作用对象是第四节的协议层 RecordBatch，不是单条消息。

算法CPU 开销压缩率典型定位
none最低无消息体已压缩、或追求最低延迟
gzip高中到高兼容性好，CPU 换网络；老旧环境常用
snappy低低到中快速压解压，压缩率让步
lz4很低低极致的压解压速度，适合 CPU 紧张的场景
zstd中高兼顾速度与压缩率，Kafka 官方文档推荐用于追求高压缩比的场景

具体压缩率与 CPU 消耗强烈依赖消息内容（JSON、Avro、Protobuf 这类带重复结构的编码压缩率高；二进制、图片、已加密的载荷几乎压不动），必须用自己的消息样本实测，不能按上表选了就上线。

什么时候值得开：

  • 消息字段重复度高、序列化后冗余明显
  • 网络是瓶颈（跨机房、跨可用区）
  • 批量已经做得足够大（原因见第六节）

什么时候别开：

  • 载荷本身不可压缩（图片、音视频、加密后的字节流），开了只白烧 CPU
  • CPU 已经是瓶颈，压缩在生产者 I/O 线程上跑，会挤占发送能力
  • 延迟要求极端严格，压缩的 CPU 时间不可接受

六、压缩与批量的耦合关系

这两件事不是并列的两个优化，而是同一条流水线上的前后两段，且第二段的收益完全由第一段决定。

batch 大小每条消息摊薄的批次开销压缩效果结果
很小（1 到 2 条）批次头、CRC、offset 元数据被 1 到 2 条分摊几乎等于不压缩（无跨消息可复用的重复模式）负优化：白烧 CPU 还多花带宽
中等（10 到 20 条）开始摊薄重复字段被有效合并收益开始显现
接近 batch.size（16 KiB，Kafka 4.x）摊薄充分压缩率接近最优区间批量与压缩的组合收益最大

核心结论：压缩放大了批量配置的收益，而批量太小会让压缩变成负优化。 只调 compression.type 不调批量，收益很有限；反之只调批量不压缩，网络开销仍然偏高。两者一起调，才是 Kafka 高吞吐的完整来源。

顺带澄清一个常见混淆：压缩与顺序性无关。压缩发生在发送路径上，不改变 offset 的分配与语义；key 决定的分区归属也不受压缩影响。

七、面试高频追问

按面试出现频率排序。

1. batch.size 和 linger.ms 分别控制什么？想降低发送延迟该调哪个？

答题骨架：batch.size 控制批次封口的粒度（满了就发，默认 16384 字节即 16 KiB，Kafka 4.x）；linger.ms 控制不满时最多等多久（默认 5 毫秒，Kafka 4.x，且 4.0 起由 0 改为 5）。要降延迟优先调小 linger.ms，因为它是「主动等待」的那一项；调小 batch.size 也能提发送频率，但会降低压缩率并增加请求数，通常不是首选。注意 Kafka 4.x 上两者开箱即带攒批行为，「立刻发」需要显式把 linger.ms 设为 0。

2. 把 batch.size 调大一定会变快吗？

答题骨架：不一定，且可能变慢。小消息量时，调大 batch.size 会让批次更难填满，反而延长每条消息的等待时间；消息体本身大于 batch.size 时，该条独占一个批次，批量收益为零。真正有效的方向是先让消息量与分区数匹配，再谈 batch.size 与 linger.ms。

3. 压缩和批量必须一起做吗？

答题骨架：必须。压缩作用在协议层批次上，批次越小压缩率越差，接近单条时压缩等于白做。先把批量调大到能稳定填满的量级，再开压缩，收益才是叠加的。反过来，「消息体不可压缩」的场景（图片、已加密载荷）两个都不必开。

4. 要保证同一实体的消息有序，key 该怎么设？什么时候会失效？

答题骨架：key 必须恰好是「需要有序的那组实体的标识」，同 key 经哈希落同一分区，由单 Leader 追加写入兑现顺序。失效场景四个：扩分区（取模基数变化）、并发消费同一分区、失败重试（重试单位是批次，批量化会放大乱序）、多个 Producer 实例发同一实体（实例间无排队机制）。还要补一句代价：设 key 会把同一实体的消息压在单个分区，有效并行度下降，分区数不足时吞吐会掉。

5. buffer.memory 不够用时，Producer 会怎样？为什么这个问题比想象中难处理？

答题骨架：三种状态分开答。可恢复的是「等待分配」，生产者等待（有上限，超时抛异常）；不可恢复的是「单批超限」，消息体或批次大于整个缓冲池时分配永远不满足，必须调大 buffer.memory 或缩小消息体；最隐蔽的是「静默丢弃」，批次因超过总时长上限被判定失败，但它可能已经写进了 Broker 的日志，调用方重试就会产生重复。难处理的原因是第三种状态：客户端报的是失败，Broker 那边却可能有数据，只能靠幂等机制去重（详见 幂等、acks 与事务）。

6. 自定义分区器的代价是什么？

答题骨架：见第二节。核心一句是：你放弃了官方对请求合并、负载均衡与版本兼容性的全部优化，并把「顺序性正确」从框架保证降级为自己的代码责任。最常见的错误实现是无 key 时返回固定分区，会把单分区变成写入热点。

7. linger.ms=0 是不是延迟最优？

答题骨架：这是版本陷阱题。linger.ms=0 的「来一条发一条」语义只适用于 Kafka 4.0 之前的版本；Kafka 4.0 起默认值改为 5 毫秒，Kafka 4.x 上必须显式配置 0 才是即时发送。而且即使设为 0，也不等于「每条一个请求」：批次一满会立即触发发送。因此正确答法是「设为 0 去掉了主动等待，但实际发送时机仍由批次状态决定」。
