幂等、acks 与事务

来源

基于 Kafka 4.x 官方文档与ProducerConfig 的配置校验逻辑整理。所有配置默认值均标注适用版本；acks 的默认值本篇刻意不给，理由见第一节末。 文中出现的分区数、副本数、请求超时等数值，除明确标注为官方配置项默认值者外，一律是为讲解假设的示例值。

「消息发出去了，但客户端说是失败」是生产者最常见的一类线上事故。本篇回答三个问题：为什么会重复、acks 三档怎么选、幂等到底覆盖到哪里为止。生产者的性能侧（分区选择、批量、压缩）在 分区选择、批量与压缩；端到端的投递语义在 投递语义与消息去重。

一、acks 三档的可靠性与吞吐阶梯

acks 决定客户端在发送后等待到什么程度才算成功。三档构成一条可靠性与吞吐成反比的单调阶梯。

档位客户端等待什么典型丢失窗口吞吐与延迟代价
只等 LeaderLeader 本地 append 成功即返回Leader 确认之前宕机，该批消息丢失往返最短，吞吐最高
等 ISR 全部确认ISR 内所有副本确认后才返回取决于 min.insync.replicas，见下方联动分析需等最慢副本，延迟与吞吐都最差
不等任何确认请求发出即返回包含「发出即丢」，且客户端无法感知成败表面最快，可靠性与可观测性最差

1.1 acks 与 min.insync.replicas 的联动

这是本节最容易被跳过、也最容易答错的一段。

Kafka Streams 官方文档的 resiliency 表给出：min.insync.replicas 的 Default 是 1，Recommended 是 2。由此可以推出两个结论：

配置组合实际效果
等 ISR 档 + min.insync.replicas=1当分区只有 Leader 一个副本在 ISR 里时，「等全部 ISR 确认」退化为「只等 Leader」，可靠性没有提升。多数单副本部署就是落在这个组合上
等 ISR 档 + min.insync.replicas 大于 1达不到副本数时，写入直接失败（典型异常为副本不足类）。这是显式用可用性换可靠性
只等 Leader 档 + 任意 min.insync.replicas对写入确认路径无作用：acks 只等自己，min.insync.replicas 抬到几都不会让客户端多等一个确认。但它并非完全无效，见下方可见性说明

必须补上可见性这一层：官方文档对 min.insync.replicas 的语义有两句，其中第二句是「无论 acks 怎么设，消息都要等到复制到所有 ISR 副本、且 min.insync.replicas 条件满足之后，才对消费者可见」。也就是说这个配置有两个作用域，acks 只决定生产者什么时候收到确认，min.insync.replicas 决定数据什么时候对消费者可见（以及副本不足时是否拒绝写入）。把「只等 Leader」当成「消息立刻对消费者可见」是错的。

官方给出的典型组合原文是：创建副本因子为 3 的 Topic，把 min.insync.replicas 设为 2，用 acks=all 生产，官方称这会确保多数派副本持久化后才算成功。

也就是说：想把「等 ISR」这一档用出真实收益，必须同时把 min.insync.replicas 抬到 2 或以上。 只改 acks 不改它是自欺欺人。

1.2 「不等任何确认」这一档的额外问题

它不只是「可靠性低」，而是会同时破坏可观测性：

  1. 重试机制失去意义：没有响应就没有成败判定，客户端无从判断该不该重试
  2. 超时也救不了：delivery.timeout.ms（默认 120000 毫秒即 2 分钟，Kafka 4.x）到期只是客户端放弃等待，消息可能早已写进 Broker 的日志。于是同一次调用既可能丢也可能重复，而客户端两种情况看到的都是超时
  3. 与幂等互斥：无法区分「没写成功」与「写了但没收到响应」，就没有去重的前提

1.3 关于 acks 的默认值

本篇不给出 acks 的默认值。原因有两条，都不是偷懒：

  • 事实清单中该项的置信度为未核验：官方配置文档页是一整张长表，搜索摘录经常把某个配置的说明与下一行配置的默认值配对，历史上已经因此误取过别的配置的值
  • 凡「拿到的值与配置名语义不符」的，一律按未核验处理

结论：acks 的默认值随版本变化，以你所用版本的官方文档为准。 需要说明的是，无论默认值落在哪一档，上面 1.1 与 1.2 的分析都成立，因为它们讨论的是语义与联动关系，不是数字。

二、幂等生产者解决了什么

2.1 问题的根因：网络超时不等于写入失败

客户端发送一个批次后，在总时长上限（delivery.timeout.ms，默认 120000 毫秒即 2 分钟，Kafka 4.x）内没收到响应，就判定失败并重试。但第一次请求可能已经成功写入。于是 Broker 的日志里出现两条内容相同、offset 不同的消息，而客户端只发出了一条。

放大因素是批量：批次越大，一次重复的量越大。这就是为什么 分区选择、批量与压缩 里的攒批策略与本篇的幂等必须一起考虑。

2.2 幂等的定义与边界

幂等生产者保证：同一次逻辑发送，在客户端重试之后，只被 Broker 接受并写入一次。

它不保证：

  • 业务上只处理一次（消费侧重放导致的重复不在其列）
  • 业务重复生产被去重（同一条业务消息被代码主动发两次，幂等管不了）
  • 跨分区、跨 topic 的原子性（那是事务的职责，见第五、七节）

enable.idempotence 自 Kafka 3.0 起默认 true（Kafka 4.x 沿用），且一旦为 true，部分冲突配置会使它被禁用而不是生效（见第四节）。

三、PID + 序列号的去重原理

幂等不是靠「消息里带个指纹让 Broker 查重」实现的，而是靠单调序列号加状态比对。

要素是什么谁分配
ProducerId（PID）生产者在 Broker 侧的逻辑身份客户端向事务协调器发起 InitProducerId 时由协调器分配
epoch同一 PID 下的世代号，防旧实例继续写入协调器分配，随 fencing 递增
序列号（sequence number）该生产者在某个分区内的追加序号，从 0 开始单调递增客户端按分区维护
去重窗口Broker 为每个「PID + 分区」维护的已见最大序列号Broker 维护

Broker 侧的去重判定逻辑：

三点必须说清：

  1. 重复批次返回的是「成功」而不是错误。这很关键：客户端收到成功就停止重试，重试链路自然收敛。若返回错误，客户端会继续重试，形成活锁。
  2. 序列号是每分区独立的。同一 PID 在分区 0 的序列号 5 与在分区 1 的序列号 5 毫无关系，也不存在跨分区的顺序保证。
  3. epoch 防的是旧实例。同一 transactional.id 的新实例启动时，协调器会提升 epoch 并把旧实例 fence 掉，旧实例即使还持有旧 PID 也无法继续写入。

四、幂等的前提条件与失效场景

4.1 配置前提

幂等不是一个独立开关，它有一组必须同时成立的配置前提。违反其中任何一条，结果不是「顺序有点乱」，而是幂等直接被禁用或客户端启动失败。

配置项幂等开启时的要求或约束违反后果
enable.idempotence为 true（自 Kafka 3.0 起的开箱值）不满足时其他约束不生效
retries必须大于 0冲突配置会使幂等被禁用
acks必须是「等全部确认」那一档禁用幂等。理由：只有全确认才能区分「没写成功」与「写了但没收到响应」
max.in.flight.requests.per.connection硬校验不超过 5超出即在启动时抛配置异常，不是运行时才暴露
事务超时相关参数需与实际事务时长匹配事务被超时中止，数据不可见（事务生产者场景）

其中 retries 与 acks 的特点是「冲突不报错，只是静默降级」，这类降级最难发现，因此排障时要主动去核对生产的实际配置，而不是相信「我开了幂等」。

4.2 为什么在途批次硬校验不超过 5

先说事实：幂等开启时，max.in.flight.requests.per.connection 超过 5 会在客户端启动时抛 ConfigException。

再说原因。同一分区上，客户端可以同时有多个未确认的批次在途。当其中一个批次因超时被判定失败并重发时，它与后续已在途或已成功的批次在实际到达顺序上就可能交错：

  • 若无上限在途，一条排在后面的消息可能先被追加写入
  • 而前面失败的消息随后重发并被写入
  • 结果是同一分区内的实际写入顺序与客户端的发送顺序不一致

Broker 依据序列号做出的「重复 / 过期 / 乱序」判定，在这种交错下不足以保证分区内顺序。因此 Kafka 把边界定在 5，官方选择这个值而不是 1，是在「顺序性」与「单分区吞吐」之间取的一个经测试验证的点：单分区可以同时有 5 个未确认批次，网络往返期间不空转，吞吐显著高于串行发送 1 个，而顺序性仍由序列号保住。

必须补上的一句：这个 5 是配置约束（客户端校验），不是性能默认值。想调得更大只有两条路，关掉幂等并接受乱序，或者靠加分区提升总吞吐而不是加在途并发。

这条约束的消费侧后果见 顺序消费与积压处理：分区内顺序一旦被破坏，消费者的按序处理就失去前提。

4.3 幂等覆盖不到的场景

场景幂等是否覆盖说明
同一 Producer 实例重试同一批次覆盖序列号相同，Broker 判重丢弃
同一实体由多个 Producer 实例各发一次不覆盖PID 不同，Broker 视为两次独立追加
业务代码主动把同一条业务消息发两次不覆盖两次是不同的逻辑发送，序列号也不同
跨分区的顺序与去重不覆盖序列号与去重状态都按分区独立维护
跨 topic 的原子可见性不覆盖需要事务
消费者位点回退导致的重复消费不覆盖幂等只管写侧
消费组重平衡导致的重复消费不覆盖同上
客户端被显式配置为「不等确认」不覆盖且无法真正开启无确认就没有判定去重的前提

结论：幂等是「重试去重」，不是「业务去重」。 只要回答里出现「幂等保证不重复」而不加限定，就是错的。

五、事务生产者的两阶段提交

幂等的边界在第五节被推到尽头：它能保证「一次逻辑发送不重复」，但保证不了「多次发送要么全成要么全不成」。

5.1 事务解决什么问题

假设一个业务操作要同时写 orders 与 inventory 两个 topic。幂等保证每条消息各自不重复，但不能保证两个 topic 的写入进度一致：第一个写成功、第二个失败时，数据已经不一致。事务就是为这个场景设计的。

transactional.id 是客户端配置的稳定标识，与运行时分配的 PID 是两个东西：前者写在配置文件里、跨进程重启保持不变；后者是运行时由协调器分配的、可能变化。同一 transactional.id 的新实例启动会 fence 掉旧实例（提升 epoch），这是防止两个实例同时写同一逻辑事务的关键。

5.2 完整流程

abortTransaction 是同一条链路的另一分支，效果是这批消息对所有消费者都不可见。

5.3 事务的代价

事务不是免费的，代价有四处：

  1. 多一次与协调器的交互（InitProducerId、AddPartitionsToTxn、EndTxn），每笔事务都增加往返
  2. 事务状态日志：协调器要持久化事务元数据，Broker 上有额外的存储与清理开销
  3. 控制记录：每个事务在分区日志尾部写入提交或中止标记，占用日志空间
  4. 消费侧阻塞：read_committed 消费者会停在未决事务之后，吞吐下降（见第六节）

选型判断：绝大多数业务不需要事务。 先确认自己是不是在用事务解决幂等就能解决的事。只有当业务确实要求「跨分区、跨 topic 原子可见」或「把消费位点与生产动作放进同一次提交」时，事务的成本才划得来。

六、read_committed 隔离级别

事务写入的消息在提交前处于「未决」状态，消费侧要不要看它，由隔离级别决定。两档语义如下：

隔离级别对未决事务数据的处理代价
读未提交照常返回，可能读到随后被中止的事务数据吞吐最高，语义最弱
只读已提交只返回已提交事务的数据；遇到未决事务会阻塞等待，直到其提交或中止吞吐下降，可读到的位置可能落后于日志末尾

「只读已提交」的实现依赖一个概念：消费者能读到的最远位置由未决事务决定，而不是由日志末尾决定。因此当上游存在长时间未决的事务时，只读已提交的消费者会表现为「消费位点不动」，但日志其实还在增长。

这个症状是很好的排障线索：只读已提交的消费者卡住，先去查上游有没有长时间未决的事务（生产者事务既没 commit 也没 abort），而不是去查消费者本身。次要线索是保留策略压力：事务状态本身也要保留，保留配置过紧会让未决事务的状态先被清掉，进而影响恢复。

Kafka 官方定义的端到端 exactly-once语义读，是四个条件的组合，缺一不可：

  1. 幂等生产者（去重写侧重试）
  2. 事务生产者（跨分区原子可见）
  3. 消费侧使用只读已提交隔离级别
  4. 消费位点通过 sendOffsetsToTransaction 纳入同一事务

只开幂等不满足第 2 到第 4 条，就不构成 exactly-once。这一点在 投递语义与消息去重 里会再展开。

七、幂等与事务的边界

能力幂等生产者事务生产者
单分区内重试去重支持支持（内部依赖幂等机制）
跨分区原子可见不支持支持
跨 topic 原子可见不支持支持
消费位点与生产原子提交不支持支持（sendOffsetsToTransaction）
端到端 exactly-once不支持支持（需消费侧配合只读已提交）
额外成本序列号 + Broker 侧去重状态事务协调往返、事务状态日志、控制记录、消费侧阻塞

一句话切分边界：幂等解决「重试重复」，事务解决「原子性」。

这是面试里最常被压缩成一句话、也最容易因此答错的地方。两个常见错误：

  • 错误一：「事务包含幂等，所以开了事务就不用管幂等」。方向反了，是幂等是事务的前提，不是反过来。事务在实现上依赖 PID 与序列号这套机制，没有幂等就没有事务。
  • 错误二：「想要 exactly-once 就开事务」。事务只是四件套里的两件，缺了消费侧的只读已提交与位点入事务，业务仍然会看到重复。

八、面试高频追问

1. 幂等能保证 exactly-once 吗？

答：不能，这是高频陷阱题。 幂等的保证范围是「同一次逻辑发送在重试后只被 Broker 接受一次」，且仅限单生产者会话、单分区内。它管不了三件事：消费侧位点回退或重平衡导致的重复消费、业务代码主动重复生产、跨分区跨 topic 的原子性。Kafka 官方定义的 exactly-once 语义是幂等 + 事务 + 消费侧只读已提交 + 消费位点纳入事务四件套，只开幂等最多拿到「写侧不因重试而重复」，不是端到端的 exactly-once。业务侧去重表仍然是兜底手段，详见 投递语义与消息去重。

2. 为什么 max.in.flight.requests.per.connection 不能超过 5？

答：先给硬事实：幂等开启时该值超过 5 会在启动时抛 ConfigException。原因是同一分区上多个未确认批次在途时，失败批次的重发会与后续批次在实际到达顺序上交错，可能出现「后面的先写入、失败的前面随后补写」，导致分区内实际顺序与客户端发送顺序不一致；Broker 依据序列号做的重复、过期、乱序判定在这种交错下不足以守住顺序。5 是 Kafka 取的一个经测试验证的平衡点：单分区可同时保持 5 个未确认批次，网络往返期间不空转，吞吐明显高于串行发 1 个，顺序性仍由序列号保住。要更高并发，正确做法是加分区，不是加在途并发。顺序被破坏的消费侧后果见 顺序消费与积压处理。

3. acks 该怎么选？要不要设成「等全部 ISR」？

答：先说三档的语义（只等 Leader、只等 ISR、不等确认），再说选型。关键是不能只看 acks，必须和 min.insync.replicas 联动看：官方 Streams 文档的 resiliency 表给出该配置 Default 为 1、Recommended 为 2。只把 acks 调到「等全部 ISR」而 min.insync.replicas 还是 1 的部署，在副本数为 1 的分区上等于「只等 Leader」，可靠性一点没提升。反过来把它抬到 2，写入在副本不足时会直接失败，这是显式用可用性换可靠性。至于默认值是多少，请以你所用版本的官方文档为准，本篇刻意不给数字（官方配置页是单一大表，摘录极易错位配对）。

4. min.insync.replicas 设 1 还是 2？

答：Streams 官方文档的 resiliency 表给的建议是 Default 1、Recommended 2，即生产环境建议 2。但要说清生效条件：它只对「等全部 ISR 确认」那一档 acks 有意义；acks 若只等 Leader，这个配置对写入确认路径基本无作用。副本因子为 1 的 Topic 更是完全用不到它，这种情况下谈 min.insync.replicas 没有意义，先把副本因子提到 2 或 3 才是有效动作。详见 复制模型与 ISR。

5. 幂等开了，还需要业务侧去重吗？

答：需要。幂等的边界之外至少还有两类重复它管不了：消费侧的重复（位点回退、消费组重平衡导致同一条消息被处理两次）以及业务侧的重复生产。幂等解决的是「网络重试导致的写重复」这一个特定成因。实践中把「业务唯一键 + 去重表」作为兜底是常规做法，幂等是把兜底之前的重复率降下来，两者不冲突。

6. transactional.id 和 ProducerId 有什么区别？为什么需要 transactional.id？

答：PID 是运行时由事务协调器分配的逻辑身份，可能变化；transactional.id 是配置里的稳定标识，跨进程重启不变。transactional.id 的核心作用是防脑裂：同一 transactional.id 的新实例启动时，协调器提升 epoch 并 fence 掉旧实例，旧实例即使还持有旧 PID 也无法再写入。如果每次启动都生成新的 transactional.id，旧实例就不会被 fence，可能出现两个实例同时写「本该是一个事务」的数据，原子性彻底失效。

7. 消费侧用了只读已提交，位点不动但日志还在涨，怎么排查？

答：只读已提交的消费者能读到的最远位置由未决事务决定，而不是日志末尾。所以现象是「位点卡住但日志在长」，指向的是上游事务而不是消费者本身。排查顺序：先确认上游是否有一个事务既没提交也没中止（生产端进程挂起、异常路径漏掉 abortTransaction 是典型原因）；再看事务超时相关参数是否与实际事务时长匹配；最后看保留策略压力，事务状态本身也要保留，配置过紧会让未决事务的状态先被清理，反而掩盖根因。

8. retries 和幂等是什么关系？

答：幂等开启要求 retries 大于 0，这是官方配置校验里的硬性要求；更重要的是，冲突配置下幂等会被禁用。这一类降级不抛异常，只是悄悄把幂等关掉，是最难发现的故障类型之一。因此排障时不能相信「我配置里开了幂等」，要去核对生产的实际配置里 retries、acks、max.in.flight 三项是否与幂等一致。
