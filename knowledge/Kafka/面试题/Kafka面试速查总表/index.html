Kafka 面试速查总表

来源

基于 Kafka 4.x 官方文档与源码整理，并逐条对照本库核对清单分级。凡标注「不写数字」的配置项，只讲语义不报数值，默认值随版本变化，以你所用版本的官方文档为准。

本页是全库 11 篇正文的浓缩面，按主题排成可直接扫读的速查表。每一行给出「问题 → 一句话结论 → 追问点 → 出处」，其中「追问点」是面试官顺着这句继续往下问的方向，答出它才算答完。凡是「陷阱题」一节的题，答错比不会更扣分，因为错答通常来自一个似是而非的直觉。

一、答题总纲：四段式与三条纪律

Kafka 面试的高分答案有固定形状，结论 → 机制 → 边界 → 代价。缺任何一段都会被打回：

段落回答什么反例
结论一句话说清是什么、会不会、能不能「Kafka 的高可用主要靠副本机制」（等于没答）
机制靠哪个结构、哪个变量实现只说结论不给机制，追问一句就空
边界什么情况下不成立、什么情况下被破坏「开了幂等就不重复」（边界全错）
代价得到这个保证付出了什么只讲收益不讲代价，等于推销不是分析

三条通用纪律：

  1. 每个数值类回答必须带版本。 Kafka 的默认值跨版本变动过，linger.ms 就是现成例子。带版本不只是严谨，也是区分「读过文档」与「背过」的最快信号。
  2. 每个可靠性类回答必须说清丢的是哪一段。 「可能丢消息」等于没答。要指明是生产端未确认、Broker 端未复制，还是消费端位点已推进。
  3. 不确定就说语义与口径，不硬凑数字。 「三档语义分别是……，默认值以你所用版本文档为准」是完整答案；「默认是 1」若错了，整段可信度一起崩。

问题一句话结论追问点详见
Kafka 属于 MQ 还是流平台？定位偏事件流：消费不删数据只推进位点，因此可重放、可多组独立消费这个定位的代价是什么Kafka 架构全景与角色分工
Broker 与 Controller 职责边界？两者是并列的进程角色：Broker 存数据与收发消息，Controller 只维护元数据与选主，不存数据Controller 挂了集群还能读写吗Kafka 架构全景与角色分工
Topic 与分区什么关系？Topic 是逻辑名，数据只存在于分区；分区只能增不能减，直接决定消费并行度上限扩分区对顺序有什么影响Kafka 架构全景与角色分工
为什么每分区只放一个 Leader？为了读写路径无协商；本质是用副本数换可用性，不换读扩展性Leader 切换期间会怎样Kafka 架构全景与角色分工
offset 是全局唯一的吗？不唯一。offset 只在分区内唯一且单调递增，跨分区重号，位点必须成对表示 (partition, offset)为什么早期不用全局唯一 IDKafka 架构全景与角色分工
一条消息从 send() 到被读到经过什么？取路由、选分区、发给 Leader、分配 offset 并写日志、按 acks 确认、异步复制、消费者拉取、处理、提交位点处理与提交的先后决定什么Kafka 架构全景与角色分工
Controller 与 Broker 是同一个进程吗？一个 Broker 进程可同时承担两种角色，但 Kafka 4.x 官方建议关键环境不要用合并模式合并模式的代价KRaft 协调与选主

四、存储与页缓存：速查

问题一句话结论追问点详见
为什么追加写而不是原地更新？日志流读多写少，追加写换顺序吞吐、offset 自描述、天然有序三个好处；代价是删除变粗粒度、不能改单条删除怎么做分区日志与稀疏索引
段文件为什么以 offset 命名？offset 就是位置，先对段首 offset 二分就能跳过整段，连 .index 都不用打开段数量多了会怎样分区日志与稀疏索引
为什么不是每个分区一个文件？删除的最小单位是文件，保留策略必须以文件为粒度；分小段还让压实可以增量推进元数据开销分区日志与稀疏索引
稀疏索引的扫描上界是多少批？min(采样间隔, 平均批大小) 个批头；Kafka 4.x 采样间隔 index.interval.bytes 为 4096 字节批比间隔大时扫描几次分区日志与稀疏索引
能不能做到 O(1) 按 offset 定位？理论要靠稠密索引，代价是索引体积接近数据体积（压缩后消息长度可变）且索引变随机写热点，不划算实际的复杂度是多少分区日志与稀疏索引
零拷贝真的零次拷贝吗？不是。省掉的是「内核页缓存到用户空间缓冲」这一跳与随之而来的上下文切换，DMA 拷贝始终存在省下的到底是哪两次零拷贝、页缓存与保留策略
Kafka 有把数据写盘吗？Kafka 4.x 默认不主动 fsync，acks=all 的可靠性依据是「任意单节点故障不丢」，不是「已落盘」单机掉电不丢怎么办零拷贝、页缓存与保留策略
delete 与 compact 有什么区别？delete 按保留时间与大小删段；compact 按相同 key 保留最新版本，且 offset 不变，所以位点提交与消费者进度不受影响压实最多浪费多少空间零拷贝、页缓存与保留策略
正在被读的段被删会怎样？段列表写时复制，读侧继续在不可变快照上二分，删除要等引用释放才真正 unlink引用登记在哪一步分区日志与稀疏索引
怎么防止日志被写坏？三层：顺序写避免并发冲突，RecordBatch 自带 CRC-32C 覆盖「追加垃圾」这种静默损坏，启动恢复逐条校验并截断到最后一个有效 offsetCRC 能防丢失吗分区日志与稀疏索引

五、生产者：速查

问题一句话结论追问点详见
Partitioner 怎么决定分区？三级判定：显式指定 partition 优先，其次按 key 哈希取模，都没有则用轮询或粘性策略保证同一 Producer 均匀分布key 相同就一定严格有序吗分区选择、批量与压缩
什么时候真的需要自定义分区器？只有内置哈希表达不了业务语义时。正当理由是业务维度亲和或热点规避，代价是放弃请求合并优化与版本兼容，顺序正确性从框架保证变成自己的责任复合 key 能不能替代分区选择、批量与压缩
batch.size 与 linger.ms 怎么权衡？batch.size（默认 16384 字节即 16 KiB，Kafka 4.x）定批次封口粒度，linger.ms（默认 5 毫秒，Kafka 4.x，4.0 起由 0 改为 5）定批次不满时的等待上限调大 linger.ms 一定提高吞吐吗分区选择、批量与压缩
压缩和批量是什么关系？压缩作用在批次上，批次太小几乎等于没压；所以先调批量再开压缩，只开压缩通常是白做压缩算法怎么选分区选择、批量与压缩
acks 三档语义0 不等确认、1 只等 Leader、all 或 -1 等全部 ISR 副本确认；可靠性与吞吐成反比。默认值随版本变化，以你所用版本的官方文档为准必须和什么联动看幂等、acks 与事务
幂等靠什么去重？Broker 依据 ProducerId 加序列号识别重复、过期与乱序批次；覆盖范围只有单生产者会话、单分区的重发等于 exactly-once 吗幂等、acks 与事务
幂等开启后还必须配什么？retries 必须大于 0；max.in.flight.requests.per.connection 在幂等下硬校验不超过 5，超出启动即抛 ConfigException，这是硬约束不是性能取值，要更高并发应加分区静默降级怎么发现幂等、acks 与事务
事务解决什么幂等解决不了的问题？跨分区跨 topic 的原子可见性，以及把消费位点纳入同一次提交；transactional.id 跨重启稳定，用于把旧实例 fence 掉幂等够用就别开事务吗幂等、acks 与事务
read_committed 能读到哪？上界是 LSO，即最后一个未完成事务的 offset 减一，不是 HW；这类消费者算出的 lag 会偏高lag 偏高怎么区分根因幂等、acks 与事务

六、消费者与消费组：速查

问题一句话结论追问点详见
消费组之间会互相影响吗？机制上三层独立：位点按 group.id 分键存储、各组独立分配与独立 Rebalance 节奏、各组独立发 FETCHgroup.id 复用的表现消费组、位点提交与 Rebalance
一个分区能同时给几个消费者？同一消费组内同一时刻只给一个成员，多出的成员只发心跳不消费，并行度上限因此等于分区数加消费者为什么没用消费组、位点提交与 Rebalance
位点存在哪？内部 topic __consumer_offsets，键是 group 加 topic 加 partition，值是下一条要读的 offset；提交的是一组分区的位点集合位点会自己消失吗消费组、位点提交与 Rebalance
auto commit 为什么丢消息？提交的是 poll 返回的位置而非处理完成的位置，业务处理落后的那一段被永久跳过手动提交就不丢了吗消费组、位点提交与 Rebalance
什么情况触发 Rebalance？成员加入或离开、订阅变化、心跳失联、poll 间隔超时，四类触发源频繁 Rebalance 怎么定位消费组、位点提交与 Rebalance
eager 与 cooperative 怎么选？eager（range 与 roundrobin）先撤销全部分区再分配，单成员进出即全组停顿；cooperative 需 CooperativeStickyAssignor，只撤销本轮要移走的分区，剧烈变动时轮次可能更多新老成员同时存在会怎样消费组、位点提交与 Rebalance
poll 间隔超时击穿会怎样？成员被踢出组，eager 协议下触发全组 Rebalance，表现为进程活着、心跳正常、消费毫无进展的循环和心跳失联窗口什么关系消费组、位点提交与 Rebalance
auto.offset.reset 什么时候生效？只在没有已提交位点时（新组、位点已被保留策略清理）填空白，不覆盖已有位点新组上线看不到历史怎么办消费组、位点提交与 Rebalance
积压了加消费者行不行？先看分区级 lag：均匀涨是整体能力不足，个别涨是单分区瓶颈，加了也无效扩分区呢顺序消费与积压处理
怎么实现顺序消费？生产侧用 key 绑定分区，消费侧每分区单线程串行加位点按已处理的连续前缀提交；重试插队、扩分区、无 key 并发生产、多线程消费都会破坏毒消息卡住怎么办顺序消费与积压处理
Kafka 有死信队列吗？没有。跳过坏消息必须由应用实现重试上限与旁路存储阻塞式重试为什么没告警顺序消费与积压处理

七、复制与 ISR：速查

问题一句话结论追问点详见
ISR 是谁维护的？Leader 自己维护，Controller 完全不参与判定，只负责副本分配与选主Controller 挂了 ISR 还判吗复制模型与 ISR
HW 怎么算出来？ISR 内所有副本 LEO 的最小值减一，它同时是消费者的可见上界生产者拿到成功确认但消费者读不到复制模型与 ISR
HW 停滞算丢消息吗？不算。数据在 Leader 日志里，副本追平即立刻前进，这是用延迟可见换不丢数据真正的丢消息形态是什么复制模型与 ISR
ISR 收缩由什么控制？replica.lag.time.max.ms（默认 30000 毫秒即 30 秒，read-only）：Follower 在这么长时间内没有发起任何 fetch 请求、或没有消费到 Leader 的 LEO，Leader 就把它移出 ISR扩张需要人工干预吗复制模型与 ISR
ISR 收缩为什么会导致写不进去？min.insync.replicas（默认 1，Kafka 官方推荐 2）按分区逐个判定，ISR 规模掉到门槛以下就拒写，对应指标 UnderMinIsrPartitionCount收缩后为什么还能服务复制模型与 ISR
副本数 3 能容忍 2 个故障吗？副本数只是上界。unclean 关闭时实际容错等于当前 ISR 规模减 min.insync.replicas，默认 1 时理想状态可扛 2 个，但一个副本变慢或重启就让容错降为 1官方推荐值下容错变多少复制模型与 ISR
unclean 选举开不开？官方原文就是「可能导致数据丢失」。开它等于明确接受用丢消息换可用性，订单与支付类必须关闭关了之后 ISR 空了怎么办复制模型与 ISR
min.insync.replicas 解决什么？它是 Broker 侧对可用副本数设的硬门槛，acks 配得再高，ISR 规模掉到门槛以下仍然拒写；且无论 acks 怎么设，消息都要等复制到全部 ISR 且满足该条件才对消费者可见acks 配得很低时它还有意义吗复制模型与 ISR

八、可靠性与投递语义：速查

问题一句话结论追问点详见
三种投递语义各对应什么写法？at-most-once 先提交位点后处理，崩溃丢消息；at-least-once 先处理后提交，崩溃重复；exactly-once 需要四件套业务该选哪个投递语义与消息去重
幂等的保证范围多大？只覆盖单生产者会话、单分区的写侧重试去重；消费侧重放、业务主动重复生产、跨分区原子性都不在范围内边界之外怎么兜底幂等、acks 与事务
业务侧怎么做去重？用业务唯一标识而不是 offset 做去重键落库，或用版本号做条件更新；offset 会随重放变化，不能当去重键为什么不能用消息 ID投递语义与消息去重
丢消息窗口在哪几段？生产端（重试耗尽、异步回调丢失）、Broker 端（Leader 确认后尚未复制即宕机）、消费端（auto commit 快于处理）三段彼此独立哪一段最难补投递语义与消息去重
端到端 exactly-once 怎么拿？四件套：幂等生产者、事务、消费侧 isolation.level=read_committed（Kafka 4.x 默认为 read_uncommitted）、消费位点纳入事务，缺一件语义就退化多数业务真的需要吗投递语义与消息去重

三段窗口里，B2 是唯一由集群内部机制造成、客户端无法预防的一种，其余五种都能在应用层收口。答题时把这三段分开讲，比笼统说「Kafka 可能丢消息」强得多。

九、KRaft 与选主：速查

问题一句话结论追问点详见
为什么放弃 ZooKeeper？把外部最终一致存储换成内置共识日志：省掉一套外部集群，元数据变更走 RAFT 带任期与多数派保证，且可回放快照恢复迁移成本在哪KRaft 协调与选主
为什么放弃 watch 改拉取？watch 是易丢事件，登记到收到之间有窗口；拉取是状态驱动，错过多少次只要状态最新就一定收敛代价是什么KRaft 协调与选主

ZooKeeper 时代怎么迁？官方要求必须经由一个过渡版本（bridge release）之后再迁到 KRaft，不能直接跳版本需要停机吗KRaft 协调与选主

十一、高频陷阱题：错答与正解

这一节的题答错比不会更扣分。错答几乎都来自一个似是而非的直觉，而追问一句就会露馅。

陷阱题常见错答正解详见
消费组之间会互相影响吗？「会，共享同一批分区，一个组 Rebalance 会拖累另一个组」机制上三层独立：位点按 group.id 分键存储、各组有各自的成员集合与 Rebalance 节奏、各组独立发 FETCH。真正的例外只有两个：同一 topic 被 N 个组读会近似放大 N 倍 Broker 读 IO；group.id 被不同程序错误复用会抢分区，因为分配范围是成员订阅分区的并集消费组、位点提交与 Rebalance
副本数 3 就能容忍 2 个故障吗？「能，3 副本就是能挂 2 个」副本数是上界不是承诺。unclean 关闭时实际容错等于当前 ISR 规模减 min.insync.replicas（默认 1），理想状态确实能扛 2 个，但一个副本变慢或重启就让 ISR 变成 2、容错立刻降为 1；改成官方推荐的 2 之后容错只有 1，靠拒绝写入换数据安全复制模型与 ISR
幂等等于 exactly-once 吗？「开了幂等就不会重复消费了」不等于。幂等只覆盖单生产者会话、单分区内的写侧重试去重；官方定义的 exactly-once 是幂等加事务加消费侧只读已提交加消费位点纳入事务四件套。消费侧重放、业务重复生产、跨分区原子性都不在幂等范围内幂等、acks 与事务
offset 是全局唯一的吗？「是，Kafka 用 offset 做消息唯一标识」不唯一，offset 只在分区内唯一且单调递增，跨分区重号。所以位点必须成对表示，__consumer_offsets 存的键也是 group 加 topic 加 partition。同一推论：offset 不能当业务去重键，因为重放时它会变Kafka 架构全景与角色分工
消费者越多吞吐越高吗？「是，水平扩展就行」受分区独占约束。同一分区在同组内同一时刻只给一个成员，多出的成员只发心跳不消费，并行度上限等于分区数。扩消费者前必须先看分区级 lag 是均匀涨还是个别涨顺序消费与积压处理
acks 默认是 1 还是 all？「默认 1」不给数字。三档语义分别是不等确认、只等 Leader、等全部 ISR 副本确认；默认值随版本变化，以你所用版本的官方文档为准。而且就算配成等全部 ISR，若 min.insync.replicas 仍是 1，在副本数为 1 的分区上等于只等 Leader，可靠性一点没提升幂等、acks 与事务
写成功返回就等于落盘了吗？「是，Kafka 确认了就安全了」不等于。Kafka 默认不主动 fsync，副本「收到」意味着数据进了各自页缓存。多副本下 acks=all 的可靠性依据是「任意单节点故障不丢」，不是「已落盘」。单机掉电不丢要自己调低 flush.ms 并接受吞吐损失零拷贝、页缓存与保留策略
Controller 挂了集群就不可用了吗？「是，Controller 是集群大脑」不一定。已有分区的读写不依赖 Controller 在线，它只在元数据变更时参与。不可用的后果是失去动态能力：无法自动创建分区、无法完成 Leader 重选、无法执行需要元数据变更的管理操作Kafka 架构全景与角色分工
扩分区能解决积压吗？「能，加分区就并行了」不能直接解决。历史积压仍在老分区上，而且 key 哈希取模基数变化会让同一 key 迁到新分区，扩容瞬间破坏原有顺序。只有当瓶颈确实是分区数限制并行度、且积压量不大时才值得做顺序消费与积压处理
Kafka 能保证全局有序吗？「能，Kafka 本质是有序日志」只保证分区内有序。要全局有序只有三条路：全部进单分区（吞吐塌陷）、写侧串行化（生产端塌陷）、应用层按业务序号重排（要处理缺口与缓冲）。Kafka 把有序粒度交给 key 控制是刻意取舍顺序消费与积压处理
lag 高一定是消费端慢吗？「是，加消费者」不一定。read_committed 消费者只能读到 LSO 而不是 LEO，用 LEO 相减会把「已写入但事务未提交」的部分计成积压，lag 虚高，根因可能在上游有长事务悬着顺序消费与积压处理
开 unclean 选举能提高可用性吗？「能，避免 ISR 空了写入全挂」它确实提高可用性，但官方文档对它的描述就是「可能导致数据丢失」。落后副本被选为 Leader 时其上未复制的数据被永久丢弃。这是显式的取舍，不是免费的开关复制模型与 ISR

十三、跨系统追问

本库与 RocketMQ 库在结构上平行但不建跨库双链，对照库同名的速查总表里有配对的答案要点。以下四问按设计文档的跨系统追问清单给出 Kafka 侧的答题骨架。

  1. Kafka 的 ISR 机制与 RocketMQ 的主从同步，数据丢失窗口分别有多大？谁更小，为什么？ 答题骨架：Kafka 的窗口是「Leader 确认后、复制尚未完成时 Leader 宕机」，宽度由 acks 与 min.insync.replicas 的组合决定；RocketMQ 侧的窗口由主从复制是同步还是异步决定。同步复制那档窗口更小但吞吐受主从往返约束。要点是先说清各自的窗口定义，再比大小，否则比的不是同一个量。
  2. Kafka 的顺序消费与 RocketMQ 的顺序消息，实现代价差在哪里？ 答题骨架：两者都把有序粒度绑在最小分片单位上（Kafka 是分区，RocketMQ 是队列），所以代价结构相似：并行度被有序实体数压住，扩分片会破坏顺序，失败重试会插队。差异在强制手段：Kafka 靠 key 哈希加消费侧单线程自觉，没有 Broker 端强制；RocketMQ 在消费模式层面把有序做成显式选项。
  3. Kafka 没有 Broker 端消息过滤，RocketMQ 有。这对两者的适用场景有什么影响？ 答题骨架：Kafka 若要按 tag 或 SQL 条件过滤，只能应用侧收下再丢，或引入 Streams 之类的流计算层；这使 Kafka 适合「全量事件流 + 下游各自消费」的定位，不适合「Broker 精准分发以省带宽」的场景。RocketMQ 的 Tag 与 SQL92 过滤让一份数据能低成本分给不同订阅方。
  4. 两套系统都支持事务，但实现思路完全不同，各自代价是什么？ 答题骨架：Kafka 走事务协调器加两阶段提交，代价是要开事务生产者、引入 transactional.id 的 fencing 逻辑，消费侧还得切 read_committed 并把位点纳入事务；RocketMQ 走 half 消息加本地事务回查，代价是回查在极端情况下不可靠（本地事务已提交但回查超时）以及长期占用 half 消息的存储。对比落点是Kafka 是先写日志后确认回滚，RocketMQ 是先发半消息再探测本地事务。

本库有意不覆盖的内容，面试问到时按下面的方式处理，不要硬答。

未覆盖理由面试时怎么答
源码级内部结构（LogManager、KafkaApis 等）超出面试与排障需求明说「了解设计意图，没读过实现」，然后回到数据结构层面回答
Kafka Streams 与 Flink CDC 集成属流计算范畴，独立知识域承认不在准备范围，重点说清 Kafka 作为流平台的定位差异
MirrorMaker 2 跨地域复制运维专题与主从复制的共性可以讲，细节不编
客户端 SDK 深度优化、限流与灰度工程实践专题，非原理层归到「工程落地按团队规范」
定时器与延时消息Kafka 不原生支持直接说不原生，需要应用层或外部调度实现
