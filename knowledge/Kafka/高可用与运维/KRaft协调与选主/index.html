KRaft 协调与选主

来源

基于 Kafka 4.x 官方文档整理，覆盖 KRaft 部署指南（Process Roles、Controllers、Provisioning、Controller membership changes、Static versus Dynamic KRaft Quorums、Debugging）与 Broker 配置参考。文中未标注「需实操验证」的结论可直接用于面试应答。 本篇只写结构性事实。配置默认值仅在同时给出取值与适用版本处出现；其余配置的默认值随版本变化，以你所用版本的官方文档为准。

Controller 挂了集群还能不能读写？分区 Leader 和 Controller Leader 是一回事吗？动态 Quorum 到底动态在哪？——这三个问题是 KRaft 面试的高频分水岭。角色边界的前置铺垫见 Kafka 架构全景与角色分工，指标与排障落地见 Kafka 监控与排障。

一、KRaft 为什么取代 ZooKeeper

Kafka 4.x 已移除 ZooKeeper，KRaft 是唯一的元数据协调模式。 替换的根因不是「RAFT 比某个旧协调器更先进」，而是元数据的存放位置变了：从「外部系统的私有协议」变成「Kafka 自己的一个内部主题」。

带来的直接后果有两个：元数据天然获得 Kafka 已有的复制、持久化、快照能力，不必自研存储引擎；元数据可用性不再依赖跨系统的网络可达性，Controller 与 Broker 之间统一了协议与序列化格式。旧版与新版的逐项对比见本节末尾的旧版做法 callout——正文只讲 KRaft 本身。

旧版做法（ZooKeeper 时代）

元数据存放：旧版本把 topic、broker、partition Leader、ACL 等元数据放在一套独立的 ZooKeeper 集群内存 + 快照里；KRaft 改为 Kafka 自己的元数据日志 __cluster_metadata。 一致性协议：旧版用 ZooKeeper 自己的 Zab；KRaft 用 RAFT，Leader 追加 + 多数派复制。 Broker 启动依赖：旧版要连 ZK、建 /brokers/ids/<id> 之类的临时节点并注册 watcher；KRaft 只需 controller.quorum.bootstrap.servers，再与 Active Controller 建连。 权限模型：旧版用 ZooKeeper 自己的 ACL；KRaft 复用 Kafka 自己的 principal 与 ACL。 组件数量：旧版是一套 ZooKeeper 集群（通常 3 或 5 台独立机器）；KRaft 是若干 Controller 节点，可与 Broker 合并部署。 主控权获取：旧版 Controller 是每个 Broker 内的一个模块，通过竞争创建 /controller 临时节点来争抢主控；KRaft 是独立进程的 Quorum 走 RAFT 选举。 迁移约束：此机制为旧版，新版由 KRaft Controller Quorum + 元数据日志 整体替代。迁移必须经过一个桥接版本（bridge release），不能把旧模式原地切到 KRaft；桥接版本与具体步骤以你所用版本的官方迁移文档为准。本 callout 仅用于维护存量系统时对照，新版设计请以正文各节为准。

面试追问

  1. Kafka 为什么放弃 ZooKeeper？ —— 根因是元数据一致性与持久化从「外部系统的内协议」下沉为「Kafka 自己的复制日志」。收益是统一复制/快照/分段机制、去掉两套权限体系、Broker 与协调层只需一套协议、并能把 Controller 拆成独立进程做资源隔离。
  2. ZooKeeper 的写性能是瓶颈吗？ —— 不是主要理由。ZK 的问题主要是架构耦合与运维成本：多一套集群、多一套升级节奏、多套 ACL 语义、两个网络故障域。元数据写入频率远低于消息写入频率。只答「ZK 写性能差」是把结论建立在错误前提上。
  3. KRaft 引入的额外成本是什么？ —— 三点：Controller 把全集群元数据放内存与磁盘（官方量级参考约 5GB 主内存 + 元数据目录 5GB 磁盘）；必须显式 kafka-storage.sh format，否则可能选出缺失已提交数据的 leader；迁移是离线操作，必须经桥接版本。
  4. 为什么把 Controller 从 Broker 里独立出来？ —— 数据面负载是磁盘/网络/页缓存/批量 IO，控制面负载是内存里的全集群元数据、周期快照与事件队列。混部时 Controller 的内存 GC 与快照 IO 直接干扰 Broker 请求延迟，因此官方把 broker,controller 合并模式限定为开发环境。

二、RAFT 的角色与术语

Controller Quorum 就是一组跑 RAFT 的成员。官方 Monitoring 文档给出的成员状态取值只有六个，可直接背：leader（当前 Quorum Leader，承担元数据写入）、candidate（正在发起选举）、voted（已投票给某 candidate 但其尚未成为 leader）、follower（正常跟随）、unattached（刚启动尚未与 Quorum 建立状态同步）、observer（非投票成员）。

关键认知：Kafka 里的 Broker 就是元数据 Quorum 的 observer。 Broker 完整复制元数据日志（这样才能在 Controller 切换后无缝接管），但不投票、不可能成为 leader——因为它不是 voter。把它称为 observer，是理解后面所有故障域划分的起点。

三个必须分清的概念：**term（任期）**是单调递增的逻辑时钟，Leader 每次当选开启新 term，candidate 见更大 term 立即退回 follower；epoch 分为 Quorum 级的 Current Epoch 与分区级的 leaderEpoch（Leader 变更时递增）、partitionEpoch（仅分区配置变更时递增）；commit / 高水位指条目被多数派复制后才算 commit，这是「已确认元数据不会丢」的核心。

面试追问

  1. RAFT 的安全性来自多数派复制，还是来自 Leader？ —— 来自多数派。任意两个多数派必有交集，所以条目一旦被某多数派持久化，之后选出的新 Leader 必然包含它。Leader 只是写入入口，挂掉不影响已提交数据。
  2. Candidate 为什么不能只靠自己一票就成为 Leader？ —— 那会退化成单点，网络隔离的假 Leader 无法被区分，就会出现双写。必须拿到超过半数、且不是从同一 Candidate 转授的投票。
  3. Broker 作为 observer 落后会影响数据面吗？ —— 落后不影响正确性，只影响它对最新元数据变更的感知。短期落后时它按缓存的 Leader 继续服务已知分区。官方也正因此要求移除 Controller 前先确认复制进度。
  4. 为什么元数据日志要用 Kafka 的存储引擎而不是单独做 KV？ —— 三个收益：复用复制与快照机制，Controller 故障转移与数据面 Leader 切换在同一套设计哲学下；元数据变更是有序追加流，可像消费日志一样回放；共享段文件、稀疏索引、保留策略等已验证的工程实现。

三、元数据日志：记录什么、怎么回放

元数据日志的物理形态是名为 __cluster_metadata 的内部分区，目录形如 metadata_log_dir/__cluster_metadata-0/，内含普通段文件与 .checkpoint 快照。记录分两类：注册表级（Broker 注册/注销、Topic 创建/删除、ACL 变更、Quorum 成员变更、特性版本变更）低频；分区级（分区 Leader 变更、副本集合变更、ISR 收缩/扩张、分区 epoch 推进）高频，在 Broker 故障与网络抖动时集中产生。

回放机制：新加入或重启的节点，从本地最新快照开始，向 Leader 拉取快照之后的所有 record 并逐条应用。 这与数据面的 follower 追赶是同一个套路。配套指标：kafka.server:type=MetadataLoader,name=HandleLoadSnapshotCount（加载快照次数）、kafka.server:type=SnapshotEmitter,name=LatestSnapshotGeneratedBytes（最新快照字节数）、kafka.server:type=SnapshotEmitter,name=LatestSnapshotGeneratedAgeMs（距最新快照的毫秒数）、kafka.server:type=MetadataLoader,name=CurrentMetadataVersion（当前生效元数据版本）。快照生成的触发条件是时间间隔上限与字节上限任一满足即生成，兼顾低流量集群不生成无意义快照与高流量集群限住回放窗口。

面试追问

  1. 元数据日志和普通数据分区有什么本质区别？ —— 三点：它有且只有一个副本集（Quorum 成员），不是 N 副本；它没有 acks 这类客户端侧配置，写入路径由 RAFT 多数派语义固定；保留策略由快照接管，不会无限增长。
  2. 为什么取消自动格式化存储目录？ —— 官方理由是自动格式化会掩盖错误状态。若多数 Controller 的日志目录为空，它们会认为日志为空而掌握全部历史，从而选出一个缺失已提交数据的 leader，导致已确认元数据凭空消失。
  3. 快照会丢数据吗？ —— 不会丢已提交数据。快照是「把截至某 offset 的元数据状态取物化副本」，与日志中对应 offset 之前的记录等价。丢的是回放所需的中间过程，不是状态本身。
  4. 元数据日志积压（MaxFollowerLag 高）要紧吗？ —— 单个 follower 落后只要 Active Leader 仍是多数派成员就不影响主控权。真正要处理的是它持续增长，通常意味着某 Controller 网络或磁盘异常，会成为下次切换的隐患节点。

四、Controller Quorum 与引导选举

规模选择是纯算术题：官方明确说明要承受 N 个并发故障，Controller 数量必须满足 2N+1。 因此 1 个容忍 0 个故障、3 个容忍 1 个、5 个容忍 2 个、7 个容忍 3 个。每个 Controller 节点的角色是要么 Active，要么 hot standby，多数派存活即可保持可用。关键配置全部是 Update Mode: read-only（改完需重启）：node.id（KRaft 下必填）、process.roles、controller.quorum.voters（KRaft 版本 1 起被废弃）、controller.quorum.bootstrap.servers、controller.listener.names、metadata.log.dir。

controller.quorum.bootstrap.servers 的定位值得单独强调：官方明确说它的作用很像客户端的 bootstrap.servers——不需要列出全部 Controller，但应尽可能列全，以保证所有节点都能定位到 Quorum。这是它与 controller.quorum.voters 最重要的语义差别：后者必须完整列举且静态不变，前者是「够用即可」的引导地址集合，且每个 broker 与 controller 都必须配置。metadata.log.dir 不配置时落在 log.dirs 的第一个目录，生产环境应显式分开，让元数据目录有独立的容量与 IO 预算。

两个决定故障域宽窄的超时（read-only）： controller.quorum.election.timeout.ms 在 Kafka 4.x 默认值 1000（1 秒），语义是成员拉取 Leader 失败超过该时长后成为 candidate；controller.quorum.fetch.timeout.ms 在 Kafka 4.x 默认值 2000（2 秒），语义是 Leader 收不到多数派 fetch / fetchSnapshot 超过该时长后主动退位。两者的比例关系才是设计要点：fetch 超时必须大于 election 超时，Leader 才有时间完成一轮心跳往返，否则正常抖动也会被误判为 Leader 失效。

选举安全性靠两道检查而非投票本身：投票前置条件要求 candidate 日志至少和接收方一样新（先比 lastLogTerm 再比 lastLogIndex），保证新 leader 拥有全部已提交记录；日志匹配检查由 Leader 的 AppendEntries 携带 prevLogIndex / prevLogTerm，follower 不匹配就拒绝、Leader 回退重试，保证 epoch 不会在同一位点冲突。

面试追问

  1. 一个 Controller 重启会导致集群不可用吗？ —— 不会，只要多数派存活。3 个 Controller 重启 1 个仍是 2 个存活，Quorum 可用且不发生选举。Quorum 会等它从快照 + 增量追平，期间 MaxFollowerLag 升高。
  2. 什么情况下会发生选举（哪怕 Controller 都没挂）？ —— 两类：Leader 侧收不到多数派 fetch 超过 fetch.timeout.ms 主动退位；follower 侧拉取 Leader 超过 election.timeout.ms 发起选举。都是超时驱动，所以网络分区是主要触发源，观测点是 kafka.server:type=raft-metrics 的 Election Latency。
  3. 网络分区时会不会出现两个 Leader？ —— 不会。两道多数派检查挡住了：互不通信的两个多数派不可能同时存在。分区侧唯一「多出来」的是 candidate 状态，它会在超时内反复尝试投票后退回 follower，用 Current Voted 观测（未投票时为 -1）。
  4. 为什么用「热备」而不是「主备切换」描述 Controller？ —— 因为切换无需人工介入也无需外部协调，follower 一直在被动接收 AppendEntries，一旦 Leader 消失只需一次投票就能接任，没有需要转移的状态——状态就在日志里。

五、任期与 epoch：fencing 的真正机制

关键认知：Kafka 的 fencing 不靠外部票据，靠 term 与 epoch 的单调性。

概念归属作用官方指标
Current EpochQuorum 级每次成功选举推进，是写权限凭据kafka.server:type=raft-metrics
leaderEpoch分区级Leader 变更时推进，标识 Leader 世代kafka-metadata-shell.sh 读快照可见
partitionEpoch分区级仅分区配置变更时推进同上
Current Leader / High WatermarkQuorum 级未知时均为 -1同上

三层防护的具体形态：Quorum 层拒绝旧 term 的写入——被隔离的旧 Leader 恢复后，follower 因看到更大 term 而拒绝其 AppendEntries；分区层用 leaderEpoch 拒绝旧世代请求——客户端与 follower 带上自己知道的 epoch，Leader 换过则旧 epoch 请求被拒绝而非被错误接受；配置层用 partitionEpoch 拒绝过期变更——一批副本移动请求若跨越 Leader 变更会因 epoch 不匹配被丢弃，避免执行基于陈旧视图的变更。

排障时先看 LeaderId 是不是 -1，再看 MaxFollowerLag 是否持续增长。 前者说明无主控，后者说明有节点掉队。

面试追问

  1. fencing 到底防住了什么？ —— 防住陈旧写入。分布式系统最难处理的问题之一是「已失去 leadership 的组件慢一拍地执行了它此前计划的写操作」。RAFT 把 fencing token 内嵌进协议本身，旧 term 的一切消息在协议层就被拒绝，不需要额外的锁服务或租约中心。
  2. 只用 term 一个 epoch 不够吗？ —— 不够。term 是 Quorum 级全局变量，一次选举推进一次；分区 Leader 可能因网络抖动在同一 term 内多次变更。leaderEpoch 提供分区粒度的世代标识，粒度更细。
  3. HighWatermark 一直不变说明什么？ —— 稳态下正常。持续不变且 MaxFollowerLag 同时增长才是异常：Leader 没推进高水位，follower 却在拉取。前者查 Leader 事件队列与磁盘，后者查网络与磁盘 IO。
  4. Controller 的 term 变化会影响数据面吗？ —— 间接但有限。term 变化意味着可能发生分区 Leader 重新分配，新任 Active Controller 会按当前 Broker 存活状况重算 preferred leader。数据不丢（RAFT + ISR 双重安全性），但分区级写入延迟会有一次抖动。

六、Broker 注册与心跳：两个独立的故障域

本篇最容易被讲错的地方：Controller Quorum 的可用性与 Broker 集合的可用性，是两件独立的事。

故障域成员机制掉线后果关键指标
控制面Controller Quorum（voter）RAFT AppendEntries + fetch跌破多数派 → 无 Active ControllerCurrent State / Current Leader / Current Epoch
数据面Broker 集合（observer）向 Active Controller 发送注册与心跳，Controller 下发元数据该 Broker 负责的分区失去 Leader 或副本不足LeaderCount / OfflineReplicaCount / UnderReplicatedPartitions

Broker 掉线时 Controller 做三件事：把它负责的分区从 ISR 中摘除；为失去 Leader 的分区在存活副本中选出新 Leader；更新分区级元数据并追加到元数据日志。Controller 掉线时数据面的行为：Broker 仍持有完整元数据日志副本，能继续服务元数据未变化的分区，所以「Controller 不可用」不等于「数据读不了」。

观测这个通道用 kafka.controller:type=ControllerChannelManager,name=RequestRateAndQueueTimeMs,brokerId=N，官方定义为「Controller 从指定 Broker 的请求队列取请求的速率，以及请求在该队列中的停留时间」，配套还有 kafka.controller:type=KafkaController,name=ActiveControllerCount（官方定义为取值 0 或 1，全集群只应有一个节点为 1）。

面试追问

  1. Broker 注册失败会导致它承载的分区数据丢失吗？ —— 不会。只要其他副本存活，Controller 会选出新 Leader。注册失败意味着新元数据变更无法下发到这个 Broker，以及它被判定掉线后无法自动恢复。丢失风险只来自「唯一副本」这种退化配置，那是配置问题不是协议问题。
  2. 为什么 Controller Quorum 应该与 Broker 分散部署？ —— 故障域要独立。合并模式下一次机器故障同时打掉一个 voter 和多个 Broker，控制面与数据面的冗余度被同一事件同时消耗。
  3. controller.quorum.bootstrap.servers 只配部分节点会怎样？ —— 官方说明它不需要列出全部 Controller，作用类似 bootstrap.servers，但应尽可能列全；完全不知道任何地址的节点无法加入 Quorum。已加入的成员之间会通过元数据日志互相学到其它 voter。
  4. 热备 Controller 会不会浪费资源？ —— 协调层不浪费，只有 Active Controller 承担事件处理与快照生成。成本是内存与元数据日志目录的磁盘副本（官方量级参考 5GB / 5GB），换来等于一次选举时间的切换速度，因为切换不需要重新加载任何状态。

七、Controller 不可用时的系统边界

结论先行：Controller 全部不可用时，集群不是「完全不可用」，而是从「可写可管」退化为「按最后一次已知元数据继续服务数据面」。

能力Controller 不可用时原因
已有分区的数据读取可用只需知道分区 → Leader 映射
已有分区的数据写入可用Leader 已在 Broker 上
Consumer 位点提交可用__consumer_offsets 走数据面复制，不经元数据日志
Leader 故障后的分区切换不可用选新 Leader 必须由 Controller 执行
创建 / 删除 Topic、扩分区不可用分区级元数据变更必须写元数据日志
副本重分配、动态 topic 配置变更不可用同上
ACL 变更、Broker 增删不可用注册表级元数据变更

数据面的稳态路径不依赖 Controller，元数据变更路径完全依赖 Controller。 这也解释了「Controller 挂了集群就完全不可用吗」为什么答案是「不是」——真正的不可用发生在故障叠加时：Controller 无主控的同时恰好又有 Broker 挂掉，它负责的分区无法选出新 Leader，数据面才开始真正不可写。单点故障不致命，故障叠加才致命。

面试追问

  1. Controller 挂了集群就完全不可用吗？ —— 不是，分三类看。已建立的数据面读写继续可用，位点提交也可用；所有元数据变更不可用（建删 Topic、扩分区、副本重分配、ACL、动态配置、Broker 上下线）；自愈能力失效——此时若再发生 Broker 故障，受影响分区无法选新 Leader。准确表述是：Controller 不可用把系统从「自愈」降级为「维持现状」，本身不立即造成不可用，但移除了故障自愈能力。
  2. Controller 恢复后需要人工做些什么？ —— 通常不需要，恢复是自动的（新成员从本地快照拉增量追平）。唯一需人工确认的是「刚做过的变更是否已提交」——若故障发生在变更已发起但未 commit 的窗口期，要用 kafka-metadata-shell.sh 或 kafka-dump-log.sh --cluster-metadata-decoder 核对元数据日志末尾状态，而不是凭操作记忆判断。
  3. Controller 不可用期间集群会不会把磁盘打满？ —— 不会无限增长。写入仍受 retention 与分区数限制，清理器是数据面组件独立于元数据日志照常工作。受影响的是能否新增分区或 Topic 来扩容。
  4. 这种「降级可用」能作为设计目标吗？ —— 不能，只能当故障窗口。它会积累「无法自愈」的脆弱性，每次 Broker 故障都让更多分区失去自愈能力。所以必须对 ActiveControllerCount 全集群求和设硬告警（全集群应有且仅有 1），并对 Current Leader = -1 设告警，目标是把故障窗口压到足够短。

八、静态配置与动态配置

先分清两个完全不同维度的「静态 / 动态」，混在一起是常见错误。

维度一：Quorum 成员是静态还是动态。 kraft.version 这个特性版本决定成员管理方式：取值 0 或未设置为静态，成员必须完整写在每个 broker 与 controller 的 controller.quorum.voters 里，变更需改配置 + 重启全部节点；取值 1 及以上为动态，启动时给 controller.quorum.bootstrap.servers，运行期由元数据日志中的 voter 集合决定，用 kafka-metadata-quorum.sh 在线增删。官方明确说明：静态还是动态在 format 那一刻决定——判据是格式化时若 controller.quorum.voters 不存在、且指定了 --standalone、--initial-controllers、--no-initial-controllers 三者之一，则格式化为动态。

命令场景结果
format --cluster-id <ID> --standalone --config <f>引导第一个 Controller写 meta.properties（含随机 directory.id），生成只含本节点为唯一 voter 的 00000000000000000000-0000000000.checkpoint（内含 KRaftVersionRecord 与 VotersRecord）
format --cluster-id <ID> --initial-controllers "0@h0:1234:<UUID>,..." --config <f>一次引导多个 Controller同一 cluster id 下所有 Controller 必须传完全相同的参数，checkpoint 中的 VotersRecord 包含全部 Controller
format --cluster-id <ID> --config <f> --no-initial-controllers加入已存在集群的新节点不写初始 voter 集合，作为新成员加入

--initial-controllers 的副本描述格式是 replicaId@host:port:directoryId，如 0@controller-0:1234:3Db5QLSqSZieL3rJBUUegA，四项依次是副本 ID、目录 ID、主机、端口。动态 Quorum 增员必须严格按官方四步：format --no-initial-controllers → 启动新 Controller → kafka-metadata-quorum.sh describe --replication 观察复制追平 → 追平后才 add-controller。减员有一条易被忽略的硬约束：官方建议先把待移除 Controller shutdown，再执行 remove-controller，原因是 KIP-996 的 Pre-vote 尚未实现，停机可让该节点彻底从 Quorum 通信中消失，避免多轮无谓选举。

维度二：Broker 配置项能否在线改。 Update Mode 分三档：read-only（必须重启）、per-broker（按 Broker 粒度动态更新）、cluster-wide（可作集群级默认值动态更新，也可单独设某 Broker 的值）。node.id、process.roles、controller.quorum.voters、controller.quorum.bootstrap.servers、controller.listener.names、metadata.log.dir、metadata.log.segment.bytes、两个 Quorum 超时——全部是 read-only。

可动态更新的默认 topic 配置（官方完整清单 25 项）： log.segment.bytes、log.roll.ms、log.roll.hours、log.roll.jitter.ms、log.roll.jitter.hours、log.index.size.max.bytes、log.flush.interval.messages、log.flush.interval.ms、log.retention.bytes、log.retention.ms、log.retention.minutes、log.retention.hours、log.index.interval.bytes、log.cleaner.delete.retention.ms、log.cleaner.min.compaction.lag.ms、log.cleaner.max.compaction.lag.ms、log.cleaner.min.cleanable.ratio、log.cleanup.policy、log.segment.delete.delay.ms、unclean.leader.election.enable、min.insync.replicas、max.message.bytes、compression.type、log.preallocate、log.message.timestamp.type。其中 log.retention.hours 在 Kafka 4.x 默认值 168 小时（7 天），min.insync.replicas 在 Kafka 4.x 默认值 1（只等 Leader 一份确认就返回，这也是它常被建议调高的原因）。unclean.leader.election.enable 本篇只写语义（是否允许不同步的副本成为 Leader），默认值随版本变化，以你所用版本的官方文档为准。

面试追问

  1. log.retention.hours 改了为什么没立即生效？ —— 它可动态更新，但清理器按自己的节奏扫描，不是配置一改就立刻删数据。log.segment.delete.delay.ms 控制段被标记删除后延迟多久物理删除。正确预期是：变更影响后续段滚动与清理判定，已存在的段要等清理器扫到。
  2. 动态更新某个 topic 的配置会不会影响其他 topic？ —— 取决于变更层级。--entity-type topics --entity-name <topic> 改的是该 topic 的覆盖值，--entity-type brokers 改的是集群默认值，未设置覆盖值的 topic 跟随集群默认值。改之前先用 --describe 确认当前实际生效值。
  3. 为什么元数据相关配置全是 read-only？ —— 它们在启动时就被用于确定节点身份与 Quorum 连接方式。node.id 决定自己在元数据日志中的身份，运行期改等于让同一节点以两个身份同时存在；controller.quorum.bootstrap.servers 决定启动期如何定位 Quorum。
  4. 从静态 Quorum 迁到动态 Quorum 要做什么？ —— 官方路径是先升级特性版本再改配置：kafka-features.sh upgrade --feature kraft.version=1，确认 describe 的 FinalizedVersionLevel 已变为 1，然后从所有节点移除 controller.quorum.voters、加入 controller.quorum.bootstrap.servers。顺序反了会错配。

九、两处「Leader」必须分清

Kafka 里有两个完全不同的 Leader 概念，混淆它们是本主题最常见的表达错误。

维度分区 LeaderKRaft Controller Leader
存在数量每个分区一个，全集群成千上万个全集群一个
由谁选出数据面复制协议，按副本同步状态选择RAFT，按投票结果选择
选举依据副本是否存活、是否在 ISR、是否为 preferred replica多数派投票 + 日志新旧比较
作用处理该分区的 produce / fetch 请求写入元数据日志、发起分区 Leader 分配
数据结构分区日志（.log 段文件）元数据日志（__cluster_metadata）
切换触发Broker 故障、ISR 收缩、preferred leader 变化选举超时、Leader 收不到多数派心跳
观测指标kafka.server:type=ReplicaManager,name=LeaderCountkafka.server:type=raft-metrics 的 Current Leader

两者的关系必须分两层说，混淆「发起方」与「执行方」是这里最容易讲错的地方。

第一层：Controller 不在数据路径上。 它不代理 produce / fetch 请求，也不参与消息读写。分区 Leader 一旦确定，就在 Broker 上直接服务客户端，Controller 只在旁路。

第二层：但分区 Leader 的「任免」由 Controller 发起。 Controller 计算出某个分区应该由哪个 Broker 当 Leader，把结论写进元数据日志；各 Broker 完整复制了元数据日志，读到这条变更后把自己置为该分区的 Leader。KRaft 没有 Broker 自行选主的路径——Broker 不会因为同伴失联就自行顶上。

由此推出三条结论：

  1. Controller 不可用时，已在服务的分区继续正常读写——它们的 Leader 已经在 Broker 上运行，不需要 Controller 参与。
  2. 但 Leader 故障后的切换不可用。 没有 Active Controller 就没有人计算并下发新的 Leader 分配，受影响分区会停在「无 Leader」状态直到控制面恢复。这正是第七节表格里那一行的由来。
  3. 扩副本、换副本、下线 Broker 也必须等 Controller，因为这些变更本身就是「变更副本集合」，必须先写元数据日志。

两处选举的安全性基础不同：Controller Leader 由 RAFT 多数派保证唯一；分区 Leader 由 ISR 语义保证（正常情况只能从 ISR 内选）。两条路径都遵守「超时不丢安全性」——不允许靠超时选出一个会丢数据的 Leader，除非显式打开非同步选举。

补充一个官方细节：非同步 Leader 选举在 KRaft 模式下由专门的 unclean leader election 线程定期触发，默认周期 5 分钟。若 unclean.leader.election.enable 是动态改上去的，配置生效要等该线程下一轮触发；需要立即生效时用 kafka-leader-election.sh --election-type unclean 手动触发。这个 5 分钟窗口就是「Leader 挂了却迟迟不选新 Leader」的常见解释——很多人在这里误判为故障，实际是等待线程周期。

面试追问

  1. 分区 Leader 一定在 ISR 里吗？ —— 正常情况是，KRaft 的分区 Leader 只能从 ISR 中选择。例外是开了非同步 Leader 选举：允许从不同步副本中选，会丢数据。这正是 unclean.leader.election.enable 的全部风险，观测点 kafka.controller:type=ControllerStats,name=UncleanLeaderElectionsPerSec 官方正常值是 0，非 0 就是数据可能已丢的信号。
  2. LeaderCount 应该是多少？ —— 等于全集群分区总数，且应均匀分布在各 Broker。不均说明副本分布有问题或 preferred leader 未被采纳（看 kafka.controller:type=KafkaController,name=PreferredReplicaImbalanceCount）。官方对 LeaderCount 与 PartitionCount 标注的正常值都是「大致均匀分布」。
  3. Controller Leader 切换期间会影响正在写的分区吗？ —— 不会中断写入，但会造成一次副本层面抖动。新任 Controller 会按当前 Broker 状况重算 preferred leader，不可用就触发分区 Leader 变更。数据不丢，但客户端可能短暂重试。要区分「抖动一次就恢复」和「持续抖动」——后者说明副本健康度有问题。
  4. 为什么 ActiveControllerCount 要全集群求和而非逐节点看？ —— 正常态全集群有且仅有 1 个节点为 1、其余为 0。逐节点看无法区分「我在热备（正常）」和「Active 挂了（异常）」。求和等于 0 是 P0，等于 2 是脑裂信号，等于 1 但频繁跳变是选举抖动。

场景控制面表现数据面表现可用性处置动作

新 Controller 未追平就 add复制进度落后无影响视后续而定严格执行先追平再 add
直接下线待移除 Controller可能触发无谓选举无影响抖动先 shutdown 再 remove-controller

成员变更上，多数资料会把 RAFT 论文的机制直接套到 Kafka 上，这是错的。 Raft 论文用 joint consensus 解决成员变更：先让「旧配置」与「新旧并集」同时生效、决策需两套配置各自多数派同意，再切到纯新配置，从而保证变更期间不存在两个互不相交的多数派。Kafka 的官方 KRaft 文档并没有描述 joint consensus 过渡配置，官方给出的路径是逐个增删 + 复制追平 + 移除时先停机：

工程含义必须说清： 逐个增删意味着一次只改一个成员，变更期间不存在「新旧配置同时生效」，因此不需要 joint consensus 来防多数派分裂；代价是无法并行批量变更，扩缩容按成员数串行执行，每步都要等复制追平，移除侧还有 Pre-vote 缺失带来的顺序约束。

面试追问

  1. Kafka 为什么不用 joint consensus？ —— 从官方流程可反推取舍：逐个增删把「配置变更」转化成「一次普通元数据日志提交」，变更本身走 RAFT 既有的一致性通道，无需引入过渡配置概念。代价是批量扩缩容串行等待。这是基于官方文档流程的推论，官方未直接给出取舍理由，展开这一层建议标注为「需实操验证」。
  2. add-controller 之前必须等复制追平吗？ —— 官方流程明确要求，describe --replication 用来观察进度。原因是只有追平后才能保证新成员参与后续选举时不因日志不完整破坏安全性——RAFT 的投票前置条件会拒绝日志不够新的 candidate，但一个刚加入的落后成员若参与投票过程，可能让本可成功的选举反复失败。
  3. 移除 Controller 时为什么必须先停机？ —— 官方给出的直接原因是 KIP-996 的 Pre-vote 尚未实现。Pre-vote 让候选人在正式发起选举前先做一轮试探性拉票，确认有资格竞选才启动 term 递增。没有它时，一个已停机的节点不会主动参与交互，剩余节点的投票收集会变得不可预期，可能触发多轮无谓选举。停机就是让该节点彻底从 Quorum 通信中消失。
  4. add-controller 和 remove-controller 该连 Broker 端点还是 Controller 端点？ —— 两种都行，官方给了两套命令：--command-config 配合 --bootstrap-server（连 Broker）或 --bootstrap-controller（连 Controller）。排查元数据问题时优先连 Controller 端点，它绕过数据面，信号更干净。
  5. 如果 ActiveControllerCount 全集群求和等于 2 说明什么？ —— 出现脑裂，正常 RAFT 下不应发生。典型环境成因是 controller.quorum.bootstrap.servers 导致两组节点互相不可见、各自组成独立「多数派」（如 6 个 Controller 分成 3+3 且组间不通），或同一 cluster id 下存在两套独立元数据日志（如重复 --standalone 引导）。这是 P0 故障，必须立即隔离。
