Kafka 监控与排障

来源

基于 Kafka 4.x 官方文档整理，主要取自 Monitoring 指标清单（broker / controller / KRaft / client 四类指标表）与 Basic Kafka Operations 的命令行示例。文中未标注「需实操验证」的结论可直接用于面试应答。 本篇按症状组织而非按指标名组织：先说「你看到什么」，再说「该看哪个指标」，最后给出可直接粘贴的命令。每个章节以「如何确认」收尾。 指标名一律给出完整 MBean 形式，因为实际检索时 MBean 名才是主键。配置默认值仅在同时给出取值与适用版本处出现；其余配置的默认值随版本变化，以你所用版本的官方文档为准。

排障的效率取决于排除顺序而非指标数量。本篇给的是顺序：先分层（数据面还是控制面），再定位到具体分区，最后才动配置。角色与选主机制的前置铺垫见 KRaft 协调与选主，副本与位点机制见 复制模型与 ISR 与 消费组、位点提交与 Rebalance。

一、监控指标分层与数据源

症状：告警响了，但不知道该看哪块面板。 根因通常是把这四类指标混在一张图里。

Kafka 的可观测面分四层，排障时必须按层隔离，不要跨层猜。

层指标归属代表性 MBean故障时先看什么
数据面（Broker）kafka.server:*BrokerTopicMetrics、ReplicaManager、RequestMetrics请求量、错误率、ISR 状态
控制面（Controller）kafka.controller:*KafkaController、ControllerStats、ControllerEventManager是否有 Active Controller、事件队列是否堆积
元数据一致性（KRaft）kafka.server:type=raft-metricsCurrent State、Current Leader、Current Epoch是否有主控、是否在反复选举
客户端kafka.consumer:* / kafka.producer:*consumer-fetch-manager-metrics、producer-metrics是消费端慢还是 Broker 端慢

关键认知：客户端指标和服务端指标必须成对看。 单看服务端正常而客户端报积压，结论只能有一个——慢在客户端或链路上。

官方监控文档有两条使用前提必须知道：

  • Kafka 使用 Yammer Metrics 上报服务端指标，Java 客户端使用内置的 Kafka Metrics 库；两者都通过 JMX 暴露
  • Kafka 默认禁用远程 JMX；启用需设置 JMX_PORT 或 KAFKA_JMX_OPTS，且生产环境必须同时启用认证——JMX 认证默认是关闭的
  • 所有 rate 指标都有对应的 -total 累计指标。例：records-consumed-rate 对应 records-consumed-total

排查指标缺失时的第一个问题永远是「能不能读到指标」，不是「指标为什么是 0」。 官方建议的确认手段是用 jconsole 指向运行中的客户端或服务端浏览全部 JMX 指标。

面试追问

  1. 为什么 rate 类指标一定要配一条 total 累计指标？ —— rate 会因为窗口滑动而剧烈抖动，判断「到底有没有流量」需要长时间尺度的累计值。同时 total 是重启动作后的对照基准：重启后 total 归零，rate 不归零。
  2. 客户端指标和服务端指标口径不同会造成什么误判？ —— 客户端的 records-lag-max 官方定义是「该窗口内任一分区的最大 lag，基于 current offset 而非 committed offset」；服务端 FetcherLagMetrics 的 ConsumerLag 统计的是 follower 副本与 Leader 的滞后。两者都叫 lag 但含义完全不同，混用会得出相反结论。
  3. 远程 JMX 为什么默认关闭？ —— JMX 暴露的是监控与运维能力，历史上多次成为攻击面。官方要求生产启用时必须覆盖认证设置，因为 Kafka 的 JMX 认证默认关闭。
  4. 指标采集应该抓 rate 还是 total？ —— 两者都要。rate 用于告警与容量规划，total 用于验证重启后是否真的恢复、以及排查「曲线看起来正常但业务没数据」。

如何确认

  1. 用 jconsole 指向目标进程的 JMX，确认能浏览到 MBean 列表——读不到就是采集链路问题，不是 Kafka 问题
  2. 按 kafka.server:* / kafka.controller:* / kafka.server:type=raft-metrics / kafka.consumer:* 四个前缀分组检索，先确定告警落在哪一层
  3. 对任一异常 rate 指标，取同名 -total 指标对比：total 在涨而 rate 显示 0，说明是采集窗口问题而非业务停止

二、消费者积压与 lag

症状：kafka-consumer-groups.sh --describe --group <g> 显示 LAG 持续增长。 这是最常见的告警，也是最容易被误判的一个。

第一步：先分清「真的慢」还是「看错了」。 官方 --describe 输出的列是 TOPIC / PARTITION / CURRENT-OFFSET / LOG-END-OFFSET / LAG / CONSUMER-ID / HOST / CLIENT-ID，其中 CURRENT-OFFSET 为 - 表示该分区无位点（lag 为 0）。

现象含义下一步
LAG 单调增长，--state 显示 Stable消费端处理速度 < 生产速度看是消费逻辑慢还是分配不均
LAG 增长且 --state 的成员数在变持续 Rebalance，消费根本来不及推进位点转查 Rebalance，展开见 消费组、位点提交与 Rebalance
只有一个分区积压单分区热点（key 倾斜）或该分区业务分支卡住用 --members --verbose 确认分配
LAG 增长且客户端 fetch-rate 下降消费端被节流或 poll 线程阻塞看 fetch-throttle-time-avg
LAG 在涨但 read_committed 视角的 LAG 不涨未提交事务在积压，read_uncommitted 把它算进去了见下方「隔离级别陷阱」

关键认知：LAG 的绝对值不是健康指标，LAG 的趋势才是。 一个每天固定时间批量消费一次的作业，LAG 白天增长夜间清零完全正常。反之 LAG 稳定在一个很大的数上但持续下降，也不该告警。

隔离级别陷阱是这一节的核心。 read_committed 消费者只能读到已提交的数据。如果生产侧开了事务但存在长时间未完成的事务，LOG-END-OFFSET 反映的是 LEO（物理末尾），而 read_committed 消费者的可读上限被压在 LSO（Last Stable Offset）。此时会出现「LEO 在涨、消费者位点也涨、但 LAG 就是不降」的现象。这不是消费端的问题，是生产端有事务卡住。 排查方向是生产侧未完成的事务，而不是加消费者。

客户端侧的确认信号在 kafka.consumer:type=consumer-fetch-manager-metrics,client-id="{client-id}"：records-consumed-rate / records-consumed-total（是否在消费）、fetch-rate / fetch-total（拉取频率）、fetch-size-avg / fetch-size-max（单次拉取量）、fetch-latency-avg / fetch-latency-max（拉取延迟）、fetch-throttle-time-avg / fetch-throttle-time-max（被节流时长）、records-per-request-avg（每次请求的记录数）、records-lead-min（最小「领先」量，消费快于生产时为正）。

面试追问

  1. LAG 到底怎么算的？ —— 官方 --describe 给出 CURRENT-OFFSET 与 LOG-END-OFFSET 两列，LAG 是两者之差。CURRENT-OFFSET 是消费组已提交的位点，LOG-END-OFFSET 是分区日志末尾偏移。所以 LAG 的精度取决于位点提交频率，提交间隔越大，LAG 读数越滞后。
  2. read_committed 消费为什么可能永远追不上 LEO？ —— 因为它的可读上限是 LSO 而非 LEO。LSO 被最早的未完成事务挡住。生产侧有事务卡住，LSO 就停在那里，消费者的位点就永远到不了 LEO。判据是「LEO 涨、committed offset 也涨、LAG 不降」。
  3. LAG 大但消费速率正常，需要处理吗？ —— 看趋势。稳态消费只要 LAG 趋于稳定且能被持续消化，就不需要处理；需要处理的是持续单调增长（说明产能永久性不足）或增速超过消化能力。另外要排除「定时批量作业」这种正常尖峰。
  4. --members --verbose 相比 --members 多了什么？ —— --members 输出 CONSUMER-ID / HOST / CLIENT-ID / #PARTITIONS；--members --verbose 额外输出 ASSIGNMENT 列，列出该成员被分配到的具体分区。定位单分区热点必须用 --verbose。

如何确认

  1. kafka-consumer-groups.sh --bootstrap-server <h:p> --describe --group <group> —— 拿 LAG 的分区级分布，确认是全部积压还是个别分区
  2. ... --describe --group <group> --state —— 看 COORDINATOR (ID) / ASSIGNMENT-STRATEGY / STATE / #MEMBERS，确认不是反复 Rebalance
  3. ... --describe --group <group> --members --verbose —— 看 ASSIGNMENT 列确认分配是否倾斜
  4. 客户端 JMX 查 kafka.consumer:type=consumer-fetch-manager-metrics 的 fetch-throttle-time-avg 与 records-per-request-avg —— 区分「被节流」与「业务处理慢」
  5. 若 LAG 不降且 read_committed 场景，转查生产侧未完成事务：对比 LEO 与该组已提交位点的差值是否稳定不收敛

三、URP 与离线分区

症状：UnderReplicatedPartitions 或 OfflinePartitionsCount 报警。 这两个指标指向的是副本不足，比 LAG 更紧急——它意味着副本因子已经低于配置值。

指标官方正常值含义归属层
kafka.server:type=ReplicaManager,name=UnderReplicatedPartitions0|ISR| < |all replicas| 的分区数数据面
kafka.server:type=ReplicaManager,name=UnderMinIsrPartitionCount0|ISR| < min.insync.replicas 的分区数数据面
kafka.server:type=ReplicaManager,name=AtMinIsrPartitionCount—|ISR| = min.insync.replicas，危险边界预警数据面
kafka.server:type=ReplicaManager,name=OfflineReplicaCount0离线副本数数据面
kafka.server:type=ReplicaManager,name=IsrShrinksPerSec / IsrExpandsPerSec / FailedIsrUpdatesPerSec0ISR 收缩 / 扩张 / 更新失败速率数据面
kafka.controller:type=KafkaController,name=OfflinePartitionsCount0Controller 视角的离线分区数控制面
kafka.controller:type=ControllerStats,name=UncleanLeaderElectionsPerSec0非同步 Leader 选举速率控制面
kafka.controller:type=KafkaController,name=PreferredReplicaImbalanceCount0Leader 不是 preferred leader 的分区数控制面

关键认知：UnderReplicatedPartitions 增长是「副本掉队」，OfflinePartitionsCount 增长是「分区彻底不可用」。前者可读可写但冗余度下降，后者已经不可写。两者的处置优先级完全不同。

其中 AtMinIsrPartitionCount 值得单独强调：它是危险边界预警。当 |ISR| 恰好等于 min.insync.replicas 时，只要再掉一个副本，写入就会因为达不到 min ISR 而被拒绝。min.insync.replicas 在 Kafka 4.x 的默认值是 1（只等 Leader 一份确认就返回），这也是它常被建议调高的原因。

UncleanLeaderElectionsPerSec 是本节唯一的数据已经可能丢失的信号。官方正常值 0，一旦非 0 就说明发生了用不同步副本当 Leader 的选举，该副本上未同步的数据已被丢弃。这与 unclean.leader.election.enable 直接相关，本篇只写其语义（是否允许不同步的副本成为 Leader），默认值随版本变化，以你所用版本的官方文档为准。

ISR 收缩不等于故障，但持续收缩就是故障。 判定方法看 IsrShrinksPerSec 与 IsrExpandsPerSec 的比值：只有收缩没有扩张，说明有副本永久性追不上，通常是磁盘 IO 瓶颈或网络带宽不足，而不是瞬时抖动。

面试追问

  1. UnderReplicatedPartitions 和 UnderMinIsrPartitionCount 有什么区别？ —— 前者是 |ISR| < |all replicas|，即副本数不足配置值，但可能仍满足写入所需的 min ISR；后者是 |ISR| < min.insync.replicas，意味着写入会被拒绝。前者是冗余度告警，后者是可用性告警。
  2. 为什么 ISR 收缩会拖慢写入？ —— 副本数不足本身不拖慢写入，但通常伴随 Leader 变更或更强的同步要求。当启用 min.insync.replicas 且 ISR 恰好卡在边界时，写入直接失败；即使未到边界，可用副本变少也会让故障时的恢复时间变长。
  3. UncleanLeaderElectionsPerSec 非 0 为什么是 P0？ —— 它意味着已经用不同步的副本做了 Leader，该副本上未提交到主副本的数据被丢弃。这不是「可能丢」，是「已经丢了」。而且这个计数是累计的，不会归零，必须查清发生时间点。
  4. 副本一直追不上，除了加副本还能做什么？ —— 先定位瓶颈类型：磁盘 IO 饱和看 LogFlushRateAndTimeMs 与 kafka.log:type=LogManager 相关指标，跨机架带宽看 ReplicationBytesInPerSec，节流限制看是否处于 kafka-reassign-partitions.sh 设定的 throttle 期间。盲目加副本常常只是把瓶颈复制成更多份。

如何确认

  1. kafka-topics.sh --bootstrap-server <h:p> --topic <t> --describe —— 逐分区看 Leader / Replicas / Isr 三列，Isr 短于 Replicas 即为 URP 分区
  2. 查 kafka.server:type=ReplicaManager,name=IsrShrinksPerSec 与 IsrExpandsPerSec 的比值，判断是瞬时抖动还是永久掉队
  3. 查 kafka.server:type=ReplicaManager,name=AtMinIsrPartitionCount —— 非 0 说明已在写入拒绝边界
  4. 查 kafka.controller:type=ControllerStats,name=UncleanLeaderElectionsPerSec —— 非 0 立即按数据丢失处理
  5. 查 kafka.server:type=ReplicaFetcherManager,name=MaxLag,clientId=Replica —— 确认是 follower 侧追赶问题

四、请求链路：服务端、网络还是客户端

症状：端到端延迟升高，但不知道该找谁。 这是最需要方法论的一节。

关键认知：Kafka 把一次请求的耗时拆成了五段，定位延迟就是定位它落在哪一段。 官方 kafka.network:type=RequestMetrics 提供完整拆解：

指标消耗的环节异常指向
TotalTimeMs,request={Produce|FetchConsumer|FetchFollower}全程合计，拆为下面四段起点
RequestQueueTimeMs在 Broker 队列里等服务端过载：请求处理不过来
LocalTimeMs在 Leader 本地处理服务端逻辑慢：磁盘 IO、加密、ACL、压缩
RemoteTimeMs等 follower 响应复制慢；官方注明 produce 且 acks 为 -1 时非 0
ResponseQueueTimeMs在响应队列里等服务端响应侧积压
ResponseSendTimeMs把响应发回去网络出口或客户端接收慢

这个拆解的价值在于它把「服务端慢」和「网络慢」彻底分开了：RequestQueueTimeMs / LocalTimeMs / ResponseQueueTimeMs 是服务端问题，ResponseSendTimeMs 是链路问题。

配套的服务端健康度信号：

  • kafka.network:type=SocketServer,name=NetworkProcessorAvgIdlePercent —— 网络处理线程的空闲比例，官方给的参考是「0 到 1 之间，理想值大于 0.3」。持续低于此说明请求线程不够用
  • kafka.network:type=RequestMetrics,name=RequestsPerSec,request=... 与 ErrorsPerSec,request=...,error=... —— 按请求类型和错误码分类的速率；error=NONE 表示成功
  • kafka.server:type=BrokerTopicMetrics,name=FailedProduceRequestsPerSec,topic=... / FailedFetchRequestsPerSec,topic=... —— 主题级失败速率
  • kafka.server:type=BrokerTopicMetrics,name=TemporaryMemoryBytes,request={Produce\|Fetch} —— 临时内存使用量，配合生产端 buffer-available-bytes 判断是否内存不足

客户端侧的对照信号：生产端 kafka.producer:type=producer-metrics,client-id=... 的 buffer-available-bytes（未使用缓冲区，官方语义是「未分配的加上空闲链表上的」）与 buffer-exhausted-rate / buffer-exhausted-total（因缓冲区耗尽被丢弃的发送数）。buffer-exhausted-rate 上涨说明生产端内存或 batch.size 有问题，与 Broker 无关。

面试追问

  1. TotalTimeMs 的五段拆解分别对应什么？ —— RequestQueueTimeMs（队列等待）、LocalTimeMs（Leader 本地处理）、RemoteTimeMs（等 follower，仅 produce 且 acks 为 -1 时非 0）、ResponseQueueTimeMs（响应队列等待）、ResponseSendTimeMs（发送响应）。前三段加后两段构成全程。
  2. 怎么用这套指标区分「Broker 慢」和「网络慢」？ —— 看 ResponseSendTimeMs。它是唯一纯粹反映「把字节发出去」的耗时，高它说明链路或对端接收有问题；其余四段都在 Broker 进程内。同时 NetworkProcessorAvgIdlePercent 若健康（大于 0.3）则进一步支持「不是 Broker 线程不够」。
  3. 为什么 RemoteTimeMs 只对 produce 有意义？ —— 官方注明非 0 条件是 produce 且 acks 为 -1（即等所有 ISR 副本确认）。fetch 请求不需要等 follower 跟随自己，所以该段对 fetch 恒为 0。
  4. 客户端报 buffer-exhausted，需要动 Broker 吗？ —— 不需要先动。buffer-exhausted-rate 统计的是「因缓冲区耗尽被丢弃的发送」，这发生在客户端进程内。先看客户端内存与 batch.size / linger.ms 是否匹配真实吞吐，再看 Broker 端的 TemporaryMemoryBytes 是否打满——只有后者才指向 Broker。

如何确认

  1. 取 kafka.network:type=RequestMetrics 的 TotalTimeMs 并按五段拆开对比，延迟落在哪一段一目了然
  2. 查 kafka.network:type=SocketServer,name=NetworkProcessorAvgIdlePercent 是否低于 0.3——低于则确认是服务端线程池饱和
  3. 查 kafka.network:type=RequestMetrics,name=ErrorsPerSec,request=...,error=... 按错误码拆分，确认是超时类、权限类还是其它
  4. 客户端 JMX 查 kafka.producer:type=producer-metrics,client-id=... 的 buffer-available-bytes 与 buffer-exhausted-rate
  5. 查 kafka.server:type=BrokerTopicMetrics,name=TemporaryMemoryBytes,request={Produce|Fetch} 判断 Broker 临时内存压力

五、磁盘、容量与节流

症状：Broker 磁盘接近写满，或副本迁移后复制长期不收敛。

先说一个必须纠正的常见错误：官方 4.x 监控清单中并不存在名为 LogDirSize 的指标，不能把它当成官方指标名引用。容量监控的正确做法是三件套：

目的手段说明
主机级水位操作系统文件系统监控官方指标清单不含聚合目录容量指标，这是业界通行做法
分区级占用kafka.log:type=Log,name=Size,topic=(...),partition=(...)官方定义「分区磁盘占用字节数」，逐分区上报
日志目录可用性kafka.log:type=LogManager,name=LogDirectoryOffline（1=离线 0=在线）、OfflineLogDirectoryCount、kafka.log:type=LogFlushStats,name=LogFlushRateAndTimeMs目录真的掉盘时才会出现，此时分区不可用

配套还有 kafka.log:type=Log,name=LogStartOffset（分区首 offset）、LogEndOffset（末 offset）、NumLogSegments（段数），以及恢复进度 kafka.log:type=LogManager,name=remainingLogsToRecover / remainingSegmentsToRecover（官方定义为「该日志目录待恢复的日志数 / 当前恢复线程负责的待恢复段数」）。

关于保留策略的一个已核验事实：log.retention.hours 在 Kafka 4.x 的默认值是 168 小时（7 天），它属于可动态更新的 topic 配置（详见 KRaft 协调与选主 第八节的完整动态配置清单）。但改了这个值不会立刻删数据——清理器按自己的节奏扫描，配置变更影响的是后续段滚动与清理判定，已存在的段要等清理器扫到。log.segment.delete.delay.ms 正是控制段被标记删除后延迟多久物理删除的参数。

节流是容量章节的另一半，也是最容易造成二次故障的地方。 官方给出的安全规则必须背：

  1. 重分配完成后必须及时用 --verify 移除节流。 官方明确警告未及时移除会导致常规复制流量被节流
  2. 节流过低会导致复制不前进。 官方公式：复制不前进发生在 max(BytesInPerSec) > throttle 时
  3. 判断是否在前进的指标：kafka.server:type=FetcherLagMetrics,name=ConsumerLag,clientId=...,topic=...,partition=...，官方原话是复制期间该 lag 应持续下降；若不下降，管理员应调高节流阈值

涉及的五个配置项：Broker 级（dynamic）leader.replication.throttled.rate、follower.replication.throttled.rate、replica.alter.log.dirs.io.max.bytes.per.second；topic 级 leader.replication.throttled.replicas、follower.replication.throttled.replicas。五项均由 kafka-reassign-partitions.sh 自动赋值，也可用 kafka-configs.sh 手工查看与调整。

节流值单位是字节每秒。官方示例：Broker 间迁移不超过 50MB/s、单 Broker 内跨目录不超过 100MB/s，对应 --throttle 50000000 --replica-alter-log-dirs-throttle 100000000；进行中可用 --additional 配合同一 JSON 重跑 --execute 调整阈值。

面试追问

  1. 怎么估算一个 Broker 还能撑多久？ —— 用 kafka.log:type=Log,name=Size,topic=...,partition=... 按分区聚合出总占用，加上 ReplicationBytesInPerSec 对应的副本净增速，再结合主机文件系统的可用空间。注意要按 topic 分别估算而不是全集群平均——单个大 topic 就能打满一块盘，而全局平均值完全看不出来。
  2. 为什么保留策略调小后磁盘不降？ —— 清理器按自己的节奏扫描，配置只影响后续段滚动与清理判定；已存在的段要等被扫描到。另一个常见原因是 log.segment.delete.delay.ms 造成的延迟删除。
  3. 节流配错了会有什么后果？ —— 两个方向都会出事：太低则复制不收敛，副本一直追不上，URP 长期不恢复；太高或忘记移除则常规复制流量被节流，正常同步被拖慢。官方要求重分配完成后及时 --verify 移除。
  4. 官方监控清单里没有目录容量指标，那容量怎么监控？ —— 走主机层文件系统监控，逐分区占用用 kafka.log:type=Log,name=Size 聚合，目录可用性用 kafka.log:type=LogManager,name=LogDirectoryOffline。三者互补，不要指望单一指标。

如何确认

  1. 主机层：df 查看日志目录所在文件系统的使用率，确认是整个文件系统而非 Kafka 逻辑占用
  2. 分区级：JMX 查 kafka.log:type=Log,name=Size,topic=...,partition=...，找出占用最大的 topic
  3. 可用性：查 kafka.log:type=LogManager,name=LogDirectoryOffline 是否为 1，以及 OfflineLogDirectoryCount 是否大于 0
  4. 节流状态：kafka-configs.sh --bootstrap-server <h:p> --describe --entity-type brokers 查三个 broker 级节流配置，--describe --entity-type topics 查两个 topic 级配置
  5. 复制是否前进：JMX 查 kafka.server:type=FetcherLagMetrics,name=ConsumerLag,clientId=...,topic=...,partition=... 是否持续下降；不下降则按官方建议调高节流

六、元数据与 Controller

症状：元数据变更类操作全部失败（建 Topic、扩分区、改 ACL），但已有数据的读写正常。 看到这个组合，直接跳到本节。

本节的指标全部来自官方 KRaft 指标表，机制背景见 KRaft 协调与选主。

指标官方语义正常值
kafka.controller:type=KafkaController,name=ActiveControllerCount该节点是否为 Active Controller取值 0 或 1，全集群求和必须等于 1
kafka.server:type=raft-metrics 的 Current Leader当前 Quorum Leader 的 id-1 表示未知（即无主控）
kafka.server:type=raft-metrics 的 Current State成员状态leader / candidate / voted / follower / unattached / observer
kafka.server:type=raft-metrics 的 Current Epoch当前 Quorum 任期单调递增
kafka.server:type=raft-metrics 的 Election Latency选举耗时（avg / max）稳定态应接近 0
kafka.controller:type=ControllerEventManager,name=EventQueueSize / EventQueueTimeMsController 事件队列长度与排队时间稳态接近 0
kafka.controller:type=KafkaController,name=MetadataErrorCount该节点处理元数据日志时遇到错误的次数0
kafka.controller:type=KafkaController,name=TopicsToDeleteCount / ReplicasToDeleteCount待删除的 topic / 副本数0
kafka.controller:type=KafkaController,name=TopicsIneligibleToDeleteCount / ReplicasIneligibleToDeleteCount无法删除的 topic / 副本数0
kafka.server:type=MetadataLoader,name=HandleLoadSnapshotCount该进程启动以来加载快照的次数启动后趋于稳定

TopicsIneligibleToDeleteCount 与 TopicsToDeleteCount 一起看才有意义：TopicsToDeleteCount 增长说明删除在进行中（正常）；TopicsIneligibleToDeleteCount 非 0 且持续增长说明删除卡住了，通常需要人工介入。官方把这两组指标都列进了监控清单，说明它们是真实运维中会遇到的状态。

三种典型成因的区分方法：

症状组合成因
ActiveControllerCount 全集群求和 = 0，且各节点 Current State 为 follower/candidate 反复横跳Quorum 跌破多数派或无主控，正在反复选举
ActiveControllerCount = 1 稳定，Event 队列持续堆积，MetadataErrorCount 增长Active Controller 活着但处理不过来或元数据日志有问题

面试追问

  1. 为什么「元数据变更失败但数据读写正常」几乎必然是控制面问题？ —— 因为数据面的稳态路径只需要「分区 → Leader」映射，而这个映射每个 Broker 自己就有一份完整副本。元数据变更必须写元数据日志，需要 Active Controller。两者路径不同，所以症状可以完全解耦。
  2. ActiveControllerCount 逐节点看和求和看有什么区别？ —— 正常态全集群有且仅有 1 个节点为 1、其余为 0。逐节点看无法区分「我是热备（正常）」和「Active 挂了（异常）」，因为每个节点都可能是 0。求和等于 0 是 P0，等于 2 是脑裂信号，等于 1 但频繁跳变是选举抖动。
  3. Controller 事件队列堆积说明什么？ —— EventQueueSize / EventQueueTimeMs 反映请求在 Controller 事件队列里的等待。堆积说明 Active Controller 的事件处理速度跟不上元数据变更的提交速度，常见原因是元数据日志写入慢（磁盘 IO）或单次变更量过大。
  4. Topic 删不掉有哪些可能原因？ —— 一是删除正在进行中（TopicsToDeleteCount 增长，属正常）；二是删除被卡住（TopicsIneligibleToDeleteCount 非 0）；三是元数据变更通道本身不可用（无 Active Controller）。第三种最容易被误判成「Kafka bug」。

如何确认

  1. kafka-metadata-quorum.sh --bootstrap-controller <h:p> describe --status —— 先看 LeaderId 是否为 -1，再看 MaxFollowerLag 是否持续增长
  2. JMX 查 kafka.controller:type=KafkaController,name=ActiveControllerCount 全集群求和，必须等于 1
  3. JMX 查 kafka.server:type=raft-metrics 的 Current State 与 Current Leader，确认各节点状态与是否有主控
  4. JMX 查 kafka.controller:type=ControllerEventManager,name=EventQueueSize 与 MetadataErrorCount
  5. 核对元数据日志末尾的实际状态：kafka-metadata-shell.sh --snapshot <snapshot-path>（注意官方提示 00000000000000000000-0000000000.checkpoint 不包含集群元数据，须用有效的快照文件），或 kafka-dump-log.sh --cluster-metadata-decoder --files <path>
  6. 确认 kraft.version 模式：kafka-features.sh --bootstrap-controller <h:p> describe —— 该字段为 0 或缺失即为静态 Quorum

症状：手上有一堆指标和一堆命令，不知道先点哪个。 本节是前六节的收敛。

这张表的使用方式是「先按症状定位行，再按列逐步排除」，不是从上到下逐行扫描。 Kafka 排障最大的时间浪费是并行猜测多条路径，而症状到指标的第一列映射是唯一的。

面试追问

  1. 为什么排障必须先分层？ —— 因为同一个表面症状可能来自完全不同层。LAG 增长可能是消费端慢（客户端层）、磁盘慢导致 fetch 变慢（数据面）、或元数据操作阻塞（控制面）。不先分层就会在三处同时查，效率最低。
  2. 「写入被拒绝但集群看起来健康」怎么解释？ —— 典型的 AtMinIsrPartitionCount 非 0 场景：ISR 恰好等于 min.insync.replicas，再掉一个副本就达不到要求。集群整体健康但该分区的冗余已到边界。处置是恢复副本，而不是调小 min.insync.replicas——后者是用可靠性换可用性。
  3. 为什么「重分配完成后集群变慢」是很典型的故障？ —— 因为节流在重分配期间是必要的，结束后如果不及时移除，常规复制流量也会被节流。官方明确警告这一点并要求用 --verify 移除。症状是「做完变更反而更慢了」，很容易被误判为变更本身有问题。
  4. 这张决策表能覆盖多少场景？ —— 覆盖的是症状可观测的运维类问题，不覆盖逻辑错误、数据格式错误、权限模型设计问题。遇到表里没有的症状，说明问题可能在应用侧或协议语义层，继续查指标收益不高。

如何确认

  1. 把告警映射到决策表的具体行，取该行的「第一步查」作为唯一入口，避免并行猜测
  2. 每一步都用可复现的命令或指标确认，不接受「看起来像」
  3. 走完两步仍无法归因时，回到第一层重新确认告警落在数据面、控制面、KRaft 还是客户端层
  4. 处置后必须回到第一步复查同一个指标，确认趋势真的改变（而非采样窗口内的偶然波动）

五条最容易踩的操作约束（均为官方明确说明）：

  1. --reset-offsets 一次只支持一个消费组，必须先选一个 scope（--all-topics 或 --topic），且必须先确保消费者实例不活跃。它有三个执行选项（默认仅显示 / --execute 真正执行 / --export 导出 CSV）和多个场景（--to-earliest / --to-latest / --to-offset / --shift-by <n> / --by-duration / --to-datetime / --to-current / --from-file）。越界 offset 会被自动调整到可用边界——例如末位为 10 而请求 shift 15，实际选中 10。
  2. kafka-reassign-partitions.sh 的三个模式互斥：--generate 只生成候选方案、不开始移动；--execute 按 JSON 执行；--verify 校验状态（输出 completed / still in progress）。--verify 同时负责移除节流。
  3. 优雅关机需 controlled.shutdown.enable=true，它做两件事：停止前把日志全部 sync 到盘（重启时无需 log recovery），停止前把本机担任 Leader 的分区迁移出去（使切换降到几毫秒）。前提是本机上所有分区都有副本（副本因子 > 1 且至少一个副本存活）——这也正是下线 Broker 的正确做法。
  4. 默认会把 leadership 恢复到 preferred replica（auto.leader.rebalance.enable=true）。Broker 崩溃重启后只会作为 follower 存在；置 false 则需手动跑 kafka-leader-election.sh --election-type preferred --all-topic-partitions。preferred replica 是副本列表中靠前者（如列表 1,5,9 中 1 为 preferred）。
  5. kafka-dump-log.sh 会自动按文件后缀分派，不同后缀走不同检查，所以「把路径丢进去就行」是错的用法。它对 .log 走段解码、对 .index / .timeindex 走索引检查、对 .snapshot / .txnindex 各走自己的解析，未知后缀会直接打印 Ignoring unknown file 并跳过——命令不报错但什么都没查，是典型静默失败。段损坏分诊看三类输出：Found N invalid bytes（段尾有无效字节）、Mismatches in（索引 offset 与日志 offset 对不上）、%d is followed by %d（offset 不连续）。其中 --index-sanity-check 与 Broker 启动时判断索引是否需要重建的是同一个检查，可在不重启 Broker 的前提下预判要不要重建索引。

另有一条授权相关的坑值得记：--describe 消费组时，使用 consumer 协议的场景下 admin client 需要该组所有 topic 的 DESCRIBE 权限，而 classic 协议不要求。所以同一命令在两种协议下的报错行为不同。

面试追问

  1. --generate 和 --execute 有什么区别？ —— --generate 只根据「要移动哪些 topic + 目标 broker 列表」生成一份候选分配方案，不开始任何数据移动，输出当前分配与建议分配两份 JSON。建议把当前分配另存以便回滚。--execute 才是按 JSON 真正开始搬迁。
  2. 为什么 --verify 除了查状态还要用来移除节流？ —— 因为节流是重分配期间为保护现网流量而设的，重分配结束后若不移除，常规复制流量也会被节流。官方把节流清理作为 --verify 的一部分并明确要求及时执行。
  3. 下线一个 Broker 的正确顺序是什么？ —— 先确认其上所有分区都有可用副本，然后用 kafka-reassign-partitions.sh 把副本迁走并 --verify 确认完成（含移除节流），然后用 controlled.shutdown.enable=true 做优雅关机。不能直接 kill——官方说明直接停机会跳过日志 sync，重启时需要做 log recovery。
  4. 为什么同一个 --describe 命令在不同协议下会报不同的权限错误？ —— 因为 consumer 协议要求 admin client 对组内所有 topic 有 DESCRIBE 权限，classic 协议不要求。所以从 classic 迁移到 consumer 协议时，原本能跑的运维命令会开始失败，但故障表现与「权限配置漏了」不同。

如何确认

  1. 不带任何参数运行 bin/ 下的工具会打印所有可用命令行选项——不确定参数时以此为准，不要凭记忆猜
  2. 优先用 --bootstrap-controller 查元数据类问题（绕过数据面，信号更干净），用 --bootstrap-server 查数据面问题
  3. --reset-offsets 执行前必须确认组内无活跃成员；先不带 --execute 跑一次看输出，再决定是否真正执行
  4. 重分配类操作全程保留「当前分配」JSON，必要时用它做回滚输入
