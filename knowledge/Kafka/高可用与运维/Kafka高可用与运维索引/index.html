关键结论

  1. Kafka 4.x 已移除 ZooKeeper，KRaft 是唯一元数据协调模式。 根因不是协议更先进，而是元数据从「外部系统的私有协议」下沉为「Kafka 自己的内部主题」，直接白拿复制、持久化与快照能力。

  2. Controller 不可用 ≠ 集群不可用。 准确表述是「从自愈降级为维持现状」：已建立的数据面读写与位点提交继续可用，所有元数据变更不可用，且 Leader 故障后的切换失效。单点故障不致命，故障叠加才致命。

  3. KRaft 没有 Broker 自行选主的路径。 分区 Leader 的任免由 Active Controller 计算并写进元数据日志，Broker 读到后执行；连非同步选举都由 Controller 侧专用线程按周期发起（默认周期 5 分钟，可用 kafka-leader-election.sh --election-type unclean 立即触发）。

  4. Broker 就是元数据 Quorum 的 observer。 它完整复制元数据日志（因此 Controller 切换后能无缝接管），但不投票、不可能成为 Leader。理解这一点是划清控制面与数据面两个独立故障域的起点。

  5. 元数据是否可靠，关键看 LeaderId 与 ActiveControllerCount。 前者是 -1 即无主控；后者全集群求和必须等于 1——等于 0 是 P0，等于 2 是脑裂信号，等于 1 但频繁跳变是选举抖动。逐节点看无法区分「我是热备」和「Active 挂了」。

  6. 排障先分层，再按症状定位，最后才动配置。 指标分数据面 / 控制面 / KRaft / 客户端四层，同一表面症状可能来自任意一层。TotalTimeMs 的五段拆解负责把「服务端慢」和「网络慢」彻底分开。

  7. 变更类操作有两个高危尾巴。 其一，kafka-reassign-partitions.sh 完成后必须及时 --verify 移除节流，否则常规复制流量会被节流，症状是「做完变更反而更慢」；其二，--reset-offsets 执行前必须确认组内无活跃成员。

学习顺序

  1. 先补前置：确认已掌握分区、副本、ISR 三个概念，以及 Broker 与 Controller 的角色分工（见「相关阅读」前两项）。跳过这步会让两篇正文里的对照都失去参照。
    • 产出：能一句话说清「谁存消息、谁存元数据」。
  2. 再读 KRaft 协调与选主 的第一、二节：先建立「元数据存放位置变了」这个根因认知，再掌握 RAFT 的六个成员状态与 term / epoch 三层 fencing。这一节是整个主题的骨架。
    • 产出：能默写六个状态名，并解释为什么 term 之外还需要 leaderEpoch。
  3. 接着读同篇第三、四节：元数据日志的记录内容与快照回放、Quorum 的规模算术（2N+1）与两个超时的比例关系。配置 controller.quorum.bootstrap.servers 之前必须先看第四节。
    • 产出：能解释为什么 fetch 超时必须大于 election 超时。
  4. 然后读同篇第五到七节：任期与 epoch 的 fencing、Broker 注册与心跳这条独立通道、以及最关键的第七节系统边界表——它是「Controller 挂了还能不能读写」这个问题的完整答案。
    • 产出：能背出边界表里「可用 / 不可用」各三行，并说得出「自愈失效」这个准确表述。
  5. 再读同篇第八到十节：静态 / 动态两维度配置、两种 Leader 的区分、以及成员变更的官方路径与陷阱。注意第十节明确指出 Kafka 官方并未描述 joint consensus 过渡配置，不要把 Raft 论文直接套用。
    • 产出：能说出动态 Quorum 增员四步，以及减员停机约束各自的理由。
  6. 最后读 Kafka 监控与排障 全文：前六节按症状展开、第七节是收敛成一张决策表、第八节是官方 CLI 工具链。建议边读边把第七节的决策表抄成自己的值班卡片。
    • 产出：一张自己能在十秒内查完的值班卡片。
  7. 实战校验：装一套本地集群，照第八节的命令清单跑一遍 describe 与 describe --status，把真实输出与正文里的示例列名对齐。
    • 产出：确认列名与正文一致；若不一致，以你所用版本的官方文档为准并就地修正笔记。
