主从复制与读写分离

来源

基于 MySQL 8.0 官方文档整理。Binlog 的生成机制（写入流程、缓存、两阶段提交、Group Commit）不在本文展开，见 Binlog - 生成流程、格式与两阶段提交；本文只讲从 Binlog 到从库落地的消费链路。

一、为什么需要主从复制

目标说明
高可用主库故障时可提升从库为新主，RTO 取决于切换流程
读扩展读多写少场景把读请求分流到多台从库，突破单库 QPS 上限
数据备份备份跑在从库上，避免影响主库性能与稳定性
异地容灾跨机房延迟备，用于机房级故障恢复

注意：从库默认只读（super_read_only=ON），它不是”备份一切”的银弹——延迟与数据丢失风险见第五、七章。

二、复制原理：三线程 + 两日志

组件作用
Binlog（主库）主库记录所有变更，复制的数据来源
IO 线程（从库）建立到主库的连接，拉取 Binlog 并写入 Relay Log
Relay Log（从库）中继日志，从库的”本地 Binlog”
SQL 线程（从库）读 Relay Log 并重放——串行是延迟的根源

关键点：IO 线程与 SQL 线程解耦。IO 线程拉取不受 SQL 重放阻塞（Master_Info/Slave_Info 记录位点），因此 IO 线程通常不是延迟瓶颈。

三、Binlog 格式与复制一致性

三种格式的写入机制详见 Binlog - 生成流程、格式与两阶段提交。从复制角度看，差异在一致性与日志量：

格式记录内容复制一致性日志量典型风险
STATEMENTSQL 语句原文可能不一致小NOW()、UUID()、非确定性函数导致主从数据分叉
ROW（推荐）每行变更前后的值精确一致大大批量 UPDATE 导致日志膨胀、从库重放慢
MIXED自动在 S/R 间切换不完全可预测适中行为随版本/语句变化，排查困难

生产建议：默认使用 ROW（binlog_format=ROW）。STATEMENT 的不一致问题难以事后修复，而 ROW 的代价（体积）通常可通过保留策略与并行复制缓解。

四、复制模式

4.1 异步复制（默认）

主库写入 Binlog 后立即响应客户端，不等待任何从库。性能最好，但主库宕机时可能丢失尚未传走的 Binlog——存在数据丢失窗口。

4.2 半同步复制（MySQL 5.7+）

主库等待至少 N 个从库 ACK 后才向客户端返回成功，在一致性与性能间取平衡。

参数说明
rpl_semi_sync_master_wait_for_slave_count需要等待的 ACK 从库数
rpl_semi_sync_master_timeout等待超时（毫秒）；超时后退化为异步，而非报错
rpl_semi_sync_master_wait_pointAFTER_SYNC（默认，无损半同步）/ AFTER_COMMIT

⚠️ 关键陷阱：AFTER_SYNC 才是真正无损的（主库先落盘 Binlog 再等 ACK），AFTER_COMMIT 在等 ACK 期间若主库宕机，从库可能收到该事务而主库已回滚，导致数据不一致。

4.3 GTID

GTID（Global Transaction Identifier）用 server_uuid:transaction_id 标识事务，使故障切换与自动补数不必依赖 master.info 中的文件位点。5.6+ 推荐开启，是自动切换的前提。

五、主从延迟：原因与排查

根因：从库 SQL 线程串行重放。主库并发写入时，从库单线程追不上，延迟持续累积。

常见诱因：

诱因说明
主库并发写压力同一事务的变更必须按序重放，无法并发
大事务单事务改百万行 → 从库需串行执行同样时长
无主键/无索引表的 UPDATE从库全表扫描定位每一行，耗时被放大
从库硬件差从库配置低于主库，或混部受其他负载抢占
DDL 阻塞从库 ALTER 与重放争锁，或 slave_preserve_commit_order 等待
单线程重放未开并行复制，瓶颈固定在单核

排查步骤：

  1. SHOW SLAVE STATUS 看 Seconds_Behind_Master——⚠️ 不可单独信任：主库无写入时它会瞬间归零，即便实际已积压几十秒。
  2. 对比主从 GTID 集合：SELECT @@GLOBAL.gtid_executed。
  3. 检查是否有大事务或 DDL 积压在重放队列。
  4. 逐表比对：pt-table-checksum / pt-slave-delay

推荐判据：优先看主从 GTID 差集与从库上仍存在的中继日志大小，而非 Seconds_Behind_Master。

六、延迟解决方案

方案作用层级原理代价
并行复制从库多线程并行重放不同事务需 slave_parallel_type=LOGICAL_CLOCK，8.0 默认 LOGICAL_CLOCK
大事务拆分业务批量改写拆成多个小事务需业务配合，破坏原子性
补齐索引优化避免从库全表扫描一次性改造成本
半同步复制一致性降数据丢失风险增加主库 RT
强制走主库读路由写后立即读打主库丧失部分读扩展能力
分库架构单库写并发降低复杂度上升
延迟监控+自动降级运维超阈值则暂停读从库需要中间件支持

并行复制的演进：8.0 引入 WRITESET（binlog_transaction_dependency_tracking=WRITESET），按行冲突而非事务提交顺序判断依赖，同一行的事务串行、不同行并行——比 LOGICAL_CLOCK 的无冲突事务并行更精确。

原则：并行复制只对”无冲突”事务有效。真正的瓶颈是单行热点（如同一库存行高频更新），这类场景只能靠分片解决。

七、读写分离的实现方式

方式实现优点缺点
应用层代码内按业务判断写后读主库无额外组件，可控侵入代码，逻辑分散
中间件/ProxyShardingSphere、ProxySQL、MyCat 等对业务透明，可统一限流与路由多一跳延迟，运维复杂度上升
云托管云厂商 RDS 提供的读写分离地址免运维，自动切换厂商锁定，成本高

路由策略要点：

  • 写操作 → 主库，并记录该事务的去从标记（如 session 变量）。
  • 同一 session 内的后续读 → 仍走主库，直到延迟回落或显式失效。
  • 其余普通读 → 按权重分发到从库。

八、一致性问题与规避

写主库后立即读从库，会读到旧数据（read-your-writes 被破坏）。规避手段：

手段说明
强制读主库写后 N 秒内或特定 session 内强制走主库，最常用
等待延迟归零延迟降到阈值以下再放读请求，简单但不稳定
消息队列串行化写后把”读请求”通过 MQ 排到写之后，顺序保证
GTID 等待等从库 GTID 追上写事务的 GTID，再放读

权衡：没有零成本方案。强制读主库最简单，代价是这部分流量不再被分摊；MQ 顺序化最精确，代价是链路上多一个组件与延迟。

九、常见故障处理

现象排查/处理
Slave_IO_Running=No凭据/网络/主库已清理 Binlog；报错 1236 时需按位点重新同步
Slave_SQL_Running=No看 Last_Error：重复键冲突需跳过该事务（sql_slave_skip_counter），慎用
复制报错 1236主库 Binlog 被清理且无位点 → 需重新初始化从库
复制报错 1045授权问题，检查主库 replication slave 账号
从库 super_read_only=ON 无法写需显式关闭；这是 MySQL 5.7+ 的防误写保护
主从数据不一致pt-table-checksum 校验，pt-table-sync 修复（需谨慎）
Binlog 撑爆磁盘调小 expire_logs_days / binlog_expire_logs_seconds；主库不可随意删——从库未取走就删会导致复制断裂

十、面试速答模板

问：主从复制的原理？延迟怎么解决？

原理是「三线程 + 两日志」：主库写 Binlog；从库 IO 线程拉取 Binlog 落地为 Relay Log；SQL 线程串行重放 Relay Log。

延迟根因是 SQL 线程串行重放。解决方向： ① 技术层开并行复制（8.0 用 WRITESET 按行冲突判断依赖，精准度高于 LOGICAL_CLOCK）； ② 业务层拆大事务、补索引，避免从库全表扫描； ③ 架构层读扩展扛不住的场景做分库。

排查不能只看 Seconds_Behind_Master（无写入时会假性归零），要看 GTID 差集。 数据一致性方面，异步复制有丢数据窗口，需零丢失选半同步（注意用 AFTER_SYNC），写后读一致性靠强制读主库解决。
