Redo Log - 记录内容、LSN 与崩溃恢复

很多人对 Redo Log 的理解只停留在“记录数据修改，用于崩溃恢复”，但具体写进 Redo 的二进制数据长什么样、每种操作分别记录什么，往往比较模糊。下面用图文详细拆解。

一、Redo Log 的记录类型速览

InnoDB 的 Redo Log 是物理逻辑日志：它记录的是“对哪个页面的哪些偏移量做了什么修改”，而不是 SQL 语句本身。

二、场景复现：事务 A 各阶段 Redo 内容拆解

回到我们的场景，事务 A（TRX_ID=100）依次执行：

  1. UPDATE t SET name='AA' WHERE id=1;
  2. DELETE FROM t WHERE id=2;
  3. INSERT INTO t VALUES (4, 'D');
  4. COMMIT;

阶段 1：UPDATE 的 Redo 内容

二进制层面示意（MLOG_REC_COMP_UPDATE_IN_PLACE）

为什么不记录 SQL？ Redo 不关心是不是 UPDATE ... SET name='AA'，它只认“页 10 偏移 200 处 3 个字段改成这些值”。崩溃恢复时拿着这个记录去覆盖对应位置就行了。

阶段 2：DELETE 的 Redo 内容

delete_flag 在行记录中的位置

Redo 只记录这个 bit 从 0 变成 1，以及关联的 DB_TRX_ID 和 DB_ROLL_PTR 变化。

四、Redo 与 Undo 的双写保护机制

关键认知：Redo Log 不仅保护数据页，也保护 Undo 页。 这样即使崩溃，Undo 页的旧版本也能恢复，MVCC 版本链就不会断裂。

五、Redo 记录结构速查表

操作Redo 类型记录内容作用
UPDATEMLOG_REC_COMP_UPDATE_IN_PLACE页号、偏移、新字段值、新 DB_TRX_ID、新 DB_ROLL_PTR恢复数据页的修改
UPDATE (Undo)MLOG_UNDO_HDR_CREATEUndo 页号、旧版本数据（name='A'，DB_TRX_ID=80）保护 Undo 页，回滚时可用
DELETEMLOG_REC_COMP_UPDATE_IN_PLACE页号、偏移、delete_flag=1、新 DB_TRX_ID、新 DB_ROLL_PTR恢复删除标记
DELETE (Undo)MLOG_UNDO_HDR_CREATEUndo 页号、删除前完整记录保护 Undo 页
INSERTMLOG_REC_COMP_INSERT页号、插入位置、整行数据（id=4, name=‘D’, DB_TRX_ID=100）恢复新行插入
INSERT (Undo)MLOG_UNDO_HDR_CREATEUndo 页号、主键值 id=4保护 Undo 页，回滚时删除该行
COMMITMLOG_TRX_COMMIT事务 ID、提交 LSN崩溃恢复时判断事务是否已提交

六、总结

Redo Log 的核心特征：

  1. 记录的是“对物理页的修改”，不是 SQL 语句
  2. 先写 Redo 再改数据页（WAL 原则），只要求 Redo 落盘即可保证持久性
  3. 不仅保护数据页，也保护 Undo 页，形成双重保护
  4. 事务提交时写入 MLOG_TRX_COMMIT 标记，这是崩溃恢复判断是否前滚的依据
  5. INSERT 的 Redo 包含完整新行，而 UPDATE/DELETE 只记录差异部分（哪个偏移、改了多少、新值是什么）
