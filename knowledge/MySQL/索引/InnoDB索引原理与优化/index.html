InnoDB 索引原理与优化

本文按「原理 → 结构 → 策略 → 实战」四层递进，配合表格与 Mermaid 图解，覆盖大厂高频深水区考点。

一、索引基础认知

1.1 索引的本质与代价

维度说明
本质排好序的、便于快速查找的数据结构（B+Tree / Hash / Full-text）
收益减少扫描行数、避免排序、避免临时表、加速 JOIN
代价占磁盘、写放大（INSERT/UPDATE/DELETE 需维护索引）、优化器选择成本
适用WHERE、ORDER BY、GROUP BY、JOIN ON、DISTINCT 列
不适用区分度极低（如性别）、频繁更新、超大文本、极少查询的列

三、聚簇索引 vs 二级索引（回表本质）

回表代价：二级索引查到主键后，再回聚簇索引取整行 = 2 次 B+Tree 查找。

索引类型叶子存储是否需回表
聚簇索引完整行数据否

#场景示例原因
1最左前缀缺失WHERE b=1（索引a,b）无法定位

6.2 key_len 计算规则

类型utf8mb3 字节utf8mb4 字节备注
INT44定长整型，与字符集无关
BIGINT88同上
CHAR(n)3n4n定长字符串
VARCHAR(n)3n+24n+2变长字符串 +2 长度前缀字节
DATETIME5~85~8版本相关
每列允许 NULL+1+1可为 NULL 才 +1（存 NULL 标记位）

例：idx(a INT NOT NULL, b VARCHAR(20))，字符集 utf8mb4

  • a=1 → key_len = 4（a 为 NOT NULL，省掉 NULL 标记的 +1）
  • a=1 AND b='x' → key_len = 4 + 20×4 + 2 + 1 = 87 = a 的 4 字节 + b 的 20×4 字符 + 2 字节长度前缀 + 1 字节 NULL 标记（b 可为 NULL）

为什么 utf8mb4 的 key_len 更大

utf8mb4 每个字符最多4 字节（utf8mb3 为 3 字节），所以同一列的 key_len 在 utf8mb4 下会变大。 这直接影响索引的选择性判断：key_len 越长说明单行索引数据越大，同样页容量下能放的键值越少、树高可能增加。 用 key_len 估算选择性时，务必确认当前列的字符集，否则会低估索引占用的空间。

十、实战面试题精选

Q1：WHERE a=1 AND b>2 AND c=3，索引 (a,b,c) 用了几列？

答：a、b 两列。b 为范围查询，其后 c 在 B+Tree 中无序，无法用于定位，仅能在 ICP 下用于过滤。

Q2：ORDER BY a,b 与索引 (a,b) 关系？

答：若 WHERE 已用 a 等值，则 ORDER BY b 可用索引排序；若直接 ORDER BY a,b 且无 WHERE，也可用索引有序性避免 filesort。

Q3：为什么推荐自增主键？

维度自增主键UUID
插入位置顺序追加随机插入
页分裂少频繁
空间4/8 字节16/36 字节
二级索引小大

Q4：SELECT * 为何不推荐？

  • 破坏覆盖索引，强制回表
  • 传输无用列，增加网络/内存开销
  • 表结构变更时结果不稳定

Q6：索引越多越好吗？

否。代价：

  • 写操作需维护所有索引（写放大）
  • 占磁盘空间
  • 优化器选择成本上升
  • 建议单表 ≤5~6 个，写多读少表更少

Q7：LIKE '%x%' 如何优化？

方案说明
全文索引FULLTEXT + MATCH AGAINST
倒排/搜索引擎Elasticsearch
前缀索引仅 LIKE 'x%' 有效
覆盖索引减少回表，但仍全扫索引

十一、总结脑图

一句话总结：索引优化的本质是「用有序结构换查询效率」，核心是最左前缀 + 覆盖索引 + 避免失效 + 控制数量，配合 EXPLAIN 与慢查询日志形成闭环。
