Redis 主从复制与数据同步

核心结论

一句话

主从复制是异步的，靠 PSYNC 命令实现”能增量就增量、不能就全量”。它复用 RDB 做全量快照，用 repl-backlog 这个环形缓冲区记住最近的写命令以便断线重连时补齐——backlog 被覆盖就必然退化为全量同步。

一、整体架构

默认是异步的：主库返回 write 成功时，数据只保证到了主库内存和复制缓冲区，不代表从库已收到。

特性说明
复制类型异步、全量 + 增量
全量载体RDB 快照（复用持久化的 fork 机制）
增量协议PSYNC（2.8+ 引入，替代旧的 SYNC）
是否阻塞主库全量同步的 fork 会短暂阻塞；增量不阻塞
级联支持（A 的从库 B，B 还能有从库 C）

二、全量同步流程

为什么全量也要”增量 + 缓冲”两步：

  • 从库 fork 载入 RDB 期间，主库仍在接收客户端写命令
  • 这些命令先进入主库的复制缓冲区（与 backlog 不同的专用缓冲）
  • RDB 传输完再补发这段增量，保证从库不丢 fork 之后的数据

RDB 传输方式

  • repl-diskless-load disabled（默认）：主库先把 RDB 写到磁盘，再发给从库
  • repl-diskless-load on：主库边生成边通过 socket 直接推给从库，不落盘

无盘方式省掉一次磁盘 IO，大实例下能明显缩短全量同步时间。Redis 5.0 起 repl-diskless-sync yes 让主库主动采用无盘（由主库决定是否走无盘路径）。

三、增量同步：PSYNC 与 repl-backlog

3.1 断线重连的两种结果

两个判定条件对应两个必须”还记得”的量：

要素含义存放在哪
replication ID主库身份标识（主库重启会生成新的 runid）主库
offset复制字节流位置主库 backlog 与从库自身状态

3.2 repl-backlog 环形缓冲区

主库维护一个固定大小的环形缓冲，存放最近产生的复制字节流。

参数默认说明
repl-backlog-size1MB缓冲区大小。主库重启后失效
repl-backlog-ttl3600 秒缓冲区保留时长（无连接时也保留）

backlog 太小 = 频繁全量同步

若主库每秒产生 100MB 复制流量而repl-backlog-size 只有 1MB，从库几乎必然每次重连都全量同步。全量同步对主库是 fork 阻塞 + 网络与 CPU 开销，频繁发生会严重伤害主库。

经验值：repl-backlog-size 按 主库峰值写入量 × 能容忍的最长断线时间 × 2 估算，并预留磁盘空间。1MB 只适合极低写入量或纯静态数据场景。

主库重启必然触发全量

主库重启会生成新的 replication ID，从库带着旧 replid 来PSYNC 必然匹配不上 → 直接全量。这是复制方案无法回避的代价，也是必须跨机房复制的根本原因。

3.3 主从各自维护 offset

参数名随版本变化

6.0 之前用slaveof / slave-read-only / min-replicas-*，6.0+ 改为 replicaof / replica-read-only / min-replicas-*。配置项的语义没变，名字改了。老配置在 7.x 已移除，迁移时注意。

四、关键配置项

参数默认说明
replicaof <master-ip> <master-port>—从库指向主库（或用 replicaof no one 提升为主）
replica-read-onlyyes从库只读。设 no 可让从库也可写（双写易冲突）
replica-serve-stale-datayes断连期间从库是否继续服务旧数据
repl-diskless-syncyes（5.0+）主库是否主动采用无盘复制
repl-diskless-sync-delay5 秒无盘模式下积攒一批写再发起同步
repl-diskless-loaddisabled从库被动要求无盘加载
repl-backlog-size1MB环形缓冲大小
repl-backlog-ttl3600 秒缓冲保留时长

该选哪个

缓存场景倾向yes（可用性优先，旧数据比报错好）；强一致读场景倾向 no（宁可失败也不给旧数据）。两者都要配合客户端的降级逻辑。

五、从库如何处理过期与删除

行为说明
过期 key从库不独立删除已过期的 key；由主库发送 DEL 指令同步过来
懒过期replica-lazy-expire 控制从库是否自行惰性清理（默认 no）
读已过期 key主库会过滤（返回 nil），从库默认跟随主库逻辑

别在从库上做淘汰淘汰

从库的maxmemory-policy 对淘汰行为影响有限——主库淘汰后会把 DEL 同步到从库。如果从库自身内存也吃紧并触发了淘汰，会导致从库的数据集与主库不一致，后续无法靠增量同步修复，只能全量重来。因此从库一般配置比主库更宽松的 maxmemory，从而不触发淘汰。

六、数据一致性问题（最常追问）

6.1 三个必然存在的丢失/不一致窗口

6.2 防止主库孤立无援（脑裂防线之一）

参数含义
min-replicas-to-write N至少有 N 个”健康”从库，主库才接受写
min-replicas-max-lag T从库延迟超过 T 秒就视为不健康

“健康”的判定就是这两个参数：连接正常且延迟在阈值内。达不到时主库拒绝写（返回错误），以牺牲可用性换取数据不丢。

配置陷阱

设为min-replicas-to-write 1 而集群只有一个从库时，一旦该从库因短暂网络抖动掉线，主库会同时对所有客户端不可写。从库数量要留出冗余，并谨慎设定这个参数。

七、常用运维命令

必配监控

  • master_link_status —— 主从链路是否 up
  • slave_repl_offset 与 master_repl_offset 的差值 —— 复制延迟
  • sync_full 增长速度 —— 突然频繁全量同步 = backlog 不够或主库在重启
  • sync_partial_err 增长 —— 部分重同步持续失败，backlog 可能有问题

八、面试速答模板

“主从复制是异步的，分全量和增量两步。全量走 fork 生成的 RDB 快照传输，从库 fork 载入期间主库的新写入先进复制缓冲区，RDB 发完再补发这段增量。

增量靠 PSYNC <replid> <offset>。主库重启会换新的 replication ID，从库带旧 ID 来就匹配不上，必然全量；ID 匹配但 offset 已被 repl-backlog 覆盖，只能 +FULLRESYNC 退化为全量。所以 backlog 大小直接决定重连成本，必须按峰值写入量乘以可容忍断线时间来估，1MB 那个默认值只适合低写入场景。另外主库重启本身也必然触发全量，这是方案层面的固有代价。

数据一致性上要认清三个窗口：异步复制在 write 返回到从库之前崩了会丢、backlog 太小导致重连全量期间的增量会丢、主库重启必全量。min-replicas-to-write 配合 min-replicas-max-lag 能挡住主库孤立无援的情况，但代价是主库可能在网络抖动时直接不可写，从库数要留冗余。

从库只读是默认值，别随便开 replica-read-only no 双写；从库的 maxmemory-policy 也不建议触发淘汰，一旦从库自己淘汰了 key，数据集就和主库不一致，后续增量同步修不回来，只能全量重来。”
