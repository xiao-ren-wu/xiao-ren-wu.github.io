RDB 与 AOF 两种持久化机制

核心结论

一句话

RDB 是某一时刻的全量快照，恢复快但可能丢数据；AOF 是写命令的追加日志，数据完整但文件大、恢复慢。两者都靠 fork() 拿到一致的数据视图，fork 的那一刻之后写入的数据都不在快照里——这是理解所有持久化问题的起点。

一、RDB：全量二进制快照

1.1 工作方式

属性值
文件名dbfilename（默认 dump.rdb）
存放目录dir（默认 Redis 启动目录）
压缩rdbcompression yes
校验rdbchecksum yes（CRC64）
数据格式二进制，非文本

1.2 触发条件

另有两类触发：

  • SHUTDOWN（非 NOSAVE）—— 优雅关闭时自动存一次
  • 主从复制的全量同步 —— 从库向主库请求全量时，主库会做一次 RDB

官方建议

三条save 全都关掉（save ""）由运维在低峰期手动 BGSAVE，或改用 AOF everysec。三条同时开着不会叠加触发——Redis 取最”严格”的那条，而不是三条都执行。

二、COW 写时复制：RDB 的真实代价

fork() 后父子进程共享同一批物理页（页表指向相同物理页）。写操作会触发”复制这一页再改”，这就是 COW。

风险点：

  1. fork 瞬间内存翻倍。实例 8G → fork 期间可能需要 16G 虚拟内存（实际靠 overcommit 保证不立即占用）
  2. 改大 key 灾难性放大。改一个 100MB 的 Hash，若逐页触发 COW，可能瞬间多出接近 100MB
  3. fork 本身会短暂阻塞主线程。数据量大时 fork 耗时可达数百毫秒到秒级，期间所有请求延迟飙升
  4. 依赖内核 overcommit。必须设 vm.overcommit_memory 1，否则 fork 可能因”无法分配虚拟内存”失败

缓解手段

  • Redis 4.0 起会在 fork 后让父进程减少对已有页的修改（推迟复制、合并写），降低 COW 放大
  • 生产上避免对超大 key 频繁写
  • 容器中要留足 fork 所需空间，或用 maxmemory 提前卡住水位
  • 纯内存实例（可丢失）直接关掉持久化

三、AOF：写命令追加日志

3.1 工作方式

AOF 记录的是执行过的写命令（RESP 协议文本），不是数据本身。恢复时重放这些命令重建数据。

参数取值说明
appendonlyno / yes是否开启
appendfilenameappendonly.aof文件名（7.0 起为目录）
appenddirnameappendonlydir7.0 的 multi-part AOF 目录
appendfsyncalways / everysec / no见下表
aof-use-rdb-preambleyes（4.0+ 默认）混合持久化
no-appendfsync-on-rewriteno（默认）rewrite 期间是否暂停 fsync

3.2 三种 fsync 策略（高频考点）

策略刷盘时机最坏丢数据量性能
always每条命令后 fsync几乎不丢最差（QPS 下降一个数量级）
everysec每秒 fsync 一次约 1 秒推荐默认
no交给操作系统决定可能 30 秒甚至更久最快

为什么

everysec 是默认 它把”可能丢 1 秒数据”换成了”每秒多一次 fsync”。经验上 always 的吞吐损失远大于业务能接受的数据损失。若业务要求零丢失，应在架构层用主从/集群兜底，而不是靠 always——always 会把磁盘 IOPS 打满，连主从复制都会被拖慢。

3.3 AOF 重写（rewrite）

AOF 会不断追加，同一个 key 被改 1000 次就记录 1000 次。重写用当前内存数据重新生成一份最小 AOF。

rewrite 也 fork，同样有 COW 风险

rewrite 和 RDB 一样要 fork，且它要遍历全部 key。数据量大时 BGSAVE 和 BGREWRITEAOF 都是延迟毛刺来源。生产上通常限制数据量、或在低峰期手工触发。

3.4 混合持久化与 multi-part AOF

混合持久化（aof-use-rdb-preamble yes，4.0+ 默认）：AOF 文件开头写一段 RDB 格式的全量快照，后面才追加增量命令。

multi-part AOF（7.0 引入）：把 AOF 组织成一个目录，文件更合理也更好清理。

收益

恢复时只加载 base + 尾部 incr，而不是从 AOF 开头逐条重放。混合持久化 + multi-part 让 AOF 的恢复速度接近 RDB，这是 4.0 之后”可以用 AOF 又不担心恢复慢”的关键。

四、RDB vs AOF 全维度对比

维度RDBAOF（everysec）
记录内容全量数据快照写命令追加
文件大小小（压缩）大（混合持久化后中等）
恢复速度快较慢（7.0 后改善明显）
数据丢失可能丢 fork 之后全部约 1 秒
写命令开销无（只在快照时）每条写都追加（无 fsync 时）
追加脏页刷盘不需要需要
文件可读性二进制，不可读RESP 文本，可人工审查/修复
fork 时机快照点rewrite 时

选型建议

场景选择
纯缓存，可丢数据全关（save "" + appendonly no）
允许丢几秒，换最高性能save 900 1 + appendonly no
要求数据完整性appendonly yes + appendfsync everysec
零丢失要求不靠 always；用主从/集群 + 持久化组合，并接受”已确认写入”的语义边界

常见误区

“开了 AOF 就不丢数据了” —— 不成立。everysec 仍可能丢 1 秒；no 可能丢 30 秒；AOF 写入成功也不等于业务持久（还要看 write 返回值与主从状态）。真正的零丢失需要跨机房复制，这是另一套设计。

五、实战排查命令

必须配监控的两条

  • rdb_last_bgsave_status / aof_last_write_status —— 失败时 Redis 不会主动告警，数据会静默停止持久化
  • rdb_last_bgsave_time_sec —— 反映 fork 耗时与 COW 压力

六、面试速答模板

“RDB 是二进制全量快照，通过 save 配置或 SHUTDOWN、主从全量同步触发，优点是文件小、恢复快，缺点是 fork 之后写入的数据会丢。核心风险在 fork() 的写时复制：父子进程共享物理页，父进程每改动一页就要复制一份，实例大或改大 key 时内存会显著放大，还会因 fork 阻塞主线程导致延迟毛刺，所以生产必须设 vm.overcommit_memory 1。

AOF 记录写命令，fsync 三档：always 每条、几乎不丢但 QPS 掉一个数量级；everysec 默认、丢约 1 秒；no 交给 OS、可能丢 30 秒。AOF 文件靠 auto-aof-rewrite-min-size 默认 64MB 加 auto-aof-rewrite-percentage 默认 100% 触发重写，重写同样 fork。

关键的优化是 4.0 起的混合持久化 aof-use-rdb-preamble：AOF 头部是 RDB 全量、后面才跟增量命令，配合 7.0 的 multi-part AOF 把 base 和 incr 分文件存，恢复时只加载 base 加尾部 incr，AOF 恢复速度就接近 RDB 了。选型上，纯缓存全关，要性能接受丢数据就只开 RDB，要完整性就 everysec，我不建议用 always，因为它打满磁盘 IOPS 会连带拖慢复制，零丢失应该靠架构层解决而不是调 fsync。”
