Redis 数据结构与底层编码

核心结论

一句话

Redis 对外只暴露5 种基本类型，但每个类型在内部会根据元素数量与元素大小自动切换底层编码——小对象用紧凑编码省内存，大对象用哈希/跳表换 O(1) 查找。“一个类型对应一个编码”是初学者最常见的误解。

同一份数据在不同规模下，内存占用可以相差 5-10 倍。理解编码切换规则，才知道 hash-max-listpack-entries 这类参数存在的意义。

一、5 种基本类型 → 底层编码全景

基本类型小规模编码大规模编码切换阈值参数
Stringint / embstrraw长度 44 字节（硬编码）
Hashlistpackhashtablehash-max-listpack-entries=128
hash-max-listpack-value=64
Listquicklist（节点=listpack）同左，节点内切 hashtablelist-max-listpack-size=128
Setintsethashtableset-max-intset-entries=512
ZSetlistpackskiplist + hashtablezset-max-listpack-entries=128
zset-max-listpack-value=64

怎么查看当前用的哪个编码

OBJECT ENCODING key —— 这是排查”为什么内存比预期高”的第一条命令。

二、String：三种编码的内存账

String 的三种编码差别只在分配次数和头部开销：

编码适用条件内存构成分配次数
int值能表示为 long直接存 8 字节整数，无 sds 头部—
embstr≤ 44 字节sdshdr8(3B) + 字符串 + \01 次
raw> 44 字节sdshdr16(6B) 或 sdshdr32(10B) + 字符串 + \02 次

44 字节怎么来的：sdshdr8 占 3 字节，加上字符串本体和结尾 \0，在 jemalloc 的 size class 中恰好落在 44 字节这一档（超过就跳到 48 或 56 档，浪费变大）。

embstr 的优势：分配次数少 → 碎片更少、创建/释放更快。raw 分两次分配，容易在内存池里留下不连续的小块。

常见误解

“44 字节是配置项” ——不是。它是编译期常量，无法通过配置修改。想调只能从”控制 value 大小”入手。

三、listpack：7.0 的关键升级

3.1 为什么要有 listpack（替代 ziplist）

Hash/ZSet 小规模时用紧凑的连续内存布局，历史上用的是 ziplist。它的问题：

  • ziplist 每个节点都存一个 prevlen（1 或 5 字节）记录”前一个节点有多长”，用于反向遍历
  • 节点之间没有独立的分配边界，任何扩容都要把整个 ziplist 重新分配并内存拷贝

listpack（Redis 7.0 引入，取代 ziplist）的改进：

维度ziplistlistpack
尾部预留空间无有 num-elements，可预留扩展空间
单个节点长度记录每节点 prevlen只记录总长度（backlen），遍历正序无需 prevlen
支持元素类型仅字符串/整数扩展性好，后续可放非字符串
内存布局连续，含 prevlen 开销更紧凑，节省内存

版本差异

listpack 是 7.0 引入的。若你在 6.x 上运维，配置名仍是 hash-max-ziplist-entries 等；7.0+ 改名为 hash-max-listpack-entries。迁移时注意别照抄旧配置名。

3.2 切换阈值（两个条件都要满足）

以 Hash 为例，只有同时满足下面两条才继续用 listpack，任一不满足立刻转 hashtable：

转换是单向的

从listpack 升到 hashtable 之后，不会自动降级——即使你删到只剩 3 个字段，也仍然用 hashtable。这是 Redis 主动用内存换性能的取舍：编码切换涉及数据搬迁，而 Redis 不确定这次切换是不是临时的。

实践含义：如果你的 Hash 字段数会在 128 附近抖动（比如平时 100、高峰 200），它会永久停在 hashtable 上。想控制内存只能自己限制字段数，别依赖自动降级。

四、intset：最容易被忽略的编码

Set 有一种专用紧凑编码 intset：当所有成员都是整数且数量 ≤ set-max-intset-entries（默认 512）时使用。

它的结构是一个排序好的整数数组，用 intsetLen 记录个数，查找用二分查找（O(log N)），插入是数组内移位（O(N)）。

关键点：

  • 升级只发生在加入非整数时；单纯加入整数只会继续追加（超过 512 才转）
  • 转成 hashtable 后不会退回 intset
  • SISMEMBER 在 intset 上是 O(log N)，在 hashtable 上是 O(1)——512 个以内差异可忽略，超过后差距才明显
  • 常见踩坑：用 SADD 存了一堆纯数字 ID（如关注列表），白白占用 hashtable 的空间，删掉也不会换回来

五、List：quicklist 是唯一形态

List 没有”小规模/大规模”两种形态，它始终是 quicklist——一个由 listpack 组成的双向链表。

参数作用默认
list-max-listpack-size每个节点最多存多少个元素128
list-compress-depth连续多少个节点后开始 LZF 压缩0（默认永不压缩）

版本演进

  • 7.0 之前：quicklist 的节点是 ziplist
  • 7.0 及之后：节点改为 listpack

压缩默认关闭，是因为 LZF 压缩/解压要消耗 CPU，而列表通常访问频繁、且元素本身不大——多数场景压缩不划算。内存吃紧时可调 list-compress-depth（如 1），但要实测延迟变化。

六、ZSet：唯一”双结构”的类型

ZSet 大规模时同时维护两个结构，这是它和其他类型最大的不同：

为什么两个都要：

操作靠谁复杂度
ZSCORE key memberhashtableO(1)
ZRANGEBYSCORE key 90 100skiplistO(log N)
ZADD两边都要写O(log N)

只用 skiplist → 按 member 查 score 要 O(log N)；只用 hashtable → 范围查询要遍历全部元素排序。两者结合才能同时满足点查与范围查。这也意味着内存成本翻倍（zset 往往是 Redis 里最占内存的类型之一）。

跳表（skiplist）为什么是红黑树的替代：实现简单、无需旋转、插入删除只改局部指针、并发下更友好；单线程场景下红黑树的平衡优势用不上。

参数默认6.x 旧名（7.0 前）

生产排查顺序

  1. OBJECT ENCODING key 看实际编码
  2. MEMORY USAGE key [SAMPLES n] 看真实字节数
  3. 若是 hashtable 且元素远少于阈值 → 说明历史上曾超阈值，已不可逆，只能重建 key 才能回到紧凑编码
  4. redis-cli --bigkeys 全局扫一遍大 key

八、面试速答模板

“Redis 对外是 5 种基本类型，但底层编码是动态的。String 按值类型和长度分 int/embstr/raw，embstr 的 44 字节是 jemalloc 分配档位决定的硬编码常量；Hash 和 ZSet 小规模用 listpack，7.0 开始取代 ziplist——主要是省掉每节点的 prevlen 并支持尾部预留；大规模 Hash/Set 转 hashtable，ZSet 转 skiplist 加 hashtable 双结构，因为要同时支持按 member 点查和按 score 范围查，代价是内存翻倍。List 始终是 quicklist，节点是 listpack。intset 是 Set 的专用编码，要求成员全是整数且不超过 512。所有切换都是单向不可逆的，因为编码迁移要搬数据，而 Redis 无法预判这次超阈值是不是暂时的——所以生产上看到 hashtable 编码的 key 元素数很少，不用感到意外，那是历史遗留。调优时优先用 OBJECT ENCODING 和 --bigkeys 定位，而不是盲目调阈值。”
