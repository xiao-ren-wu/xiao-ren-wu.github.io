内存管理与过期淘汰策略

核心结论

一句话

Redis 的过期删除是惰性 + 定期双保险，其中”定期”是随机采样而非全量扫描；内存超 maxmemory 时按 maxmemory-policy 淘汰。两套机制独立且可叠加——过期管”该不该留”，淘汰管”必须删谁”。

一、两套机制的分工

机制触发时机谁决定会不会误删
过期删除TTL 到期key 自己声明的生命周期不会（业务主动设的）
内存淘汰used_memory > maxmemorymaxmemory-policy 策略会（没设过期的 key 也可能被删）

关键认知

设了 TTL 不代表 key 一定在 TTL 到期时被回收，只代表”在它被访问到或被定期扫描扫到时会被删”。而没设 TTL 的 key，在内存超限时可能被淘汰策略直接干掉——如果用的是 allkeys-* 策略。这两类丢失对业务的意义完全不同：过期是”我不要了”，淘汰是”我被迫放弃”。

二、过期删除：惰性 + 定期

2.1 惰性删除（Lazy Expiration）

  • 每次访问 key 都要检查一次 TTL（读取额外开销，但极小）
  • 优点：实现简单、删除精准、不占用额外 CPU 做后台任务
  • 缺点：永远不被访问的过期 key 内存不会释放——如果业务写入大量一次性 key 后再也不读，内存会持续上涨

2.2 定期删除（Active Expire Cycle）

这是”近似”不是”精确”

Redis不会为了清理过期 key 而全量扫描。随机采样意味着：

  • 采样比例低时，一部分过期 key 会滞留内存一段时间
  • 但 CPU 消耗可控——全量扫描百万级 key 会造成明显卡顿

所以”内存里有过期 key 未被回收”是正常现象，不是 bug。只有当过期 key 占比极高时，采样循环才会持续运行（因为每轮都超过 10% 阈值）。

2.3 从库上的过期删除（易被忽略）

  • 从库不会主动物理删除过期 key，只等主库的 DEL
  • 从库在本地检查到过期时只做逻辑删除（标记不可见），不回收内存——这样从库即使误判也不会真丢数据
  • 结果：从库内存占用可能显著高于主库。给从库配 maxmemory 时要比主库宽松

三、maxmemory 与淘汰策略

3.1 基本配置

参数说明
maxmemory 00 表示不限制内存（默认），此时所有淘汰策略都不生效
maxmemory-policy淘汰策略，默认 noeviction
maxmemory-samplesLRU/LFU 采样数量，默认 5

内存限制 ≠ 物理内存

maxmemory 只在数据总量上设卡口。即使 maxmemory 小于物理内存，Redis 的实际 RSS 仍可能超：

  • 内存碎片（见第五节）
  • 客户端缓冲、输出缓冲、复制缓冲

容器化部署时 maxmemory 应设为物理内存的 60-70%，给碎片和缓冲留余量。

3.2 八种淘汰策略

策略候选范围淘汰依据适用场景
noeviction—不淘汰，写命令返回错误数据不能丢（如 Redis 当队列用）
allkeys-lru所有 key最近最少使用通用缓存（最常用）
allkeys-lfu所有 key最不经常使用缓存有明显访问频次差异
allkeys-random所有 key随机简单无脑，基本不用
volatile-lru仅设了 TTL 的最近最少使用混合内存：DB 数据为主
volatile-lfu仅设了 TTL 的最不经常使用同上
volatile-random仅设了 TTL 的随机基本不用
volatile-ttl仅设了 TTL 的剩余 TTL 最短集中清理即将过期的

禁忌

volatile-* 的致命陷阱 volatile-* 只从设了 TTL 的 key 中选。如果实例上没有任何 key 设置了 TTL，那么所有 volatile-* 策略都退化为 noeviction——写命令会直接返回 OOM command not allowed。

更糟的场景：候选 key 还没用完就全过期了，此时也会退化为 noeviction，即使内存还有余量。

结论：除非你明确知道”所有可能被淘汰的 key 都设了 TTL”，否则一律用 allkeys-*。

补充

maxmemory-samples 的权衡 样本越多越精确，但每次淘汰的计算越贵。默认 5 是”够用且便宜”的折中。 典型 LRU 近似算法（sample 5 + 排最久）的失真度在实践中可以接受——它保证的是”大致合理”而非”精确最优”。

4.2 LFU 的计数器与衰减

LFU（Least Frequently Used）不只看最近用不用，还看用得多不多，比 LRU 更适合”少数 key 被反复访问”的缓存场景。

参数默认说明
lfu-log-factor10计数器递增速度。越大则计数涨得越慢
lfu-decay-time1（分钟）计数器衰减周期。设 0 则不衰减（慎用）

衰减机制解决的问题

早期高频访问的 key，计数器会涨到 255 并饱和。若没有衰减，这类”过气热点”会永远霸占高计数位，新出现的真实热点反而被低估。

每分钟减 1 的衰减让计数逐渐回归真实热度——这让 LFU 在负载变化时能自我调整。

反面教材：lfu-decay-time 0 关闭衰减 → 计数器永不下降 → 永远不要这么做，除非你的 key 集合完全静态。

什么时候 LFU 明显优于 LRU

存在持续性热点 key 时（如商品详情页被反复访问）LFU 更稳，因为热点计数器高不容易被误淘汰。 而 LRU 更容易污染——偶尔来一次的扫描式查询会把一批 key 推成”最近用过”，挤掉真正有用的数据。

五、内存碎片与整理

5.1 碎片是什么

Redis 的内存分配器（默认 jemalloc）按 size class 分配内存——申请 100 字节可能占用 112 字节那档。key 被删掉后那档空间留在内存池里等待复用，就形成了碎片。

5.2 关键指标

指标含义关注点
used_memoryRedis 逻辑上占用的内存数据本身
used_memory_rss进程实际 RSS（含碎片、缓冲）容器 OOM 判定看这个
mem_fragmentation_ratiorss / used_memory> 1.5 需警惕，> 3 基本是问题

5.3 主动碎片整理（activedefrag）

Redis 4.0+ 提供主动碎片整理：

参数说明
activedefrag-yes开启主动整理（需编译支持 jemalloc）
active-defrag-ignore-bytes碎片量低于此值不整理，默认 100MB
active-defrag-threshold-lower整理的最低碎片率，默认 10%
active-defrag-cycle-min / -max单轮整理时长上下限
active-defrag-max-scan-fields单轮最多扫描的字段数

主动整理不是免费的

整理过程会消耗 CPU 并对延迟有影响。activedefrag-threshold-lower 设太低（比如 1%）会让 Redis 不停地整理，得不偿失。合理的做法是：先看 mem_fragmentation_ratio 趋势，确实偏高再开，并把阈值设在 10%-20%。

六、过期事件通知

当 key 过期或被淘汰时，Redis 可主动发布事件：

配置作用
notify-keyspace-events "Ex"E = 过期事件，x = 过期已删除
notify-keyspace-events "EA"附加 A = 别名，g$lshztdxe = 各类事件

不要用它替代 keyspace 通知的可靠性

Redis 官方明确不建议依赖过期通知做关键业务逻辑：通知可能丢失（未持久化、订阅者断连），且默认关闭。可以用它做”尽力而为”的清理提示，但不能作为唯一的一致性保证。 更可靠的等价做法是：轮询扫描已过期的 key（SCAN + 检查 TTL），或直接在业务侧判断 TTL。

七、选型建议

场景推荐配置
纯缓存，允许偶尔丢数据allkeys-lru 或 allkeys-lfu
缓存有稳定热点allkeys-lfu（配好 lfu-decay-time）
内存里 DB 数据占大头，不能丢volatile-lru（必须确保所有可淘汰 key 都设了 TTL）
Redis 当队列/锁用，绝不能淘汰noeviction + 监控内存水位
混合：永不过期的元数据 + 有 TTL 的缓存allkeys-lru（接受元数据也可能被淘汰）

通用原则

  1. maxmemory 一定要设，否则物理 OOM 风险远大于 OOM 报错
  2. 容器里 maxmemory 留 30-40% 余量给碎片和缓冲
  3. maxmemory 不要设成物理内存的上限——一旦触发 swap，Redis 延迟会退化到灾难级别
  4. 从库的 maxmemory 要比主库宽松，且尽量避免从库触发淘汰（会导致与主库数据集不一致，只能全量同步修复）

八、面试速答模板

“过期删除是惰性 + 定期双保险。惰性是每次访问 key 时检查 TTL，过期就删并返回 nil，精准但只能删’被访问到’的。定期是 activeExpireCycle 后台跑，随机采样 20 个 key，如果已过期比例超过 10% 就再来一轮，否则结束。必须强调这是随机采样不是全量扫描——全量扫描百万级 key 会卡顿，所以内存里滞留一些过期 key 是正常现象，不是 bug。hz 配置决定 cron 频率，默认 10 也就是大约 100ms 一轮。

从库有个坑：从库不主动物理删除过期 key，等主库发 DEL；从库自己本地检查到过期只做逻辑删除、不释放内存，所以从库内存可能明显高于主库。

淘汰是另一套机制，maxmemory 触发才生效。八种策略分三组：noeviction 直接报错不删；allkeys-* 从所有 key 里选，volatile-* 只从设了 TTL 的 key 里选。volatile-* 的陷阱是：实例上如果没有 key 设 TTL，它会退化成 noeviction，写命令直接 OOM 报错——所以除非明确知道所有可淘汰 key 都有 TTL，否则一律用 allkeys-*。

LRU 和 LFU 都是近似不是精确。LRU 是采样 maxmemory-samples 默认 5 个挑最久未用的，因为精确 LRU 要维护全序链表、每次访问改指针，代价太大。LFU 用 8 bit 计数器，lfu-log-factor 控制增速，lfu-decay-time 默认每分钟衰减 1——衰减的意义是防止早期热点把计数器打满到 255 后永远霸榜，让计数能回归真实热度。

另外内存限制不等于物理内存限制，used_memory_rss 还要算碎片和缓冲，mem_fragmentation_ratio 超过 1.5 要警惕。容器里 maxmemory 一般只设物理内存的 60-70%，而且绝对不能大到触发 swap。”
