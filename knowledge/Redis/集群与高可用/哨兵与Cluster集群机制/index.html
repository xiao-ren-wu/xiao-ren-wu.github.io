哨兵与 Cluster 集群机制

核心结论

一句话

哨兵解决”主库挂了自动选新主”，但不解决容量瓶颈——数据仍在一台机器上；Cluster 用 16384 个哈希槽把数据横向切片，代价是客户端必须自己处理重定向。两个机制解决的是不同维度的问题，经常一起用。

维度哨兵（Sentinel）Cluster
解决什么高可用（自动故障转移）高可用 + 数据分片（水平扩展）
容量上限单机N 台之和
写入口单主库多个主节点
客户端复杂度低（只连主库）高（要处理 MOVED / ASK）
代理层通常配合代理（Twemproxy / codis）不自带代理

一、哨兵：自动故障转移

1.1 三种下线状态

必须记住

quorum 与 majority 的区别

  • quorum：达到多少个哨兵认定 SDOWN，就升级为 ODOWN
  • majority：超过哨兵总数一半（如 5 个要 3 个）才会授权 Leader 执行故障转移

两者不是同一个数。例如 5 个哨兵、quorum=2：2 个哨兵即可判 ODOWN，但必须 3 个授权才能真正 failover。quorum 写太小会让故障转移更快，但也让误判更容易发生。

1.2 新主的选举顺序

哨兵 Leader 按以下顺序挑选继任主库：

第三个条件为何必要

如果偏移量相同，多个哨兵必须选出一个相同的结果才能达成一致，否则会出现”两个新主”的分裂。用 node ID 做确定性 tie-break 是最简单的共识手段。

1.3 客户端如何找到主库

两种方式：启动时主动轮询哨兵 + 运行期订阅哨兵事件（或定期复查）。多数客户端库两者都做，订阅失败时回落到轮询。

1.4 关键参数

参数默认说明
down-after-milliseconds10000超时多久判为 SDOWN
failover-timeout180000故障转移超时
parallel-syncs1故障转移时同时同步的从库数。调大可加速但消耗主库资源
quorum—SDOWN → ODOWN 的门槛

哨兵数量必须是奇数且 ≥ 3

偶数个哨兵在分区时无法形成严格多数（如 2 个哨兵只能容忍 0 个故障，等于没冗余）。3 个哨兵容忍 1 个故障，5 个容忍 2 个。而且这些哨兵必须分布在不同物理机/可用区——同机房的 3 个哨兵抗不住机房级故障。

哨兵不存数据

哨兵只存配置与监控状态，数据全在主从节点上。哨兵挂了不影响数据，但会失去自动故障转移能力（除非客户端自己发现问题）。

二、Cluster：数据分片

2.1 16384 个哈希槽

为什么是 16384 而不是 65536？ 官方设计里有两个明确理由：

  1. 位图要跟着心跳包互相广播。每个节点都持有一张”我负责哪些槽”的位图，16384 位 = 2KB，65536 位 = 8KB。用位图而非整数列表传输，是为了让每个节点都能用固定大小的包做全量交换。
  2. 节点数 × 槽数的分布精度。在 1000 个节点时，65536 槽平均每槽约 65 个 key，而 16384 槽平均每槽约 16 个 key——16384 在小集群下的分配更均匀，同时又足够大，不会让单个槽成为热点。

槽是”逻辑分片”，不是”物理分片”

一个节点负责一段连续的槽区间。扩容/缩容时迁移的是槽，迁的是槽里的 key。

2.2 客户端重定向：MOVED 与 ASK

Cluster 不做代理，重定向由客户端处理。两种响应含义完全不同：

MOVED 与 ASK 的区别是核心考点

  • MOVED：迁移已完成。客户端要永久更新拓扑缓存，从此直接访问目标节点。
  • ASK：迁移正在进行。这个地址只对当前这一条命令有效，客户端不能改缓存——否则迁移完成后缓存就错了。迁移完之后的请求会自然变成 MOVED。

很多客户端 bug 就是把 ASK 也当 MOVED 缓存了。

2.3 Hash Tag：保证多 key 同槽

Hash Tag 是双刃剑

它让多 key 操作成为可能，但也极易造成数据倾斜与热点。如果所有用户的 key 都写成 user:{all}:xxx，整个 Hash 只能落在一个槽、只能由一个节点承载——等于放弃了 Cluster 的分片能力。Tag 的粒度要细到单个用户/单个业务对象，绝不能粗到整个业务线。

2.4 节点故障判定

PFAIL 是单节点判断（可能是自己网络出问题的误判），FAIL 是多数节点的共识。这一层间接层和哨兵的 SDOWN/ODOWN 思路是一致的。

2.5 关键参数

参数默认说明
cluster-enabledno需显式开启
cluster-node-timeout15000超过多久判为 PFAIL
cluster-require-full-coverageyes槽未完全覆盖时是否拒绝服务
cluster-config-filenodes.conf集群拓扑持久化文件

注意

cluster-require-full-coverage yes 的双刃性 设为 yes（默认）：只要有任何一个槽没被任何节点覆盖，整个集群拒绝服务。好处是避免”数据不知道去哪”的静默错误；坏处是扩缩容中途整集群不可用。

设为 no：只对未覆盖的槽返回 CLUSTERDOWN，其余槽正常服务。可用性更好，但要求业务能处理部分失败。迁移期间必须临时设为 no，否则每迁一个槽就全集群抖动一次。

2.6 脑裂与防止数据丢失

这套参数与哨兵共用（定义在主从复制那层），作用相同：宁可主动不可写，也不要在无法复制时接受写入。

三、选型：哨兵还是 Cluster

场景推荐
纯缓存、单机能装下单机；高可用要求低则不必上哨兵
单机能装下但要自动容灾哨兵（1 主 2 从 3 哨兵）
数据量超单机容量Cluster（客户端需支持重定向）
客户端库不支持 Cluster代理方案（自研 proxy 同样要处理 MOVED/ASK）
要跨机房强一致任何单机房 Redis 方案都不够，需异地多活或专用云服务

“有哨兵就是高可用集群”是误解

哨兵只保证服务不中断（自动换主），不保证容量可扩展。数据 100G 用哨兵，100G 全压一台机器上，机器内存和 IO 都不可能撑住。先判断瓶颈是可用性还是容量，再选方案。

四、常用命令速查

必配监控

  • cluster_state —— 变成 fail 时集群整体不可用
  • cluster_known_nodes / 槽覆盖是否完整 —— 迁移期间尤其要看
  • 各槽的 key 数量分布 —— 识别数据倾斜
  • master_link_status 与复制延迟 —— 判定 FAIL 前置状态

五、面试速答模板

“Redis 高可用分两层。哨兵解决主库故障：单个哨兵收不到 PING 先标 SDOWN，达到 quorum 升级 ODOWN，再由选出的哨兵 Leader 执行故障转移，从从库里按 replica-priority、复制 offset、node ID 依次挑新主。注意 quorum 决定 ODOWN，而 majority 是超过半数哨兵授权 failover，这两者可以不等。对了，哨兵必须是奇数且分布在不同物理机，偶数在分区时无法形成多数。

Cluster 在此之上做水平分片，把 key 用 CRC16 % 16384 分到 16384 个哈希槽。为什么是 16384？因为每个节点要广播自己负责哪些槽，用位图传输最省——16384 位正好 2KB，65536 位就是 8KB；同时在千级节点下 16384 槽的分配更均匀。

Cluster 不做代理，靠客户端处理重定向。MOVED 表示槽已永久迁走，客户端要永久更新拓扑缓存；ASK 表示正在迁，只对当前这条命令有效，绝不能缓存。多 key 操作要同槽，就得用 hash tag {1001} 把花括号里的部分当 key 来算——但这也最容易造成数据倾斜，如果图省事写成 {all} 就等于没分片。

故障判定是两层的 PFAIL 到 FAIL，也是单节点判断升级为多数共识。cluster-require-full-coverage 默认 yes，扩缩容迁移期间会导致整集群抖动，得临时设 no。

最后要分清：哨兵只解决可用性，不解决容量。数据量超单机就得 Cluster，而 Cluster 又要求客户端能处理重定向，改造成本要算进去。”
