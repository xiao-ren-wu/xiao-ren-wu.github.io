集群与高可用索引

本页用途

本主题回答”主库挂了怎么办、数据量超单机怎么办”。两个机制解决的是不同维度的问题：哨兵解决可用性，Cluster 在此之上解决容量。混淆这两者是这一主题最常见的错误。

本篇笔记

笔记内容什么时候读
哨兵与 Cluster 集群机制哨兵 SDOWN/ODOWN 与选举、Cluster 16384 槽、Hash Tag、MOVED/ASK、PFAIL/FAIL、选型对比决定部署拓扑、客户端接入方式、排查集群故障

关键结论

  1. 哨兵只解决可用性，不解决容量。数据 100G 用哨兵，100G 全压一台机器上，内存和 IO 都不可能撑住。先判断瓶颈是可用性还是容量，再选方案
  2. quorum 与 majority 不是同一个数。quorum 决定 SDOWN→ODOWN 的门槛，majority（超半数哨兵）才授权 Leader 执行 failover
  3. 哨兵必须是奇数且 ≥3，且分布在不同物理机。偶数在分区时无法形成多数；同机房的 3 个哨兵抗不住机房级故障
  4. MOVED 与 ASK 语义完全不同。MOVED = 已永久迁走，客户端永久更新拓扑缓存；ASK = 迁移中，只对当前这一条命令有效，绝不能缓存
  5. cluster-require-full-coverage 默认 yes，槽未完全覆盖时全集群拒绝服务。迁槽期间必须临时设为 no，否则每迁一个槽就抖一次

哨兵：三种下线状态

状态判定者含义
SDOWN单个哨兵超过 down-after-milliseconds（默认 10s）收不到 PING 响应
ODOWNquorum 个哨兵集群共识的客观下线
Leader 选举多数授权由 Leader 主导执行故障转移

新主选举顺序：replica-priority → 复制 offset 最大 → node ID 字典序最小。 第三步是确定性 tie-break，保证多个哨兵选出同一个结果，否则会出现”两个新主”的分裂。

Cluster：核心机制

为什么是 16384 而不是 65536：

  1. 位图要随节点心跳包互相广播。16384 位 = 2KB，65536 位 = 8KB。用位图而非整数列表，是为了让每个节点都能用固定大小的包做全量交换
  2. 千级节点下 16384 槽的分配更均匀（平均每槽约 16 个 key，65536 则约 65 个）

故障判定两层：PFAIL（单节点判断）→ FAIL（多数共识），与哨兵的 SDOWN/ODOWN 是同一思路。

Hash Tag 是双刃剑

它让多 key 操作成为可能，但极易造成数据倾斜与热点。如果所有 key 都写成 user:{all}:xxx，整个 Hash 只能落在一个槽、只能由一个节点承载——等于放弃了 Cluster 的分片能力。Tag 粒度必须细到单个用户/单个业务对象。

选型对照

场景推荐
纯缓存、单机能装下单机；高可用要求低则不必上哨兵
单机能装下但要自动容灾哨兵（1 主 2 从 3 哨兵）
数据量超单机容量Cluster（客户端需支持重定向）
客户端库不支持 Cluster代理方案（codis / twemproxy）
要跨机房强一致任何单机房 Redis 方案都不够，需异地多活或专用云服务

排查流程

必配监控

  • cluster_state —— 变成 fail 时集群整体不可用
  • 槽覆盖是否完整 —— 迁移期间尤其要看
  • 各槽的 key 数量分布 —— 识别数据倾斜
  • master_link_status 与复制延迟 —— 判定 FAIL 前置状态
