RocketMQ知识地图

来源

基于 RocketMQ 5.x 官方文档与源码整理。文中凡标「RocketMQ 5.x 源码默认」的数字都可直接引用，标「默认值随版本变化」的只讲语义。 本页是全库唯一入口，不引入正文之外的结论——每条结论都能沿双链回到出处。

本页覆盖 RocketMQ 5.x 的架构、存储、生产、消费、可靠性、高可用运维与面试应答七个主题，共 20 篇笔记（1 张根地图 + 7 张索引页 + 12 篇正文）。基线是「Proxy 承接 gRPC 接入、Controller 承载高可用协调」的 5.x；4.x 的 DLedger 主从、FilterServer、传统 Master-Slave 只作为存量系统对照，保留在正文的 warning callout 中，不作为主线叙述。

版本口径与阅读约定

本库所有结论按三档标注可信度，写作时不允许把 B/C 档的具体数字写成确定值。

档位含义允许的写法
A官方源码行、release notes 或官方文档明文可写具体数值，并标注适用大版本
B官方文档给了语义但未给数值，或数值随版本漂移只写语义，注明「默认值随版本变化，以你所用版本的官方文档为准」
C来自社区实践、源码阅读、推断或尚未核实只写结论方向，不写数值，并说明这是实践口径

旧版做法（4.x 时代）

5.x 主线是 Proxy 承接 gRPC 接入、Controller 模式承载高可用协调。以下三项都是 4.x 做法，本页正文一律新版在前：Broker DLedger 模式已被 5.x release notes 标注 legacy 并弃用，由RocketMQ 5.x Controller 模式 替代；FilterServer 由 5.x Proxy 加 Tag/SQL92 过滤链 替代；无 Controller 的传统主从由 Controller 模式 接管选主与切换。存量系统仍需维护，面试也可能问到，但它不作为 5.x 的主线叙述。

配置默认值必须标注适用版本，例如 flushDiskType 默认 ASYNC_FLUSH、brokerRole 默认 ASYNC_MASTER（均为 RocketMQ 5.x 源码默认，随包 broker.conf 同值）。凡未标注版本的数字，视为误写。另有一条拼写口径：mappedFileSize* 在 5.x 是带 p 的正确拼写，老资料里少一个 p 的写法在 5.x 源码中不存在。

全库主线

主线的因果是单向的：存储层的 CommitLog、ConsumeQueue 与 IndexFile 用一条 CommitLog 顺序写换来了高吞吐，这决定了发送链路的写入判定（发送流程、可靠性配置与重试）和刷盘必须单独配置（刷盘策略与内存映射）；收发两端跑通之后，事务、延时、顺序这三项能力（事务消息、延时与顺序消息）才有挂靠点；消费失败后的回流由 Broker 侧重试与死信接管（重试、死信与消费堆积）；这一切的丢失窗口最后汇总成 消息丢失场景与保障 的三段表，而去重责任落在业务侧由 事务边界与去重约束 收口。运维层不引入新概念，只把前面每一环的失败模式变成可观测指标与处置动作。

推荐学习路线

阶段读什么为什么是这个顺序
第 1 轮 · 地基RocketMQ 架构全景与角色分工先立坐标系。NameServer 无状态、无共识算法、路由最终一致这三条不立住，后面所有「为什么找不到 Broker」类问题都答不上
第 2 轮 · 存储CommitLog、ConsumeQueue 与 IndexFile → 刷盘策略与内存映射架构讲数据模型，存储讲这份数据怎么变成文件。全部 Topic 共用单一 CommitLog 是后面几乎所有默认值的根
第 3 轮 · 两端发送流程、可靠性配置与重试 → 事务消息、延时与顺序消息 → 消费模式、位点管理与推送拉取 → 重试、死信与消费堆积生产与消费是一对约束。发送结果不是二值、消费重试发生在服务端，这两点必须对照读，否则会把三层重试混成一类
第 4 轮 · 可靠性收口消息丢失场景与保障 → 事务边界与去重约束前三轮的机制在这里合成可对外承诺的语义。「会不会丢」与「去重靠谁」是两个问题，混答就答不完整
第 5 轮 · 运维落地主从复制与故障转移 → RocketMQ 监控与排障只会原理不会定位等于不会。把每个机制对应到指标与只读命令
第 6 轮 · 冲刺RocketMQ 面试速查总表不重新通读，按主题回扫，用四段式答题结构查漏，重点练第 10 节的数字陷阱题

第 3 轮刻意画成分叉：生产侧与消费侧不分先后读完，因为 事务消息、延时与顺序消息 里的顺序保证假设，要靠 消费模式、位点管理与推送拉取 里的队列独占分配才能验证；而 重试、死信与消费堆积 的回流路径同时挂在发送结果与消费回调两端，只能放在最后收。

默认值口径

写具体数字前先确认它是不是 A 级事实。可以报数值的项统一带「RocketMQ 5.x 源码默认」前缀：flushDiskType = ASYNC_FLUSH、brokerRole = ASYNC_MASTER、maxMessageSize = 4 MiB、defaultTopicQueueNums = Broker 侧 8 而 Producer 侧 4、retryTimesWhenSendFailed = 2、retryAnotherBrokerWhenNotStoreOK = false、transactionCheckMax = 15、transactionTimeOut = 6000 毫秒、transactionCheckInterval = 30000 毫秒、订阅组 retryMaxTimes = 16 与 retryQueueNums = 1 与每组死信队列 1、maxReconsumeTimes 默认 -1（并发消费展开为 16，顺序消费展开为 Integer.MAX_VALUE）、mappedFileSizeCommitLog = 1 GiB、mappedFileSizeConsumeQueue = 30 万条 entry（每条 20 字节）、mappedFileSizeConsumeQueueExt = 48 MiB、flushIntervalCommitLog = 500（⚠️ 源码未标单位）。

只讲语义、不报数字的项：消费线程池上下界（consumeThreadMin 与 consumeThreadMax）、sendMessageThreadPoolNums、syncFlushTimeout、slaveReadEnabled、maxTransferBytesOnMessageInMemory、异步发送路径的重试上限、mqadmin 子命令参数默认值，以及 5.x 定时器与事务回查的实现精度。这些一律保留口径句「默认值随版本变化，以你所用版本的官方文档为准」。

另有两个限定最容易答错：fileReservedTime 必须并列报类默认 72 小时与随包 broker.conf 覆盖的 48 小时，两者都是官方事实；请求头 maxReconsumeTimes 覆盖订阅组 retryMaxTimes 这条规则以 remoting 协议版本 ≥ 3.4.9（协议版本，非发布版本号）为门槛。逐项对照见 RocketMQ 面试速查总表 第三节。

与 Kafka 对照速查

两者都常被归为「消息中间件」，但在元数据协调、存储单元、消费模型三件事上结论相反。被追问「这两个有什么区别」时，下面这张表是骨架。

维度Kafka 4.xRocketMQ 5.x
元数据协调KRaft（Controller Quorum，RAFT 共识）NameServer（无状态，双 master 互备）
存储单元每个分区一个独立日志段全部 Topic 共用单一 CommitLog
消费模型消费者组 + 分区独占集群 / 广播消费模式 + 队列
事务事务生产者（read_committed 读）事务消息（half 消息 + 回查）
延时消息不原生支持原生支持（5.x 定时器）
消息过滤不支持（需应用侧或 Kafka Streams）Tag + SQL92，Broker 端过滤
顺序保证分区内有序队列内有序
消息堆积靠消费者扩容靠消费者扩容

这张表是骨架，不是结论。最容易讲错的是元数据协调那一行：Kafka 用 RAFT 达成元数据一致，RocketMQ 的 NameServer 无状态、无共识算法，路由是最终一致。这正是两者在「Controller 挂了会怎样」这个问题上答案完全不同的原因，架构对照读 Kafka 架构全景与角色分工 与 RocketMQ 架构全景与角色分工。

消息堆积那行两边相同，可用的旋钮却不同：Kafka 侧并行度上限由分区数封顶，RocketMQ 侧由队列数与消费线程数共同封顶，且顺序消息的并行度被有序队列数压住。四条跨系统追问的答题骨架见 RocketMQ 面试速查总表 第十一节，对照库总入口是 Kafka知识地图。
