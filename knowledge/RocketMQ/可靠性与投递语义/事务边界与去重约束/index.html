事务边界与去重约束

来源

基于 RocketMQ 5.x 官方文档（特性行为、客户端 API、Broker 配置）与客户端SendResult、Message 的公开接口整理，half 消息与回查机制承接 事务消息、延时与顺序消息，投递语义结论对照 投递语义与消息去重。5.x 主线架构为 Proxy 加 gRPC 接入，Broker 侧高可用协调由 Controller 模式承载；Broker DLedger 模式在 5.x 已被官方标注为 legacy 并弃用。 数值口径：half 消息回查的三个配置项（transactionTimeOut、transactionCheckInterval、transactionCheckMax）已由 RocketMQ 5.x 源码逐条核实，可直接写具体值并标注「RocketMQ 5.x 源码默认」。仍要保留的限制有两处：5.x 回查定时器的实现精度未核实，因此本篇只给配置默认值，不对实际触发时刻作毫秒级结论；消息 ID 的具体构造格式未核实，见第三节。

本篇解决一个具体问题：RocketMQ 给出去重与一致性承诺的边界在哪里。 「RocketMQ 有事务消息，所以支持分布式事务」「RocketMQ 有消息 ID，所以能去重」这两句话都只对了一半，而漏掉的那一半正是面试官追问的地方。本篇把两句话拆开，标明能兑现的部分与不能兑现的部分，并给出可落地的替代方案。

先给结论，压在后面逐节展开：

  1. 事务消息对齐的是**「消息」与「本地事务」**，不是「消费」与「本地事务」。
  2. 消息 ID 是定位符，不是幂等键。它在受控范围内可靠，跨范围会失稳。
  3. RocketMQ 没有端到端 exactly-once，消费端幂等是必需项而不是优化项。

一、事务消息的一致性边界

事务消息常被描述成「解决了分布式事务的一致性」。这句话的方向是对的，但省略了被对齐的是哪一对对象。RocketMQ 事务消息处理的是这样一个场景：

本地事务（写数据库）与发消息是两个独立动作。发消息成功但本地事务回滚，下游收到了一个从未发生过的业务事件；或者本地事务提交了但发消息失败，下游永远不知道这件事发生过。

事务消息的机制是把「发消息」拆成两段：先发一条对消费者不可见的 half 消息，执行本地事务，再由 Broker 回查本地事务的终态来决定这条消息是提交可见还是回滚丢弃。机制细节见 事务消息、延时与顺序消息。

它对齐的是「消息的终态」与「本地事务的终态」。 表述这一点时必须带上成立前提：本地事务的最终状态是可以被回答的，也就是回查时能查到一个确定结果。

边界之内能兑现的：

能保证成立条件
本地事务回滚时，消息不会投递到消费端回查能答出回滚
本地事务提交时，消息最终会投递到消费端回查能答出提交，且 Broker 侧该消息未被清理
消息终态与本地事务终态一致，不出现「消息可见但库没改」上面两条同时成立

边界之外管不了的，逐条都要说清：

管不了为什么替代方案
消费端不重复事务消息解决的是发送侧对齐，消费位点与业务处理跨系统，没有共同事务消费端幂等，见 消息丢失场景与保障 第五节
消费与本地事务原子消费位点写 Broker，业务处理写业务库，两者没有共同事务先处理后提交位点加幂等
多条消息的批量原子事务消息的对齐单位是单条消息上层用业务状态位控制可见性
本地事务与第三方副作用原子回查只能查自己的存储，查不到调出去的 HTTP 调用调用侧做幂等，加对账
回查一直答不出时的语义达到上限后消息既不提交也不回滚监控未决消息，人工或补偿任务收口
消费时延的确定性提交可见要等回查触发不能把事务消息用在有时延上限的场景

这张图要能自己画出来。 高频错误是把 G 画成有明确终态的箭头，回查耗尽之后消息去了哪里说不清。准确说法是：达到回查次数上限之后消息既不提交也不回滚，处于未决状态，需要人工或补偿任务收口。 RocketMQ 5.x 源码里这个上限是 transactionCheckMax，默认为 15。未决消息必须有监控，否则它就是一条静默的死信。

事务消息的发送失败有固定收口

事务消息路径上，客户端拿到三种失败态（FLUSH_DISK_TIMEOUT、FLUSH_SLAVE_TIMEOUT、SLAVE_NOT_AVAILABLE）时，RocketMQ 5.x 源码统一映射为 LocalTransactionState.ROLLBACK_MESSAGE。发消息这一侧的失败会被直接转成回滚，本地事务若已提交，只能靠后续回查去对齐。这也是事务消息不能靠「发送失败就重发」解决的原因：重发只是重走一遍 half 消息流程，第一次那次的终态仍要靠回查收口。

还有一条与 half 消息直接相关的源码事实：事务 half 消息会被强制把逐条消息属性 waitStoreMsgOK 置为 false，即 half 消息不等待落盘结果。该属性缺省值是 true，那是普通消息的常态。该属性的定位与「异步刷盘下成功响应 ≠ 已落盘」的关系见 消息丢失场景与保障 第二节。

面试追问：RocketMQ 的事务消息解决了什么问题？

答题骨架：先说对齐的对象是「消息终态」与「本地事务终态」，不是消费侧。机制是 half 消息加本地事务加回查三段。成立前提是回查能答出确定结果。然后主动划边界：消费端不重复、管不了跨系统副作用、管不了批量原子、回查耗尽会留下未决消息。最后给替代方案，说明这些缺口分别由幂等消费、业务状态位、调用侧幂等和对账收口。答到这一层，基本就把这题的分数拿满了。

二、half 消息回查的代价

回查机制本身就是一次「把决策权交回给业务方」的设计，所以它的代价必须能被说清。机制见 事务消息、延时与顺序消息 第五节，本节只列代价与它们对可靠性的影响。

控制回查节奏的三个配置项，RocketMQ 5.x 源码默认值如下：

配置项语义RocketMQ 5.x 源码默认
transactionTimeOuthalf 消息发出后多久之内不来回查，留给业务线程完成本地事务6000 毫秒
transactionCheckInterval两次回查之间的间隔30000 毫秒
transactionCheckMax一条 half 消息最多被回查多少次，耗尽仍未决即放弃15

三点必须一起讲：

  1. 这三个值都是「配置默认」，不是「时延保证」。 5.x 回查定时器的实现精度未核实，所以不能推出「业务提交后消息一定在 6000 毫秒内可见」这类结论。可靠的说法只有一条：默认口径下，一条迟迟答不出终态的 half 消息在 15 轮回查之后仍然未决。
  2. transactionTimeOut 是给业务线程的窗口，不是超时上限。 它划的是「这 6 秒内我不来问你」，本地事务跑得更久不会让消息立刻被判失败，只会让回查来得更晚。
  3. 找不到 TransactionCheckConfig 这个类，不等于找不到这三个字段。 该类在 5.x 已不存在，相关字段已并入 BrokerConfig。按老资料去搜独立配置类会得到「查无此类」的结论，从而误判这三个配置项也不存在。
代价表现对可靠性的影响
本地事务状态机要额外维护每个参与事务消息的本地事务都要能按消息维度查出终态状态机复杂度上升，漏实现就直接丢消息
half 消息对消费者不可见的时间不可忽略业务已提交而消息还没可见有时延上限的场景不适用
回查是带外调用，不受业务事务保护回查期间应用重启、网络不通都会让回查失败回查失败即未决，必须有监控
回查次数耗尽留下未决消息消息既不提交也不回滚一条静默的死信，需要收口机制
排查链路变长「消息为什么还没到」要同时看业务事务状态与回查记录可观测性要求高于普通发送
业务代码与消息发送耦合本地事务里多出「写终态查询」这一职责后续迭代容易把它删掉，成为隐患

回查耗尽后的处置是最容易被漏答的一条。 很多设计只写「回查若干次后丢弃」，但丢弃意味着业务已提交而下游永远不知道。默认口径是 transactionCheckMax 为 15 轮、每轮间隔 transactionCheckInterval 为 30000 毫秒，一旦本地事务状态机在整段回查窗口里都答不出结果，消息就停在未决状态。如果业务真的不能承受这件事，正确的做法是把回查设计成不会耗尽，例如把本地事务的终态持久化到一张不会被清理的表里，让回查总能答出结果。这比调大回查次数上限可靠得多，因为它不依赖任何具体配置值。

三条实践建议：

  1. 终态查询必须幂等且只读。 回查可能被并发发起，也可能被重复发起，查到结果之后不能有任何副作用。
  2. 未决消息要有独立指标。 「half 消息提交数减回滚数」长期不为零就要告警，指标口径见 RocketMQ 监控与排障。
  3. 本地事务表要与业务表同库。 放跨库就等于把「查终态」变成一次跨系统调用，故障率直接翻倍。

三、消息 ID 唯一性的实际范围

SendResult 里带回消息 ID 与队列内偏移，这是排查问题时最常用的两个定位符。但它们能回答的问题比大多数人以为的窄。

需要实操验证

消息 ID 的具体构造方式与 Broker 侧存储结构、客户端标识的取值来源相关，不同版本之间存在差异。本篇不写具体拼接格式，只按「客户端标识加单调递增的队列内偏移」这两个语义成分来讨论其唯一性范围。确切的格式请以你所用版本的源码或实操验证为准。

先说它能回答的问题：这条消息在 Broker 上是否存在、位于哪个队列的哪个位置、被投递了几次。这三件事它是可靠的。

它不能回答的问题：这条业务动作之前有没有做过。这需要一条跨越消息生命周期的判据，而消息 ID 不具备这个性质。

唯一性的有效范围，按场景判：

场景消息 ID 是否稳定说明
同一客户端标识、同一进程内，同一条消息稳定这是它的设计区间
同一客户端标识、同一进程内，重试产生的新消息不稳定重试写出的是另一条消息，ID 不同
客户端标识被复用不稳定新进程可能算出与旧消息相同的标识与偏移组合
进程重启后继续发送不稳定偏移的起点与旧进程不再连续
消息被重放或补数不稳定重放走的是新的写入，不是原消息的再次投递
队列扩缩容或路由变化不稳定同一条业务消息可能落到不同队列的不同偏移

结论：消息 ID 是定位符，不是幂等键。 它在「一个客户端标识的生命周期内、这一份未被重放的队列状态上」是可靠的定位符；一旦跨出这个范围，它既不保证同一条业务消息拿到同一个 ID，也不保证不同的业务消息不会撞上同一个 ID。

这两个方向的失效后果完全不同，必须分开讲：

  • 同一条业务消息拿到不同 ID：按 ID 去重会失效，退化成「重复被执行」。后果是重复，靠幂等键可以兜。
  • 不同业务消息撞上同一个 ID：按 ID 去重会误判成「重复」而丢弃。后果是丢失，而且没有任何告警。 这比重复严重得多。

因此如果确实要用消息 ID 做辅助判重，必须给它加限定范围，例如同时带上客户端标识与发送时刻，并且只在明确的短时间窗内有效。更稳的做法是根本不用它做判重，理由在下一节。

四、clientId 与 offset 组合的保证

消息标识的两个语义成分分别提供了一部分保证，保证只在成分有效的范围内成立，把它单独拎出来说才不会被追问到底。

偏移量提供的保证。 在同一个客户端标识对应的写入序列里，偏移单调递增。含义是：只要能确定「这还是同一个写入序列」，就可以用偏移判断先后顺序，重复的偏移不会出现两次。

它在哪里断掉。 偏移的「同一个序列」这个前提由客户端标识维持。标识一旦变化或复用，偏移的连续性就不再有意义。具体三种断法：

  1. 标识写死。 多个实例配了同一个标识，于是它们写进同一个序列。此时偏移仍然单调，但两个实例的偏移被混在一起，按偏移做的任何范围推断都会出错。
  2. 标识来自可复用的资源。 容器重建、IP 被回收、客户端信息里带了会变的字段，都可能让新进程算出与旧进程相同的标识。
  3. 序列起点重置。 进程重启或队列重建后，偏移从当前状态重新开始，可能落到曾经用过的值上。

断掉之后的后果，要说准方向。 新写入的消息可能落到一个曾经被用过的偏移上，于是「按标识加偏移判重」把一条全新的真实消息判成了「之前处理过的那条」，直接丢弃。这是所有去重方案里唯一会主动制造丢失的一种。

实践结论有一条：判重键要用业务唯一键，不要用消息标识的成分。 订单号、请求 ID、支付流水号这类由业务生成的标识，跨进程、跨部署、跨重放都稳定；消息标识的两个成分都不是。

面试追问：消息 ID 能用来做幂等吗？

答题骨架：先分清它是定位符还是幂等键。定位问题它完全可靠，判重问题不行。然后按方向讲两种失效：同一条业务消息拿到不同 ID，会导致判重失效、退化成重复；不同业务消息撞上同一个 ID，会导致真实消息被当成重复丢弃，这是唯一会主动制造丢失的方向，而且没有告警。最后给结论：判重键用业务唯一键，消息 ID 只留在排查链路里。

五、RocketMQ 去重能力的真实边界

把「RocketMQ 有没有去重」这个问题拆成一张能力清单，答案会比一句话清楚得多。清单里有「不提供」比清单本身更有价值。

能力RocketMQ 是否提供说明
生产端重试去重不提供生产侧重试一次就是多一条消息，没有默认判重
端到端 exactly-once不提供位点提交与业务处理跨系统，没有共同事务
消费位点与业务处理同事务不提供位点写 Broker，处理写业务库
消息 ID 辅助判重部分提供在受控范围内可定位，跨范围不稳定，见第三、四节
本地事务与消息发送对齐提供事务消息，范围有限，见第一节
消费失败重试与死信收口提供保证最终有出口，不保证不重复
顺序消息提供队列级串行，前提是发送与消费两端都按序，见 事务消息、延时与顺序消息
延时消息提供定时器机制，精度口径见 事务消息、延时与顺序消息

与 Kafka 逐项对照，两套库的能力恰好互补，各自拥有对方没有的那一半：

能力Kafka 4.xRocketMQ 5.x
幂等生产者有无等价默认机制
事务（跨分区跨主题原子可见）有无等价概念
只读已提交消息（read_committed）有无等价概念
本地事务与消息发送对齐无有（事务消息）
队列级顺序保证的客户端接口无，按 key 分区实现有（MessageQueueSelector）
服务端延时投递无，靠延迟队列有（延时消息）

这张表值得记住的地方不是「谁强谁弱」，而是「两套库解决的问题不在同一层」。 Kafka 事务管的是 Kafka 内部的原子可见与位点提交，管不到业务库；RocketMQ 事务消息管的是业务本地事务与发消息的一致性，管不到 Kafka 那种跨分区原子可见。详见 幂等、acks 与事务。

六、为什么仍然需要业务去重

前面五节把边界划完了，这一节回答「那到底靠什么」。三个理由，按说服力排序。

理由一，重复的最大来源在消费侧，任何消息系统都消不掉。 消费端为了不丢失必须选「先处理后提交位点」，而位点写 Broker、业务处理写业务库，两个系统没有共同事务。这个「没有共同事务」是结构性的，不是配置问题。 换任何消息中间件都一样。处置见 消息丢失场景与保障 第三节。

理由二，Kafka 的四件套在跨到 MySQL 时同样失效。 见第四节表格的说明：事务协调器协调不到数据库提交。能覆盖 exactly-once 的边界永远止步于消息系统内部，这一点与用哪套库无关。

理由三，部署形态的变化会打破一切内置去重假设。 容器重建、客户端标识复用、扩容缩容、故障恢复后的重放，这些动作都会让「消息系统认为的同一件事」和「业务认为的同一件事」错开。任何只依赖消息系统内部标识的判重，都会在这些时刻失效。

端到端 effectively-once 的分层结论：

边界内置机制能否保证 exactly-once需要什么
Broker 到 Broker部分。RocketMQ 侧仍需业务幂等；Kafka 侧四件套可覆盖 Kafka 到 Kafka幂等键仍建议保留，作为部署变更时的兜底
Broker 到业务数据库不能业务唯一键 + 唯一索引，或 inbox 去重表
Broker 到第三方接口不能调用侧幂等 + 定期对账
故障恢复后的重放不能幂等键必须与重放路径共用同一套
运维补数与数据修复不能补数入口也要走去重，不能绕开

落地三原则，与 消息丢失场景与保障 第五节互为表里，这里只列判据：

  1. 幂等键由业务生成，不由消息系统提供。 订单号、请求 ID、支付流水号。
  2. 幂等记录与业务写入同事务。 否则幂等表自己会变成新的不一致来源。
  3. 幂等键在所有入口复用同一套。 正常消费、失败重试、死信重投、运维补数，四个入口的键必须一致。

七、面试高频追问

1. RocketMQ 支持分布式事务吗？

答题骨架：支持，但要说清对齐的是哪一对。事务消息对齐「消息终态」与「本地事务终态」，机制是 half 消息加本地事务加回查，成立前提是回查能答出确定结果。它不管消费端重复、不管跨系统副作用、不管批量原子。

2. half 消息对消费者可见吗？

答题骨架：不可见。half 消息先落盘但对消费者不可见，本地事务执行完之后由回查决定提交可见还是回滚丢弃。所以「业务已提交但消息还没到下游」是一个正常状态，事务消息不适合有时延上限的场景。

3. 回查一直失败会怎样？

答题骨架：达到回查次数上限之后消息既不提交也不回滚，处于未决状态，需要人工或补偿任务收口。RocketMQ 5.x 源码里 transactionCheckMax 默认为 15、transactionCheckInterval 默认为 30000 毫秒、transactionTimeOut 默认为 6000 毫秒。要补一句这是配置默认而不是时延保证，回查定时器精度未核实。更稳的做法是把本地事务终态持久化在一张不会被清理的表里，让回查总能答出结果，这样不依赖任何具体配置值。

4. 消息 ID 能做幂等键吗？

答题骨架：不能，它是定位符。稳定范围是「同一客户端标识、同一写入序列、未重放」这个区间内。两种失效方向要分开：同一条业务消息拿到不同 ID 导致判重失效（重复，可用幂等键兜），不同业务消息撞上同一个 ID 导致真实消息被丢弃（丢失，无告警，更严重）。

5. RocketMQ 有没有 exactly-once？

答题骨架：没有。消费位点提交写 Broker，业务处理写业务库，没有共同事务，这是结构性的。事务消息解决的是另一个层的问题。能给出的最强保证是 at-least-once 加业务幂等，即 effectively-once。

6. Kafka 的 exactly-once 四件套是什么？

答题骨架：幂等生产者消除生产侧重试的重复，事务生产者提供跨分区跨主题的原子可见并让位点可与生产同事务，read_committed 隔离未提交消息，分区有序保住同一 key 的相对顺序。必须补一句：它只在 Kafka 边界内成立，跨到 MySQL 那一跳仍然需要业务幂等。 见 投递语义与消息去重。

7. 两套库的事务有什么区别？

答题骨架：Kafka 事务是 Kafka 内部的原子可见与位点提交，管不到业务本地事务；RocketMQ 事务消息是业务本地事务与发消息的一致性，管不到跨分区原子可见。两边各有一半对方没有的能力，这是对照里最值得记的部分。详见 幂等、acks 与事务。

8. 幂等怎么落地才不出事？

答题骨架：幂等键用业务唯一键而不是消息 ID 或偏移；幂等记录与业务写入同一事务；唯一约束建在业务键上而不是靠应用层先查后插；保留窗口要有下限理由，即大于最大重放时长；正常消费、失败重试、死信重投、运维补数四个入口共用同一套键。详见 消息丢失场景与保障 第五、六节。

9. 有没有哪些场景不需要业务幂等？

答题骨架：只有当写入目标本身天然幂等时才不需要，例如覆盖写或按绝对值累加。除此之外都要做。顺序消息、延时消息、事务消息都不会消除重复，它们各自解决的是顺序、时点与本地事务对齐。
