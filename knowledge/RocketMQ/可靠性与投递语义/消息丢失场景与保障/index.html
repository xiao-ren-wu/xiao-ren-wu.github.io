消息丢失场景与保障

来源

基于 RocketMQ 5.x 官方文档（架构、特性行为、客户端 API、Broker 配置）与客户端SendResult、Message 的公开接口整理，机制结论承接 发送流程、可靠性配置与重试 与 刷盘策略与内存映射。5.x 主线架构为 Proxy 加 gRPC 接入，Broker 侧高可用协调由 Controller 模式承载；Broker DLedger 模式在 5.x 已被官方标注为 legacy 并弃用。 数值口径：本篇的 flushDiskType 与 brokerRole 默认档位、SendStatus 枚举取值、发送重试次数、waitStoreMsgOK 缺省值与 half 消息强制值，均已由 RocketMQ 5.x 源码逐条核实，可直接写具体值并标注「RocketMQ 5.x 源码默认」。syncFlushTimeout 仍无官方数值，保留「默认值随版本变化，以你所用版本的官方文档为准」措辞不变。

本篇回答一个具体问题：一条消息从业务代码调 send 到消费端处理完成，会在哪些环节消失，以及每个环节对应的可操作保障手段。先立三条判断口径，它们是全篇的地基。

  1. 返回成功不等于落盘。 「写成功」最多覆盖到字节进入 CommitLog 的内存映射区那一刻。
  2. 落盘不等于已有副本。 主节点写好并刷完盘，从节点可能还没有这段数据。
  3. 能读到不等于已处理。 消费端读到位点与业务处理完成是两个独立动作。

不区分这三层，「我的系统不丢消息」就是一句无法验证的承诺。

一、生产阶段的丢失点

生产阶段的丢失可以归为四类，判定标准只有一个：这个「没发出去」有没有被业务代码看见。

编号丢失点现象保障手段代价
P1单向发送，失败不可感知消息从未到达 Broker，业务侧没有任何信号业务消息禁用单向发送，只留给埋点、采集、日志无
P2结果处于「不确定」档却被当成成功刷盘超时与复制超时，消息已写入 Broker 但未满足判定条件同步发送并检查 SendResult，只把明确成功当成功业务要处理不确定分支
P3发送失败但异常未被捕获同步路径返回值被忽略，或异步回调里抛了异常同步路径显式处理返回与异常；异步路径在回调里处理并接入自己的监控异常处理代码变长
P4路由陈旧，打向已下线 Broker连续失败，原地重试无效依赖重试队列与路由刷新，机制见 发送流程、可靠性配置与重试 第五节消息延迟到达

P2 是最容易被答错的一类。刷盘超时与复制超时不是失败，是不确定：消息已经进了 Broker，只是没拿到「已落盘」或「已复制」的确认。重发若实际已写入就是重复，当成功接受则存在丢失窗口。正确处置是先用消息 ID 查 Broker 侧是否可查，查到即视为成功，查不到再按业务对「重复」与「丢失」哪个更不能容忍来决定。

「不确定」只有三个取值，不是一团模糊状态。 SendStatus 枚举在 5.x 源码里完整只有 4 个值：

SendStatus语义RocketMQ 5.x 源码默认是否重试
SEND_OK写入成功，满足本次发送的等待条件不适用
FLUSH_DISK_TIMEOUT消息已写入，但未在等待窗口内拿到落盘确认否
FLUSH_SLAVE_TIMEOUT消息已写入，但未在等待窗口内拿到复制确认否
SLAVE_NOT_AVAILABLE需要复制确认但没有可用从节点否

三个失败态默认都不重试，开关是 retryAnotherBrokerWhenNotStoreOK，RocketMQ 5.x 源码默认为 false。这条默认值直接决定 P2 的处置方式：框架默认既不会替你重发，也不会替你判定成功，处置责任落在业务代码上。

两套重试机制必须分开，混为一谈是高频错误。 触发路径根本不同：

机制触发路径RocketMQ 5.x 源码默认覆盖的失败
retryResponseCodes异常路径，Broker 抛出 MQBrokerException 才进重试响应码白名单 8 个明确的「没写进去」
retryAnotherBrokerWhenNotStoreOK正常返回路径，SendStatus 非 SEND_OK 时换 Broker 重试false三个失败态，默认关

retryResponseCodes 白名单的 8 个响应码：TOPIC_NOT_EXIST、SERVICE_NOT_AVAILABLE、SYSTEM_ERROR、SYSTEM_BUSY、NO_PERMISSION、NO_BUYER_ID、NOT_IN_CURRENT_UNIT、GO_AWAY。它们都属于「消息压根没写进去，重发安全」这一类。

差别决定处置方式： 白名单里的 8 个码可以放心让框架重试；三个失败态属于「重发可能重复」，框架默认也确实不重试。把后者当前者处理，或反过来指望框架默认重发，都是错的。

还有一条容易被当成「丢失原因」的因素要先排除：RocketMQ 生产侧重试默认不去重。 整体发送重试次数 retryTimesWhenSendFailed 在 RocketMQ 5.x 源码默认为 2，而这 2 次重试每次都可能在 Broker 上留下一条独立消息。重试制造的是重复而不是丢失。排查时如果只盯着「少了什么」，会一直在错误的方向上找。机制对照见 幂等、acks 与事务。

5.x 的 Proxy 接入让 P2 与 P4 更容易发生。链路变成「客户端到 Proxy」与「Proxy 到 Broker」两段，客户端只能看到 Proxy 侧的响应，Proxy 之后的写入失败常常只表现为超时。「超时」在 5.x 下更接近「结果未知」而不是「明确失败」，而只有后者可以安全重试。

面试追问：你们的系统能丢消息吗？

答题骨架：不要答「不能」，按三段给出「每一段的丢失点与对应保障」。生产端四类丢失点逐个说清，重点强调「单向发送放弃失败感知」与「超时属于不确定而非失败」这两条。Broker 端按刷盘与复制两档分别说，进程崩溃与主机断电要分开。消费端按位点提交时机说，并明确「选先处理后提交就是把丢失换成了重复」。最后给结论：经过逐段收紧之后，剩下的风险可列举、可估算、可监控，而不是「理论上不会丢」。

二、Broker 阶段的丢失点

Broker 侧的丢失点必须按四层落点拆开，因为不同层需要不同手段来兜：

层落点失败后消息去哪对应保障
第一层写入 CommitLog 的内存映射区数据在页缓存里，进程崩了还在，整机断了没了返回成功之前强制落盘
第二层落盘完成数据在磁盘上，受磁盘损坏威胁副本冗余
第三层复制到从节点主有从没有，主挂了就跟着没了同步复制
第四层异步分发到 ConsumeQueue 与 IndexFile消息体在 CommitLog 里但没有可消费条目复制侧兜底加保留期约束

四个丢失点逐个展开。

B1　已返回成功但字节只在页缓存。 触发条件是主机断电或内核 panic，不是进程崩溃。页缓存属于内核，进程退出不影响它。

这条路的默认状态必须先讲清，因为它是「零配置」的那个坑。flushDiskType 的合法值只有 SYNC_FLUSH 与 ASYNC_FLUSH，RocketMQ 5.x 源码默认为 ASYNC_FLUSH，随包 broker.conf 同样是异步刷盘。也就是说默认部署下，字节写进 CommitLog 的内存映射区之后并没有落盘，Broker 就把成功返回给了客户端。

客户端拿到「成功」这一步还受另一个旋钮控制：逐条消息属性 waitStoreMsgOK，源码标识 MessageConst.PROPERTY_WAIT_STORE_MSG_OK。该属性缺省时返回 true，语义是「本次发送是否等待 Broker 的落盘结果再响应」。

两个旋钮作用域不同，必须分开看：

旋钮作用域回答的问题RocketMQ 5.x 源码默认
flushDiskTypeBroker 级Broker 落盘这一步本身是同步还是异步ASYNC_FLUSH
waitStoreMsgOK逐条消息这次发送要不要等落盘结果才响应属性缺省为 true

两个默认值叠加起来的净效果，就是本篇开头那条口径的真实含义：默认配置下客户端拿到的成功响应，只覆盖到「字节进入 OS 页缓存」，而不是「已落盘」。 这段时间里 Broker 宕机或主机断电，这批消息就丢了，而客户端侧的日志与监控显示一切正常。默认档位就是最坏档位，这是可靠性设计里最反直觉也最容易漏掉的一条。

定位纠正

waitStoreMsgOK 已不是 Broker 配置项，而是逐条消息属性。4.x 时代写在配置文件里、靠 MixAll 时代常量读写的写法已不适用。看到有资料把它列成 broker 侧开关，那个版本已经不适用。

要关掉这个窗口有两个独立动作，两个都要做：把 flushDiskType 改成 SYNC_FLUSH，让 Broker 落盘这一步同步完成；再确认本次发送确实等落盘结果，即 waitStoreMsgOK 为 true（缺省即是，通常不用动）。

同步刷盘路径上还有一个配置 syncFlushTimeout，语义是同步刷盘时允许等待落盘的上限，也就是「最多等多久」。它是「等待多久」的上限，不是「是否写入」的上限，默认值随版本变化，以你所用版本的官方文档为准。 这个上限与丢失窗口直接相关：超过上限之后如何计入本次发送结果，以你所用版本的实现为准，不要凭印象描述。

B2　主已确认，从尚未同步。 触发条件是主节点故障切换。异步复制下主节点确认成功不代表从节点已有数据，主挂之后切到从，这段消息就永久消失了。这条路只有同步复制能兜，刷盘档位帮不上忙，因为刷盘只管「这台机器的盘」。

B3　索引未落盘或条目缺失。 CommitLog 里有消息，ConsumeQueue 里没有对应条目时，消息体存在但消费侧查不到。索引类文件主要靠周期性刷盘任务落盘，存在天然延迟，所以掉电时可能出现「已返回成功的消息对应不到消费条目」。兜底靠复制侧覆盖加保留期约束：消息保留期不得短于系统可能的最大故障恢复时间，否则恢复之后消息已被清理。

B4　磁盘损坏且无副本。 任何刷盘档位都挡不住介质损坏，唯一手段是存储冗余。这一层的判定与配置无关，取决于部署形态。旧版做法在此提醒一句：Broker DLedger 模式在 5.x 已被官方标注为 legacy 并弃用，新版由 Controller 模式接管选主与切换，机制见 主从复制与故障转移。

面试追问：发送成功到底保证了什么？

答题骨架：只保证消息写进了 CommitLog 的内存映射区，也就是数据在页缓存里。异步刷盘下它不保证落盘，也不保证 ConsumeQueue 已更新，更不保证从节点已有。要说清「成功」覆盖的是四层里的哪一层，以及要覆盖到第几层就得配什么。

三、消费阶段的丢失点

消费阶段的核心事实只有一句：位点提交与业务处理是两次落在不同系统上的操作，没有共同的原子性保证。 因此这一段只有两个可选动作，选哪个决定了丢还是重。

编号动作顺序崩溃时刻的后果语义
C1先提交位点，后处理位点已过，消息不再投递，业务动作丢失at-most-once
C2先处理，后提交位点位点未过，重启后重复投递at-least-once
C3处理与位点提交放进同一事务事务回滚则两者都不生效只在数据库侧成立

这套系统只能在这两栏里选，没有第三栏。 位点提交写 Broker，业务处理写数据库，两者没有共同事务，因此端到端的 exactly-once 不可能由消费框架单独提供。默认应选 C2：重复可去重，丢失不可恢复。 详见 事务边界与去重约束。

三类具体的丢失点：

C1　位点提交早于业务处理完成。 若启用了自动提交，位点按周期推进而与业务处理进度没有任何绑定关系，可能把尚未处理完的消息标记为已消费。保障手段是关闭自动提交，改为处理完成后显式提交。消费模式与位点管理的完整机制见 消费模式、位点管理与推送拉取。

C2　消费失败被当成成功。 消费端的返回成功必须由业务代码在真正处理完成之后才给出。典型错误是捕获异常之后仍然返回成功，或者把「已投递到下游」当作「已完成」。这类丢失没有任何框架层兜底，只能靠代码纪律与业务幂等。

C3　消费组重平衡带来的位点错位。 成员被移出组后分区转交他人，新成员从上次已提交位点开始。这一条要精确一点：重平衡本身产生的是重复而不是丢失，因为未提交的那批会被重新投递。它出现在这张表里是因为排查时必须先排除它，否则会一直以为消费端有问题。重复的处置见 事务边界与去重约束，重试与死信机制见 重试、死信与消费堆积。

面试追问：消费端自动提交为什么危险？

答题骨架：因为提交点与业务处理进度没有绑定。自动提交按周期推进，可能把尚未处理完的消息标记为已消费（丢），也可能在处理完成之后尚未提交时崩溃（重）。要严格语义时必须关闭自动提交，改为处理完成后手动提交，机制见 消费模式、位点管理与推送拉取。

四、刷盘、主从与同步复制的组合

三档组合，RocketMQ 5.x 源码默认落在第三档，这一点必须先说，因为默认档不是最安全的那一档：

档位刷盘复制主机掉电风险主从切换风险吞吐适合
高可靠档同步刷盘同步复制极小，只剩刷盘等待窗口内的一小段无，主不确认不算成功最低账务、支付、对丢失零容忍
折中档同步刷盘异步复制极小，同步刷盘已覆盖有，主已确认但从尚未同步的窗口中一般业务、可接受极小概率丢失
高吞吐档异步刷盘异步复制有，已确认未回写的窗口有，与折中档是同一个风险最高埋点日志、监控数据、可容忍丢失的流

关键点

复制档位决定的是「主节点故障切换」这条路上的风险，刷盘档位决定的是「单机整机掉电」这条路上的风险，两条路要分别答。折中档与高吞吐档在主从切换上的风险是同一个，异步复制下主节点确认成功不代表从节点已有数据，这部分风险不能靠更快的响应弥补。

复制这一列对应 Broker 配置 brokerRole：合法值 ASYNC_MASTER、SYNC_MASTER、SLAVE，RocketMQ 5.x 源码默认为 ASYNC_MASTER，随包 broker.conf 同样是异步 Master；同步复制对应 SYNC_MASTER。刷盘那一列对应 flushDiskType，默认 ASYNC_FLUSH。两个默认值都指向吞吐优先，所以默认部署同时具备「单机整机掉电丢」与「主从切换丢」两个窗口，不存在「默认就安全」这种假设。

决策规则按顺序问三句：

  1. 业务能接受「返回成功后整机断电仍不丢」吗？不能，就要同步刷盘。
  2. 业务能接受「主节点突然挂了、切到从之后少掉一部分已确认消息」吗？不能，就要同步复制。
  3. 前两问答应的组合下吞吐预算够吗？不够就回去重新审视前两问的答案，而不是去调中间参数。

4.1 业务侧的三种写入顺序

前两问只能覆盖 Broker 侧。业务侧还有一个更早的一致性问题：「改数据库」与「发消息」两个动作没有共同事务。 三种常见写法，代价完全不同。

写法步骤一致性可用性失败形态
先写库再发消息提交事务，然后发消息不一致，库已改但消息发不出去，下游永远不知道高，发消息失败不回滚业务静默丢失，最难发现
同步双写同一个业务方法里先写库、再发消息，都成功才算成功强一些，任何一步失败都明确报错低，Broker 抖动会让整个业务接口不可用明确失败，可观测
事务消息发 half 消息，再执行本地事务，由回查对齐消息终态与本地事务对齐高，业务线程不因发消息而阻塞引入不可见窗口与回查往返

同步双写相对「先写库再发消息」的实质改进只有一条：把静默丢失变成明确失败。 它没有消除不一致，只是让它可观测。代价必须一起说清楚。

  1. 可用性下降。 数据库事务与网络调用被绑在一个业务方法里，Broker 不可用时业务接口整体不可用。这在很多系统里不可接受，尤其当下游只是「收到通知」而不是业务主干时。
  2. 两个事务仍然没有共同提交点。 同步双写只保证「本方法内按顺序都做完了」，不保证跨方法、跨系统的原子性。上游是订单服务、下游是积分服务时，一次调用失败留下的半成品状态仍要靠补偿。
  3. 超时是最坏的一种失败。 同步双写卡在发消息上时，数据库事务已经提交，业务方法超时返回，调用方以为失败而重试，于是数据库被重复更新。同步双写反而放大了重复，因为它给了调用方「重试一次应该没事」的错觉。

因此同步双写只适合一个很窄的场景：本地事务本身是单资源、状态变更极关键、并且「发不出去就整体失败」在业务上确实可以接受。其余情况更该用事务消息，机制见 事务消息、延时与顺序消息，它的一致性边界与去重约束见 事务边界与去重约束。

对照 Kafka 侧：Kafka 没有「本地事务与消息发送对齐」这个机制，Kafka 事务的边界完全在 Kafka 内部。机制对照见 幂等、acks 与事务。

4.2 Kafka 侧的四件套对照

Kafka 上被称作「端到端 exactly-once」的组合通常被拆成四件。必须说清的是，它同样只在 Kafka 边界内成立。

件作用覆盖的重复来源覆盖的丢失
幂等生产者消除生产端重试产生的重复生产侧重试无
事务生产者跨分区跨主题的原子可见，位点可与生产同事务消费后再生产链路的重复无
read_committed只读已提交的事务隔离未提交消息无
分区有序同一 key 固定落同一分区，保住该 key 的相对顺序顺序类错误无

四件套一件都不解决「消息写进 MySQL」这件事。 事务协调器协调不到数据库的提交，因此从 Kafka 到数据库这一跳仍然是 at-least-once，需要业务幂等键或 inbox 表兜底。完整讨论见 投递语义与消息去重。

面试追问：同步双写和事务消息怎么选？

答题骨架：先说同步双写改进了什么，只改了一条，把静默丢失变成明确失败，代价是可用性下降与重复被放大（超时后调用方重试会重复更新数据库）。再说三个前提：本地事务是单资源、发不出去整体失败在业务上可接受、超时重试不会造成重复。任一条不成立就换事务消息，因为它把一致性边界交给 half 消息与回查，业务线程不因发消息而阻塞。详见第四节。

五、幂等消费与去重表设计

为什么幂等消费是必需项而不是可选项。 两个原因叠加。

  1. RocketMQ 生产侧重试默认不去重，同一条业务消息被重试写入多份是正常结果。整体发送重试次数 retryTimesWhenSendFailed 在 RocketMQ 5.x 源码默认为 2，每次重试都可能多写一条。
  2. 消费端为了不丢失，必须选「先处理后提交位点」，于是重复投递是正常结果。

两个「正常结果」相乘，重复就是这套系统的默认语义。所以消费端幂等不是优化，是前置条件。

三种去重模式：

模式做法覆盖范围代价适合
业务唯一键 + 唯一索引用订单号之类的业务唯一键做唯一索引，重复插入被数据库拒绝全部重复来源一次唯一索引开销写数据库的场景几乎必选
去重表（inbox）独立表存「已处理消息标识」，配合保留期清理全部重复来源，含跨系统一次插入加一次清理需要跨系统判定、消息量大
天然幂等操作目标动作本身可重复执行（覆盖写、按绝对值累加）取决于业务语义零状态覆盖类写入

去重表结构示意：

字段类型作用
业务唯一键变长字符串去重键本身。优先用业务唯一键（订单号、请求 ID），不要用消息字节的哈希值
消息 ID变长字符串辅助排查用，定位同一条消息的多次投递。不作为去重键，见下文
队列内偏移数值类型定位消息在队列中的位置，用于排查位点问题。不作为去重键，见下文
处理状态枚举或短整型区分「处理中」与「已完成」，支持处理与去重记录分两步的写法
创建时间时间类型保留期清理的依据

两个「为什么不作为去重键」必须讲清，它们是去重设计里最容易错的地方。

  1. 不能用消息 ID 做跨投递的唯一判定。 消息 ID 与客户端标识和队列内偏移相关，当客户端标识复用或进程重启导致偏移变化时，同一条业务消息可能对应到不同 ID。ID 在它的有效范围内是好的定位符，在跨范围的重放场景里不是稳定的去重键。范围分析见 事务边界与去重约束。
  2. 不能用队列内偏移做去重键。 消息重放、队列扩缩容、路由变化都会让同一条业务消息落到不同偏移。偏移只对「这一份未被重放的队列状态」有意义。

三个必须遵守的实现要点：

  1. 去重键用业务唯一键。 消息字节的哈希值会随序列化格式、字段顺序、版本升级而变化，一旦变化，去重就静默失效，而且极难发现。
  2. 去重记录与业务写入必须在同一事务。 否则会制造出「去重记录写了、业务没写」这种新的不一致，重复消息被吃掉但业务没生效。这类 bug 在重复率低的正常时期几乎不会暴露。
  3. 去重表的唯一约束要建在业务键上。 只靠应用层先查后插挡不住并发：两个消费实例同时处理同一条消息时，两边都查不到然后都插入，唯一索引才是最终防线。

六、去重表的生命周期取舍

去重表会变成新的故障源，这一条必须在设计时就处理。

保留窗口的下界是最大重放时长。 它至少要覆盖消息本身的保留期、故障到恢复完成的最长时间、以及恢复后可能发生的重放窗口。保留期不得短于最大故障恢复时间，这一条与第二节的 B3 是同一个约束。

三种清理策略：

策略做法优点风险
按时间清理定期删掉创建时间超过窗口的记录实现简单，容量有上界窗口设置错误直接导致漏去重
按业务归档清理业务对象进入终态时连带删掉容量与业务量同步，不留垃圾业务没有明确终态的实体无法覆盖
分表加定期归档按时间分表，整表归档或删除清理是批量的，不与写入竞争需要维护多表路由，查询要带分表键

三条实践建议：

  1. 优先按业务终态清理。 订单已完结，对应的去重记录就没有保留价值了，容量与在途业务量同步，不会在库停机之后还堆着一张永远增长的历史表。
  2. 必须按时间清理时，窗口要有下限理由。 下界是最大重放时长，答不上这个数就说明还没算清故障恢复流程，不要凭「留一个月」这种直觉。
  3. 容量按日增乘保留天数估算，不按消息总量。 去重表的行数是「保留窗口内的消息条数」，不是「系统累计处理过的消息条数」。高峰日流量明显高于均值时，窗口要按高峰估。

七、面试高频追问

1. 你们的系统能丢消息吗？

答题骨架：不给「不能」这种答案，按三段答。第一段生产端，四类丢失点，其中单向发送放弃失败感知、刷盘与复制超时属于「不确定」而不是失败这两条必须说。第二段 Broker 端，按四层落点拆，每层的兜底手段不同，并明确刷盘管单机掉电、复制管主从切换。第三段消费端，位点提交时机决定丢还是重，默认选先处理后提交。结论是剩余风险可列举、可估算、可监控。

2. 发送成功等于落盘吗？

答题骨架：不等。成功最多覆盖到字节进入 CommitLog 的内存映射区。要主动说清默认情况：RocketMQ 5.x 源码 flushDiskType 默认为 ASYNC_FLUSH，brokerRole 默认为 ASYNC_MASTER，所以默认部署下「返回成功但未落盘」就是常态而不是例外。 要覆盖到落盘需要把 flushDiskType 改成 SYNC_FLUSH，要覆盖到从节点已有需要 brokerRole 设成 SYNC_MASTER。四层落点与两层配置的关系要能一口气说出来。

3. 刷盘超时算成功还是失败？能重试吗？

答题骨架：算不确定，不能直接重试。事实层是消息已写入 Broker 但未拿到落盘确认，5.x 源码里对应 FLUSH_DISK_TIMEOUT 与 FLUSH_SLAVE_TIMEOUT 两个 SendStatus 值。判断层是重发若实际已写入就是重复，而且框架默认也不重试（retryAnotherBrokerWhenNotStoreOK 默认为 false）。处置层是先用消息 ID 查 Broker 侧是否可查。还要补一句 syncFlushTimeout 的语义是「同步刷盘时最多等落盘多久」，默认值随版本变化，以你所用版本的官方文档为准。

4. 同步刷盘加异步复制够吗？

答题骨架：不够，但要说清它覆盖了什么、没覆盖什么。它覆盖「单机整机掉电」，没覆盖「主节点故障切换」。异步复制下主已确认而从尚未同步的窗口，切主之后那批消息永久消失，这部分只能靠同步复制关掉。

5. 同步双写和先写库再发消息相比，好在哪？

答题骨架：只改了一条，把静默丢失变成明确失败。代价三条：可用性下降（Broker 抖动让业务接口整体不可用）、两个事务仍无共同提交点、超时最坏（库已提交而调用方重试导致重复更新）。适用面很窄，本地事务单资源加发不出去整体失败可接受加超时重试无副作用，三条同时成立才用。

6. 消费端自动提交为什么危险？

答题骨架：提交点与业务处理进度没有绑定。自动提交按周期推进，可能把未处理完的消息标记为已消费（丢），也可能在处理完成后未提交时崩溃（重）。要严格语义必须关闭自动提交，改为处理完成后显式提交。

7. 为什么说 RocketMQ 没有端到端 exactly-once？

答题骨架：先说清端到端 exactly-once 要求什么。要求消息系统与业务存储之间有共同事务或等价机制，而 RocketMQ 侧的位点提交写 Broker、业务处理写数据库，两次操作没有共同事务。事务消息解决的是「本地事务与消息发送的原子性」，不是「消费与本地事务的原子性」。Kafka 侧的四件套能做到 Kafka 到 Kafka 的 exactly-once，但跨到 MySQL 同样失效。详见 事务边界与去重约束。

8. 幂等消费怎么落地？

答题骨架：去重表加业务唯一键唯一索引。三个要点：去重键用业务唯一键而不是消息字节哈希；去重记录与业务写入同一事务；唯一约束建在业务键上而不是靠应用层先查后插。另外主动排掉两个错误做法：用消息 ID 或队列内偏移做去重键，理由是它们在重放与客户端标识变化时不稳定。保留窗口要有下限理由，即大于最大重放时长。

9. 排查「消息没到下游」的正确顺序是什么？

答题骨架：先分清是「没发出去」还是「发出去了没消费」。按第四节的三段逐层排除，每段只看本段的信号：生产端的返回与异常、Broker 侧的发送状态与消费位点、消费端的堆积与重试记录。不要一上来就调重试次数，那只会制造重复。见 RocketMQ 监控与排障。
