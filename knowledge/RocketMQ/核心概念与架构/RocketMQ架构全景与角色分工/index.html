RocketMQ 架构全景与角色分工

来源

基于 RocketMQ 5.x 官方架构文档与 release notes 整理。文中未标注 ⚠️ 的结论可直接用于面试应答。 本篇只讲结构性事实（角色职责、数据流向、路由与高可用机制），不涉及具体配置默认值。刷盘档位、发送线程池、延时级别时长、事务回查次数、消费线程数等参数类陈述分别归入存储机制、生产者、可靠性各篇。 ⚠️ 标注 ⚠️ 的条目属社区实践或源码推断方向，面试中只讲机制、不报数值。

RocketMQ 由哪些角色组成、一条消息从产生到被消费要经过哪些环节、路由信息存在哪、高可用由谁协调——这是读后续所有篇目的前提。如果分不清 NameServer、Broker、Controller、Proxy 四者的职责边界，后面的存储、复制、延时、事务、排障都会退化成背概念。

一、消息中间件的定位与选型维度

1.1 两种定位

RocketMQ 常被笼统归为「消息队列」，但它同时满足两类诉求，而这两类诉求决定了它几乎所有的设计取舍。

定位核心诉求典型指标RocketMQ 的取舍
消息队列（MQ）解耦、按路由投递、削峰单条投递延迟、投递成功率用「按队列消费 + 消费即位移」换低延迟，代价是消息默认不长期留存
队列化事件处理可回溯、按消费组独立进度、堆积后追赶消费组隔离、积压消化能力消费组各存一份位点，同一份数据可被多个组独立消费；堆积靠扩消费者或扩队列消化

关键认知：RocketMQ 的默认语义是「消费位移」而不是「消费删除」。

消息被某个消费组成功消费后，该组在对应队列上的位点前移，但消息本体仍留在存储里，直到按保留策略或磁盘回收清理。因此：

  • 同一个 Topic 可以被多个消费组各自独立消费，彼此看不到对方进度
  • 消费者短暂宕机不会丢消息——只要位点没被推进，重启后从上次位点继续
  • 消费进度回退（重置位点）有产品化支持，但它是运维动作而非默认行为

面试追问：RocketMQ 和 Kafka 在「消息被消费后」最本质的区别是什么？

答：两者都不消费即删除，都靠位点标记进度，所以都可重放、多个消费组互不干扰。真正的差别在位点的位置与隔离粒度：RocketMQ 的位点以消费组 + 队列为粒度，消费模式还分集群与广播（广播模式下每个消费者维护自己的进度，不共享）；Kafka 的位点以消费组 + 分区为粒度，且位点是集群级元数据。

换个角度说：Kafka 是「日志先落盘，消费者去追日志」，心智模型天然是流；RocketMQ 是「队列先排队，消费者来取队列」，心智模型天然是队列。选型时先问自己业务更像哪一种。补充加分点：RocketMQ 额外把过滤、延时、事务、顺序做进了 Broker 端能力，这几项在 Kafka 侧要靠应用层或 Streams 补齐。

1.2 选型维度速查

面试被问「为什么选 RocketMQ 不选 Kafka」时，按这张表逐行说，比零散罗列优缺点更稳。

维度RocketMQ 的选择面试里的说法
消息模型Topic → MessageQueue 两级队列即并行度单位，与「分区」概念对应
路由与协调NameServer 无状态路由表，不引入共识算法部署轻、无脑裂风险，代价是路由最终一致
存储单元全部 Topic 共用单一顺序写入的 CommitLog写入恒为顺序 IO，磁盘利用率高；代价是过滤与定位依赖额外索引
消费模型集群消费 / 广播消费一个队列同一时刻只被集群内一个消费者处理；广播则每个消费者都收全量
高可用协调5.x 由 Controller 模式承载选主与切换替代了需要自建选主的旧方案
事务事务消息（half + 回查）把「本地事务与发消息」的原子性交给业务回查兜底
延时消息Broker 端原生支持Kafka 侧不原生支持，靠应用层或 Streams 实现
服务端过滤Tag 精确匹配 + SQL92 表达式减少无效网络传输；Kafka 需应用侧或 Streams 过滤
顺序保证队列内有序靠队列选择器把同 key 消息固定到同一队列
接入协议5.x 主线 Proxy + gRPC多语言、多网络环境接入成本低

跨库对照的完整版本见 [[Kafka 架构全景与角色分工]]，本表只列 RocketMQ 一侧。

二、NameServer：无状态路由表

NameServer 是整个集群里最容易被误解的组件。它名字像 ZooKeeper、行为像 ZooKeeper，但设计目标恰好相反：它放弃了一致性，换来部署与运维的极简。

2.1 三条必须背下来的性质

  1. 无状态：NameServer 不保存集群的持久化真相，进程重启后靠 Broker 重新注册把路由表填回来
  2. 不引入共识算法：没有多数派、没有任期、没有日志复制，因此不存在脑裂，也不存在「等 quorum」这种阻塞
  3. 不参与消息存储：任何消息字节都不经过 NameServer，它只回答「去哪个 Broker 找哪个队列」

官方口径是两台 NameServer 互备（双 master），两台之间不互相同步、不做选主，各自独立对外服务。路由信息是最终一致的：Broker 周期性向 NameServer 注册并上报自己的队列列表，客户端周期性地向 NameServer 拉取路由、拉下来后在本地缓存，并自行做故障切换。

「双 master 互备」的真实含义是两台互为备份，而不是互为副本。停掉任意一台，集群照常工作；两台都停，客户端缓存里的路由还在，短时间内已建立的连接不受影响，但新连接拿不到路由。

2.2 职责边界表

角色负责什么不负责什么典型故障影响
NameServer维护 Broker 注册信息与队列路由表、响应路由查询不存消息、不做共识、不做选主、不参与数据面全部 NameServer 不可用 → 客户端在缓存有效期内仍可用，缓存过期后新连接无法获取路由
Broker存储消息、接收生产与消费请求、主从复制、执行过滤、事务回查不做选主决策（5.x 交由 Controller）、不维护集群级路由单 Broker 故障 → 该 Broker 承载的队列写入与消费受影响
Controller（5.x）选主与故障切换的协调不存消息、不承载读写请求协调能力暂停，已在服务的队列读写通常继续
Proxy（5.x）统一接入层，协议转换、连接管理不存消息、不掌握集群真相（真相在 NameServer）见第七节
Producer选队列、设置可靠性档位、按路由发往 Broker不参与选主、不做消息存储决策生产端故障 → 消息发不出去，已存数据不受影响
Consumer按消费模式与队列拉取、处理消息、维护位点不直接操作存储文件消费端故障 → 集群消费模式下队列重分配，广播模式下该消费者进度不再推进

最容易搞混的一点：NameServer 不是「集群的大脑」，它只是「路由表」。

它不做任何决策。哪个 Broker 是主、谁是备、要不要切换，全部不在它这里。正因为它不决策，才能做到无状态、不做共识、随便重启。

面试追问：NameServer 挂了，RocketMQ 集群就不可用了吗？

答：不一定，要分三档说。

  1. 停掉一台（双 master 互备）：完全无感，另一台继续服务。
  2. 两台都停，但客户端本地路由缓存仍在有效期内：存量连接上的收发继续，新连接拿不到路由。因为数据面路径不经过 NameServer，这是「最终一致」换来的可用性。
  3. 两台都停且缓存过期：新连接拿不到路由，生产与消费都无法建立。恢复方式是启动 NameServer 并等 Broker 周期注册、客户端重新拉取。

必须补一句对比才算完整：换成 Kafka 的 KRaft，Controller Quorum 不可用时分区的已有读写通常仍能继续（元数据已提交到日志），但会失去新建分区、Leader 重选等动态能力。两者都把「数据面与元数据面解耦」当作可用性的关键，Kafka 用共识换强一致，RocketMQ 用无状态换部署简单。 对照侧见 [[KRaft 协调与选主]]。

面试追问：为什么 RocketMQ 的 NameServer 敢不做共识？换成 ZooKeeper 或 Raft 不好吗？

答：因为它承担的职责小到可以容忍不一致。

  • 它不存消息。数据放错路由最多导致「找不到消息」或「连错 Broker 后重试」，不会丢数据、更不会写坏数据
  • 路由不一致是自愈的：客户端拿到旧路由发失败，会重新拉取；Broker 上下线变化后周期性注册会覆盖旧值
  • 真正不能容忍不一致的是「两个 Broker 都自称主」，所以这部分职责被单独拿出去，5.x 交给 Controller 模式处理

代价也要讲清：最终一致意味着存在一个短暂窗口，客户端可能拿着过时路由发消息，表现为偶发失败需要重试；也意味着排障时不能只查 NameServer 日志，要同时看 Broker 侧注册日志与客户端路由缓存。⚠️ 客户端路由缓存的具体时长与失效策略随版本变化，以你所用版本的官方文档为准。

三、Broker：Master-Slave 与存储职责

3.1 5.x 主线：Controller 模式接管选主

RocketMQ 5.x 的高可用协调由 Controller 模式承载。 Broker 以 Master / Slave 形态部署，Master 承担读写、Slave 承担同步复制与（可选）读请求，而**「谁是 Master、主备切换怎么触发」这件事由 Controller 模式统一协调**。

这一点是理解 5.x 的关键：Master-Slave 是数据形态，Controller 模式是协调机制，两者不是二选一。5.x 的正确说法是「Master-Slave 部署形态 + Controller 模式做协调」，而不是「要么 Controller 要么 Master-Slave」。

⚠️ Controller 模式的部署拓扑、Broker 数量约束、选主超时等具体参数以你所用版本的官方文档为准，本篇不写数值。

3.2 Broker 承担的六件事

职责说明展开见
存储与写入消息统一顺序追加写入 CommitLog，Topic 下的各队列在存储层是索引视图[[CommitLog、ConsumeQueue 与 IndexFile]]
读写服务处理生产请求与消费拉取请求，按消费模式分配队列[[消费模式、位点管理与推送拉取]]
主从复制Master 写完按配置把数据同步给 Slave[[主从复制与故障转移]]
服务端过滤按 Tag 或 SQL92 在 Broker 端完成筛选，减少无效传输第六节
事务回查对处于「未知」状态的 half 消息回查业务本地事务状态[[事务消息、延时与顺序消息]]
管理接口提供 mqadmin 一类工具所需的运行时接口第六节

⚠️ brokerIP1 / brokerName 只做一件事：作为注册到 NameServer 的地址与身份标识。前者是 Broker 对外暴露的地址（多网卡或容器环境下需要显式指定，否则注册出去的地址可能客户端不可达），后者是集群内唯一标识。⚠️ slaveReadEnabled 决定是否允许从 Slave 读，是否开启取决于业务能否接受读到略旧的数据。刷盘由 flushDiskType 的 SYNC_FLUSH（同步刷盘）/ ASYNC_FLUSH（异步刷盘）控制，syncFlushTimeout 是同步刷盘路径上的超时上限。这几项的具体默认档位与数值本篇不写，见 [[刷盘策略与内存映射]]。

旧版做法（无 Controller 的传统 Master-Slave）

RocketMQ 4.x 及更早的部署里，主备切换依赖人工或外部脚本干预：Master 挂掉后，运维要手动把某个 Slave 提升为 Master，并处理客户端路由切换。这套做法已被 RocketMQ 5.x Controller 模式替代——5.x 由 Controller 模式接管选主与切换，不再依赖人工介入。 保留本节是因为存量系统仍是这个形态，且面试常问「RocketMQ 的 HA 是怎么做起来的」。新搭的集群不要再按人工切换的方式设计，否则等于放弃了 5.x 引入 Controller 的全部收益。

3.3 写入路径的三个存储对象

Broker 收到一条消息后，不是「按 Topic 写进一个文件」，而是：

三个对象的分工：

  • CommitLog：全集群共用的顺序写入主体，一个 Broker 的所有 Topic 消息都写进它。这是 RocketMQ 写吞吐高的根因：磁盘永远只顺序写，不管业务有多少 Topic
  • ConsumeQueue：每个 Topic 队列一条逻辑索引，把「哪个 CommitLog 物理位置的第几条」串成消费可用的有序序列
  • IndexFile：按消息 Key 建立的索引，支撑按 key 查询消息（如按订单号反查）

⚠️ 三者的文件大小、页大小、单文件条数等具体数值本篇一律不写，存储结构的细节在 [[CommitLog、ConsumeQueue 与 IndexFile]]。

面试追问：所有 Topic 共用一个 CommitLog，会不会互相影响？某个大 Topic 打满会不会拖垮其他 Topic？

答：磁盘层面共享的是写入通道，不是隔离单位。CommitLog 满了会影响整个 Broker，所以磁盘容量规划必须按 Broker 总量算，不能按 Topic 算。 但消费层面是隔离的：每个 Topic 队列有自己的 ConsumeQueue，消费进度、堆积量、过滤结果都按队列独立计算，某个 Topic 堆积不会让其他 Topic 的消费者阻塞。 隔离真正做不到的是写入：共享通道意味着没有按 Topic 的写入 QoS。⚠️ 官方有流控相关设计，但具体限流档位与触发条件随版本变化，面试讲清「共享写入通道 + 消费侧隔离」这个结构判断即可，不要报具体限流参数。

四、Topic 与 Queue：为什么是两个层级

这是 RocketMQ 最该先想明白的数据模型，它直接决定了消费并行度、顺序性和扩容方式。

4.1 两层结构，第三层是 Tag

  • Topic：逻辑上的消息分类名，比如 order-topic。它本身不存数据
  • MessageQueue（队列）：Topic 的物理分片与消费并行单位。数据只存在于队列对应的索引里
  • Tag：Topic 内部的业务分类标签，用于服务端过滤，不构成新的存储层级

队列数直接决定消费并行度上限：集群消费模式下，一个队列同一时刻只被消费组内一个消费者处理，消费者数量超过队列数时，多出来的拿不到队列。

4.2 为什么必须分两层

如果只有 Topic 一层，Topic 就是并行单位，那么扩并行度就得改 Topic 的物理分片（已在跑的消费者全部要重新分配），也没法做「重要消息独占一个队列」这种精细规划，不同重要级的消息无法在同一 Topic 下分开治理。拆成两级之后，Topic 是命名与权限的单位，Queue 是并发与存储的单位，两者解耦，扩容只动 Queue 不动 Topic 语义。

旧版做法

「队列数一旦设定就完全不能变」是早期版本的限制。当前 RocketMQ 5.x 支持对 Topic 扩缩队列，但扩容会改变队列到消息的映射关系，正在运行的顺序消息保证会被打断（同 key 消息可能落到新队列）。新版做法是：需要扩容时先评估顺序性影响，或直接新建 Topic 迁移，而不是在原 Topic 上硬扩。

面试追问：顺序消息怎么保证？为什么顺序性以队列为粒度？

答：顺序性由队列保证，不跨队列。做法是用 MessageQueueSelector（队列选择器）按消息 key 计算目标队列，同一 key 的消息永远落进同一个队列，该队列由单一消费者顺序处理，于是顺序天然成立。 必须补充的边界：

  • 顺序性以队列为粒度，跨队列无序，全局有序需要单队列，等于放弃并行
  • 顺序消费下失败不能原地无限重试——第 1 条卡住重试、第 2 条已通过，业务看到的就是乱序。所以顺序消息的失败处理要挂到重试/死信链路，见 [[重试、死信与消费堆积]]
  • 扩缩队列会改写映射，顺序保证失效
  • 消费端必须单线程按序处理同一队列；并发消费同一队列，顺序照样被破坏

面试追问：RocketMQ 为什么要做 Topic/Queue 两级，Kafka 只有 Topic/Partition 一级，是多此一举吗？

答：不是多此一举，是关注点不同。Kafka 把「逻辑分类」和「并行度」压在同一层（Partition 同时是存储分片、并行度单位、位点单位），模型极简；RocketMQ 把两者拆开，多了一层间接，换来两个具体好处：

  1. 过滤正交：Tag 是 Topic 之上的第三维，Topic 相同但 Tag 不同的消息走同一队列模型，服务端过滤后消费，不必为每类业务建 Topic
  2. 顺序与并发分开调：队列数决定并发上限，同一队列内保证顺序，粒度清晰

代价是心智模型多一层，扩容时要注意顺序性影响。⚠️ 更细的对照见 [[Kafka 架构全景与角色分工]]，本篇不展开。

五、Producer 与 Consumer 的交互方式

5.1 生产端：从路由到确认

一条消息的发送按顺序经过四步：

  1. 取路由：Producer 从本地路由缓存查 Topic → 队列 → Broker 的映射；缓存为空或过期时向 NameServer 拉取
  2. 选队列：指定队列就用指定的；指定 key 就用队列选择器按 key 计算；都不指定则轮询，保证同一 Producer 的消息能均匀落到各队列
  3. 发请求：连到目标队列所在 Master 写入
  4. 确认：按同步 / 异步 / 单向三种方式拿结果。同步路径的失败重试次数可配，异步路径有独立的重试配置；单向不等待结果

⚠️ 发送线程池大小、失败重试次数、内存单次搬运字节上限等默认值本篇不写，见 [[发送流程、可靠性配置与重试]]。关键点：可靠性档位不是「一个开关」，而是「同步还是异步 + 刷盘档位 + 主从同步方式」的组合，三者任一放松，消息就可能丢。

5.2 消费端：集群消费与广播消费

消费模式是 RocketMQ 消费侧最上位的一个选择，它决定位点怎么存、队列怎么分。

维度集群消费广播消费
位点粒度消费组 + 队列，组内成员共享每个消费者自己一份，同一队列内成员各存各的
队列分配组内每个队列同一时刻只被一个消费者处理每个消费者都消费所有队列的全量消息
扩容加消费者可提升并行度，超过队列数后无效加消费者等于增加重复处理量，通常只在「每个消费者都要全量」时用
适用常规业务消费、分摊压力本地缓存刷新、配置全量下发、每个实例都要收到全量
风险消费进度滞后会引发堆积一个消费者落后不影响其他消费者，但重启后可能重复消费

消费位点默认由客户端本地持久化；把位点集中存到 Broker 需要显式开启远程位点存储。⚠️ 该行为与相关配置项随版本演进，具体以你所用版本文档为准，机制细节见 [[消费模式、位点管理与推送拉取]]。

5.3 拉取还是推送

客户端 API 看起来分推送与拉取两种，但底层都是客户端主动拉取。区别只在于什么时候来拉：拉取由客户端自己控制节奏；「推送注册式」则是客户端向 Broker 注册监听，Broker 用长轮询把请求挂住，直到有数据或超时才返回。

旧版做法

早期版本的「推送」是 Broker 主动往客户端连接推数据，客户端被动接收。当前 RocketMQ 的推送模式已改为客户端拉取 + Broker 长轮询挂起，由客户端掌握实际拉取时机。新版请按长轮询模型理解，不要按「Broker 主动推」去设计容量或排障思路。

六、MQAdmin 与过滤链

6.1 服务端过滤：Tag 与 SQL92

RocketMQ 把过滤放在 Broker 端完成，这是它相对 Kafka 的一处原生优势。

过滤方式表达能力代价适用
Tag 精确匹配只能「等于某个或某几个 Tag」表达能力最弱，但索引代价最低绝大多数业务场景够用
SQL92 表达式支持 AND / OR / IN / BETWEEN / IS NULL 等条件需要 Broker 承担表达式求值开销需要多维条件筛选
应用侧过滤任意逻辑无效消息仍占用网络与磁盘，且要先落盘过滤条件复杂到无法下推

过滤发生在消费请求抵达 Broker 之后、消息返回客户端之前。好处是不匹配的过滤掉、客户端不浪费 CPU；代价是 Broker 要为每条消息做求值，Tag 数很多时 SQL92 的开销明显高于 Tag 匹配。⚠️ Tag 与 SQL92 的开关方式、Broker 侧的过滤执行路径随版本变化，具体以你所用版本文档为准。

旧版做法（FilterServer）

早期版本用独立进程 FilterServer 来承担消息过滤，Broker 把过滤请求转发给它。这套机制已被 RocketMQ 5.x 的 Proxy + Tag/SQL92 过滤链替代——过滤现在在 Broker 与 Proxy 侧按 Tag 或 SQL92 完成，不再需要额外部署 FilterServer 进程。 保留本节是因为存量集群里可能还有 FilterServer 进程，在 5.x 上不要再额外部署 FilterServer。

6.2 mqadmin：管理入口

⚠️ 工具子命令清单属社区实践总结，以你所用版本的 mqadmin 帮助输出为准。本篇只列常见用途，不写参数默认值。

用途常见子命令方向
查看集群与 Broker 状态集群列表、Broker 状态、Broker 配置查询
维护 Topic创建/更新 Topic、查询 Topic 配置、删除 Topic
维护消费组查询消费进度、重置消费位点、查询订阅关系
排障查看消息轨迹、查看消费堆积、查询生产者与消费者连接

⚠️ mqadmin 与 Kafka 的 kafka-topics.sh / kafka-consumer-groups.sh 不是同一套工具链，子命令名与参数都不通用。跨库迁移时不要照抄命令，见 [[RocketMQ 监控与排障]]。

面试追问：把过滤放到 Broker 端，代价是什么？

答：三条，按面试优先级排：

  1. CPU 与内存：每条消息都要在 Broker 上过一遍表达式求值，Tag 基数大时开销明显。所以生产上优先用 Tag，只有 Tag 不够才上 SQL92
  2. 过滤维度固化：过滤条件写在订阅关系里，改条件要改订阅关系，不能像应用侧那样随便改代码
  3. 可观测性变差：客户端收不到未匹配消息，排障时「我明明发了为什么收不到」要先确认是不是被过滤掉了，而不是没投递到位

反过来说收益也很实在：无效消息不跨网络、客户端不浪费 CPU。对于 Tag 分流清晰的业务，这个交换非常划算。

七、RocketMQ 5.x Proxy 架构（gRPC）带来的变化

RocketMQ 5.x 的主线架构是 Proxy + gRPC 接入，Broker 侧的高可用协调由 Controller 模式承载。 这一节讲清 Proxy 带来的三件事。

7.1 三件事

第一，协议统一为 gRPC。 5.x 把客户端与集群之间的接入协议统一到 gRPC，原有的 Remoting 私有协议作为兼容路径保留。第二，客户端无感。 业务代码里的发送与消费语义不变，Topic、队列、Tag、事务、延时这些概念一个没改，升级换来的不是 API 变化而是接入方式的标准化。第三，Broker 侧新增 Proxy 组件。 Proxy 是独立的接入层，承担连接管理、协议转换与请求转发；它不经手选主，也不存消息——集群真相仍在 NameServer，消息仍在 Broker。

7.2 为什么要在 Broker 前面加一层

收益说明
多语言接入gRPC 生态成熟，非 JVM 语言不必自己实现私有协议
接入层可水平扩展连接压力与协议开销从 Broker 上剥离，Proxy 可按需扩容，Broker 的资源更多用于存储与计算
路由与接入解耦Proxy 负责「怎么连上」，NameServer 负责「连哪个」，两个关注点独立演进

⚠️ Proxy 的具体部署形态（独立进程还是嵌入 Broker、可否与 Broker 同机）、容量规划方式随版本与场景变化，以你所用版本的官方文档为准，本篇不写形态结论。

面试追问：加了 Proxy 之后，消息路径变长了吧？会不会明显增加延迟？

答：路径上确实多了一跳，但要区分「跳数」和「延迟」。多一跳引入的是网络往返与转发开销，而不是一次序列化加反序列化级别的开销；相比 Broker 端的存储与刷盘开销，接入层这一跳通常不是延迟的主要来源。 真正需要关注的是别让 Proxy 成为瓶颈：它是所有客户端连接汇聚的点，一旦它 CPU 打满或连接数触顶，影响面是整个集群的收发，而不是单个 Topic。⚠️ 具体容量与瓶颈判据随版本与配置变化，以你所用版本文档为准。

补充加分点：这也是 Proxy 与 NameServer 必须分开的原因——NameServer 不经手消息，所以它可以无状态随便重启；Proxy 经手每条消息，所以它需要容量规划和扩缩容意识。把两个关注点塞进一个组件，两边都会变差。

八、旧版机制：FilterServer 与 DLedger

本节集中收拢三条旧机制，方便一次性对照。三条都已降级为旧版做法，5.x 上不再推荐使用。 保留本节是因为存量集群里三者仍需维护，且「RocketMQ 有没有自己的选主」「为什么 4.x 要靠人工切主」都是高频面试题。

旧机制旧版做法5.x 的替代物替代物由谁承担
Broker DLedger 模式Broker 内部用 DLedger 做多副本与选主，追求「不引入独立控制面」RocketMQ 5.x Controller 模式独立的控制面组件统一协调选主与切换
传统 Master-Slave（无 Controller）主备切换靠人工或外部脚本干预RocketMQ 5.x Controller 模式Controller 模式接管选主与切换触发
FilterServer独立进程承担消息过滤，Broker 转发过滤请求RocketMQ 5.x Proxy + Tag/SQL92 过滤链Proxy 与 Broker 侧按 Tag 或 SQL92 完成过滤

旧版做法（Broker DLedger 模式，已弃用）

旧版用DLedger 在 Broker 内部实现多副本与自选主，好处是不用额外部署控制面组件。这一机制已被 RocketMQ 5.x Controller 模式替代：官方 release notes 已把 legacy Broker DLedger mode 标注为弃用。 保留本节的原因：存量集群里 DLedger 模式的部署仍需维护，且「RocketMQ 有没有自己的 Raft 选主」是高频面试题。标准答法是：RocketMQ 的高可用协调在 5.x 由 Controller 模式承载，DLedger 模式是已弃用的旧方案。

旧版做法（传统 Master-Slave，无 Controller）

传统 Master-Slave 部署下，Master 故障需要人工或脚本把 Slave 提升为 Master 并处理客户端路由。这套做法已被 RocketMQ 5.x Controller 模式替代，切换由控制面协调完成。 面试里要能说清为什么「人工切换」是问题：切换时间不可控（RTO 取决于人的响应速度）、切换过程缺少一致性保证、多机房场景下路由更新容易不一致。

旧版做法（FilterServer）

旧版用独立进程 FilterServer 承担消息过滤。这套机制已被 RocketMQ 5.x 的 Proxy + Tag/SQL92 过滤链替代，不再需要额外部署 FilterServer 进程。面试里说清代价差异即可：FilterServer 模式下多一个需要部署、监控、扩缩容的进程，且过滤能力有限；替代方案把过滤收进已有链路，能力（Tag 之外的 SQL92 表达式）反而更强。

面试追问：RocketMQ 的高可用是怎么做的？

答题骨架分三层，按这个顺序讲最稳：

  1. 数据层：Master 写入、Slave 同步复制；是否允许从 Slave 读可配置
  2. 协调层：RocketMQ 5.x 由 Controller 模式承载选主与故障切换——这正是它替代 DLedger 模式与传统人工切换 Master-Slave 的地方
  3. 路由层：NameServer 拿到 Broker 注册变化后返回给客户端，客户端在缓存有效期内自动切换

必须补的对照：Kafka 的对应答案是 KRaft Controller Quorum（RAFT 共识、元数据强一致），RocketMQ 的 NameServer 本身无状态、无共识，一致性靠「最终一致 + 客户端重试」兜底。详见第五节与 [[主从复制与故障转移]]。

九、面试高频追问

按面试出现频率排序，每条给出答题骨架。骨架里的粗体是必须说到的点，其余可以按面试官追问深度展开。

1. RocketMQ 有哪些组件？NameServer 是干什么的？

答题骨架：NameServer 是无状态路由表，不引入共识算法，不参与消息存储。集群里另有 Broker（存储与收发）、Producer、Consumer，5.x 多了 Proxy（统一接入层）与 Controller（高可用协调）。NameServer 停掉之后，客户端在本地路由缓存有效期内仍可继续收发——因为数据面不经过它。详见第二、五节。

2. NameServer 挂了集群还能用吗？和 Kafka 的 Controller 挂了有什么区别？

答题骨架：先分档：停一台无感；全停但缓存有效期内，存量连接继续；全停且缓存过期才真正不可用。再讲对照：Kafka KRaft 的 Controller Quorum 不可用时，已有分区读写通常继续，失去的是新建分区与 Leader 重选这类动态能力。两者都把数据面与元数据面解耦，区别在 Kafka 用共识换强一致、RocketMQ 用无状态换部署简单。详见第二节。

3. 为什么 RocketMQ 的 NameServer 不做共识？

答题骨架：因为它承担的职责小到可以容忍不一致。不存消息，所以路由错乱不会丢数据、不会写坏数据；不一致是自愈的，客户端重新拉取即可；真正不能容忍的是双主并存，那部分职责被单独交给 Controller 模式。代价是存在短暂窗口拿到过时路由，表现为偶发失败需重试。详见第二节。

4. Topic 和 MessageQueue 有什么区别？为什么要分两级？

答题骨架：Topic 是逻辑分类与权限单位，MessageQueue 是物理分片与消费并行度单位。拆两级让「改名/授权」与「扩并发」互不干扰，也给 Tag 过滤留出正交的第三维。代价是心智模型多一层，扩缩队列会打断顺序消息的保证。详见第四节。

5. RocketMQ 怎么保证顺序？什么情况下不保证？

答题骨架：顺序性以队列为粒度，靠 MessageQueueSelector 把同 key 消息固定到同一队列，消费端单线程按序处理。破坏顺序的四种情况：扩缩队列改写映射、失败原地无限重试、同一队列并发消费、跨队列消费。顺序消息的失败要走重试与死信链路，见 [[重试、死信与消费堆积]]。

6. 集群消费和广播消费有什么区别？

答题骨架：集群消费下位点按消费组 + 队列共享，一个队列同一时刻只被组内一个消费者处理，加消费者能提并行但超过队列数就无效；广播消费下每个消费者各存一份位点、都收全量，加消费者等于增加重复处理。选错的典型后果：集群模式当广播用会导致部分消息漏处理。详见第五节。

7. RocketMQ 的高可用怎么做？和 Kafka 的复制模型有什么不同？

答题骨架：三层作答——数据层 Master 写 Slave 同步复制、协调层 5.x 由 Controller 模式承载选主与切换、路由层 NameServer 下发新路由由客户端切换。对照点：Kafka 是 ISR 收缩 + KRaft 选主，RocketMQ 旧版是 DLedger 或人工切换，5.x 统一到 Controller 模式。详见第三、八节与 [[主从复制与故障转移]]。

8. 5.x 的 Proxy 解决了什么问题？它和 NameServer 有什么区别？

答题骨架：Proxy 把接入协议统一到 gRPC，把连接管理与协议转换从 Broker 剥离，使接入层可独立水平扩展。关键区分：NameServer 在数据面之外，Proxy 在数据面之内——消息条条穿过 Proxy，所以它需要容量规划；NameServer 不经手消息，所以可以无状态、随时重启。详见第二、七节。

9. RocketMQ 的消息过滤怎么做？放在服务端有什么代价？

答题骨架：Tag 精确匹配 + SQL92 表达式，都在 Broker 端完成。代价三条：Broker 侧求值开销（所以优先用 Tag）、过滤条件固化在订阅关系里改起来麻烦、客户端收不到未匹配消息导致可观测性变差。FilterServer 是旧版机制，5.x 已由 Proxy + Tag/SQL92 过滤链替代。详见第六节。

10. 延时消息、事务消息、顺序消息的实现都靠什么？

答题骨架：三者都是 Broker 端能力而非应用层模拟——延时消息由 Broker 内部定时器到期后投递，事务消息靠 half 消息加业务回查把本地事务与发消息的原子性交给业务兜底，顺序消息靠队列选择器。⚠️ 具体的定时器精度与回查次数上限属随版本变化的参数，面试讲机制方向即可，数值以你所用版本文档为准。详见 [[事务消息、延时与顺序消息]]。
