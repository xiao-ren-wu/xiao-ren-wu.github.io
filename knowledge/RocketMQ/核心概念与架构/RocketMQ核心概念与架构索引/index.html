RocketMQ 核心概念与架构索引

本页用途

本主题回答 RocketMQ 最上位的三个问题：集群由哪些角色组成、各自的职责边界在哪、一条消息从产生到被消费要经过哪些环节。适合第一次系统接触 RocketMQ 的人，以及面试时被问「RocketMQ 有哪些组件」「NameServer 挂了还能用吗」「为什么高可用不用 ZooKeeper 那种做法」而需要成体系作答的人。

它在全库学习顺序上是第 1 步。后面六个主题里的每一个术语——CommitLog、MessageQueue、Tag、消费模式、重试队列、Controller 模式——都挂在本页建立的心智模型上；跳过本页直接读参数类笔记，结果是每条结论都能背但推不出因果。

本主题目前只有一篇深度正文，架构层面的细节全部沉淀在那篇里。本页的职责是给出入口、结论速览与后续顺序，不重复正文的细节。

关键结论

以下 5 条各自可独立作为一道面试题的答案，全部出自 RocketMQ 架构全景与角色分工，没有一条是本页新增的推断。

  1. NameServer 是无状态路由表，不引入共识算法，不参与消息存储：官方口径是两台互备（双 master），彼此不互相同步也不做选主；路由是最终一致，靠 Broker 周期注册加客户端周期拉取维持。它不做任何决策——哪个 Broker 是主、要不要切换，全不在它这里。正因为不决策，才能无状态、随便重启。RocketMQ 架构全景与角色分工
  2. NameServer 无状态无共识，故障后可短暂不可用；Kafka KRaft 有共识，元数据强一致。两者都把「数据面与元数据面解耦」当作可用性的关键，差别在 Kafka 用共识换强一致、RocketMQ 用无状态换部署简单。答这题时必须分三档说清降级路径：停一台无感；全停但客户端路由缓存有效期内存量连接继续收发；全停且缓存过期才真正不可用。RocketMQ 架构全景与角色分工
  3. 数据模型是 Topic → MessageQueue 两级，Tag 是第三维过滤维度：Topic 是逻辑分类与权限单位，MessageQueue 是物理分片与消费并行度单位，队列数直接决定消费并行度上限。顺序性以队列为粒度，靠 MessageQueueSelector 把同 key 消息固定到同一队列；扩缩队列、失败原地重试、同一队列并发消费都会破坏顺序。RocketMQ 架构全景与角色分工
  4. RocketMQ 5.x 的高可用协调由 Controller 模式承载：Master-Slave 是数据形态，Controller 模式是协调机制，两者不是二选一。三条旧机制均已降级——Broker DLedger 模式已被官方 release notes 标注弃用、无 Controller 的传统 Master-Slave 靠人工切换、FilterServer 已被 5.x 的 Proxy + Tag/SQL92 过滤链替代。RocketMQ 架构全景与角色分工
  5. NameServer 在数据面之外，Proxy 在数据面之内，这是两者不可合并的根本原因：NameServer 只回答路由、不经手任何消息字节，所以可以无状态、随时重启；Proxy 是每条消息都要穿过的接入层，有连接、有缓冲、有流量压力，必须做容量规划与水平扩展。5.x 把接入协议统一到 gRPC，换来多语言接入与接入层独立扩容。RocketMQ 架构全景与角色分工

落到具体参数与实现时不要停在本页：刷盘档位与内存映射看 RocketMQ 存储机制索引，发送端可靠性组合与重试看 RocketMQ 生产者索引，端到端语义与业务去重看 RocketMQ 可靠性与投递语义索引。

学习顺序

第 1 步（本页所在主题）。 读完应能独立回答：集群有哪些角色、NameServer 和 Broker 的边界在哪、为什么 NameServer 可以不做共识、为什么 Topic 要拆成两级、5.x 相比 4.x 变了什么。

正文只有一条阅读路径，但刻意分两遍。第一遍通读正文一至五节（定位与选型维度、NameServer、Broker、Topic/Queue、生产消费交互），先把模型立住；第二遍回看第六至八节（过滤链与 mqadmin、5.x Proxy 架构、旧版机制对照）补上版本演进这条线——这几节信息密度最高、最容易被跳过，而「5.x 换了什么」在面试里几乎是必问题。

第 2 步 RocketMQ 存储机制索引。模型立住后才看得懂 CommitLog、ConsumeQueue、IndexFile 三者的分工，以及为什么所有 Topic 共用一个顺序写入的 CommitLog。

第 3 步 RocketMQ 生产者索引 与 RocketMQ 消费者与消费组索引。把第五节的发送端与消费端分别展开，两端参数互相牵连，建议对照读而不是一端读完再读另一端。

第 4 步 RocketMQ 可靠性与投递语义索引。前三步的机制在这里收束成可对外承诺的语义保证，事务消息也在这一层落定。

第 5 步 RocketMQ 高可用与运维索引。把第三、八节的 Controller 模式与主从复制接到实际排障动作上。

第 6 步 RocketMQ 面试题索引。全部读完后按主题回扫，用答题结构查漏，而不是重新通读。

读完怎么检验

别用「读完了」当标准，用能否脱口回答这 5 个问题当标准。这 5 题全部在正文范围内，答不上来说明卡在了某一节而非「需要复习」：

  1. NameServer 挂了，集群在什么情况下还能用？三档降级路径分别是什么？
  2. 为什么说 NameServer 的路由「最终一致」是可以接受的？如果它要保证强一致，代价会落在哪？
  3. 顺序消息靠什么绑定队列？四种会破坏顺序的情况分别是什么？
  4. 5.x 相比 4.x，高可用协调换成了什么？被换掉的旧机制有哪三条，各自由什么替代？
  5. Proxy 和 NameServer 都被叫「中间层」，为什么不能合并成一个组件？
