RocketMQ 消费者与消费组索引

本页用途

RocketMQ 消费者与消费组主题的索引页。只做两件事：列出本主题的两篇正文，并把两篇里最容易被答错的结论集中列一遍。本页不引入正文之外的新结论，出现分歧以正文为准。消费模式、位点、推送拉取见 消费模式、位点管理与推送拉取，重试、死信与堆积见 重试、死信与消费堆积。

数值口径

本主题涉及的消费线程数上下限、长轮询挂起时长、死信队列保留窗口、延迟级别总表等条目，默认值随版本变化，以你所用版本的官方文档为准。本主题不给出这些数值。

消费重试次数相关的事实已升级为 A 级：客户端 maxReconsumeTimes 的位置与默认值、其 -1 在并发与顺序下的两种展开值、Broker 订阅组 retryMaxTimes、每组死信队列数、Broker 侧覆盖优先级与进 DLQ 判定、顺序锁特殊路径、重试延迟级别算法。本主题凡引用均标注「RocketMQ 5.x 源码默认」。

关键结论

  1. 「推」是客户端对长轮询的封装。 数据流向永远由客户端发起，Broker 没有通向消费者的推送通道。推与拉的选择取决于要不要控制拉取时机（抢锁后再拉、需要自定义批量与背压就要用 Pull），与实时性无关。
  2. Kafka「并行度上限 = 分区数」这条规则不能照搬。 分区自带独立日志，是物理分片，加分区同时扩写与扩读；RocketMQ 队列只是 CommitLog 之上的逻辑视图，加队列只改消费分配、不动写路径。RocketMQ 的消费并行度是 min(可分配队列数, 消费者实例数 × 每实例消费线程数) 三个闸门。
  3. 位点默认存在客户端本地。 集群模式按「消费组 + 队列」存、广播模式按「实例 + 队列」存；集中到服务端需要显式开启远程位点存储。运维可见性因此比 Kafka 差一档，排障第一个动作是确认实例的位点文件还在不在、记的位点是多少。
  4. 过滤必须放在 Broker 端。 三条代价：无关消息照样传输并占用客户端内存；位点会与业务实际处理进度脱节；ConsumeQueue 的定长条目自带过滤码，服务端判不命中就不用读消息体，省掉一次磁盘读。第三条是 RocketMQ 存储布局换来的独有收益，Kafka 侧没有对应物。
  5. 消费侧重试是服务端行为，而且带一个终点。 回调失败进重试队列、按重试次数阶梯延迟后重投回原队列；超过最大消费重试次数进死信队列，不再自动投递。Kafka 侧这两步都在应用侧，是每个应用各写一遍的成本。但「默认重试 16 次」只对并发消费成立，顺序消费的预算展开为 Integer.MAX_VALUE，推导见 重试、死信与消费堆积。

两条最容易踩的事故链

把这两条链条背下来比记 API 更省力，因为它们分别对应两篇正文的核心机制。

链条一：静默卡死型积压。 顺序消费的某条消息失败，无法进重试队列（重投会打乱队列内顺序），该队列后续消息全部停等。此时进程健康、没有报错、位点不动。扩容对它完全无效，唯一出路是查死信、做业务侧兜底、或放弃严格顺序。

链条二：静默跳数型数据丢失。 运维为了快速清空堆积重置消费位点，指标立刻变好，但跳过区间内的消息从未被消费。此后问题在下游以「状态莫名缺失」的形式爆发，而根因在几小时前的这次操作。跳过必须留记录，事后必须补数。

学习顺序

  1. 先读 消费模式、位点管理与推送拉取 的前两节。 消费模式决定位点怎么存、队列怎么分，是所有后续问题的地基。位点那节要连带读完「与 Kafka 位点的六点对照」，那是两库差异最大的地方。
  2. 再读同一篇的第三、四节（推与拉、长轮询）。 目标是能一句话说清「推是客户端封装」并给出理由，而不是只背结论。
  3. 然后读同一篇的第五到七节（过滤）。 过滤是 RocketMQ 相对 Kafka 少数几处明确优势之一，ConsumeQueue 过滤码省掉读消息体那条要能讲出因果。
  4. 接着读 重试、死信与消费堆积 全文。 这篇依赖上一节的位点概念。重点是三层「重试」的区分，以及「顺序消费为何不能重试」。
  5. 最后读同篇的第五、六节（积压诊断与应急）。 目标是能对着一条积压曲线先判形态再选手段，并且说得出每种手段的代价。
  6. 最后对读 Kafka 侧。 用 Kafka 消费者与消费组索引 与 消费组、位点提交与 Rebalance 逐项对照，重点看位点存放位置、并行度闸门个数、坏消息收口这三处。它们恰好是 RocketMQ 与 Kafka 取材取向不同的地方。
