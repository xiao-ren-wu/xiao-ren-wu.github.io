消费模式、位点管理与推送拉取

来源

基于 RocketMQ 5.x 官方文档的 consumer、filter、remoting 特性页与客户端DefaultMQPushConsumer / DefaultMQPullConsumer 接口整理。5.x 主线架构为 Proxy 加 gRPC 接入，Broker 侧的高可用协调由 Controller 模式承载。 数值口径：本篇涉及的消费线程数上下限、长轮询挂起时长、单批拉取条数、批量消费条数等条目，在事实清单中处于「尚未核实」或「只给语义不给数值」档位。因此这些条目全篇不给出任何具体数值，只写语义与机制；凡出现该类配置处均附「默认值随版本变化，以你所用版本的官方文档为准」。

本篇唯一引用的具体数值是顺序消费的重试预算 Integer.MAX_VALUE，属 A 级事实并标注「RocketMQ 5.x 源码默认」；其推导与并发侧对照见 重试、死信与消费堆积。

消费侧最容易答错的地方不是记不住 API，而是把 Kafka 的心智模型直接搬过来。Kafka 那边「一个分区只给一个消费者，所以并行度上限等于分区数」是一条能直接当运维口诀用的规则；RocketMQ 也有「一个队列只给一个消费者」的约束，形状一模一样，但两者踩在完全不同的单位上，所以这条规则不能照搬。本篇先把消费模式与位点钉住，再讲清「推」为什么不是推送，最后把过滤为什么必须放在 Broker 端说透。

一、集群消费与广播消费

1.1 消费模式是最上位的一个选择

消费模式决定两件事：位点怎么存、队列怎么分。它选错之后，所有参数调整都是在错的前提下微调。

维度集群消费广播消费
位点粒度消费组 + 队列，组内成员共享每个消费者实例自己一份，同一队列被多个实例各存各的
位点默认位置客户端本地持久化客户端本地持久化，不与其他实例共享
队列分配组内按队列独占分配，成员增减触发重新分配不分配，每个实例都消费自己订阅到的全部队列
新实例上线接管分配到的队列，从组内共享位点继续无位点可继承，从头开始消费
实例故障队列重新分配给组内其他实例，消费继续该实例直接停止消费，其他实例不受影响；它不重启就不再消费
积压统计成立，队列级 diff 有意义基本不成立，进度分散在各实例本地，汇总不出组级堆积
重复消费组内一条消息同一时刻只被一个实例处理同一条消息每个实例各处理一次，这是设计意图
适用场景订单、库存、账务等「一份数据只处理一次」本地缓存预热、配置广播、每个节点都要执行一次的通知

两条容易被跳过的推论：

  1. 广播模式没有故障转移。 它换来的是「每个实例都拿到全量」，代价是任一实例停机就等于有一份数据永远停在它那里。集群模式才有「消费组」这个概念的实质意义。
  2. 广播模式重启会全量重放。 位点在本地、进度不共享，实例重建后从零开始。对幂等操作无害，对有副作用的操作就是一次全量重复。

1.2 与 Kafka 消费组的对照

维度Kafka 消费组RocketMQ 消费组
成员标识group.id，同 id 即同组消费组名（ConsumerGroup），同组名即同组
分配单位分区队列
组内是否共享进度共享，提交给协调者集群模式共享同一位点文件，广播模式不共享
成员变化触发 Rebalance，eager 或 cooperative 两套协议触发队列重新分配，机制在服务端与客户端协同完成
进度可查性任何人都能 describe 一个组看每个分区的 lag默认只看得到消费者实例本地；开启远程位点存储后才可集中查看
位点回放直接指定 offset 任意位置重放可按位点或按时间重置，同样属于运维动作
顺序责任位置压在消费侧：同一分区单线程压在路由侧加消费侧：同 key 固定进同一队列，该队列单线程

1.3 为什么「并行度上限 = 分区数」这条规则不能照搬

Kafka 那条规则的形状是「消费者数超过分区数，多出来的拿不到分区，空转」。RocketMQ 集群模式形式上完全一样：消费者数超过可分配的队列数，多出来的实例拿不到队列。但同样的形状建立在完全不同的单位上。

问的问题KafkaRocketMQ
消费并行单位分区队列
单位是不是物理存储分片是。分区自带一整条独立日志否。队列只是 CommitLog 之上的一层逻辑视图，没有独立数据文件
加一个单位同时买到什么新的物理写通道，加上新的消费并行位只有消费分配的变化，写路径一点没动
消费并行度的全部来源只有分区数队列数、消费者实例数、每实例的消费线程数，三者取小
提升写入能力的手段加分区加 Broker 或加节点，加队列无效
实例故障时Rebalance 后新成员接手分区集群模式下队列重新分配给组内其他实例；广播模式没有转移

结论：Kafka 那条规则能当运维口诀直接用，前提是它的单位是物理分片，加单位是一石二鸟的操作。RocketMQ 的队列不是物理分片，照搬「消费慢就加队列」会得到一个看起来生效（队列数上升、分配变均匀）但写路径毫无变化的结果。 完整推导见 CommitLog、ConsumeQueue 与 IndexFile 第六节。

RocketMQ 的并行度是三个闸门取小：

一个实例内部的消费线程数由 consumeThreadMin 与 consumeThreadMax 这对配置约束：前者是线程数下界，后者是上界，客户端按订阅到的队列数与这两个值决定实际起多少条消费线程。默认值随版本变化，以你所用版本的官方文档为准。

面试追问：RocketMQ 也有「消费者超过队列数就空转」，那它和 Kafka 的规则不是一回事吗？

答题骨架：形式一样，含义不同，要从「单位是什么」讲。三点差异：

  1. 单元的物理性不同。 Kafka 分区自带独立日志，加分区同时扩写与扩读；RocketMQ 队列是逻辑视图，加队列只改消费分配。这就是两库排障口诀不可互换的根本原因。
  2. 并行度的来源个数不同。 Kafka 只有分区数一个闸门，因为一个 consumer 实例内部就是单线程 poll 循环；RocketMQ 是三个闸门取小。只扩实例而不看队列数与线程数，会得到「加了实例但没多消费」的结果，这是 RocketMQ 侧最常见的无效扩容。
  3. 故障语义不同。 Kafka 靠 Rebalance 转移分区；RocketMQ 集群模式靠队列重新分配，广播模式根本没有转移这一步。

1.4 「消费模式」其实有两个正交维度

前两节把消费模式讲成「集群 vs 广播」，这说的是位点与分配。但同一套客户端上还有第二个正交维度：队列内是并发处理还是顺序处理。

维度取值决定什么
位点与分配集群 / 广播位点粒度、队列分配方式、故障转移、能否按组汇总堆积
队列内处理并发 / 顺序同一队列内能否多线程同时处理、消费失败后能否重投

两个维度自由组合：集群 + 并发（绝大多数业务）、集群 + 顺序（订单状态机）、广播 + 并发（缓存预热）、广播 + 顺序（很少见）。面试里只答「集群和广播」是不够的，只答「并发和顺序」也不够——这是两个不同的轴。

第二个维度会直接改变失败语义。 顺序消费下消息失败不能进重试队列（重投会打乱队列内顺序），而它拿到的重试预算却是 Integer.MAX_VALUE（RocketMQ 5.x 源码默认，maxReconsumeTimes 默认 -1 在顺序消费下的展开值），实际等于永不因次数耗尽而进死信。完整的推导、Broker 侧覆盖优先级与判定符差异见 重试、死信与消费堆积。

一句话记住：「默认重试 16 次」不能无条件引用。 那个 16 是并发消费下的展开值，顺序消费的答案完全不同。答任何重试次数问题，都要先问一句「并发还是顺序」。

二、消费位点存在哪

2.1 粒度与位置

消费模式位点粒度说明
集群消费消费组 + 队列组内成员共享同一份位点，谁消费谁推进
广播消费消费者实例 + 队列每个实例在每个队列上各存一份，互不干扰

位点的默认存放位置是客户端本地文件，不是 Broker。把位点集中存到服务端需要显式开启远程位点存储。⚠️ 该行为与相关配置项随版本演进，以你所用版本的官方文档为准，机制细节见 RocketMQ 架构全景与角色分工。

这条默认值带来两个直接后果，都要提前想清楚：

  1. 位点跟着实例走，不跟着集群走。 换机器、容器重建、实例名或 IP 变化，都可能让新实例找不到旧位点文件。
  2. 运维默认看不到全局进度。 想集中查「这个消费组到底读到哪了」，需要开启远程位点存储；否则只能登到每个消费者实例上看。

2.2 与 Kafka 位点的六点对照

维度KafkaRocketMQ
存哪集群内部 topic __consumer_offsets，键 = group + topic + partition默认消费者客户端本地文件；开启远程存储后才在服务端
粒度group + partitiongroup + 队列（集群）/ 实例 + 队列（广播）
提交的是什么一组「分区 → offset」的集合每个队列一个消费位点
提交时机自动按周期推进 poll 返回位置，或手动在处理完成后提交消费成功回调返回后由客户端提交，位点跟随业务处理进度
丢失窗口自动提交时「已提交位点」可能超过「已处理位点」，形成不可逆缺口窗口小得多，提交点由消费结果驱动，不存在「提交跑在处理前面」这种默认行为
运维可见性任何人都能查、能改默认只看得到消费者实例本地

最后一行的差别在排障时最值钱。Kafka 侧可以直接 describe 一个组看每个分区的位点与 lag，RocketMQ 默认做不到。所以排障第一个要问的问题因此变成：这个实例的位点文件还在不在、它记的位点是多少，而不是「组里 lag 多少」。

2.3 位点起点与重置的两种口径

情形行为代价
找不到已有位点（全新消费组、位点文件丢失）按配置的起点开始：可配为从队列最早可用位点或从当前最大位点选「从最早」是一次全量回放；选「从最新」是静默跳过全部历史
显式重置位点运维动作，可按位点或按时间制造数据缺口，必须业务确认并留记录

起点取值的默认口径随版本演进，以你所用版本的官方文档为准。「找不到位点时从哪开始」和「重置位点」是两件事，前者是首次上线行为，后者是事故处置手段，不要混谈。

面试追问：RocketMQ 的位点和 Kafka 的位点最大的差别是什么？

答题骨架：三点，按重要性排。

  1. 位置不同。 Kafka 把位点做成集群内部的保留数据，任何人可查可改；RocketMQ 默认放在消费者客户端本地文件，集群侧看不到。这直接改变了排障的第一个动作：从「describe 一个组」变成「上实例看位点文件」。
  2. 提交时机不同，所以丢失窗口不同。 Kafka 的自动提交按 poll 位置推进，位点代表「读到哪了」而不是「处理到哪了」，因此天然有丢消息窗口；RocketMQ 的位点跟随消费结果提交，默认形态下窗口小得多。但要注意这不等于 exactly-once，重试与重启仍会带来重复，去重责任见 事务边界与去重约束。
  3. 粒度多了一个维度。 Kafka 只有一种粒度（组 + 分区）；RocketMQ 因为广播模式的存在，多出「实例 + 队列」这一层。同一个组名下可以既有共享位点又有各自位点，配置时必须显式指定消费模式，不能靠默认推断。

三、推模式本质是拉

RocketMQ 没有真正的推模式。 数据流向永远是客户端发起，Broker 从不主动连消费者。所谓 PushConsumer，是客户端在内部封装了「长轮询拉取 + 本地线程池回调」之后呈现出来的形态。

PushConsumer 的真实动作可以拆成四步：客户端发起拉取请求，Broker 挂起这个请求等待新消息，有消息时立即返回，客户端把返回的消息塞进本地线程池回调业务代码。业务代码是被动被调用的，但消息是被主动拉来的。

维度PushConsumerPullConsumer
谁发起请求客户端客户端
业务代码怎么拿到消息实现监听器回调，被动接收自己调用拉取接口，主动拿到消息后自己处理
拉取节奏交给客户端内部逻辑完全自己控制
批大小与本地缓冲由客户端内部策略决定自己定，可以完全不做缓冲
何时进入业务代码客户端投递进线程池之后拉到就处理，没有中间层
退化成短轮询做不到，内部是长轮询可以，主动不用长轮询接口
典型用途绝大多数业务场景需要自定义批量、背压、串行化编排，或需要与分布式锁配合

5.x 的 Proxy 让这件事更清楚：客户端经 gRPC 接入 Proxy，连接管理、协议转换、请求转发都在 Proxy 侧，Broker 不为每个消费者维护订阅状态。这是 Broker 能随意扩缩、下线不需要通知客户端的前提，也是「推」这个形态在实现上必须由客户端封装的原因。

面试追问：有人说「RocketMQ 是推的所以实时性比 Kafka 好」，对吗？

答题骨架：不对，这个说法把形态当成了机制。

  1. 数据流向永远是客户端发起。 推只是把长轮询包了一层，Broker 侧没有一条通向消费者的推送通道。
  2. 实时性来自挂起与唤醒，不来自推送。 消费者发出请求后请求被挂起，新消息写入时立即唤醒并返回，延迟接近于零；Kafka 的 poll 发 FETCH 同样能拿到这个效果，机制一模一样。
  3. 两种形态的差别在客户端。 RocketMQ 多给了一层封装，代价是多一跳本地线程池调度，收益是业务代码只写回调；Kafka 要求业务自己管循环，所以更容易在应用层做精细控制。

补充一句能拉开分差的：需要「先抢到分布式锁再开始拉取」这类编排时，PushConsumer 做不到，只能用 PullConsumer。选 Push 还是 Pull，取决于要不要控制拉取时机，不取决于实时性。

四、Pull 长轮询机制

长轮询是「推」的真正内核。客户端发出拉取请求后，Broker 的处理分三条路径：有可消费消息立即返回；没有就把这个请求挂起而不是立刻返回空；挂起期间有新消息写入且通过过滤，则立即唤醒并返回；挂起到期仍无消息，才返回空。

返回空不是错误，它只表示「这一轮没有新消息」。 把它当异常处理是初学者最常见的误判，症状是日志里刷满异常但业务其实正常。

事项说明
长轮询解决的没有新消息时的等待问题。延迟从「轮询间隔量级」降到「消息写入即刻」
长轮询不解决的一次取多少（由批量配置决定）、取到哪（由位点决定）、空转时的本地 CPU 开销
没有长轮询会怎样客户端只能自己定轮询间隔，延迟与间隔同量级，且 Broker 反复处理空请求
挂起时长长轮询的等待上限由服务端定时器决定，⚠️ 默认值随版本变化，以你所用版本的官方文档为准
5.x 下的差异客户端经 gRPC 接入 Proxy，挂起发生在客户端到 Proxy、Proxy 到 Broker 两段中的哪一段随版本演进，具体以官方文档为准

面试追问：长轮询和普通轮询的差别到底在哪？

答题骨架：差在「Broker 收到空请求时做什么」。普通轮询是立刻返回空，客户端睡一觉再问，延迟等于间隔量级，Broker 还要反复处理无效请求。长轮询是把这个请求挂起，新消息写入时主动唤醒并返回，延迟接近零、空转几乎不耗服务端资源。代价是服务端要为挂起的请求保留状态，所以挂起时长有上限，超时必须返回空，客户端要能正确处理这种正常返回。

五、为什么过滤必须放在 Broker 端

若在客户端过滤，机制上是可行的，但代价有三层，每一层都实打实。

第一，无关消息照样传输、照样占用客户端内存。 客户端过滤意味着 Broker 必须把所有消息都发过来。堆积十万条时，其中九万条与该消费者无关，这九万条仍然要走网络、仍然要进客户端堆内存、再在客户端被丢掉。客户端变成了第二个 Broker，而它没有 Broker 的存储能力。

第二，位点无法精确表达「这一批一条都不要」。 客户端过滤时，位点仍然要跨过这些消息，但服务端不知道它们被丢掉了，于是「消费进度」这个数字开始和「业务实际处理进度」脱节。要修正就得客户端自己记账，记账又和位点提交分成两套状态，故障时对不齐。Broker 端过滤让无关消息根本不进入消费序列，位点跨过的每一条都是真正处理过的消息。

第三，过滤码在索引里，服务端可以在只读定长索引阶段就完成判定。 ConsumeQueue 的每条元信息里带着标签过滤码，这是定长结构且不含消息体。服务端判不命中就不用去 CommitLog 取消息体，一次磁盘读都省掉。 这是 RocketMQ 存储布局直接换来的收益，详见 CommitLog、ConsumeQueue 与 IndexFile 第三节。

旧版做法

早期 RocketMQ 用独立进程 FilterServer 承担消息过滤，Broker 把过滤请求转发给它。这套机制已被 RocketMQ 5.x 的 Proxy + Tag/SQL92 过滤链替代：过滤现在在 Broker 与 Proxy 侧按 Tag 或 SQL92 完成，不再需要额外部署 FilterServer 进程。面试里说清代价差异即可，旧方案多一个需要部署、监控、扩缩容的进程，且过滤表达能力有限。

六、Tag 过滤

Tag 是消息自带的标签，订阅时给出表达式：全量订阅用通配写法，多个 Tag 用分隔符并列。语义稳定，可以在面试里直接写结论。

维度说明
打标位置生产侧，Tag 随消息一起进入 CommitLog 与索引
匹配方式精确匹配或全量订阅，没有范围与比较
求值位置服务端。订阅关系里的表达式被下推给 Broker
表达力只能表达「这一类消息我要」或「全部都要」
变更性Tag 随消息发出即不可改。改 Tag 等于发一条新消息，下游按 Tag 分流的逻辑会静默失效

一个订阅要多个 Tag 时的细节，是过滤必须在服务端的直接证据。 客户端没法只报一个过滤码集合去换消息，因为「A 或 B 或 C」不是一个可枚举的定长码值；必须由服务端按订阅表达式求出命中集合再筛选。表达式求值这件事天然长在服务端。

七、SQL92 过滤

SQL92 过滤是 5.x 的表达式过滤：把过滤条件当成 SQL92 的一个子集下推给 Broker，用属性级条件表达「这条消息我要不要」。

维度Tag 过滤SQL92 过滤
表达能力标签相等或全量数值比较、范围、IS NULL、IN、AND / OR / NOT、括号组合
求值位置服务端服务端
配置成本低，几乎零成本需要服务端具备表达式过滤能力并为目标 topic 声明过滤表达式
服务端成本低，索引里的过滤码比对即可每次拉取都要求值，条件越复杂、扫描面越大成本越高
适用按业务类别分流按数值区间、时间、状态字段等属性条件筛选

前提条件里的开关与配置项名称随版本演进，以你所用版本的官方文档为准。

Tag 过滤是 SQL92 过滤的退化形态：能力更弱但成本更低，两者都在服务端完成，差别只在表达力与运维成本。决策规则很朴素：

需求选择
按业务类别分流，同类别就是同一条业务含义Tag
需要数值区间、时间窗口、状态字段判断SQL92
两者都不够（要跨消息聚合、要关联查询）业务侧过滤，但要明确接受网络与内存代价，并重新评估位点记账

代价必须一起说：表达式过滤把服务端从「按索引比对」升级成「按条件求值」，写得越宽泛，越接近全量扫描。 建议是能用 Tag 就不上表达式，上表达式就尽量写成能被属性索引直接命中的形态。

八、面试高频追问

1. RocketMQ 有消费组吗？和 Kafka 消费组有什么区别？

答题骨架：有，集群消费模式下的消费组与 Kafka 消费组承担同样的职责，都是「组内共享进度 + 按队列独占分配 + 成员变化重新分配」。三点差别：一是分配单位从分区换成队列；二是位点默认存在客户端本地而不是集群内部，运维可见性差一档；三是 RocketMQ 多一种广播模式，位点不共享，因此消费组的语义只在集群模式下成立。详见第一节。

2. 集群消费和广播消费怎么选？

答题骨架：按「这份数据需要被处理几次」选。需要且只需要处理一次，用集群消费；需要每个节点都处理一次（缓存预热、配置广播），用广播。要主动说两个代价：广播模式没有故障转移，实例停了就停在那儿；广播模式重启会全量重放，因为进度不共享。

3. RocketMQ 有真正的推模式吗？

答题骨架：没有。推是客户端对长轮询的封装，消息永远由客户端发起拉取。Broker 侧没有通向消费者的推送通道。选 Push 还是 Pull 取决于要不要控制拉取时机（抢锁后再拉、需要自定义批量与背压就要用 Pull），不取决于实时性。详见第三、四节。

4. 为什么过滤必须在 Broker 端做，不能在客户端过滤？

答题骨架：三条代价，按重要性排。一是无关消息照样传输与占用客户端内存，客户端变成第二个 Broker。二是位点会与业务处理进度脱节，「已消费」这个数字不再等于「已处理」。三是 ConsumeQueue 的定长条目里带过滤码，服务端判不命中就完全不读消息体，省掉一次磁盘读。第三条是 RocketMQ 存储布局换来的独有收益，Kafka 那边没有对应物。

5. Tag 过滤和 SQL92 过滤有什么区别，什么时候用哪个？

答题骨架：Tag 是标签相等或全量，成本几乎为零；SQL92 是 SQL92 子集的属性条件，能表达数值区间、状态判断与逻辑组合，但每次拉取都要服务端求值，配置成本与服务端成本都更高。Tag 是 SQL92 的退化形态。决策规则：能按业务类别分流就用 Tag，需要字段条件才上表达式，两者都不够才考虑业务侧过滤并接受网络与内存代价。

6. 消费慢了加消费者行不行？

答题骨架：先看是哪个闸门在挡。RocketMQ 的消费并行度 = min(可分配的队列数, 消费者实例数 × 每实例消费线程数)。队列数不够时加实例完全无效；队列数够但每实例线程数远小于队列数时，加实例同样无效。这与 Kafka「加实例只能加到分区数」不同：Kafka 只有一个闸门，RocketMQ 有三个。 再叠加一句：加队列只改消费分配、不动写路径，照搬 Kafka 的「加分区」口诀是错的。

7. 位点存在哪？为什么重启能续上？广播模式重启会怎样？

答题骨架：位点默认持久化在消费者客户端本地，集群模式按「消费组 + 队列」存、广播模式按「实例 + 队列」存。重启能续上的前提是位点文件还在、且实例标识没有变化；把位点集中存到服务端需要显式开启远程位点存储。广播模式重启因为进度不共享，等于从零开始全量重放。运维可见性因此比 Kafka 差一档：Kafka 能直接 describe 一个组看每个分区的 lag，RocketMQ 默认只能登到实例上看。

8. RocketMQ 的队列数和 Kafka 的分区数是一回事吗？

答题骨架：不是，这是本题的核心。分区自带一整条独立日志，是物理分片；队列只是 CommitLog 之上的逻辑视图，不拥有独立数据文件。因此「加分区」同时扩写与扩读，「加队列」只改消费分配。Kafka「并行度上限 = 分区数」能当运维口诀用，正是因为单位是物理分片；RocketMQ 形式上一样的规则照搬过来会得到一个看起来生效但写路径毫无变化的结果。 存储侧的推导见 CommitLog、ConsumeQueue 与 IndexFile 第六节。
