重试、死信与消费堆积

来源

基于 RocketMQ 5.x 官方文档的 consumer、remoting 特性页与客户端消费失败处理路径整理。5.x 主线架构为 Proxy 加 gRPC 接入，Broker 侧的高可用协调由 Controller 模式承载。数值口径：本篇涉及的消费线程数上下限、死信队列保留窗口、延迟级别总表等条目，在事实清单中处于「尚未核实」或「只给语义不给数值」档位，因此不给出具体数值，只写语义与机制。

消费重试次数相关的事实已升级为 A 级，可直接引用并标注适用大版本：retryMaxTimes、maxReconsumeTimes 的真实位置与 -1 的两种展开值、retryQueueNums、DLQ_NUMS_PER_GROUP、Broker 侧覆盖优先级与进 DLQ 判定、顺序锁特殊路径、delayLevel 算法。本篇凡引用这些值均标注「RocketMQ 5.x 源码默认」；凡出现 C 级配置处仍附「默认值随版本变化，以你所用版本的官方文档为准」。

消费失败之后消息去哪、什么时候放弃、放弃之后怎么捞回来，这三件事 RocketMQ 全部做成了服务端结构，而 Kafka 全部留给应用。这是两库在消费侧最实质的取向差别之一。理解这个差别之前，先记住一句：RocketMQ 里有三个都叫「重试」的东西，层次完全不同，答错层次是这道题最常见的失分点。

一、消费失败后的重试链路

1.1 先分清三层「重试」

层次触发点消息去哪谁负责可观测性
客户端原地重试消费回调抛异常或返回失败回到 Broker 的重试队列Broker 侧重发消费组视图可见
消费重试队列消费回调返回失败且未超过重试次数上限消息被延迟重投回原队列Broker 侧调度消费组视图可见
死信队列超过最大消费重试次数消息进入死信队列，不再自动投递人工或工具死信视图可见

这三层之外还有第四个容易混进来的东西：生产侧重试队列，是生产者把消息重新投向 Broker 时用的，与消费侧同名不同层，机制在 发送流程、可靠性配置与重试 第五节。

1.2 一条失败消息的完整走向

  1. 客户端从队列取到消息，交给业务回调处理。
  2. 回调返回失败（抛异常、超时、显式返回非成功都算），客户端不认为这条消息已消费，位点不推进到它之后。
  3. 消息被重新投递给 Broker 上的消费重试队列，同时消息上携带的重试计数加一。
  4. 到达延迟后重投回原队列的尾部，等同一条新消息被同组重新消费一次。
  5. 重试计数未超上限则回到第 2 步；超过上限则转入死信队列，等待人工介入。

重试不是原地无限重试。 这是与「在客户端 while 循环里一直重试」的第一层区别：重试动作发生在服务端，客户端不阻塞，业务线程不会被一条毒消息占住。

1.3 「重试 16 次」这句话的适用边界

「RocketMQ 默认重试 16 次」是流传最广、也最容易答错的一句。准确表述只有一句：并发消费、且用户没有显式设置 maxReconsumeTimes 时，客户端与 Broker 双侧默认恰好都是 16。顺序消费完全不同。

层次位置RocketMQ 5.x 源码默认
消费端预算DefaultMQPushConsumer.maxReconsumeTimes 字段-1，含义是「用默认值」，不是「不重试」
-1 在并发消费展开为DefaultMQPushConsumerImpl16
-1 在顺序消费展开为ConsumeMessageOrderlyServiceInteger.MAX_VALUE，约 21.4 亿次，实际等于永不进 DLQ
Broker 订阅组预算SubscriptionGroupConfig.retryMaxTimes16
Broker 侧重试队列数SubscriptionGroupConfig.retryQueueNums1
Broker 侧每组死信队列数DLQ_NUMS_PER_GROUP1

三点必须说清：

  1. maxReconsumeTimes 已经是消费端字段，不是 Broker 配置项。 5.x 里它是 DefaultMQPushConsumer 上的一个 int 字段，默认 -1。答成「在 broker.conf 里配」是版本错位。
  2. -1 是哨兵值，展开结果取决于消费模式。 同一个 -1，并发消费展开为 16，顺序消费展开为 Integer.MAX_VALUE。所以「重试多少次」这个问题不问消费模式就没有答案。
  3. 16 之所以成立，靠的是双侧默认值恰好一致。 客户端展开出 16 并随请求头上报，Broker 侧订阅组默认也是 16。任一侧被显式改动，最终次数就以改动后的为准 —— 这正是下面覆盖优先级的意义。

1.4 同一套计数，谁说了算：Broker 侧的覆盖优先级

Broker 决定一条失败消息进不进 DLQ 时，取值有两个来源，请求头优先：

优先级来源生效条件
高客户端请求头 maxReconsumeTimesremoting 协议版本 ≥ 3.4.9（此处是协议版本，不是 RocketMQ 发布版本号）
低subscriptionGroupConfig.getRetryMaxTimes()上面拿不到时的回落

Broker 侧的进 DLQ 判定是 reconsumeTimes >= maxReconsumeTimes。顺序消息另有一条独立路径：检测到未过期的顺序锁记录就直接判死信，不看次数。 含义是这批消息正被顺序消费流程持有，其他线程再去并发处理就是破坏顺序，Broker 宁可隔离它也不让它插队。

由此得到一个反直觉结论：顺序消费拿到 Integer.MAX_VALUE 的重试预算，却仍然会有消息进 DLQ。 预算极大不等于不会死信，顺序锁那条路径根本不看预算。推导见第四节。

1.5 与 Kafka 的对照

面试追问：说「RocketMQ 默认重试 16 次」。这句话哪里不对？

答题骨架：先认错，再分四层。

  1. 16 只对并发消费成立。 maxReconsumeTimes 在 5.x 是 DefaultMQPushConsumer 字段、默认 -1；-1 在并发消费展开为 16，在顺序消费展开为 Integer.MAX_VALUE，实际等于永不进 DLQ。
  2. 16 是双侧默认凑巧一致的结果。 客户端展开出 16，Broker 订阅组 retryMaxTimes 默认也是 16。remoting 协议版本 ≥ 3.4.9 时请求头优先于 Broker 配置，用户改过任一侧就以改动后的为准。
  3. 位置变了。 说成 broker.conf 里的配置项是 4.x 时代的印象，5.x 里它已经是消费端字段。
  4. 顺序消费仍会死信。 预算极大，但命中未过期的顺序锁记录时直接判死信，不看次数。
维度RocketMQKafka
失败重试由谁做Broker 侧重投回原队列应用侧自己做，Kafka 没有服务端重试队列
重试节奏按重试次数走阶梯式延迟由应用自己定，通常是立即重试或固定间隔
重试消息对消费组可见吗可见，回到原队列被同组重新消费取决于应用实现，常见做法是留在本地重试不重发
超过上限后进死信队列，服务端可见、可查没有死信队列，跳过坏消息与旁路存储都由应用实现
优势隔离与可观测由服务端承担，坏消息不会静默消失模型简单，重试策略完全自由
代价失败消息被延迟拉长，且在等待期一直占着堆积统计坏消息的处理是每个应用各写一遍，漏写就是静默丢失或无限循环

这张表是本篇最该记住的对照。Kafka 侧要做「跳过坏消息 + 旁路存储」，必须自己在应用里实现重试上限与旁路 topic，漏了就是死循环；RocketMQ 侧这件事是服务端默认行为。 机制对照见 顺序消费与积压处理 第八节第 1 条。

面试追问：RocketMQ 的消费重试和 Kafka 的消费重试有什么不同？

答题骨架：分四层答。

  1. 执行位置不同。 RocketMQ 在 Broker 侧重投，客户端回调失败就返回，不阻塞业务线程；Kafka 全在应用侧，poll 循环里要自己决定是重试、跳过还是攒着重发。
  2. 节奏不同。 RocketMQ 按重试次数走阶梯式延迟，越往后间隔越长，给下游恢复留出时间；Kafka 侧节奏是应用自己写的，通常是立即重试，容易在下游故障时打成一个死循环。
  3. 有无收口不同。 RocketMQ 有服务端死信队列，超过上限自动隔离、可查可捞；Kafka 没有，「跳过」必须应用自己实现上限与旁路，漏写就变成无限重试。
  4. 对堆积的影响不同。 RocketMQ 的重试消息在等待期内计入该队列的堆积，读指标时容易把「正在重试」误判成「消费能力不足」；Kafka 侧本地重试根本不会体现为 lag 增长，所以它的堆积指标更干净但也更不诚实。

二、重试队列的层级设计

2.1 重试队列不是一条物理队列

「重试队列」这个名字容易造成误解。它不是一条独立的物理队列，而是一组部署在 Broker 上的队列，按延迟级别分层，每层对应不同的延迟档位，消息被投到哪一层取决于它当前的重试次数。

设计点语义为什么这么设计
按消费组隔离每个消费组有自己的重试队列不同消费组的失败消息不该互相看到；同一消费组的不同订阅也要能分开统计
按延迟级别分层重试间隔随次数增长给下游留出恢复时间，避免故障期间所有重试同时打过去
落回原队列重投回原 topic 的原队列消费组本来就订阅原 topic，重投即被正常消费，客户端不需要特殊分支
消息自带重试计数每重投一次加一，与消息一起流转计数跟着消息走，Broker 只需要读一个属性就能判断该不该进死信
队列数与原队列对应一个消费组在一个 Broker 上的原队列，对应它在该 Broker 上的重试队列让重试消息回到正确的 Broker，无需跨 Broker 路由

延迟级别不是随版本漂移的模糊语义，5.x 源码里是明确的算式：delayLevel = 3 + reconsumeTimes（RocketMQ 5.x 源码默认）。第一次重试落在第 4 级，30 秒起，此后每重投一次级别加一、间隔随之拉长。

这就是「阶梯式退避」的精确形状：它不是可配的退避策略，而是延迟级别表的固定映射。 消息上带着的重试计数直接决定它落进哪一级，服务端不做任何额外判断。延迟级别总表（各级具体时长）随版本变化，⚠️ 以你所用版本的官方文档为准。

由此得到一个必须一起讲的推论：重试次数越多，单条消息的端到端延迟越长，而且这个增长是叠加的。 靠「多等一会儿自然就好了」兜底的业务，超时阈值必须把整条重试阶梯算进去，只按首次投递的耗时间去设阈值必然误判。

2.2 三个必须说清的边界

  1. 重试消息对消费组是可见的。 它回到原 topic 的原队列，同一个消费组能正常消费到。这一点与生产侧重试队列恰好相反，生产侧的重试消息在业务订阅范围之外，消费者看不到。「同名不同层」在这里又咬了一次。
  2. 重试会拉长端到端延迟，而延迟不可压缩。 阶梯式延迟意味着第 N 次重试的等待时间随 N 增长。一条消息重试到后期，端到端时延可能已经很长，但只要没进死信，业务侧就会一直等。告警与补偿逻辑必须把这段延迟算进超时阈值。
  3. 重试消息计入该队列的堆积统计。 大量重试会让堆积曲线看起来像「消费能力不足」，实际可能是下游故障导致的失败重试。区分这两者的判据是消费 TPS：能力不足时消费速率稳定但小于生产速率，被重试拖累时消费速率会明显塌陷。

三、死信队列 DLQ

超过最大消费重试次数的消息进入死信队列，它不再被自动投递，也不再被消费组正常消费。DLQ 是失败消息的终点，不是中转站。

维度说明
归属按消费组隔离。5.x 源码里每个消费组的死信队列数 DLQ_NUMS_PER_GROUP = 1（RocketMQ 5.x 源码默认）
进入条件（并发消费）Broker 判定 reconsumeTimes >= maxReconsumeTimes 即进死信
进入条件（顺序消费）另有独立路径：检测到未过期的顺序锁记录直接判死信，不看次数
之后的行为不自动投递，不参与位点推进，必须人工或工具介入
保留有一个保留窗口，过期后自动清理，⚠️ 具体时长随版本变化，以你所用版本的官方文档为准
重投代价重投即再发一遍，业务侧必须幂等，否则重复副作用

并发与顺序的判定符差 1 次，这条细节别丢。 顺序消费用 >= 判定，并发消费用 > 判定（RocketMQ 5.x 源码默认）。同样一组 reconsumeTimes 与 maxReconsumeTimes，两条路径在临界点上会差出一次重试机会：并发侧要多失败一次才进死信。写方案里的重试次数预算时，这个 1 次的差异会直接改变「第 N 次失败是否还救得回来」的判断。

3.1 排查顺序

第一步分组是关键：死信里如果只有少数标识反复出现，那是脏数据或已废弃的业务对象；如果是大部分标识一起失败，那几乎一定是下游的问题，重投只会再失败一轮。

3.2 与 Kafka 的对照

Kafka 没有死信队列。跳过坏消息这件事在 Kafka 上必须由应用自己实现：设重试上限、超过就写进一个旁路 topic 或标记状态表、然后继续消费。这是应用侧成本，每个应用各写一遍，漏写就是无限重试或者静默丢弃。 RocketMQ 把它做成了服务端默认行为，代价是失败消息的处置流程变成了运维动作而不是代码逻辑。

四、顺序消费为何不能重试

顺序消息的消费失败不能进重试队列。 原因是重投会打乱队列内的顺序：第 N 条消息在重试等待中，而第 N+1 条已经消费成功，业务侧看到的状态就是「第 N+1 步生效了，第 N 步没生效」。对一个状态机来说这通常比顺序错乱更难恢复。

4.1 顺序消费拿到的是 Integer.MAX_VALUE 预算，但它仍然会死信

事实项RocketMQ 5.x 源码默认
顺序消费下 maxReconsumeTimes 默认 -1 展开为Integer.MAX_VALUE（约 21.4 亿次）
实际含义几乎等价于永不因次数耗尽而进 DLQ
顺序消费进 DLQ 的判定符>=（并发消费用 >，边界差 1 次）
顺序消息另一条死信路径未过期的顺序锁记录 → 直接判死信，不看次数

这张表看着矛盾，其实不矛盾：预算是「次数耗尽才死信」的天花板，而顺序锁那条路径根本不看天花板。 所以顺序消费的消息进 DLQ 时，原因几乎不会是「重试次数用完」，而是「撞上了别人正在顺序消费的队列」。

排查顺序消费的死信时，先查锁，别先查次数。 这是本节最省时间的一条：按重试次数去找原因，在顺序消费场景下方向就是错的。

三条出路，各有代价：

出路做法代价
业务侧兜底本地记录失败，用对账或补偿任务把它补上，然后继续消费需要额外的状态存储与对账机制；对外表现为「状态延迟到达」而不是「失败」
判定为终态并记账跳过把这条判为不可恢复，跳过并留下记录破坏严格顺序，后面的消息会先生效；需要业务明确同意
放弃顺序改并发消费 + 下游按版本号或状态机兜底破坏业务不变量，只适合业务本就能容忍乱序的场景

这解释了顺序消费最典型的积压成因：它几乎总是被一条失败消息静默卡住，而不是吞吐不足。 被卡住时进程健康、位点还在、没有任何报错，唯一的表现是该队列的位点不再推进、堆积持续上涨。Kafka 侧的同类陷阱见 顺序消费与积压处理 第四节第 2 条，两边的机制不同（Kafka 是应用侧重试插队，RocketMQ 是服务端没有给顺序场景开重试的口子），但结论一致：顺序消费必须自己做失败处置。

第三道闸门最容易被跳过。消化堆积的本质是短时间内对下游施压，下游扛不住时，扩容只是把故障从「消息来得慢」换成「下游被打挂」。

六、应急处理与跳过消费的取舍

按「安全性」从高到低排。应急手段的第一原则：任何会产生数据缺口或破坏顺序的操作，都必须先确认业务能接受。

手段做法收益代价与风险
扩消费者实例组内加实例提高并行度受队列数与线程数双重限制，见第五节三道闸门；下游可能被打垮
扩队列调整 topic 队列数提高可分配的并行度只改消费分配，不动写路径；会改写业务 key 到队列的映射，破坏顺序消息的保证
提高单条处理速度批写、异步化非关键路径提高单队列吞吐批内耗时上升，单队列推进变慢；不解决被卡住的情况
上游限流让生产者降速直接缩小缺口需要跨团队协调，影响其他消费方
按时间跳过重置位点到指定时间之后立刻放行，堆积清零数据缺口，跳过期间的消息不再被消费。必须业务确认 + 留记录
放宽或关闭过滤临时改订阅表达式让原本被过滤的消息进来流量激增；若这些消息正是压垮下游的原因，等于加速故障
重投死信消息修好下游后把死信重新投递补回被放弃的数据业务必须幂等，否则重复副作用；死信保留窗口有限，晚了就没了

三个必须点明的认知：

  1. 跳过的代价是看不见的。 跳过让指标立刻变好，问题延后爆发在下游。执行前确认数据可丢，执行后留记录，并安排事后补数。
  2. 顺序消费场景下跳过更贵。 被跳过的消息不会再生效，而它后面的消息会先生效，破坏的是业务不变量而不只是数据完整性。这类场景优先考虑第五节的第三条出路（业务侧兜底），而不是跳过。
  3. 死信是补数的主要来源，但不是全部。 被跳过的消息如果没有进死信就彻底消失了，只能靠下游对账或重新灌数找回来。所以跳过的范围要尽量小，并且逐条记录跳过了什么。

七、面试高频追问

1. 一条消息消费失败之后，在 RocketMQ 里会走哪条路？

答题骨架：回调返回失败，位点不推进，消息被投到该消费组的消费重试队列，重试计数加一；到达延迟后重投回原队列被同组重新消费。计数未超上限就继续循环，超过最大消费重试次数就进死信队列，不再自动投递，等人工或工具重投。延迟级别是固定映射 delayLevel = 3 + reconsumeTimes，第 4 级 30s 起（RocketMQ 5.x 源码默认）。关键一句：重试发生在 Broker 侧，业务线程不阻塞。 次数上限：并发消费下客户端与 Broker 双侧默认都是 16，Broker 判定 reconsumeTimes >= maxReconsumeTimes；顺序消费的预算展开为 Integer.MAX_VALUE，且另有顺序锁直判死信路径——所以这句「16 次」绝不能脱离消费模式引用。

2. RocketMQ 的消费重试和 Kafka 的消费重试有什么区别？

答题骨架：四层。执行位置（Broker 侧 vs 应用侧）、节奏（阶梯式延迟 vs 应用自定）、有无收口（有死信队列 vs 无，坏消息处理是应用成本）、对堆积的影响（重试消息计入堆积，容易误判为消费能力不足）。详见第一节第 5 小节。

3. 顺序消息消费失败了为什么不走重试队列？

答题骨架：重投会把消息甩到队列尾部，第 N 条在重试而第 N+1 条已消费成功，业务看到的状态顺序就乱了。顺序消费失败只能在当前队列上做有限的本地重试，耗尽后不再自动重投，该队列后续消息全部停等。出路只有三条：业务侧兜底加对账、判定终态并记账跳过、放弃严格顺序改并发加下游兜底。这也是顺序消费堆积几乎都由失败卡住而非吞吐不足造成的直接原因。

4. 消费堆积了，加消费者行不行？

答题骨架：先过三道闸门——队列数够不够分、每实例线程数够不够、下游扛不扛得住。再判形态：消费速率稳定但偏小是能力不足，扩容有效；速率塌陷、位点几乎不动是被重试或被某条消息卡住，扩容无效，要先查死信队列。第三句必须说：加队列只改消费分配、不动写路径，别照搬 Kafka 的「加分区」口诀。

5. 怎么把一条坏消息跳过去？代价是什么？

答题骨架：按时间或按位点重置消费进度，让位点跨过它。代价是数据缺口：这条消息及其后到跳过点的消息都不再被消费，指标立刻变好但问题延后在下游爆发。执行前必须确认业务可丢并留下操作记录，执行后要安排补数（死信里如果有，靠重投；没有的话只能靠下游对账或重新灌数）。顺序消费场景下代价更大，因为跳过的消息不生效而它后面的会先生效，破坏的是业务不变量。

6. 死信队列里的消息怎么捞回来？

答题骨架：先分组判断性质。少数标识反复失败是脏数据或已废弃对象，多数一起失败基本是下游故障。修好之后用工具或人工重新投递，重投即再发一遍，业务侧必须幂等。另外死信有保留窗口，过期自动清理，⚠️ 时长随版本变化以官方文档为准，所以发现堆积要尽快处理而不是排队等运维窗口。

7. 堆积指标怎么读？有什么读不出来的？

答题骨架：RocketMQ 侧按消费组、主题、队列三个维度看未消费条数，消费 TPS 与位点推进速度作为判据。读不出来的有两类：一是广播模式没有共享位点，按组汇总的堆积失去意义；二是重试消息计入堆积，光看堆积会把「正在重试」误判成「消费能力不足」，必须配消费 TPS 才能分辨。与 Kafka lag 的口径差异见第五节第一张表。

8. 「RocketMQ 默认重试 16 次」对吗？顺序消费也是 16 吗？

答题骨架：这句话不能无条件引用，它有三个漏洞，按顺序拆。

  1. 16 只对并发消费成立。 maxReconsumeTimes 在 5.x 已是消费端 DefaultMQPushConsumer 的字段，默认 -1，含义是「用默认值」而非「不重试」。-1 在并发消费展开为 16，在顺序消费展开为 Integer.MAX_VALUE（约 21.4 亿次），实际等于永不进 DLQ。
  2. 16 靠双侧默认一致。 客户端 DefaultMQPushConsumerImpl 展开出 16 并随请求头上报，Broker 订阅组 retryMaxTimes 默认也是 16。remoting 协议版本 ≥ 3.4.9 时请求头 maxReconsumeTimes 优先于 subscriptionGroupConfig.getRetryMaxTimes()，所以用户改过任一侧，最终次数就以改动后的为准。
  3. 判定符还差 1 次。 顺序消费用 >=，并发消费用 >，临界点上并发侧多一次重试机会。
  4. 顺序消费仍然会死信。 它的预算极大，但命中未过期的顺序锁记录时直接判死信，不看次数——所以顺序消费的死信几乎不会是「次数用完」，排查要先查锁。
