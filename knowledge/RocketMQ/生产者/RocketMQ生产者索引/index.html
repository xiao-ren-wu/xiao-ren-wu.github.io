RocketMQ 生产者索引

本页用途

生产者这一层回答三个问题：一条消息从调用发送 API 到拿到结果，中间究竟发生了什么；「重试」这个动作在 RocketMQ 里其实有哪两个层次；以及事务消息、延时消息、顺序消息这三项 RocketMQ 独有的特性各自换来什么、付出什么。读完这两篇，能独立讲清「消息为什么丢了、为什么重了、为什么没按顺序到」。

本篇笔记

笔记一句话说明何时读

关键结论

  1. RocketMQ 生产者独有的三项特性是事务消息、延时消息、顺序消息。 Kafka 侧目录里虽然有「事务」二字，但那是 Kafka 内部跨分区跨主题的原子可见性，与业务本地事务无关；Kafka 用 linger.ms 加延迟队列的思路做延时，也没有客户端级「保证同 key 有序」的队列选择器接口。名字接近的三件事在两套库里解决的是不同问题，详见下面的逐条对照。
  2. 「重试」在 RocketMQ 生产侧有两个层次，指的不是同一件事。 一个是客户端在同一 Broker 上对同一条消息的重发，由发送方式与重试次数配置决定；另一个是把消息投递到 Broker 上的重试队列，用以熬过集群抖动导致路由失效的窗口。消费失败触发的消费重试队列是第三层，机制完全不同，详见 重试、死信与消费堆积。而生产侧重试默认不去重：Kafka 的生产者在重试路径上有 ProducerId 加序列号做去重，RocketMQ 生产侧没有等价的默认机制，因此「非幂等的消息被重试一次」在 RocketMQ 上就是业务侧要处理的一次真实重复，去重责任落在消费端与业务侧，见 事务边界与去重约束。
  3. 生产侧有两套重试机制，中文资料常把它们混为一谈，这是本主题最容易讲错的一处。 一套是 retryResponseCodes，走异常路径：Broker 返回的响应码落在重试码集合内时，客户端抛 MQBrokerException 才重试，这套默认就是启用的。另一套是 retryAnotherBrokerWhenNotStoreOK，走 SendStatus 非 OK 的正常返回路径，其源码默认值是 false，因此那三个失败态默认一个都不重试；改成 true 之后，非 SEND_OK 才换 Broker 重发。两套机制的触发条件、代码路径、开关默认值全都不同，详见 发送流程、可靠性配置与重试 第四节。
  4. 发送结果不是二值成功失败，而 SendStatus 枚举完整只有 4 个取值。 SEND_OK、FLUSH_DISK_TIMEOUT、FLUSH_SLAVE_TIMEOUT、SLAVE_NOT_AVAILABLE。后三者属于「消息已进 Broker，但未满足落盘或复制判定」的不确定一类：直接当失败重发会造成重复，当成功接受则存在丢失窗口。枚举本身没有 javadoc，语义由消费点逻辑反推，标 B 级。判定规则见 发送流程、可靠性配置与重试 第七节。
  5. 数值口径分两档，不要再一律说「不给数值」。 发送侧与存储侧的多数配置默认值已完成源码核实，本主题两篇正文里凡标注「RocketMQ 5.x 源码默认」的数字都可以直接引用。仍未核实的只剩 sendMessageThreadPoolNums 与 syncFlushTimeout 两项，它们保持「默认值随版本变化，以你所用版本的官方文档为准」不变。另外要警惕**「同名不同值」**：defaultTopicQueueNums 在 Broker 侧与 Producer 侧是两个不同的默认值，这类项横向对比时最容易混用。
  6. 5.x 的客户端接入形态与 4.x 不同，失败判定的难度上升。 5.x 主线架构为 Proxy 加 gRPC 接入，客户端到 Proxy 多了一跳，Proxy 之后的写入失败对客户端可能只表现为超时。「超时」在 5.x 下更接近「结果未知」而不是「失败」，重试策略要按这个前提来设计。

一条消息的路程

学习顺序

  1. 先读 发送流程、可靠性配置与重试，因为它是整条链路的前半段，也是后一篇的前提。事务消息的 half 消息同样要走过刷盘与复制判定，延时消息的定时器到期投递也建立在同一套写入路径之上。不懂发送结果怎么判，后面的特性就只能背名词。
  2. 再读 事务消息、延时与顺序消息，因为这三项特性都是在「已经能把消息稳定发出去」这个前提上追加的语义。先建立稳定发送的心智模型，再看它如何被扩展。
  3. 读完后回到 RocketMQ 架构全景与角色分工，把链路里的每个角色对回架构。生产者的许多选择（为何能容忍路由最终一致、为何需要重试队列）都要靠 NameServer 无状态无共识这个前提才讲得通。
  4. 接着读 刷盘策略与内存映射 与 CommitLog、ConsumeQueue 与 IndexFile，补上「写进去之后放在哪」。发送侧的可靠性讨论会反复提到刷盘与复制，而这两件事的落点在存储层。
  5. 最后读 消息丢失场景与保障 与 主从复制与故障转移，把本篇的判定规则与保障手段接上。只讲生产者重试而不讲消费侧与 Broker 侧的保障，等于把整条链路只讲了开头。

常见误区

  • 把 RocketMQ 的事务消息说成「Kafka 事务消息的同类」。Kafka 事务管的是 Kafka 内部的跨分区原子可见与位点提交，RocketMQ 事务消息管的是业务本地事务与发消息的一致性，两者不是同一层问题。
  • 把两套重试机制当成一套。 retryResponseCodes 是抛 MQBrokerException 的异常路径，默认就生效；retryAnotherBrokerWhenNotStoreOK 是 SendStatus 非 OK 的正常返回路径，默认 false。混为一谈就会推出「刷盘超时会自动换 Broker 重发」这个错误结论。
  • 说「messageDelayLevel 是整数，默认 18」。 半错。源码类型是空格分隔的 String 时长表，「18 级」是 split 之后的索引推导结果，不是一个整数配置项。
  • 说「defaultTopicQueueNums = 4」。 只对 Producer 侧成立。Broker 侧同名配置的源码默认值是 8，TBW102 启动时按 8 建成，实际发送时取两者较小值。
  • 说「waitStoreMsgOK 是 Broker 配置项」。 它已不是配置项，而是逐条消息属性，缺省为 true；事务半消息会强制置为 false。
  • 看到「重试」就答「重试队列」。生产侧重试队列与消费侧重试队列同名不同层，混起来讲是高频错误。
  • 认为「重试保证了不重复」。生产侧重试在默认配置下不去重，重复是正常结果而不是异常。
  • 把刷盘超时当作失败直接重发。它属于结果不确定的一类，重发的代价是重复而不是找回消息。
  • 顺序消息只做了客户端选择队列就以为万事大吉。消费侧并发消费同一队列、失败重试阻塞、发送侧多实例同键竞争，都会破坏顺序，见 事务消息、延时与顺序消息 第七节。
  • 拿 RocketMQ 的配置默认值去和 Kafka 的默认值横向比较。两套库的默认值都随版本变化，必须各自查各自版本的文档。
