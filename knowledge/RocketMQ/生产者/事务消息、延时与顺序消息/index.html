事务消息、延时与顺序消息

来源

基于 RocketMQ 5.x 官方文档的 transaction message、delay message 特性页与客户端TransactionListener、MessageSelector 接口整理。5.x 主线架构为 Proxy 加 gRPC 接入、Broker 侧由 Controller 模式承载高可用协调。 数值口径：本篇的事务回查三项（transactionCheckMax、transactionTimeOut、transactionCheckInterval）与 messageDelayLevel 的类型和原始串已完成源码核实，直接写具体值并标注「RocketMQ 5.x 源码默认」。仍然不写的是「定时器/回查的实现精度」——5.x 定时器扫描间隔与回查调度的实际精度未核实，因此本篇只给这三项配置默认值，不给任何「实际会延迟多少毫秒」的结论。凡涉及该类配置处均附「默认值随版本变化，以你所用版本的官方文档为准」。

Kafka 侧也有一个叫「事务」的东西，名字接近，解决的却是完全不同的问题。这一篇先把这个坑填掉，再讲 RocketMQ 生产者独有的三项特性：事务消息、延时消息、顺序消息。普通发送的链路与失败判定在 发送流程、可靠性配置与重试。

一、事务消息要解决什么

1.1 问题的形状：两类失败不对称

业务代码要做的两件事是「发消息」和「提交本地事务」。它们分属两个系统，没有共同的提交点，于是出现两类方向相反的失败：

顺序第一步第二步失败后果
先发消息后提交事务消息已到 Broker本地事务回滚消费者收到一条业务上根本不存在的消息，下游据此做了动作
先提交事务后发消息本地事务已提交消息发不出去业务状态已变，下游永远不知道这次变更发生过

普通发送 API 对这两类都无能为力，因为它只负责「把消息写进 Broker」，并不知道业务事务的成败。

1.2 为什么 Kafka 的事务解决不了这件事

这是本主题最容易被面试官追着问的点，必须一次讲对。

Kafka 事务RocketMQ 事务消息
作用对象Kafka 内部的多个分区与多个 topic业务本地事务与消息发送之间的一致性
原子性范围一批消息对消费者要么全可见要么全不可见；消费位点可与生产动作一起提交一条消息与一次本地事务的最终状态对齐
涉及外部资源不涉及。数据库、缓存、第三方系统全在事务之外涉及。本地事务可以是任意关系型数据库的提交
能否替代不能不能。RocketMQ 事务消息不提供跨分区批量原子可见，也不提交消费位点

一句话切分：Kafka 事务的边界在消息系统内部，RocketMQ 事务消息的边界跨出消息系统。 两者互补，不互相覆盖。Kafka 侧机制见 幂等、acks 与事务。

1.3 事务消息给出的保证边界

它保证的是：当本地事务的最终状态可以被回答时，这条消息最终要么对消费者可见、要么永不出现。 注意前提是「可以被回答」。第四节会讲清「不能被回答」时会发生什么，这也是最容易被夸大成「绝对可靠」的地方。

二、half 消息的写入路径

half 消息是事务消息的中间态。理解它的关键只有一句：

half 消息对消费者不可见，但它已经落盘了。

三点必须说清，它们与普通消息的差别全在这里：

  1. 它走的是与普通消息完全相同的写入路径。 校验、选队列、写日志、建索引，一步不少。也就是说 half 消息同样会触发刷盘与复制判定，同样可能返回刷盘超时这类不确定状态。事务消息不是在普通发送外面套一层壳。
  2. 不可见的实现方式是「不让消费者读到」，不是「不写」。 消息在存储层是真实存在的，只是消费者的读取范围不覆盖它。这解释了为什么后续的提交与回滚可以很快完成：不需要再写一份数据，只需改变它的可见性。
  3. 不可见是有代价的。 从 half 消息写入到最终处置完成，这段时间内消息对消费者不可见。这段时间等于「本地事务耗时 + 处置往返」。事务越长，这段不可见窗口越长。顺序消息的原理见第七节，事务消息与它的组合使用见第八节。

但 half 消息在两个地方被显式区别对待，这两个细节是「事务消息为什么能成立」的关键：

事实值为什么
half 消息强制 setWaitStoreMsgOKfalse半消息写入成功即代表「已安全暂存」，不需要在这一步阻塞等落盘确认。状态判定交给之后的回查机制，所以不等待反而是必需的
SendStatus 三个失败态的映射FLUSH_DISK_TIMEOUT、FLUSH_SLAVE_TIMEOUT、SLAVE_NOT_AVAILABLE 一律映射为 LocalTransactionState.ROLLBACK_MESSAGE普通消息把这三个状态留给业务「先查再定」，事务消息保守回滚。半消息本来就不可见，回滚掉不损失任何下游可见性

第二条与普通消息正相反，是高频错点。 普通消息遇到「不确定」要查、要权衡；事务消息遇到同样的不确定直接判回滚。原因在于两者的兜底代价不同：普通消息已经对消费者可见，回滚等于制造不一致，所以宁可交给业务判定；half 消息还没人看得见，直接丢掉是安全方向。注意 waitStoreMsgOK 在 5.x 是逐条消息属性而不是 Broker 配置项，普通消息缺省为 true，详见 发送流程、可靠性配置与重试 第 2.1 节。

常见误解纠正：不是「先发消息成功、再撤销」。half 消息的存在是必需的，因为只有消息已经可靠地躺在 Broker 上，后续才有「处置」这个动作可做。如果第一步没写进去，本地事务回滚时就只能依赖业务侧自己去清理，而那正是事务消息要消除的场景。

三、本地事务与回查机制

客户端通过事务发送入口发起请求，并在回调里实现两件事：执行本地事务、报告它的结果。回调本身要区分三种结论：

回调返回的结论含义Broker 的处置
提交本地事务已成功消息转为对消费者可见
回滚本地事务已失败消息被丢弃，永不出现
未知现在判断不了暂不处置，转入回查流程

「未知」这一档是整套机制的核心。如果只有提交与回滚两种结论，Broker 就必须接受「客户端给的结论」作为最终答案，而客户端给出的结论恰好可能是在网络中断、进程崩溃这类时刻做出的猜测。允许返回「未知」，等于承认客户端无法保证自己一定知道结果，于是把裁决权交回 Broker，由它去问。

本地事务执行的常见错误写法是「执行完再报告，中途抛异常也报告提交」。 正确做法是捕获异常后报告回滚或未知，绝不能在事务实际失败时报告提交。异常路径上的这个返回值，是整套机制唯一的正确性来源。

客户端侧要实现的是一个事务状态监听器，承担两个回调：执行本地事务（返回上述三种结论之一）与回查本地事务状态（只回答状态，不再执行业务逻辑）。这个区分很重要：回查不允许再去做一遍业务动作，它只做状态回答。

四、回查的代价与局限

这是本特性最需要讲冷静的一节。回查不是「Broker 无限次问你直到你答对」，它有明确的代价与终止条件。

代价有五处，按重要性排：

  1. 回查有次数上限，达到上限后由兜底策略处置。 该上限是 transactionCheckMax，RocketMQ 5.x 源码默认为 15。要记住的是它的存在意义：回查不会永远进行，这条消息一定会得到一个终态处置，不存在永远悬着的 half 消息。
  2. 回查期间消息对消费者不可见。 本地事务慢，或者反复回查答不出，消息就迟迟不出现。现象是「下游一直没收到消息」，而上游业务其实早已完成。这是事务消息最典型的排障入口：先查本地事务耗时与状态可查性，而不是先怀疑消息丢了。
  3. 回查是 Broker 主动发起的额外往返。 每次回查都是一次跨进程调用，会增加 Broker 与生产者之间的交互量。本地事务越慢、未知状态越多，回查越频繁。
  4. 依赖「本地事务状态可查」。 进程重启后回查仍然会发生，此时只能靠持久化的状态记录回答。如果本地事务的结果只存在于内存，进程一重启就答不出，回查只能持续消耗预算直到上限。这是使用事务消息的前置条件，不是可选项。 落地方式通常是在本地事务的同一张表里写入一个状态字段，让回查有地方可读。
  5. 它不解决消费侧的重复。 事务消息对齐的是「消息」与「本地事务」，不是「消费」与「本地事务」。消费者读位点回退、消费组重平衡导致的重复仍然存在，那部分责任在消费侧，见 事务边界与去重约束。

4.1 三个回查相关配置：给默认值，但不给精度

事务回查的三个参数都已核实，可以直接引用：

配置项RocketMQ 5.x 源码默认作用归属类
transactionCheckMax15回查次数上限，达到后走兜底处置BrokerConfig
transactionTimeOut6000 毫秒（源码写作 6*1000）事务消息的判定超时时间BrokerConfig
transactionCheckInterval30000 毫秒（源码写作 30*1000）两次回查之间的检查间隔BrokerConfig

两个必须同时说清的点：

  1. 字段归属要写对。 曾有资料把这三个字段归到 TransactionCheckConfig 这个类，该类在 5.x 已经不存在，字段已并入 BrokerConfig。查资料时如果看到 TransactionCheckConfig，那是旧版结构。
  2. 这三个是配置默认值，不是实现精度。 5.x 定时器与回查调度的实际精度未核实，因此不能由「检查间隔 30000 毫秒」推出「消息一定在 30 秒内被回查一次」这类结论。间隔参数说的是「多久发起一轮检查」，实际触发时机还受调度实现影响。默认值随版本变化，以你所用版本的官方文档为准。

因此禁止的表述是把事务消息说成「绝对可靠」或「彻底解决一致性问题」。 准确的表述是：它把「消息已发出但业务回滚」这类不一致收敛掉，代价是引入一段不可见窗口与一次回查往返，而成立的前提是本地事务的最终状态可以被回答。前提不满足时，机制退化，这一点必须主动说出来。

五、延时消息：定时器机制

延时消息要解决的是「消息不能立即被消费，要等一个到期时间之后才可投递」。

实现路径可以概括为「先暂存，到期再投递」：

  1. 发送时在消息上标记延时属性
  2. Broker 校验该属性，把消息写进用于延时投递的暂存结构，而不是直接进入消费者可读范围
  3. 定时器周期性扫描，挑选出到期需要投递的消息
  4. 把它重新写入（或投递到）真实主题
  5. 消费者按普通消息消费

与传统写法的差异点在于第 2 步的暂存方式：早期版本按预设的级别把消息归入不同档位的队列，级别到点后统一转投；较新的实现引入了定时器能力，可以让到期时间表达得更细。两者的差别属于版本差异，本篇只描述「定时器到期投递」这一层语义。

三个必须说清的点：

  1. 延时不是「延迟消费」，而是「延迟可见」。 到期之前消息在 Broker 上，代价是存储占用，收益是消费者不必在线等待。消费者挂掉或消费慢都不会让消息过期。
  2. 到期不等于立刻被消费。 定时器只把消息送回真实主题，之后还要经过读取、拉取、业务处理这一整段。业务上观察到的到达时间一定晚于到期时间。
  3. 定时器是 Broker 侧的集中调度。 到期投递的精度受扫描间隔影响，不是「设了就准点触发」。见第六节。

六、延时精度与 messageDelayLevel

先划清一条界：延时消息的「精度」不是毫秒级的定时器，而是档位级的映射。 传统实现里，开发者指定的是一个「级别」，级别到时长的对应关系由 Broker 侧的 messageDelayLevel 定义。这带来一个直接后果：能表达的时间点是有限的集合，不是任意时刻。需要任意时刻的场景要靠定时器能力而不是靠调级别。

6.1 messageDelayLevel 的类型是 String，不是整数

这是本主题第二号易错点。「messageDelayLevel 是整数、默认 18」这个说法半错，错在前半句：

项目事实
源码类型String，不是 int
形态空格分隔的时长表，配置里写的是一串带单位的时长
RocketMQ 5.x 源码默认1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h
支持的时间单位s / m / h / d，5.x 的 parser 支持天
级别数量18 级，由上表 split 之后的索引推导得出
是否为配置项不是。它是运行时推导结果，配置里没有「级别数」这个字段

所以正确说法是：messageDelayLevel 是一张空格分隔的时长表，源码默认 18 个时长，18 级是 split 之后的推导结果，不是一个整数配置项。

配套的两条否定式事实，一并记清：

  • 不存在名为 defaultMessageDelayLevel 的配置项。 查不到是正常的，源码里没有这个东西。
  • 级别数由 maxDelayLevel 在 parseDelayLevel() 里运行时推导，不是读配置得到的。想改级别集合，正确的做法是改 messageDelayLevel 这张表本身。

表里能加 d（天）这件事值得单独提一句，因为很多二手文章按更老的印象说「最长只能配到小时级」，于是把超长延时（几小时后、几天后）误判为不可实现。实际上 5.x 的 parser 认天，日级延时不需要绕道。但这说的是「能配置多长」，不是「到期精度有多准」，两件事不要混。

6.2 精度受三段影响

影响段原因方向
定时器扫描间隔定时器按周期扫描，到期消息最多滞后一个扫描周期偏晚
级别映射级别本身是离散档位，指定的级别对应的是该档位的时长而非你想要的精确时刻偏晚或偏早
投递与拉取到期后还要走投递、消费者拉取、业务处理偏晚

5.x 定时器的实际实现精度未核实，因此本节只给「配置默认值」，不给「实际会偏多少毫秒」的结论。

所以「我设了延时它却早到了」通常不是 bug，而是级别映射的正常结果（选了比目标时刻更小的一个档位）。反过来「设了却没按时到」多数落在前两段，排查顺序是先确认级别选对了没有，再看定时器侧有没有积压。

两个使用建议：

  • 不要用延时消息做精密调度。 需要精确到某个业务时刻的触发（订单超时关单要用到秒级以上精度的场景），应改用外部调度系统（定时任务框架或分布式调度）加幂等检查。延时消息适合的是「大致在某个时间窗内可投递」。
  • 超长延时的消息会一直占着存储。 级别很大意味着消息可能在 Broker 上停留很久，磁盘与索引的占用是实时的。要评估的是这段时间内的消息量，而不是峰值 QPS。

七、顺序消息：MessageQueueSelector

RocketMQ 的 MessageQueueSelector 是一个客户端接口，属于「语义稳定、机制可写」那一档。它的作用非常单一：由业务代码提供一个选择函数，用业务键决定消息落到哪个 MessageQueue。

它只解决了一半问题。 完整保序需要两侧同时成立：

环节要求破坏后的现象
发送侧选择同一业务键经选择函数固定落到同一 MessageQueue同一实体的消息散到不同队列，顺序无从建立
队列写入同一队列内的消息按到达顺序追加队列本身是 FIFO，这一段天然成立
消费侧并发同一队列必须单线程串行消费并发消费直接破坏顺序
消费失败重试顺序语义下失败即阻塞，后来消息必须等若跳过失败消息继续往后消费，顺序就断了

四个破坏顺序的典型场景，面试常问：

  1. 同队列并发消费。 这是最直接的破坏。选择器保证了进哪个队列，但保证不了消费时只有一个线程。集群消费模式下多个消费者实例分摊队列，同一队列落到不同实例就可能并发处理。正确做法是让同一业务键对应的队列始终由单消费者实例串行处理。
  2. 失败重试。 顺序消费下，某个消息处理失败时不能跳过它去处理后面的消息，只能阻塞等待。因此顺序消息的重试代价是「队列停等」，这也意味着顺序消息的可用性与失败处理策略要一起设计，重试队列与死信机制见 重试、死信与消费堆积。
  3. 发送侧多实例用同一业务键。 多个生产者实例同时用同一个键发送时，消息在多个实例上并行发出，到达顺序由网络与线程调度决定，选择器救不了这一层。同一实体的生产应当集中或串行化。
  4. 队列扩缩容与路由变化。 业务键到队列的映射依赖当前的队列列表。队列数量变化后，同一业务键可能被映射到不同队列，迁移期的顺序就断了。顺序消息对拓扑变更的敏感度高于普通消息。

全局顺序只有一条路：全进一个队列。 代价是这一主题的有效并行度降到 1，吞吐塌陷。Kafka 侧的对照是 顺序消费与积压处理，两者的保序前提相近，但入口不同：Kafka 的唯一客户端入口是 key 的哈希取模，RocketMQ 这边是显式的选择器接口。

八、三种特性各自解决的问题

特性解决什么问题实现代价适用场景不适用时该用什么
事务消息业务本地事务与发消息之间的一致性，避免「消息已发但业务回滚」与「业务已提交但消息没发」一段不可见窗口 + 一次回查往返 + 要求本地事务状态可持久化查询 + 回查次数上限订单、支付、库存这类「状态变更必须通知下游」且本地事务有状态表的场景本地事务本身就是单资源且顺序无要求时，普通发送加业务侧补偿即可
延时消息消息在到期之前不可见，简化「一段时间后再说」存储占用 + 定时器集中调度 + 精度受扫描间隔与级别映射限制订单超时、延迟检查、定时提醒这类「时间窗内投递即可」需要精确到具体业务时刻的调度，用外部定时任务系统
顺序消息同一业务实体的消息按发送顺序被处理单队列串行消费带来的吞吐上限 + 失败即阻塞 + 对拓扑变更敏感状态机流转、余额变动、操作序列这类「后到的必须看到先到的」顺序不重要时用普通发送加业务侧按序号重排

三者可以叠加，但要清楚叠加后的代价是相加的：事务消息加顺序消息，意味着顺序消费下还要处理本地事务失败导致的不可见窗口；两者叠加后排查时很难分清「消息没到」是事务未提交还是队列被前一条消息阻塞。同时用上两项以上时，先确认是不是在用消息系统解决本不该由它解决的问题。

九、面试高频追问

1. RocketMQ 事务消息和 Kafka 事务是一回事吗？

答题骨架：不是，切分点是作用边界。Kafka 事务的作用对象全在 Kafka 内部：跨分区跨 topic 的原子可见，以及把消费位点与生产动作放进同一次提交，它不涉及任何外部资源。RocketMQ 事务消息解决的是业务本地事务与发消息的一致性，本地事务可以是任意数据库提交。两个方向互补：需要跨分区原子可见时 Kafka 事务更合适，需要本地事务对齐时 Kafka 事务做不到。详见第一节。

2. half 消息和普通消息有什么区别？消费者什么时候能看到它？

答题骨架：三点，缺一不可。走的是完全相同的写入路径，校验、选队列、落盘、建索引一步不少。区别只在可见性：half 消息在存储层真实存在，但不进入消费者可读范围，本地事务有确定结论（提交或回滚）之后才改变它的可见性。所以它不是「先发出去再撤销」，而是一直在，只是不可见。消费者在整个未决期间看不到它，这也正是「不可见窗口」的来源。要加两个源码级细节，显出读过源码：一是 half 消息会被强制 setWaitStoreMsgOK(false)，即不等落盘确认就返回，因为写入成功已代表安全暂存，状态判定交给回查；二是 SendStatus 的三个失败态在事务路径上一律映射为 ROLLBACK_MESSAGE，也就是直接保守回滚，这与普通消息「先查再定」正相反。详见第二节。

3. 回查机制能保证什么？不能保证什么？

答题骨架：分「能」和「不能」两侧。能：把「消息已发出但本地事务回滚」这类不一致收敛掉；当本地事务的最终状态可被回答时，消息的终态与之一致。不能与代价：回查有次数上限，transactionCheckMax RocketMQ 5.x 源码默认 15，另有 transactionTimeOut 默认 6000 毫秒、transactionCheckInterval 默认 30000 毫秒；回查期间消息对消费者不可见，本地事务越慢窗口越长；回查是额外往返，交互量随未知状态增加；最关键的是它依赖本地事务状态可持久化查询，这个前提不成立时机制退化。另外它不解决消费侧重复。再说一句这三个值不是精度：5.x 定时器与回查调度的实际精度未核实，不能由「间隔 30000 毫秒」推出「一定 30 秒内回查一次」。禁止说成「绝对可靠」。 详见第四节。

4. 事务消息的回查为什么不是无限次的？

答题骨架：先给数。transactionCheckMax，RocketMQ 5.x 源码默认 15，达到上限后按兜底策略处置。再说为什么必须有上限：Broker 侧要有终止条件，无限回查会让一条永远答不出状态的消息永久占用存储，并且把回查请求无限打给生产者，这既是资源问题也是对生产者的骚扰。附带一个源码级加分点：这三个字段在 5.x 位于 BrokerConfig，TransactionCheckConfig 这个类已不存在，查资料时看到它说明用的是旧版结构。兜底处置的目标是让消息不会停留在「消费者可见但状态错误」这个态，而是落到一个确定结果上。详见第四节 4.1。

5. 延时消息的精度能到毫秒吗？

答题骨架：不能按毫秒理解，分两层答。档位层：传统实现里指定的是级别，级别到时长的对应关系由 messageDelayLevel 定义，因此能表达的时间点是离散档位而不是任意时刻。这题的关键是把类型说对：messageDelayLevel 的源码类型是 String，是空格分隔的时长表，5.x 默认 1s 5s 10s 30s 1m 2m 3m 4m 5m 6m 7m 8m 9m 10m 20m 30m 1h 2h，共 18 级由 split 后推导，支持 s/m/h/d 四种单位。常见误解是「它是整数、默认 18」，这半错：18 是推导结果不是配置值，而且不存在 defaultMessageDelayLevel 这个配置项，级别数由 maxDelayLevel 运行时推导。精度层：实际到达时刻还要叠加定时器扫描间隔的滞后与到期后的投递、拉取；5.x 定时器的实际实现精度未核实，所以不要给「会偏多少毫秒」的结论。结论：要精确到具体业务时刻的场景应该用外部调度系统，不要靠延时消息。详见第六节。

6. 延时消息是「延迟消费」还是「延迟可见」？

答题骨架：延迟可见。到期之前消息在 Broker 上、消费者读不到，所以消费者挂掉或消费慢都不会让消息过期，代价是这段时间的存储占用。延迟消费是另一回事，意思是先给消费者看、处理时再判断该不该跳过，机制与代价完全不同。「先暂存、到期再投递」讲的是前者。

7. 顺序消息只配 MessageQueueSelector 就够了吗？

答题骨架：不够，它只解决一半。发送侧用选择器把同一业务键固定到同一 MessageQueue；消费侧同一队列必须单线程串行消费，并发消费直接破坏顺序。还要主动说三个破坏点：顺序语义下失败重试就是阻塞（队列停等，不能跳过后面的），发送侧多实例用同一键会并行发出而选择器救不了这一层，队列扩缩容或路由变化会让同一键落到不同队列。详见第七节。

8. 顺序消息能做到全局有序吗？代价是什么？

答题骨架：能，但只有一条路：所有消息进同一个 MessageQueue。代价是该主题的有效并行度降到 1，吞吐塌陷，而且队首一条处理失败就会停等后面全部。实践中做局部有序（按业务键）比做全局有序常见得多。Kafka 侧是同一个取舍，见 顺序消费与积压处理。

9. 这三项特性能不能一起用？

答题骨架：能，代价相加。最容易出事的是事务消息加顺序消息：顺序消费下还要处理本地事务未提交导致的不可见窗口，排查时很难分清「消息没到」是事务未决还是队列被前一条阻塞。给出建议：同时用两项以上时先确认是不是在用消息系统解决本不该由它解决的问题。详见第八节。
