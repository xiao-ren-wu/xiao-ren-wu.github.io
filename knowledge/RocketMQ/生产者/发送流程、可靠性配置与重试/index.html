发送流程、可靠性配置与重试

来源

基于 RocketMQ 5.x 官方文档（架构、特性行为、客户端 API）与Message、DefaultMQProducer 的公开接口整理。5.x 主线架构为 Proxy 加 gRPC 接入、Broker 侧由 Controller 模式承载高可用协调；Broker DLedger 模式在 5.x 已被官方标注为 legacy 并弃用。 数值口径：本篇涉及的配置分两档。已核实源码默认值的项（maxMessageSize、retryTimesWhenSendFailed、flushDiskType、retryAnotherBrokerWhenNotStoreOK 等）直接写具体值并标注「RocketMQ 5.x 源码默认」。仍未核实的只剩 sendMessageThreadPoolNums 与 syncFlushTimeout 两项，默认值随版本变化，以你所用版本的官方文档为准。SendStatus 各常量的语义标 B：枚举没有 javadoc，语义由消费点逻辑反推。

「消息发出去了，但客户端说失败」是生产者最常见的一类事故，而它在 RocketMQ 上的成因和 Kafka 并不完全一样。本篇回答四个问题：三种发送方式怎么选、一次发送请求中间究竟发生了什么、「重试」这个动作在这套库里其实有哪两个层次、发送结果要怎么看才算判定成功。事务消息、延时消息与顺序消息在 事务消息、延时与顺序消息。

一、三种发送方式的差异

方式客户端调用业务线程阻塞到哪里能否感知失败结果落在哪典型用途
同步发送send(msg)一直阻塞到拿到 SendResult能方法返回值订单创建这类必须确认结果的写
异步发送send(msg, SendCallback)只阻塞到请求入队能回调量大、对延迟敏感、且能正确处理回调
单向发送sendOneway(msg)请求交给发送线程就返回不能无处可取埋点、采集这类可丢数据

三点必须说清，它们决定了后面所有讨论的前提：

  1. 单向发送不是「更快的同步发送」，而是放弃失败感知。 它连响应都不等，因此「超时」这个概念在它身上不存在，客户端没有任何信号可以判断消息是写进去了还是根本没发出去。这类语义与 Kafka 把 acks 设成「不等任何确认」那一档同类，但更彻底：Kafka 那一档至少还能靠请求超时知道「结果不确定」，单向发送连这个都没有。
  2. 异步发送不降低可靠性，它只改变「结果由谁读」。 可靠性取决于 Broker 侧的刷盘与复制判定，不取决于客户端是同步等还是回调收。把异步发送当成「牺牲可靠性换速度」是常见误解，它真正的代价在别处：回调执行在你的回调线程或线程池上，回调处理抛异常或阻塞，会反压到发送路径。
  3. 5.x 的 Proxy 让失败判定更难。 客户端经 gRPC 接入 Proxy，链路是「客户端到 Proxy」「Proxy 到 Broker」两段，客户端只能看到 Proxy 侧的响应。Proxy 之后发生的写入失败，对客户端常常只表现为超时。因此在 5.x 下，「超时」更接近「结果未知」而不是「明确失败」，而明确失败是可以安全重试的，结果未知不行。

面试追问：同步、异步、单向怎么选？

答：按「要不要知道结果」和「业务线程能不能被阻塞」两个维度选，四个层次从强到弱。

  1. 业务上「发不出去就要回滚」的场景只能用同步。它是唯一在方法返回前就拿到判定结果的路径。
  2. 量大但不关成败的场景用异步，前提是回调里不做重活。回调执行占用的是发送链路上的线程，回调里再做同步 RPC 或阻塞 IO，等于把异步变回串行，还多一层排查成本。
  3. 单向只用于可丢数据（埋点、心跳、日志采集）。用单向发业务消息，等于主动放弃所有丢失排查手段。
  4. 混用是最容易出问题的做法：同一批消息里一部分同步一部分异步，出问题时无法用统一口径复盘。同一类消息统一一种方式。

二、发送请求的完整链路

分七步看，每一步都可能提前返回，且返回的都不一定是失败：

步骤做什么这一步失败的形态
拉路由向 NameServer 取队列列表，客户端本地缓存并周期性刷新路由为空或陈旧时无法定位 Broker，见第五节
组装消息设置 topic、tags、keys、延时级别、消息体纯客户端问题，直接抛异常，不产生网络请求
本地校验topic 名是否合法、消息体是否超过上限、是否属于延时消息抛异常，这条消息从未发出，重试无意义
选队列轮询，或由 MessageQueueSelector 决定选不到队列时直接失败
发送交给发送线程池，发送到该队列所在 Broker 的 Master网络异常、Broker 无响应、通道不可用
落盘按刷盘模式写入刷盘超时返回「不确定」状态，见第七节
建索引写 ConsumeQueue 与 IndexFile索引写入失败会导致消息不可消费，状态同样是不确定

必须强调「本地校验失败」与「发送失败」的区别。 前者消息根本没离开进程，重试多少次都不会成功，只会浪费次数。这类失败正确做法是修配置或改消息，不要加重试次数去掩盖。第七节会把这条判定规则展开。

本节涉及三个 Broker 侧刷盘与线程池配置，两个已核实、一个未核实：

配置项语义RocketMQ 5.x 源码默认
sendMessageThreadPoolNumsBroker 处理发送请求的线程池规模。它决定 Broker 端能同时处理多少写入，与客户端并发数是两个不同的旋钮默认值随版本变化，以你所用版本的官方文档为准
flushDiskType刷盘模式。合法取值只有 SYNC_FLUSH（同步刷盘，写入后等落盘完成才回响应）与 ASYNC_FLUSH（异步刷盘，写入后先返回，落盘由后台完成）ASYNC_FLUSH，且随包 broker.conf 里写的也是 ASYNC_FLUSH
syncFlushTimeout等待刷盘的超时上限，控制 Broker 在返回发送结果前最多等落盘多久。它是「等待多久」的上限，不是「是否写入」的上限默认值随版本变化，以你所用版本的官方文档为准

flushDiskType 默认是异步刷盘，这件事本身就是「发送成功不等于已落盘」的默认状态。 也就是说，不做任何配置时，RocketMQ 的成功响应就天然带着一个尚未落盘的窗口。第七节说的「不确定」一类状态，正是这个默认配置的直接后果。

2.1 waitStoreMsgOK：一个常见的身份错误

它已不是 Broker 配置项，而是逐条消息的属性，对应常量 MessageConst.PROPERTY_WAIT_STORE_MSG_OK。两版事实必须记清：

事实值
身份消息属性，不是 Broker 配置项。4.x 的 MixAll 时代写法已不适用
缺省行为属性缺失时按 true 处理，即「默认要求等落盘确认」
事务半消息AbstractSendMessageProcessor 强制把它置为 false，不等待 Broker 返回结果

这解释了一个看起来矛盾的现象：默认情况下普通消息要求等落盘确认，而 half 消息却显式要求不等。因为 half 消息写入成功即代表「已安全暂存」，回查机制会在之后接管状态判定，不需要在写入这一步就阻塞等结果。half 消息为什么必须已落盘但不可见，见 事务消息、延时与顺序消息 第二节。

2.2 队列数：defaultTopicQueueNums 在两侧是两个不同的默认值

这是本主题「同名不同值」的代表，横向比较时最容易出错：

位置defaultTopicQueueNums 源码默认含义
Broker 侧8托管端建主题时默认建几个队列
Producer 客户端侧4客户端声明主题时请求建几个队列

配套的自动建主题开关 autoCreateTopicEnable，源码默认 true，即允许为不存在的主题自动创建。

TBW102 这个自动建主题的测试主题把这套关系演示得最清楚，它是理解「两侧不同值如何生效」的最好样本：

  • TBW102 在 5.x 的常量名是 TopicValidator.AUTO_CREATE_TOPIC_KEY_TOPIC，值为 "TBW102"。旧资料里常见的 MixAll.AUTO_CREATE_TOPIC_KEY_PREFIX 在 5.x 已不存在，抄旧常量名会编译不过。
  • Broker 启动时按 Broker 侧的值 8 把它的队列建成 8 个。
  • 实际发送时取 min(客户端 4, Broker 8)，也就是生效 4 个。

要点是「建了几个」和「用几个」不是同一个数，中间夹了一次取较小值。排查「消息分散在几个队列上」这类问题时，要先分清问的是哪个环节。

异步刷盘与刷盘超时的组合是最容易讲错的一段。 异步刷盘模式下，消息写进操作系统页缓存后就可以返回，此时消息在 Broker 进程视角已经存在，但尚未真正落盘。如果在刷盘超时之前 Broker 宕机，这批消息可能丢失，而客户端拿到的是一个看起来正常的响应。也就是说：异步刷盘下，客户端的成功响应不等于数据已落盘。这个丢失窗口的宽度与 syncFlushTimeout 直接相关，配置值直接决定你在「写入吞吐」与「丢失窗口」之间选在哪一点。存储层的机制见 刷盘策略与内存映射。

三、producerGroup 与重试的关系

producerGroup 是客户端配置上的概念，作用有两个：标识这一组生产者实例，以及作为重试的计量单位。重试次数是按组计算的，而不是按实例或按消息。同一组里每个实例各自按组级配置执行重试，这意味着组内任何一个实例触发的重试都消耗同一份预算逻辑（各自独立计数，但配置来源相同）。

同步发送路径上的重试次数上限由 retryTimesWhenSendFailed 控制，RocketMQ 5.x 源码默认为 2。它的语义只有一句：「同步发送失败后允许重发几次」。注意 2 是次数而非总发送次数，即首次发送之外最多再发两次，最坏情况下一条消息最多产生 3 次写入尝试。

哪些失败会走这条路，必须精确到响应码。 Broker 返回的响应码落在重试码集合内时，客户端才抛 MQBrokerException 并进入重试。源码中该集合共 8 个：

响应码触发场景
TOPIC_NOT_EXIST主题不存在
SERVICE_NOT_AVAILABLE服务不可用
SYSTEM_ERROR系统错误
SYSTEM_BUSY系统繁忙
NO_PERMISSION无权限
NO_BUYER_ID无购买者 ID
NOT_IN_CURRENT_UNIT不在当前单元
GO_AWAYBroker 要求客户端离开

这 8 个码走的是异常路径，与 SendStatus 无关。 换句话说，FLUSH_DISK_TIMEOUT 这类「消息已写入但没等到落盘确认」的状态不在这个集合里，它不会抛 MQBrokerException。这一点是第四节两套重试机制的由来，也是本主题最常被讲错的地方。

三点必须补上，否则重试这一节会讲成空话：

  1. 重试的对象是同一条消息，重发的是同一个队列。 它不是「换个 Broker 再发一次」，也不是「多投几份提高成功率」。所以重试的副作用是重复，不是冗余。
  2. 重试路径上默认没有去重。 这是 RocketMQ 与 Kafka 差别最大的一处。Kafka 的生产者在重试时带 ProducerId 与序列号，Broker 侧做判重，因此重试在写侧不会产生重复；RocketMQ 生产侧没有等价的默认机制，重试一次就是多一条消息。机制对照见 幂等、acks 与事务。
  3. 重试不解决结果不确定的状态。 刷盘超时、复制超时这类状态重试，会在「本来就写进去了」的前提下再多写一条。第七节展开。

因此重试次数的正确配法不是「配大一点更保险」，而是先分类：哪些失败是明确的（可安全重试）、哪些是不确定的（不可重试）、哪些是本地校验失败（重试无意义）。第五节的重试队列引入，正是为了让第一类失败不至于浪费在无效的原地重发上。

面试追问：为什么重试次数不是越大越好？

答：三个原因，按重要性排。

  1. 重试不去重。 RocketMQ 生产侧重试默认不判重，次数翻倍意味着最坏情况下的重复量翻倍。对非幂等的下游（直接加库存、直接发通知），这是把一次故障变成多次业务事故。
  2. 重试占用同一个业务线程。 同步发送的重试在业务线程上执行，Broker 长时间不可用时，线程会被连续占住，最终表现为整个应用的请求堆积，而不是「某个接口变慢」。反压来得慢，但来得很重。
  3. 重试解决不了路由失效。 Broker 宕机或下线时，客户端缓存的路由可能还指向它，原地重试必然连续失败。真正要靠的是第五节的重试队列。

四、同步重试与异步重试

两条路径的重试都存在，差别在于执行重试的线程是谁，以及失败在哪里被观测到。

维度同步发送异步发送
重试执行位置业务线程发送链路内部的线程池
失败观测位置方法返回值SendCallback.onException
业务线程被占用是，直到重试耗尽否，只到请求入队为止
反压形态业务线程堆积，现象直接内部线程池堆积，回调延迟变大，现象间接
积压时的表现接口整体变慢甚至超时回调迟迟不来，日志里的耗时指标异常

异步路径的重试次数上限由 retryTimesWhenSendAsyncFailed 控制。默认值随版本变化，以你所用版本的官方文档为准。 它与同步路径是两个独立配置，只调其一会留下一个明显短板：同步调大而异步没调，异步发送在故障时的重复放大完全不受控。

4.1 两套重试机制：最容易讲错的一段

生产侧有两套彼此独立的重试机制。它们的触发条件、代码路径、开关默认值全都不同，中文资料经常混为一谈。这是本主题第一号易错点。

维度retryResponseCodesretryAnotherBrokerWhenNotStoreOK
路径性质异常路径正常返回路径
触发条件Broker 响应码落在第三节那 8 个重试码内，客户端抛 MQBrokerExceptionSendResult 正常返回，但 SendStatus 不是 SEND_OK
处理动作按 retryTimesWhenSendFailed 重发同一队列换一个 Broker 重发
RocketMQ 5.x 源码默认该集合本身即默认生效，无需开关false，默认不重试
覆盖的状态主题不存在、系统繁忙、无权限等FLUSH_DISK_TIMEOUT、FLUSH_SLAVE_TIMEOUT、SLAVE_NOT_AVAILABLE

因此「RocketMQ 发送失败会自动重试」这个说法是不完整的，必须拆成两句：

  1. 抛 MQBrokerException 的失败会重试。 这是默认行为，由 8 个响应码 + retryTimesWhenSendFailed 共同决定。
  2. SendStatus 非 SEND_OK 默认不重试。 因为 retryAnotherBrokerWhenNotStoreOK 默认 false。改成 true 之后，非 SEND_OK 才会换 Broker 重发。

这个默认值是有道理的，不该被当成疏漏。 非 SEND_OK 的三个状态都是「消息已进 Broker 但判定未完成」，此时换 Broker 重发会在两个 Broker 上各留下一份，重复量直接翻倍。默认关掉它，等于把「是否接受这个重复」的决定权交回业务侧。理解了这一点，就不会想当然地去把它打开。

三个实践上容易踩的点：

  1. 回调里不要做重活。 回调运行在发送链路的线程上，回调里做同步 RPC、查库、大量日志打印，都会占用发送能力。表现是「明明没打满并发，吞吐却上不去」，因为瓶颈在回调而不是网络。
  2. 回调必须处理异常。 回调里抛出的异常不会回到业务代码，发送侧通常感知不到，业务上会表现为「消息发了但下游没反应」却没有任何报错。把回调里的失败也接到自己的监控上。
  3. 同步与异步的失败率统计要分开看。 两者经过的线程池、配置、瓶颈都不同，混在一个指标里，异步路径的失败会被同步路径的正常数据稀释掉。

五、重试队列的引入

要解决的问题：Broker 宕机、主从切换、路由刷新滞后时，客户端手上缓存的队列信息可能还指向一个不可用的 Broker。此时无论重试多少次，打过去都不会成功。原地重试在这一阶段是纯粹的浪费。

解决思路：不原地重发，而是把消息投递到 Broker 上的重试队列。重试队列在客户端启动或首次失败时按组申请，消息进重试队列后由它承接，等目标 Broker 恢复后再被重新投递回正常发送路径。这段「熬过去」的时间由重试队列吸收，而不是由业务线程的阻塞吸收。

三点必须说清：

  1. 重试队列是生产侧的「排队区」，不是死信。 它承接的是「暂时发不出去」，与「业务上应该放弃」无关。消息进重试队列不代表失败终态，它会被反复尝试直到成功或耗尽预算。
  2. 进重试队列的消息对消费者不可见。 消费者看到的是正常主题里的消息，重试队列不在业务订阅范围内。所以重试期间业务侧观察到的现象是「消息延迟到达」，而不是「消息被消费了但状态错」。
  3. 同名不同层，这是高频混淆点。 消费失败触发的消费重试队列（%RETRY% 语义的内部主题）在名字与用途上都与生产侧重试队列接近，但它们是两套完全不同的机制：前者是 Broker 把消息重新投递给消费组，后者是生产者把消息重新投向 Broker。消费侧的机制见 重试、死信与消费堆积，生产侧的失败最终耗尽之后如何收口，两者的落点也不同。

面试追问：RocketMQ 的重试队列和 Kafka 的 producer 重试有什么不同？

答：分三层说，这是最能区分两套库设计取向的一题。

  1. 层次不同。 Kafka 的 retries 是同一个 Producer 进程内对同一批次重新发送，地址不变、Broker 不变。RocketMQ 的重试队列是跨 Broker 的重新投递，消息先落到重试队列，再由它投回正常路径。
  2. 去重不同。 Kafka 在重试路径上有 ProducerId 加序列号判重，重试不会产生重复写入。RocketMQ 生产侧没有这套默认机制，重试一次就可能多一条消息，这是最实质的差别。
  3. 要解决的问题不同。 Kafka 的重试是为「响应丢失但写入已成功」兜底。RocketMQ 引入重试队列主要为「路由失效、集群抖动」兜底，Kafka 应对同类抖动靠的是更长的投递超时与元数据刷新，不需要额外的排队结构。

六、消息体积限制与批量发送

6.1 消息体大小上限

maxMessageSize 是单条消息体的大小上限，RocketMQ 5.x 源码默认 4 MiB，即 1024*1024*4 = 4,194,304 字节。Broker 侧与 Producer 客户端侧是同一个值，两侧一致，这与 defaultTopicQueueNums 那种两侧不同的情况不同，不要混为一谈。

超限的判定点要记准，它决定了这条消息算不算「发出去过」：

环节事实
判定条件msgLen > maxMessageSize
Broker 侧结果AppendMessageStatus.MESSAGE_SIZE_EXCEEDED
客户端结果在本地校验阶段就拦下，这条消息从未发出

也就是说超限属于「本地失败」而非「远端失败」，重试再多次也不会成功，因为消息不会因为重发而变小。

两点比「上限是多少」更重要：

  1. 超限是本地失败，不是网络失败。 它不会消耗重试次数，也不会进入重试队列（重试它也不会变小）。看到「消息发不出去」先量一下消息体大小。
  2. 大消息的真实成本在复制时长上。 Broker 把消息写进 CommitLog 是顺序追加，这一点上大小消息没有本质差别；但一条大消息会让这一次追加的耗时变长，进而拉长从写入到复制完成的整条路径的延迟。高峰期的大消息会拖慢同一 Broker 上其他消息的复制延迟，影响面远超这条消息本身。

maxTransferBytesOnMessageInMemory 控制的是内存队列里可以直接转发的字节上限，超过这个量之后消息会被先转存到磁盘再转发出去。默认值随版本变化，以你所用版本的官方文档为准。 它是批量发送能拿到收益的物理前提：批量消息的收益来自减少网络请求数与减少落盘次数，而内存直转避免了额外的落盘。

6.2 三种提高吞吐的写法

方式做法吞吐收益来源顺序去重难度
调高客户端并发多个线程同时 send网络往返期间不空转同 key 消息会乱序不变
业务侧循环聚合业务代码自己攒一批再发由攒批策略决定，效果全靠自己需自行保证聚合不跨顺序边界需自行处理批内部分失败

必须点明 RocketMQ 与 Kafka 在批量上的结构差异。 Kafka 有 batch.size 与 linger.ms 两级旋钮由客户端攒批，开箱即带；RocketMQ 的客户端没有这一层自动攒批，批量收益要靠业务侧聚合或使用官方批量消息来实现。这直接导致一个经验差异：从 Kafka 迁过来的人往往先找「批量配置项」，在 RocketMQ 客户端上找不到，然后误判「RocketMQ 批量能力弱」。真实情况是能力路径不同，客户端自动攒批这一段在 RocketMQ 侧不存在。

另外，批量会放大重试的重复量级。一次重试重复的是整批，与 幂等、acks 与事务 里讲 Kafka 批次重复是同一个道理。

七、发送结果与失败判定

SendStatus 枚举完整只有 4 个取值，不多不少：SEND_OK、FLUSH_DISK_TIMEOUT、FLUSH_SLAVE_TIMEOUT、SLAVE_NOT_AVAILABLE。这个集合可以直接当白名单用，代码里出现第 5 个名字就说明写错了。

它的语义标 B 级：枚举本身没有 javadoc，四个常量的含义由客户端与 Broker 侧的消费点逻辑反推得到。因此「刷盘超时」到底意味着什么，只能从「哪个条件下会走到这个分支」倒推，不能引官方注释。

观察到的状态事实是什么业务上算成功吗该怎么处理
SEND_OK消息按当前刷盘模式通过了 Broker 的写入判定算正常返回
FLUSH_DISK_TIMEOUT消息已写入 Broker，但等待落盘超过上限不确定不盲目重发。等待后用消息 ID 查询确认，仍查不到再按业务容忍度决定
FLUSH_SLAVE_TIMEOUT主节点已写入，但等待从节点复制未在预期内完成不确定同上，权衡丢失与重复
SLAVE_NOT_AVAILABLE复制路径不可用，消息在主节点上不确定同上
明确失败（网络、校验、权限）消息未写入，或 Broker 返回第三节那 8 个重试码之一不算可按重试策略重发

后三个常量默认都不会重发，因为 retryAnotherBrokerWhenNotStoreOK 的 RocketMQ 5.x 源码默认是 false（第四节 4.1）。因此一个「发失败了」的返回，默认既不会自动换 Broker 重发，也不该由业务方盲目重发，而是要走下面的「先查再定」。

事务消息里这三个常量的处理完全不同。 在事务消息路径上，FLUSH_DISK_TIMEOUT、FLUSH_SLAVE_TIMEOUT、SLAVE_NOT_AVAILABLE 一律映射为 LocalTransactionState.ROLLBACK_MESSAGE。也就是说事务消息对「不确定」的处理是保守回滚，而不是等待回查，这一条与普通消息正相反，详见 事务消息、延时与顺序消息 第二、三节。

三类处理原则：

  1. 「成功」只在明确成功时才算成功。 刷盘与复制相关的状态都属于不确定，把它们当成功就等于接受一个已知的丢失窗口。
  2. 「不确定」不能直接重发。 它的定义就是「不知道写没写进去」。重发若实际已写入，就是重复。正确做法是先用消息 ID 查一次 Broker 侧是否可查，再决定。
  3. 「明确失败」可以重试，但要区分本地与远端。 本地校验失败重试无意义（消息根本没发出去，也不会变小），网络与 Broker 侧失败才值得重试。

排查口诀：先分清「有没有发出去」，再分清「对方确不确定」，最后才决定重试还是等。把三类混在一起加重试次数，是重复消息的主要来源之一。全链路的丢失场景与保障手段见 消息丢失场景与保障，消费侧的去重责任见 事务边界与去重约束。

八、面试高频追问

1. RocketMQ 的重试队列和 Kafka 的 producer 重试有什么不同？

答题骨架：分三层。层次上，Kafka 的 retries 是同一进程内向同一地址重发同一批次，RocketMQ 的重试队列是跨 Broker 的重新投递，消息先暂存再投回正常路径。去重上，Kafka 在重试路径上有 ProducerId 加序列号判重，重试不产生重复写入；RocketMQ 生产侧没有等价默认机制，重试一次就可能多一条消息，这是最本质的差别。目的上，Kafka 的重试主要兜「响应丢失但写入已成功」，RocketMQ 引入重试队列主要兜「路由失效与集群抖动」，后者靠 Kafka 那套进程内重试解决不了。详见 发送流程、可靠性配置与重试 第五节。

2. 刷盘超时算成功还是失败？能重试吗？

答题骨架：算不确定，不能直接重试。要说清三层。事实层：消息已写入 Broker，只是等待落盘超过上限，属于「写进去了但没拿到落盘确认」。SendStatus 完整只有 4 个取值，三个失败态就是刷盘超时、复制超时、从节点不可用。判断层：重试若实际已写入就是重复，所以不能把它归入可重试的明确失败。默认行为层（最容易被追问漏掉的一层）：retryAnotherBrokerWhenNotStoreOK 源码默认 false，所以它默认根本不会自动重发；而 retryResponseCodes 那 8 个码走的是抛 MQBrokerException 的异常路径，与 SendStatus 无关，两套机制不能混谈。处置层：先用消息 ID 查 Broker 侧是否可查，查到即视为成功，查不到再按业务对重复与丢失哪个更不能容忍来决定。还要补一句根因：flushDiskType 源码默认 ASYNC_FLUSH，所以「成功不等于已落盘」是默认状态而非异常配置。详见第七节。

3. 同一 producerGroup 下多个生产者实例会怎样？换 group 名有什么用？

答题骨架：两点。组的作用是标识这组生产者并作为重试的计量单位，重试次数按组配置，组内各实例按同一份配置执行。重试次数是每个实例各自计数的，不是共享一份池子。换 group 名的作用主要是隔离重试预算与重试队列，不同组申请各自的重试队列，所以两个组互不干扰。实践含义是：不同业务用不同组，可以避免一个业务的故障把另一个业务的发送能力一起拖垮；同时也意味着组名不要随意复制粘贴，组名变了等于重试预算和重试队列都换了。

4. 同步和异步发送的重试次数是同一个配置吗？

答题骨架：不是，是两个独立配置。同步路径由 retryTimesWhenSendFailed 控制，RocketMQ 5.x 源码默认为 2；异步路径由 retryTimesWhenSendAsyncFailed 控制，默认值随版本变化，以你所用版本的官方文档为准。只调一个会留下明显短板：常见的「同步调大了、异步没调」，故障时异步路径的重复放大完全不受控。要注意「默认为 2」指的是额外重发次数而非总发送次数，最坏情况下一条消息会有 3 次写入尝试。

答题骨架：先纠正前提，再摆两套机制的对照。纠正：不是「一个配置」，是两套彼此独立的机制。retryResponseCodes 走异常路径，Broker 响应码落在 8 个重试码内才抛 MQBrokerException 并重发同一队列，默认即生效。retryAnotherBrokerWhenNotStoreOK 走正常返回路径，针对 SendStatus 非 SEND_OK，源码默认 false，所以三个失败态默认都不重试；改成 true 才换 Broker 重发。关键区分点：那 8 个码里不含任何 SendStatus 失败态，所以「抛异常的重试」和「状态非 OK 的重试」互不覆盖。谁在混这两套，多半是照着「发送失败会自动重试」这句话背下来的。再补一句为什么默认值是 false：非 OK 三个状态都意味着消息已进 Broker，换 Broker 重发会在两个 Broker 各留一份，重复翻倍，所以把决定权交回业务侧。详见第四节 4.1。

6. 消息发不出去，怎么排查？

答题骨架：按第三节的失败分类逐层排除，不要一上来就调重试次数。本地校验类（topic 名非法、消息体超限、属性缺失）看异常栈，这类消息从未离开进程，重试无意义。路由类（找不到队列、路由为空）看 NameServer 连通性与客户端路由刷新，路由陈旧时任何重试都打向死地址。可达性类（网络异常、Broker 无响应）才轮到重试策略。判定类要特别区分「结果不确定」这一档，它表现为超时或异常，但重发会造成重复。观测手段见 RocketMQ 监控与排障。

7. 顺序消息要配什么才真正生效？

答题骨架：只配客户端选择器不够，四个条件缺一不可。发送侧用 MessageQueueSelector 按业务键把消息固定到同一个 MessageQueue。消费侧对同一队列必须单线程串行消费，并发消费直接破坏顺序。消费失败时的重试在顺序语义下就是阻塞（后来的消息要等），这一点与 重试、死信与消费堆积 的取舍直接相关。发送侧多实例用同一业务键会互相竞争同一队列，还要考虑队列扩缩容或路由变化导致业务键落到不同队列。详见 事务消息、延时与顺序消息 第七节。

8. RocketMQ 有没有类似 Kafka 幂等生产者的去重机制？

答题骨架：生产侧默认没有等价的机制。Kafka 有 ProducerId 加序列号加 Broker 侧去重窗口，覆盖「同一次逻辑发送在重试后只被 Broker 接受一次」。RocketMQ 生产侧重试默认不判重，所以「同一次业务消息被重试写入多份」是正常结果。去重责任落在两处：消费侧用业务唯一标识做幂等（不能用消息偏移量，重放会变），以及事务边界内的状态判断。详见 事务边界与去重约束。

9. 5.x 接入方式和 4.x 不同，对生产者的实际影响是什么？

答题骨架：三点。链路变化：5.x 主线是 Proxy 加 gRPC 接入，客户端到 Broker 之间多了一跳，客户端只能看到 Proxy 侧的响应。判定影响：Proxy 之后的写入失败对客户端常表现为超时，因此「超时」在 5.x 下更接近「结果未知」而不是「明确失败」，只有后者可以安全重试。统计影响：失败率与延迟的观测口径变了，Proxy 是新的排查入口，不能只在 Broker 侧看。Broker 侧的高可用协调在 5.x 由 Controller 模式承载，DLedger 模式已被官方标注为 legacy 并弃用，见 主从复制与故障转移。
