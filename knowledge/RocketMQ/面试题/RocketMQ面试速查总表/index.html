RocketMQ 面试速查总表

来源与用法

基于 RocketMQ 5.x 官方文档与本库源码核对清单整理。凡标「RocketMQ 5.x 源码默认」的数字都可直接引用，且有源码行可查；未核实项一律只讲语义，保留口径句「默认值随版本变化，以你所用版本的官方文档为准」。

这张表的用法是面试前 15 分钟扫一遍，不是教程。 每一行给的是「问题 → 结论 → 追问点 → 出处」，答出追问点才算答完。第十节的数字陷阱题要专门练，答错比不会更扣分，因为错答都来自似是而非的直觉，而这些数字在源码里都有明确答案，一问就露馅。

一、答题总纲：四段式与三条纪律

段落回答什么反例
结论一句话说清是什么、会不会、能不能「RocketMQ 靠主从保证不丢消息」（等于没答）
机制靠哪个结构、哪个配置项实现只说结论不给机制，追问一句就空
边界什么条件下不成立、什么会被破坏「默认重试 16 次」（缺消费模式限定）
代价得到这个保证付出了什么只讲收益不讲代价，等于推销不是分析

三条纪律：

  1. 数值必须带大版本。 本库已核实的项统一说「RocketMQ 5.x 源码默认」，未核实的宁可只报语义。错报一个数字，整段可信度一起崩。
  2. 可靠性回答必须指明丢的是哪一段。 生产端、Broker 端、消费端三段窗口彼此独立，说「可能丢消息」等于没答。
  3. 「不确定」与「失败」必须分开。 异步刷盘是出厂默认，所以「客户端成功响应不等于已落盘」是默认行为而不是小概率，这一条会被直接追问。

四、发送结果与重试速查

SendStatus 枚举完整只有 4 个取值，可以当白名单用，出现第 5 个名字就是写错了。语义标 B 级：枚举没有 javadoc，含义由消费点逻辑反推。

状态事实算成功吗默认会重试吗处置
SEND_OK按当前刷盘模式通过了 Broker 写入判定算不需要正常返回
FLUSH_DISK_TIMEOUT已写入 Broker，等待落盘超过上限不确定不会先用消息 ID 查 Broker 侧是否可查
FLUSH_SLAVE_TIMEOUT主节点已写入，等从节点复制未在预期内完成不确定不会同上，权衡丢失与重复
SLAVE_NOT_AVAILABLE复制路径不可用，消息在主节点上不确定不会同上

触发 MQBrokerException 并进入重试的响应码共 8 个：TOPIC_NOT_EXIST、SERVICE_NOT_AVAILABLE、SYSTEM_ERROR、SYSTEM_BUSY、NO_PERMISSION、NO_BUYER_ID、NOT_IN_CURRENT_UNIT、GO_AWAY。这 8 个码里不含任何 SendStatus 失败态，这是本库第一号易错点。

维度retryResponseCodesretryAnotherBrokerWhenNotStoreOK
路径性质异常路径正常返回路径
触发条件响应码落在上面 8 个之内SendStatus 不是 SEND_OK
处理动作按 retryTimesWhenSendFailed 重发同一队列换一个 Broker 重发
RocketMQ 5.x 源码默认该集合本身即默认生效false，默认不重试

五、延时级别与重试节奏速查

messageDelayLevel 的源码类型是空格分隔的 String 时长表，不是 int。18 级是 split 之后的索引推导结果，不存在 defaultMessageDelayLevel 这个配置项。

消费重试的延迟级别不是可配退避策略，而是固定映射 delayLevel = 3 + reconsumeTimes（RocketMQ 5.x 源码默认）。第一次重试落第 4 级即 30 秒起，此后每重投一次级别加一、间隔随之拉长。这解释了「重试堆积为什么迟迟不消」：重试次数越深，消息回到正常队列的时间越晚。

延时消息的两个边界要主动说：

  1. 能表达的是离散档位，不是任意时刻。 要投递到精确业务时刻应该用外部调度系统，不要靠延时消息。
  2. 不要给「会偏多少毫秒」的结论。 5.x 定时器的实际实现精度未核实，官方没有给出可引用的毫秒数。正确答法是报出档位层事实，然后明说精度层未核实。

六、事务回查速查

half 消息三步：发对消费者不可见的 half 消息 → 执行本地事务 → Broker 回查终态决定提交可见或回滚丢弃。它对齐的是「消息终态」与「本地事务终态」，成立前提是本地事务的最终状态可以被回答。

事实项RocketMQ 5.x 源码默认含义
transactionCheckMax15回查次数上限，超过按放弃处理
transactionTimeOut6000 毫秒（6 秒）距 half 消息写入多久开始认为需要回查
transactionCheckInterval30000 毫秒（30 秒）两次回查之间的间隔
waitStoreMsgOK 在 half 消息上强制 false写入成功即代表已安全暂存，回查接管终态判定

事务消息对「不确定」的处理与普通消息相反：在事务消息路径上，FLUSH_DISK_TIMEOUT、FLUSH_SLAVE_TIMEOUT、SLAVE_NOT_AVAILABLE 一律映射为 LocalTransactionState.ROLLBACK_MESSAGE，即保守回滚而不是等待回查。答「刷盘超时怎么办」时如果谈的是事务消息，这一层必须单独交代。

已知代价：回查在极端情况下不可靠（本地事务已提交但回查超时），以及 half 消息会长期占用存储。

七、消费重试与死信速查

先分清三层「重试」，这是本库最高频的混淆点：

层触发方机制是否阻塞业务线程
生产侧重试发送失败客户端按 retryTimesWhenSendFailed 重发；另有本组重试队列承接路由失效同步发送会阻塞
消费侧重试回调返回失败Broker 侧把消息投到该消费组的消费重试队列，延迟后重投回原队列不阻塞，Broker 侧行为
事务回查Broker 判定 half 消息未终结按回查间隔询问生产者不阻塞

消费重试的数值与判定：

事实项RocketMQ 5.x 源码默认备注
maxReconsumeTimes 位置消费端 DefaultMQPushConsumer 字段，不是 Broker 配置项在 broker.conf 里配是版本错位
默认值-1含义是「用默认值」，不是「不重试」
-1 在并发消费展开为16客户端与 Broker 双侧默认凑巧一致
-1 在顺序消费展开为Integer.MAX_VALUE约 21.4 亿次，实际等于永不因次数耗尽而进死信
retryMaxTimes（订阅组）16remoting 协议版本 ≥ 3.4.9（此处是协议版本，非发布版本号）时，请求头 maxReconsumeTimes 优先于它
进死信判定reconsumeTimes >= maxReconsumeTimes顺序用 >=、并发用 >，边界差 1 次
顺序消息特殊路径检测到未过期的顺序锁记录直接判死信不看次数

「重试 16 次」的准确表述只有一句：并发消费、且用户未显式设置 maxReconsumeTimes 时，客户端与 Broker 双侧默认恰好都是 16。 顺序消费完全不同。由此得出一条反直觉结论：顺序消费拿到 Integer.MAX_VALUE 的预算，却仍然会有消息进死信，因为顺序锁那条路径根本不看预算。这也是「顺序消息堆积不会自己耗尽次数走完流程进死信」的直接原因。

十、常见数字陷阱速查

这一节的题答错比不会更扣分。

陷阱题常见错答正解详见
RocketMQ 默认重试几次？「16 次」只在并发消费、且用户未显式设置 maxReconsumeTimes 时成立。该字段是消费端字段默认 -1，并发展开 16，顺序展开 Integer.MAX_VALUE重试、死信与消费堆积 1.3
写成功返回就等于落盘了吗？「是，确认了就安全」不等于。flushDiskType 默认 ASYNC_FLUSH，成功响应意味着进了 PageCache，这是默认行为不是异常配置。窗口宽度由 syncFlushTimeout 决定刷盘策略与内存映射 第二节
SendStatus 有几个？「三个：成功、超时、失败」只有 4 个：SEND_OK、FLUSH_DISK_TIMEOUT、FLUSH_SLAVE_TIMEOUT、SLAVE_NOT_AVAILABLE发送流程、可靠性配置与重试 第七节
发送失败会自动重试吗？「会自动重试」拆两句：8 个响应码走异常路径、默认生效；SendStatus 非 OK 走正常返回路径，而 retryAnotherBrokerWhenNotStoreOK 默认 false，默认不重试发送流程、可靠性配置与重试 4.1
defaultTopicQueueNums 默认多少？「4」只对 Producer 侧成立。Broker 侧同名配置默认 8，TBW102 启动按 8 建、实际生效 min(4,8) = 4发送流程、可靠性配置与重试 2.2
messageDelayLevel 是整数吗？「是，默认 18」半错。源码类型是空格分隔的 String 时长表，18 级是 split 后的推导结果，不存在 defaultMessageDelayLevel事务消息、延时与顺序消息 第六节
ConsumeQueue 文件多大？「默认 6 MB」口径误导。配置写的是 300000 * 20，语义是30 万条 entry；6,000,000 字节是乘法结果CommitLog、ConsumeQueue 与 IndexFile 第三节
waitStoreMsgOK 是配置项吗？「在 broker.conf 里配」它已不是配置项，是逐条消息属性，缺省 true；事务 half 消息强制置 false发送流程、可靠性配置与重试 2.1
fileReservedTime 默认几小时？「48 小时」或「72 小时」两个都对：类默认 72 小时，随包 broker.conf 覆盖为 48 小时。先看自己 conf 里实际生效的是哪个刷盘策略与内存映射 第五节
主从复制默认是同步吗？「是，高可用产品默认都同步」默认是异步主从。brokerRole 默认 ASYNC_MASTER、刷盘默认 ASYNC_FLUSH，两个默认叠在一起是强度最松那一格主从复制与故障转移 第一节
刷盘间隔配置叫什么？「少一个字母的那个流传拼法」网上流传的另一个拼法在任何 RocketMQ 版本的源码里都不存在，遇到时直接按「不存在」处理。真名 flushIntervalCommitLog，默认 500（⚠️ 源码未标单位）刷盘策略与内存映射 第五节
commitIntervalCommitLog 调到 50 毫秒没效果？「配置没加载」因为 transientStorePoolEnable 默认 false，这个值默认根本不参与运行刷盘策略与内存映射 第五节
事务消息和 Kafka 事务是一回事吗？「都是分布式事务」不是。RocketMQ 对齐的是业务本地事务与发消息的终态；Kafka 管的是 Kafka 内部跨分区原子可见与位点提交事务边界与去重约束 第一节
消息 ID 能当幂等键吗？「能，msgId 唯一」不能。消息 ID 是定位符不是幂等键，跨进程、重试、重放、扩缩容都不稳定。按 ID 去重的两种失效后果不同，撞号导致的丢弃比重复严重得多事务边界与去重约束 第三节
顺序消费也有死信？「预算 21 亿次，几乎不会死信」仍会。Broker 对顺序消息有一条检测到未过期的顺序锁记录即判死信的路径，根本不看次数重试、死信与消费堆积 4.1
消费重试会拖慢业务吗？「会，重试在业务线程上」消费侧重试是 Broker 侧行为，业务线程不阻塞。阻塞的是生产侧的同步发送重试重试、死信与消费堆积 第一节
有死信队列就等于有重试上限保护？「是，16 次后自动进死信」并发消费下确实有，但重试队列只有 1 个、死信队列每组也只有 1 个，长尾堆积会全挤在那一串上RocketMQ 监控与排障 第五节
5.x 只是换了个客户端？「协议兼容，差别不大」差别在链路上：Proxy 加 gRPC 接入让客户端多一跳，Proxy 之后的写入失败常只表现为超时，因此「超时」更接近「结果未知」RocketMQ 架构全景与角色分工 第七节

十一、跨系统追问

本节与 Kafka 库同节配对，见 Kafka 面试速查总表

  1. Kafka 的 ISR 机制与 RocketMQ 的主从同步，数据丢失窗口分别有多大？谁更小，为什么？ 答题骨架：先说清各自的窗口定义再比大小，否则比的不是同一个量。Kafka 侧窗口是「Leader 确认后、复制尚未完成时 Leader 宕机」，宽度由 acks 与 min.insync.replicas 的组合决定。RocketMQ 侧窗口由复制方式与刷盘方式两个正交开关共同决定，只开同步复制而刷盘仍异步，主节点进程崩溃仍可能丢已确认消息；只开同步刷盘而复制仍异步，主节点整机故障从节点缺数据。因此 RocketMQ 侧不存在单一答案，必须报出四格组合里的具体一格。
  2. Kafka 的顺序消费与 RocketMQ 的顺序消息，实现代价差在哪里？ 答题骨架：代价结构相似，因为两者都把有序粒度绑在最小分片单位上（Kafka 是分区，RocketMQ 是队列），并行度都被有序实体数压住，扩分片破坏顺序、失败重试插队。差异在强制手段与失败语义：Kafka 靠 key 哈希加消费侧单线程自觉，没有 Broker 端强制；RocketMQ 在消费模式层面把有序做成显式选项，并且顺序消费下失败不能进重试队列（重投会打乱队列内顺序），代价是拿到的重试预算展开为 Integer.MAX_VALUE、实际永不因次数耗尽而进死信。
  3. Kafka 没有 Broker 端消息过滤，RocketMQ 有。这对两者适用场景有什么影响？ 答题骨架：Kafka 若要按 tag 或 SQL 条件过滤，只能应用侧收下再丢，或引入 Streams 之类的流计算层，这使它适合「全量事件流加下游各自消费」的定位，不适合「Broker 精准分发以省带宽」。RocketMQ 的 Tag 与 SQL92 过滤让一份数据能低成本分给不同订阅方，也是它适合事务通知、订单状态这类同一份数据按条件分发给多个消费组场景的直接原因。
  4. 两套系统都支持事务，但实现思路完全不同——各自代价是什么？ 答题骨架：Kafka 走事务协调器加两阶段提交，代价是要开事务生产者、引入 transactional.id 的 fencing 逻辑，消费侧还得切 read_committed 并把位点纳入事务。RocketMQ 走 half 消息加本地事务回查，代价是回查在极端情况下不可靠（本地事务已提交但回查超时）、half 消息长期占用存储，以及事务路径上三个失败态一律保守回滚。对比落点是 Kafka 先写日志后确认回滚，RocketMQ 先发半消息再探测本地事务。
