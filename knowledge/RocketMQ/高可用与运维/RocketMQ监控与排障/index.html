RocketMQ 监控与排障

来源

基于 RocketMQ 官方文档整理。5.x 主线为Proxy + gRPC 接入 + Controller 模式，监控与排障必须先承认这一层新增接入面；NameServer 无状态、不引入共识算法、路由信息为最终一致，因此「路由发现」是独立的一层观测目标。 本文按症状组织而非按指标名组织：先说「你看到什么」，再给「该查什么」，最后给「怎么处置」。 关于指标名：RocketMQ 通过 JMX 暴露运行时统计，但具体 MBean 标识与分组随版本变化，本文只写观察目标、不列具体标识，避免记下过期名字。具体标识与参数默认值均随版本变化，以你所用版本的官方文档为准。 mqadmin 子命令只按名称列出，不给参数与默认值。

排障的效率取决于排除顺序而不是指标数量。5.x 多了一层 Proxy 接入面之后，这个顺序比 4.x 更重要：Broker 指标全绿但业务超时的第一嫌疑是 Proxy。复制与切换机制的前置铺垫见 主从复制与故障转移。

一、必须盯住的核心指标

先分层，再看指标。 5.x 的可观测面比 4.x 多一层，混在一起看会得出「Broker 正常但业务失败」这类无法收敛的结论。

层观测目标排障时先看它的理由
Proxy / gRPC 接入层（5.x 新增）客户端连接数与连接状态、请求处理耗时分布、请求队列积压、gRPC 通道是否反复重连5.x 客户端流量先到 Proxy 再到 Broker。Proxy 慢或通道抖动时，Broker 侧所有指标都可能是绿的
Broker 数据面发送与拉取请求量、失败率与其分类、CommitLog 写入与刷盘耗时、线程池活跃度、磁盘水位消息真正落在这里，RPO 结论由刷盘与复制共同决定
复制层主从同步是否在推进、同步滞后趋势、是否因从节点落后而阻塞写入直接对应 RPO；「写不进去」的根因常常在复制链路而不是磁盘
路由层（NameServer + 客户端缓存）Broker 注册是否成功、客户端是否取到目标 Topic 的路由、路由刷新是否卡住NameServer 失效表现为路由发现受损，详见 主从复制与故障转移 第六节的对照
客户端发送重试次数与失败分类、消费速率与积压趋势、消费端是否反复重平衡判断「慢在客户端」还是「慢在服务端」，这是唯一能一刀切开责任边界的方法

这张图是本篇的使用顺序，从上往下走，不要跳。 最常见的两种错误是：一上来就盯 Broker 指标（于是把 Proxy 的问题判成 Broker 的问题），二是看到发送变慢就查磁盘（于是把从节点落后导致的阻塞查成磁盘问题）。

关于指标名的纪律：RocketMQ 的运行时统计通过 JMX 暴露，可以直接用 jconsole 之类的工具连上进程浏览 MBean 列表。排查「读不到指标」时的第一个问题永远是「能不能读到指标」，不是「指标为什么是 0」——采集链路的问题会被误判成业务问题。具体 MBean 标识与分组随版本变化，以你所用版本的官方文档为准。

Kafka 侧对照一句：Kafka 客户端直连 Broker，没有 Proxy 这一层，所以「Broker 指标正常但客户端超时」在 Kafka 里要往网络与客户端查；5.x 的 RocketMQ 必须先排除 Proxy。这是两套系统在同一体检指标下排查路径不同的原因。

面试追问

  1. 5.x 排障和 4.x 最大的不同是什么？ —— 多了一层 Proxy + gRPC 接入面。同样的「客户端超时」症状，5.x 必须先排除 Proxy，4.x 没有这个环节。
  2. 为什么不能直接背 RocketMQ 的指标名？ —— 因为可用标识随版本变化，背下来的名字容易过期。稳妥的做法是记住每层要观察什么，再用 JMX 现场确认实际暴露的标识。
  3. NameServer 层要盯什么？ —— 不是盯它的 CPU，而是盯「Broker 是否注册成功」和「客户端是否取到了目标路由」。因为它无状态、无共识、路由最终一致，它只提供路由，不做故障转移决策。

二、mqadmin 工具链

mqadmin 是获取即时事实最快的通道，因为它绕开了监控采集的延迟。排障时的正确用法是：先用 mqadmin 拿到当下的确定事实，再用指标看趋势。

下面只列子命令名称。参数形式、可用子命令及其默认值随版本变化，以你所用版本的官方文档为准。 5.x 为 Controller 模式引入的选主相关子命令在 4.x 中并不存在。

要回答的问题常用子命令

某个 Broker 的角色与主从状态brokerStatus

三条使用纪律，比记住命令本身更重要：

  1. 破坏性命令与只读命令要分开对待。 上表里只读的是 clusterList / brokerStatus / topicRoute / consumerProgress / getBrokerConfig 这一类；resetOffsetByGroup / cleanOffsetByGroup / deleteTopic / deleteSubscriptionGroup / updateBrokerConfig 会改变线上状态，执行前必须确认影响范围并保留现场。它们的参数与具体行为以你所用版本的官方文档为准。
  2. 先只读，后写入。 任何排障的第一步都应该是只读命令。带着写操作去排查是最常见的事故放大器。
  3. 不确定参数就不传。 直接运行不带子命令的 mqadmin 会打印当前版本支持的命令与选项，以这个输出为准，不要凭记忆或照抄别处的文档。

面试追问

  1. mqadmin 在排障里的定位是什么？ —— 拿当下的确定事实，绕过监控采集的延迟。指标看趋势，命令取事实，两者互补。
  2. 为什么只列子命令名不列参数？ —— 参数形式与默认值随版本变化，写死会误导。稳妥做法是现场不带参数运行一次，以当前版本打印的选项为准。
  3. 应急时最该先跑哪条？ —— 只读的几条按顺序是 clusterList（Broker 在不在）→ brokerStatus（角色对不对）→ topicRoute（路由有没有）→ consumerProgress（积压在哪个队列）。四条覆盖了绝大多数告警的第一现场。

三、消费堆积的定位路径

症状：消费进度落后，且落后量在增长。 这是最常见的告警，也是最容易被误判的一个——因为「消费慢」和「消费失败在重试」在主队列进度上看起来一模一样。

第一步：先区分「没消费」和「消费失败在重试」。

现象含义下一步
主队列进度落后，同时重试队列持续增长消费在失败重试，不是消费慢转查消费失败原因（异常、超时、依赖不可用），重试与死信机制见 重试、死信与消费堆积
主队列进度落后，重试队列不涨真正的消费能力不足或消费端卡住继续往下分层
全部队列均匀落后消费端整体产能不足，或消费端在反复重平衡查消费端实例数与重平衡行为
只有个别队列落后队列分配不均、生产端 key 倾斜、顺序消息按 MessageQueueSelector 聚集、或某个消费实例卡住查队列分布与实例分配，机制见 消费模式、位点管理与推送拉取
落后量在涨但消费速率也高消费速度低于生产速度属容量问题，按业务分级处置

关键认知：均匀落后与个别落后是两条完全不同的路径。 均匀落后指向消费端整体能力，个别落后指向分配与倾斜。用 consumerProgress 的队列级分布做这个区分是整条路径的第一步，跳过它就直接加消费者实例是最常见的误操作——队列不均的情况下加实例不会改善。

「消费失败在重试」这一类堆积有四个已核实的默认值可以直接用来判断（均为 RocketMQ 5.x 源码默认）：

配置位置默认值排障含义
retryQueueNumsBroker 侧订阅组1同一消费组的重试消息全部集中在这一个队列上串行重投。重试堆积时这个队列的深度会远超主队列，且重试吞吐天然被单队列串行限死
retryMaxTimesBroker 侧订阅组16重试次数上限。配合上面那个「只有 1 个队列」，默认配置下重试堆积很容易拖成长尾
DLQ_NUMS_PER_GROUPBroker 侧1每个消费组的死信队列数也是 1，死信堆积同样会挤在一个队列上
maxReconsumeTimes消费端 DefaultMQPushConsumer-1，并发消费派生为 16-1 不是「不重试」，而是由消费模式派生出真实次数：并发消费下等于 16，与 Broker 侧一致

顺序消费的默认值完全不同，必须说准：顺序消费下 maxReconsumeTimes 派生为 Integer.MAX_VALUE，实际等于永不进死信队列。 所以**「重试 16 次」这句话只在并发消费、且用户没有显式设置 maxReconsumeTimes 时成立**，顺序消息不适用。由此得出一条重要的排障结论：顺序消息的堆积不会自己「耗尽重试次数」走完流程进入死信，它会一直重投，表现为长时间不消失的堆积。Broker 侧对顺序消息另有一条特殊路径——检测到未过期的顺序锁记录时直接判死信，不看次数。

Broker 侧的判定与覆盖优先级也有确定答案：进死信的判定是 reconsumeTimes >= maxReconsumeTimes；而请求头携带的 maxReconsumeTimes 优先于订阅组配置里的 retryMaxTimes。所以同一套环境里不同客户端可能表现出不同的重试次数，先确认客户端有没有显式设置，再去看 Broker 配置。 此外重试消息的延迟级别按 delayLevel = 3 + reconsumeTimes 递增，重试次数越深，消息回到正常队列的时间越晚——这也是「重试堆积为什么迟迟不消」的一个纯机制解释。

第二步：确认消费模式。 集群消费模式下同一消费组内消息由多个实例分担，广播消费模式下每个实例都要收到全量。模式不同，堆积的期望值完全不同——广播消费下的「落后」常常是设计使然而非故障。这一层语义在版本间稳定，但具体参数以你所用版本的官方文档为准。

第三步：往上追一层生产端。 消费能力不足的根因常常在生产端：生产速率本身涨了、或者重试消息与延时消息集中到期一次性涌出、或者某次故障恢复后积压的历史消息集中下发。判断方法是对比同一时段的生产速率曲线与消费速率曲线，看差额是突然出现还是持续拉开。

面试追问

  1. 消费堆积第一步该做什么？ —— 区分「没消费」和「消费失败在重试」。两者在主队列进度上表现相同，先分开才能确定往哪查。
  2. 加消费者实例能解决所有堆积吗？ —— 不能。只有队列级落后均匀（消费能力不足）才有效；队列不均时加实例不改变分配倾斜；重试堆积时加实例只是让失败更快地发生。
  3. 为什么堆积经常在故障恢复后出现？ —— 故障期间生产继续、消费停滞，恢复时历史消息与积压的重试 / 延时消息集中下发，形成瞬时洪峰。判断这类堆积要看生产速率曲线上是否有对应的跳变。
  4. 广播消费下的落后怎么判断？ —— 广播消费每个实例都要收全量，实例数增加会让总量成倍上升。必须按「每实例期望」而不是「全集群期望」设阈值，否则永远在报警。
  5. 重试队列只有 1 个意味着什么？ —— 同一消费组的重试消息全部串行重投在那一个队列上，所以重试堆积的深度会远超主队列、吞吐也被单队列限死。看到「重试队列极深但主队列正常」时，扩消费实例解决不了问题，瓶颈是那一条队列的串行重投。
  6. 顺序消息的堆积为什么一直不消？ —— 顺序消费的重试上限派生为 Integer.MAX_VALUE，等于永不进死信，消息会一直重投下去。顺序消息只有走「检测到未过期的顺序锁记录即判死信」那条特殊路径才会离开重试。

四、发送失败的定位路径

症状：发送超时或发送失败。 与消费堆积一样，第一步是分类，因为「找不到路由」和「找到了但写不进去」的两条排查路径几乎不重叠。

第一步：分清返回失败属于哪一类。

失败类型典型形态排查入口根因方向
路由缺失拿不到队列信息就失败clusterList → topicRouteBroker 未注册成功、Topic 不存在、客户端路由缓存为空
连接层失败建立连接即失败Proxy 连接状态、gRPC 通道是否反复重连Proxy 不可达、地址配置错、多网卡自报地址不可达
写入被拒路由正常但返回失败码磁盘水位、刷盘耗时、线程池活跃度磁盘满、刷盘阻塞、线程池打满
写入被阻塞请求挂着直到超时同步复制的从节点是否落后复制链路问题，不是磁盘问题

第二步：手工发送验证。 用 sendMessage 向目标 Topic 发一条：能发成功说明 Broker 侧与路由都通，差异必然在客户端配置或客户端自身的连接状态；发不出去则把问题收敛到服务端一侧。这一步是发送类问题最有效的二分手段，因为它把「客户端」和「服务端」彻底分开了。

第三步：分清两套重试机制，它们走的不是同一条路径。 这是发送类排障最容易漏的一环，中文资料常把两者混为一谈：

机制触发条件RocketMQ 5.x 源码默认
retryResponseCodes 路径Broker 抛异常（MQBrokerException）触发码固定为 TOPIC_NOT_EXIST、SERVICE_NOT_AVAILABLE、SYSTEM_ERROR、SYSTEM_BUSY、NO_PERMISSION、NO_BUYER_ID、NOT_IN_CURRENT_UNIT、GO_AWAY
整体发送重试次数上述异常路径内换 Broker 重发retryTimesWhenSendFailed = 2
retryAnotherBrokerWhenNotStoreOK 路径SendStatus 返回非 OK 但不抛异常默认 false，即三个失败态默认不重试

SendStatus 只有四个值，而且恰好把本主题的两个开关各对应一个失败态：SEND_OK、FLUSH_DISK_TIMEOUT（开关 B 同步刷盘超时）、FLUSH_SLAVE_TIMEOUT（开关 A 同步复制等从节点超时）、SLAVE_NOT_AVAILABLE。看到后三个就直接知道该查哪个开关，不必再猜。 异步发送路径另有一个可配的失败重试次数，其默认值随版本变化，以你所用版本的官方文档为准。

关键认知：默认配置下失败态会直接返回给业务，不会自动换 Broker 重试。 这修正了一个常见误解——「重试会掩盖问题」在默认档位并不成立，真正要追问的是**「为什么没重试」。更要紧的是事务消息**：这三种失败态会被判为 ROLLBACK_MESSAGE（回滚），不是重发。调高重试次数之前先确认失败态属于哪一类，否则你会把一个明确的失败信号变成一段漫长的延迟。

5.x 特有的检查项：确认请求是否经由 Proxy 转发。Proxy 层的连接状态与重连频率是 4.x 没有的观察点，机制背景见 主从复制与故障转移。同时注意：brokerIP1 在多网卡、容器与 NAT 环境下自报的地址可能客户端不可达，症状是超时而不是找不到路由，这类场景必须显式配置对外地址。

面试追问

  1. 发送超时先查什么？ —— 先分清是路由缺失、连接层失败、写入被拒还是被阻塞。这四类的排查入口完全不同，跳过分类就会把复制阻塞查成磁盘问题。
  2. 为什么 sendMessage 验证有效？ —— 它用一条独立于业务客户端的消息把「服务端与路由」和「客户端配置」分开。能发成功说明问题在客户端侧，发失败说明问题在服务端侧。
  3. 发送重试有哪几套，为什么容易搞混？ —— 有两套且走不同路径：retryResponseCodes 只在 Broker 抛 MQBrokerException 时触发（默认次数 2），retryAnotherBrokerWhenNotStoreOK 只在 SendStatus 非 OK 的正常返回路径上触发，而它默认是关的，所以三个失败态默认根本不重试。事务消息里这三个失败态判回滚而不是重发。混淆两套会导致「以为配了重试其实没生效」或「配了重试却把失败变成延迟」。
  4. 发送变慢但磁盘水位正常，查什么？ —— 查是否开启了同步复制且从节点落后。主节点要等从节点确认，从节点一慢，写入就跟着慢。

五、磁盘与线程池告警

磁盘水位是 RocketMQ 里唯一会造成「不可恢复」的告警类型。 消息写不进去时业务侧只看到发送失败，但成因往往是保留策略、消费停摆或单条消息体积把磁盘占满，处置方向完全不同。

观察项说明常见成因
CommitLog 所在文件系统的水位消息真正落盘的位置，布局见 CommitLog、ConsumeQueue 与 IndexFile保留策略过长、消费端停摆导致堆积写满、单条消息体积偏大
刷盘耗时趋势同步刷盘路径的耗时变化，直接影响同步发送延迟磁盘 IO 饱和、写入放大、与清理线程争抢
清理 / 删除进度历史数据是否被按时回收保留策略配置、消费位点导致数据仍被引用
发送线程池活跃度处理能力是否打满上游流量突增、单条处理耗时变长、IO 变慢间接拖慢
消费线程池活跃度消费侧处理能力消费逻辑变慢、下游依赖变慢
清理线程 / 定时线程是否堆积定时任务是否被拖住前面几项变慢后的连锁反应

三个可以写实数的存储侧配置（均为 RocketMQ 5.x 源码默认）：

配置语义RocketMQ 5.x 源码默认排障时怎么用
fileReservedTime消息文件保留时长配置类默认 72 小时，随包 broker.conf 覆盖为 48 小时磁盘将满时最先要确认它。实际生效的取决于你的 broker.conf 里写没写，照 48 小时估容量而实际跑 72 小时，容量估算会偏 50%
warmMapedFileEnable是否预热内存映射文件false（预热关闭；注意源码保留了 maped 的拼写错误）关闭意味着启动或切主时不预热文件，首次写入要现场建映射，冷启动或切主后的第一批写延迟偏高属于预期，不是故障
destroyMapedFileIntervalForcibly强制销毁内存映射文件的间隔1000 * 120 = 120,000（毫秒为推断）（同样保留 maped 拼写）文件不能正常释放时的兜底回收节奏。它管的是内存回收的及时性，不是磁盘回收，磁盘回收由 fileReservedTime 决定

fileReservedTime 的两个默认值必须并列记住，这是本节最容易记错的一条。 配置类里写的是 72 小时，但随包 broker.conf 把它覆盖成了 48 小时，所以「RocketMQ 默认保留 48 小时」和「默认 72 小时」两种说法都能找到出处，区别只在于一个说的是随包配置、一个说的是类默认值，两者不矛盾。容量评估或收紧保留策略之前，必须先确认自己 broker.conf 里实际生效的是哪个。

线程池打满的典型特征是「请求排队但 CPU 不高」——因为瓶颈往往在 IO 或锁上，线程都在等。判据是：活跃线程数长期贴着上限、请求排队时间增长、而 CPU 使用率并不高。此时加线程通常无效甚至更糟（更多线程争抢同一块磁盘），正确方向是找出谁在拖慢单条处理耗时。

容量类配置里只有一个可以写死值：单条消息体积上限 maxMessageSize，RocketMQ 5.x 源码默认 4 MiB（1024*1024*4 字节，Broker 与 Producer 两侧同值）。 超限时 Broker 在写入点直接拒绝，返回「消息大小超限」这一类结果而不是静默截断——所以「消息偶发写不进去」要先量消息体积，这个上限比很多人印象中小。

其余三个只能写语义：发送处理线程数、消费线程数上下界、内存中单次传输的字节上限。它们的默认值随版本变化，以你所用版本的官方文档为准。 调它们之前先确认瓶颈类型——线程数解决不了 IO 饱和，字节上限解决不了磁盘容量。

处置顺序永远是「先判断是磁盘满还是线程池满」：磁盘满先扩容量或改保留策略，线程池满先查单条耗时。不要在没归因前同时调多个旋钮，那会让你无法判断哪个生效了。

面试追问

  1. 磁盘满为什么是唯一不可恢复的告警？ —— 因为它阻断写入，且历史数据不能凭空补回来。线程池满只影响吞吐，磁盘满直接让业务写不进去。
  2. 请求排队但 CPU 不高，瓶颈在哪？ —— 在 IO 或锁上，线程都在等。加线程会让争抢更激烈，正确方向是降低单条处理耗时。
  3. 清理线程堆积说明什么？ —— 说明前面某项已经变慢，定时任务没按节奏跑完。它是结果指标，不是起点，排查要从磁盘 IO 或写入压力往回追。
  4. 调线程数之前该确认什么？ —— 确认瓶颈类型。线程数解决不了 IO 饱和，也解决不了磁盘容量不足。
  5. 磁盘将满，fileReservedTime 该按多少小时算？ —— 两个默认值都是官方事实：配置类默认 72 小时，随包 broker.conf 覆盖为 48 小时。先看自己的 broker.conf 里实际写的是哪个，别拿类默认当线上值——照 48 小时估容量而实际跑 72 小时，估算会偏 50%。另外收紧保留会先删最老的消息，动手前确认业务可接受。

  1. 速查表和前面的章节是什么关系？ —— 前五节按症状展开，本节把它们的入口收敛成一张表。查表定位行之后回到对应章节看细节，不是替代关系。

七、应急处置手册

应急的目标是先把影响面收住，再花时间定位。 顺序固定为四步：止血 → 定位 → 处置 → 复查。跳过止血直接定位，等于让故障持续消耗业务。

分级与响应：

级别判据响应
P0 不可用消息写不进去，或消费完全停滞立即止血，同步拉齐相关方
P1 功能受损部分 Topic、部分队列不可用，或堆积持续增长且无法消化先限制影响面，再按窗口修复
P2 风险与容量磁盘水位偏高、复制滞后在增长、观测指标异常但未影响业务按计划处置，不做临时变更

三条通用纪律：

  1. 未确认影响面前不要重启 Broker。 重启会丢掉未刷盘的数据、放大复制滞后，并把现场证据一并抹掉。第五节讲的三个时间点（故障时刻、可写时刻、客户端不再报错时刻）只有不重启才量得准。
  2. 破坏性命令执行前保留现场。 resetOffsetByGroup、cleanOffsetByGroup、deleteTopic、updateBrokerConfig 都会改变线上状态。先用只读命令把现状导出留档，再动手。
  3. 止血动作要记账。 临时提高的并发、临时摘除的 Broker、临时改的保留策略，都必须在恢复后逐条回退。应急期间做的每一个临时变更，都是故障之后的一颗雷。

面试追问

  1. 应急为什么不先定位？ —— 定位需要时间，而故障在持续消耗业务。先用已知低风险动作收住影响面，止血动作与定位可以并行推进。
  2. 为什么不能随便重启 Broker？ —— 会丢未刷盘数据、放大复制滞后、抹掉现场证据。重启应当是处置手段而不是排障手段。
  3. 降级与异步化算不算止血？ —— 算，但它们是用可靠性换可用性的交换，必须业务方明确同意，不能由值班单方面决定。
  4. 应急结束后最重要的一件事是什么？ —— 回退所有临时变更并留档。临时并发、临时摘除、临时保留策略，每一个都会在下次故障时变成新的故障源。

八、面试高频追问

面试追问

  1. RocketMQ 消费堆积怎么定位？ —— 三步：先看重试队列是否也在涨（区分「没消费」和「消费失败在重试」），再看队列级落后是否均匀（区分消费能力不足与队列不均），最后对比生产速率曲线判断是不是容量问题。
  2. mqadmin 排障时怎么用？ —— 用它拿当下的确定事实，绕开采集延迟。先只读命令后写操作，resetOffsetByGroup 这类破坏性命令执行前必须只读导出留档。
  3. 5.x 排障和 4.x 的最大差别？ —— Proxy + gRPC 接入层。Broker 指标全绿但业务超时，第一嫌疑是 Proxy；Kafka 没有这一层，同类症状要往网络与客户端查。
  4. 为什么 RocketMQ 的排障要单独盯路由层？ —— 因为 NameServer 无状态、不引入共识算法、路由最终一致，它不做故障转移决策，只提供路由。它不可用时受影响的是路由发现：存量路由在客户端缓存里仍可用，依赖新路由的操作拿不到结果。
  5. 发送变慢但磁盘正常，查什么？ —— 查是否开启同步复制且从节点落后，写入在等从节点确认。
  6. 怎么避免把采集问题当成业务问题？ —— 排查「读不到指标」时第一个问题是「能不能读到指标」，不是「指标为什么是 0」；先确认 JMX 能连上并浏览到 MBean 列表。

答题骨架

  1. 先分层：Proxy / gRPC、Broker 数据面、复制层、路由层、客户端，五层按序排除。
  2. 再分症状：消费类先分「重试堆积 / 队列不均 / 产能不足」；发送类先分「路由缺失 / 连接失败 / 写入被拒 / 被阻塞」。
  3. 再取事实：只读子命令拿现场，指标看趋势，两者互补。
  4. 再定处置：P0 立即止血，P1 限制影响面，破坏性动作前导出留档。
  5. 最后收尾：复查同一观测项的趋势是否改变，然后逐条回退临时变更。
