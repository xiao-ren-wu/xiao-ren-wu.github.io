主从复制与故障转移

来源

基于 RocketMQ 官方文档与 5.x release notes 整理。三条已核实的主线事实按官方口径引用：RocketMQ 5.x 主线是Proxy + gRPC 接入 + Controller 模式；Broker DLedger 模式在 5.x 官方 release notes 中已标注为 legacy（deprecated）；NameServer 无状态、不引入共识算法、路由信息为最终一致，两台 NameServer 互备。 本文凡涉及配置项默认值处一律只写语义并附口径句。刷盘与内存映射的机制细节见 刷盘策略与内存映射，角色分工见 RocketMQ 架构全景与角色分工，指标与命令见 RocketMQ 监控与排障。

主从复制是 RocketMQ 里最容易被当成「Kafka 那一套」讲的一块。根子在于两套系统的协调哲学不同：Kafka 把一致性做进元数据层，RocketMQ 把它留在数据层，中间那台 NameServer 刻意不做共识。把这个差别讲清，RPO / RTO 的所有结论都会自然浮出来。

一、主从复制的两种开关

先做一个区分：主从复制不是一个开关，是两个相互正交的开关。 把它们混成一个「同步还是异步」的问题，是本主题最常见的表达错误。

开关作用层取值维度影响的语义
开关 A：是否部署副本Broker 部署形态与复制方式异步主从 / 同步主从复制是否等从节点确认
开关 B：刷盘方式单个 Broker 的落盘策略ASYNC_FLUSH / SYNC_FLUSH返回客户端前是否已落盘

开关 A 的取值由 brokerRole 声明：合法值只有三个，ASYNC_MASTER（异步主从）、SYNC_MASTER（同步主从）、SLAVE（从节点）。RocketMQ 5.x 源码默认是 ASYNC_MASTER，随包 broker.conf 里写的也是 ASYNC_MASTER——也就是不配就是异步主从，想要同步复制必须显式改成 SYNC_MASTER。

开关 A 的身份标识靠两个配置串起来：brokerName 标识「这是哪一组主从」，同一 brokerName 下的多个节点按 brokerId 区分角色，主节点使用固定的约定 brokerId，从节点取其它值。brokerIP1 则是 Broker 注册到 NameServer 时对客户端公布的可达地址。主从组内 brokerId 的具体取值约定随版本变化，以你所用版本的官方文档为准。

brokerIP1 有个高频踩坑点：多网卡、容器网络、NAT 或跨 VPC 部署时，Broker 自报的地址客户端可能根本连不上，表现为「发送超时」而非「路由找不到」。这类环境必须显式指定对外地址，不要依赖自动探测。

开关 B 的两个取值就是官方文档里的 SYNC_FLUSH 与 ASYNC_FLUSH，语义分别是「返回客户端前等消息落盘」与「写入 PageCache 后即可返回」。RocketMQ 5.x 源码默认是 ASYNC_FLUSH，随包 broker.conf 里写的也是 ASYNC_FLUSH——与开关 A 一样，不配就是异步。同步刷盘路径上有一个超时上限用于兜底（syncFlushTimeout，语义为「同步刷盘时的超时上限」），超时后如何处置由版本实现决定，它的默认值随版本变化，以你所用版本的官方文档为准。

关键认知：两个开关都开到最严，才是「强一致」形态。 只开同步复制而刷盘仍是异步，主节点进程崩溃时可能丢已确认的消息；只开同步刷盘而复制仍是异步，主节点整机故障时从节点缺数据。同理，maxTransferBytesOnMessageInMemory 这类控制单批消息在内存中搬运量的配置（语义为「单次消息传输在内存中允许的字节上限」）影响的是发送路径的内存压力，默认值随版本变化，以你所用版本的官方文档为准。

出厂默认是「两头都不严」，这一点必须单独记住。 brokerRole 默认 ASYNC_MASTER、flushDiskType 默认 ASYNC_FLUSH，两个默认值叠起来正好落在第二节那张表的第一行，也就是强度最松的那一格。换句话说 RocketMQ 的 RPO 强弱不由「它是不是高可用产品」决定，而由这两个配置项有没有被显式改过决定。 高可用产品线不等于高可靠默认配置，这是本主题最反直觉、也最值得在面试里主动点出的一点。

面试追问

  1. 主从复制到底是同步还是异步？ —— 这题问出来通常意味着还没拆开两个开关。正确答法：复制方式（等不等从节点确认）与刷盘方式（等不等落盘）是两个独立开关，四种组合的强度各不相同，必须分别回答。
  2. brokerName 和 brokerIP1 有什么区别？ —— 前者是「主从组身份」，决定哪些节点互为副本；后者是「对客户端公布的地址」，决定客户端往哪发请求。两者混为一谈就会把「副本关系配错」和「地址不可达」这两类完全不同的问题当成一类查。
  3. 为什么很多环境必须显式配 brokerIP1？ —— Broker 只能自报它认为的对外地址，多网卡、容器与 NAT 场景下自动探测出来的地址客户端未必可达。症状是发送超时而不是找不到路由，容易被误判为网络问题。
  4. RocketMQ 5.x 出厂默认的主从复制和刷盘是哪一种？ —— 都是异步的那一档：brokerRole 默认 ASYNC_MASTER，flushDiskType 默认 ASYNC_FLUSH，两个默认值的随包 broker.conf 与源码一致。要更强的一致性必须显式改配置，不能指望默认值。

二、同步复制与异步复制

异步主从：主节点写入成功即向客户端返回，从节点在后台由主节点转发消息。写入延迟低，主从之间没有强耦合，但从节点的数据天然滞后于主节点。主节点整机故障时，滞后窗口内的消息在从节点上不存在。

同步主从：主节点要等从节点确认后才向客户端返回。滞后窗口被压到最小，代价是写入延迟与从节点可用性直接绑在一起：从节点一旦落后太多或链路抖动，主节点的写入就会跟着受阻，此时业务表现是「发送变慢或超时」，而根因在复制链路。

复制方式的选择本质是在写入延迟与故障时数据完整性之间换指标，不是「哪个更先进」。

必须把「复制方式」和「刷盘方式」在同一条时间线上对齐。 从客户端发出一次发送请求到收到成功返回，中间依次经过：网络到达主节点、写入主节点内存、按开关 B 决定是否落盘、按开关 A 决定是否等从节点确认。客户端拿到成功的那个瞬间，到底有几份数据在哪儿，是这两个开关共同决定的。

组合主节点进程崩溃主节点整机故障写入延迟
异步复制 + 异步刷盘可能丢已确认消息从节点缺滞后窗口内的数据最低
异步复制 + 同步刷盘已确认消息在主节点盘上，从节点仍缺同左，滞后窗口不因刷盘而收窄低
同步复制 + 异步刷盘主节点盘上有，从节点也有滞后窗口被同步复制收窄较高
同步复制 + 同步刷盘两处都有滞后窗口最小最高，且受从节点拖累

这张表是全文最该背下来的一张。 它的价值在于把「我要更强的可靠性」翻译成「我要付出哪一项代价」，而不是笼统地说「打开同步」。

面试追问

  1. 同步复制为什么会让发送变慢？ —— 因为客户端的返回时刻被压到从节点确认之后，而不只是主节点落盘那一刻。从节点落后或链路抖动时，主节点必须等，写入延迟随之上升，且此时应查复制链路而不是查磁盘。
  2. 开了同步刷盘就等于不丢消息了吗？ —— 不等于。同步刷盘只保证「已确认的消息在主节点盘上」。主节点整机故障时从节点能否拿到，取决于复制方式，两件事必须分别确认。
  3. 从节点流量太大导致主节点写入受阻，怎么缓解？ —— 这是同步复制的固有代价，不能靠调刷盘解决。方向是排查从节点为什么落后（磁盘 IO、网络带宽、单次传输内存上限），或者接受异步复制并改用其他手段兜底。

三、slaveReadEnabled 的取舍

语义只有一句：是否允许客户端从从节点读取消息。 至于它在不同部署形态下的默认取向，默认值随版本变化，以你所用版本的官方文档为准。

这一项的取舍经常被说反，因此必须分稳态与切换窗口两层来看。

稳态（主从都健康时）：开启从读是有收益的。 读流量被分摊到多个节点，主节点的压力下降，主节点故障前就已经有了一条不依赖主节点的读路径。代价是读到的是从节点的数据，从节点天然滞后于主节点，因此从读是弱一致读。

切换窗口（主从角色正在变更时）：开启从读会带来一个短暂的读不可用窗口。 原因是路由信息在客户端侧是最终一致的：NameServer 里的路由表更新完成后，客户端还要等下一轮拉取才会切换目标节点。在这段窗口里，部分读请求仍按本地缓存指向「原来的从节点」，而那个节点此刻的角色正在变化或已经变化，读请求会短暂失败。换句话说，开启从读把「主节点整体不可用」换成了「切换瞬间一部分读短暂失败」，它降低的是稳态读单点风险，引入的是切换期的可用性抖动。

关闭从读则相反：读请求全部打在主节点，读的一致性最强、没有从节点滞后问题，但主节点故障后到新主就绪之间的读请求必须全部等待。在切换窗口里，关闭从读的不可用面更大、持续时间更长。

维度开启从读关闭从读
稳态读一致性弱一致，读到从节点数据最强，读主节点数据
主节点读压力分摊全部集中在主节点
主节点故障前的读冗余有独立读路径无
切换窗口内的表现部分读因路由缓存滞后而短暂失败全部读等待新主就绪，不可用面更大
读请求一致性要求高的业务不适用适用

决策要点：如果业务能接受弱一致读且主节点读压力是瓶颈，开从读；如果读一致性是硬要求或主节点读压力不大，关闭从读。 不要用「主从切换时读不可用」这一个维度单独做决定，那只覆盖了切换窗口，没覆盖稳态收益。

面试追问

  1. 开启从读后主从切换时读会失败，这是不是说明从读不好？ —— 不是，这是两种风险的选择。开启从读把「主节点故障后全部读不可用」换成「切换瞬间部分读短暂失败」，同时在稳态下多了一条不依赖主节点的读路径并分摊了压力。只看切换窗口会得出错误结论。
  2. 从读为什么读到的是旧数据？ —— 因为复制默认是异步的，从节点收到消息存在滞后。从读是弱一致读，读一致性要求高的场景不应开启。
  3. 从读导致读到旧数据，怎么在架构上避免？ —— 方向是收紧复制方式（同步复制收窄滞后窗口）与缩短客户端感知延迟，而不是简单关掉从读，因为关掉它会把风险转移到主节点单点上。

四、故障转移流程

先说结论：5.x 的故障转移决策由 Controller 做出，NameServer 全程不参与。 这是本主题最需要说清的一点。NameServer 只提供路由表，而且是无状态、无共识、最终一致的（见第六节），它既不知道谁是主，也不做选主决策。

流程拆成五段，RTO 就是这五段之和：

阶段谁负责耗时受什么支配
故障检测Controller心跳周期与判定超时的设定
选主决策Controller集群规模与协调开销
新主就绪新主节点自身启动或角色切换、追平进度
路由更新NameServer周期性更新与注册流程
客户端感知客户端 / Proxy路由拉取周期，客户端是轮询不是推送

最后一段最容易被忽略，却是 RTO 里经常占比最大的一段。 新主可能早已就绪，但客户端仍按本地缓存把请求发给旧地址，直到下一轮拉取才纠正。因此缩短路由拉取周期对 RTO 的改善，往往比优化选主逻辑更直接。

故障检测与选主判定相关的各项超时与周期配置，其具体取值属于实现细节：默认值随版本变化，以你所用版本的官方文档为准。 调整它们的判断顺序是：先看 Broker 日志确认故障时刻，再看新主实际就绪时刻，最后看客户端日志确认路由何时被纠正。

面试追问

  1. NameServer 在故障转移里扮演什么角色？ —— 只提供路由表，且是无状态、无共识、最终一致的。它不检测故障、不选主、不参与切换决策。把它说成「协调者」是错的。
  2. 为什么新主就绪了客户端还发错地址？ —— 因为路由是最终一致，客户端靠周期性拉取更新本地缓存，不会被推送。切换新主只解决了服务端侧，客户端侧还有一段感知滞后。
  3. RTO 应该怎么拆开算？ —— 拆成检测、选主、新主就绪、路由更新、客户端感知五段相加。只盯着「选主耗时」会严重低估真实的业务不可用时长。
  4. RTO 能做到多短有下限吗？ —— 有，客户端路由拉取周期构成硬下限，除非改成推送式路由通知。

五、RPO 与 RTO 的权衡

RPO（恢复点目标）回答「故障时最多丢多少数据」，RTO（恢复时间目标）回答「多久恢复服务」。 两者不是同一个旋钮，通常此消彼长，但 RocketMQ 里它们的驱动因素并不完全重叠，值得分开看。

指标由什么决定想改善它该动什么
RPO异步复制的滞后窗口、刷盘方式、主从数据一致性收紧复制方式、收紧刷盘方式、减少批量异步转发
RTO故障检测周期、选主耗时、新主追平、路由更新、客户端路由拉取周期缩短检测与拉取周期、保证新主能快速就位、保证 Controller 可用

RPO 的推导顺序：先问「客户端拿到成功时数据有几份、分别在哪」，再问「故障点之后进来的数据在从节点存不存在」。 第一问对应开关 B 与复制方式，第二问对应同步还是异步复制。第三节表里那个「同步复制 + 异步刷盘」的组合值得单独强调：它把 RPO 压得很低（从节点有数据），但主节点进程崩溃时仍有窗口，两个指标要分别优化。

RTO 的推导顺序：按第四节的五段逐段量，不要凭感觉估。 实操上最有效的一步是分别记录 Broker 故障时刻、新主可写时刻、客户端不再报错时刻这三个时间点，差值才是真实的业务不可用时长，工具输出里的选主耗时通常只覆盖中间那一段。

代价必须说在前面：RPO 与 RTO 的改善都有成本，没有免费的组合。 收紧复制与刷盘会推高写入延迟并让从节点故障开始影响主链路；缩短检测与拉取周期会增加 NameServer 与网络的开销。只讲收益不讲代价的答案是错的。

面试追问

  1. RPO 到底由刷盘还是由复制决定？ —— 两者都决定，但管的是不同故障类型。刷盘管主节点进程崩溃，复制管主节点整机故障。只答一个就漏了一半场景。
  2. 为什么 RTO 经常比想象的长？ —— 因为真实不可用时长包含客户端路由感知这一段，而它由路由拉取周期支配。工具报告的切换耗时常只覆盖选主与新主就绪。
  3. 能不能既零 RPO 又短 RTO？ —— 不能。异步转发量、刷盘方式、复制方式、拉取周期每一个都要用延迟或资源换。把所有旋钮推到最严通常会让写入延迟先崩，需要按业务分级而不是一刀切。
  4. 怎么做成本最低的容灾方案？ —— 按 Topic 分级：核心交易类收紧复制与刷盘，日志类接受异步；再把检测与拉取周期压到业务能接受的水平，而不是全量拉满。

六、从 DLedger 到 5.x Controller 的演进

先说当前形态：RocketMQ 5.x 的主线是 Proxy + gRPC 接入，Broker 侧的高可用协调由 Controller 模式承载。 官方 5.x release notes 已把 Broker DLedger 模式标注为 legacy（deprecated），官方 release notes 与 PR #10642 是这一判断的来源。

这里必须点明与 Kafka 的一处根本不对称，它是本主题面试的高分点。 Kafka 4.x 通过 KRaft 内置的 RAFT 共识日志（Controller Quorum） 达成元数据一致：元数据本身就是一条被多数派复制的日志，Controller Leader 挂掉后由投票选出新 Leader，接管时不需要从别处加载状态。RocketMQ 的 NameServer 恰恰相反：它无状态、不引入共识算法、路由信息是最终一致，两台 NameServer 互备。

维度Kafka 4.x（KRaft）RocketMQ 5.x
元数据一致性的实现内置 RAFT 共识日志，Controller Quorum 多数派复制NameServer 无状态，不引入共识算法
协调者故障后的行为选新 Leader，无状态需加载，切换后动态能力恢复NameServer 互备，切换不涉及状态转移
一致性等级已提交元数据强一致路由信息最终一致
控制面中断的系统影响失去动态能力（新建 / 扩分区、副本重分配、Leader 变更），数据面读写存活，因为 Broker 各自持有完整元数据日志副本影响的是路由发现：客户端已缓存的路由仍可用，新建主题与队列扩容拿不到新信息，客户端长期不刷新则新客户端无法取路由
谁做故障转移决策Controller Leader（RAFT 选出）Controller 模式，NameServer 不参与

故障行为的差异要精确表述，不能含糊成「差不多」： Kafka 的 Controller 全挂时，集群不是完全不可用，而是从「自愈」降级为「按最后一次已知元数据继续服务数据面」，动态能力失效但已有数据面存活；RocketMQ 的 NameServer 不可用时，受影响的是路由发现这条链路，存量路由在客户端缓存里仍可继续用，但任何依赖新路由的操作（新建主题、队列扩容、路由变更下发）拿不到结果，新上线的客户端在缓存为空时无法取到路由。前者的失效面集中在「变更类操作」，后者的失效面集中在「路由获取」，这是两套设计各自的取舍结果。

旧版做法

当前做法：RocketMQ 5.x 由 Controller 模式接管选主与角色下发，Broker DLedger 模式已在 5.x 官方 release notes 中标注为 legacy（deprecated，见 PR #10642）。5.x 新建集群应直接采用 Controller 模式。 旧版做法：Broker DLedger 模式把多数派写的一致性协议内嵌进 Broker 进程本身，由 Broker 之间互相投票决定谁是主，Master 与 Slave 通过多数派写入互相确认。 两者差别：DLedger 把一致性协议塞进数据面进程，选主与写入耦合在一起，代价是 Broker 进程要承担共识开销，运维复杂度与资源成本都更高；Controller 模式把「谁是主」交给独立的协调者，Broker 只按指令切换角色。此机制为旧版，新版由 RocketMQ 5.x Controller 模式替代。 本 callout 仅用于维护存量 4.x 集群时对照，新版设计请以正文各节为准。

旧版做法

当前做法：5.x 集群的主从切换由 Controller 模式接管选主与切换，故障检测、选主决策与角色下发都由 Controller 完成。 旧版做法：传统 Master-Slave 部署（没有 Controller 的那一档）里，Master 故障后的切换依赖外部手段：人工介入或运维脚本把某个 Slave 提升为 Master，再手工修正配置与注册信息。 两者差别：传统方式没有常驻的选主决策者，切换是「事件驱动的人工动作」，切换时长取决于人的响应速度，且在多组主从的场景下容易漏切或误切；Controller 模式把切换变成由协调者按状态自动触发的动作。此机制为旧版，新版由 Controller 模式接管选主与切换替代。

旧版做法

当前做法：5.x 由 Proxy 层的 Tag 与 SQL92 过滤链承担消息过滤，Proxy 作为统一接入层完成订阅匹配后把消息投递给客户端。 旧版做法：FilterServer 作为 Broker 侧的过滤进程，客户端把过滤表达式下发给 Broker，由 FilterServer 承接过滤后返回结果。 两者差别：FilterServer 的过滤发生在 Broker 侧，需要客户端能把过滤逻辑表达给 Broker；Proxy 过滤链把过滤放在接入层统一完成，与存储层解耦，也更贴合 5.x 的 Proxy + gRPC 接入形态。此机制为旧版，新版由 5.x Proxy + Tag/SQL92 过滤链替代。 本 callout 仅用于理解存量 4.x 部署的架构图。

面试追问

  1. RocketMQ 5.x 还推荐用 DLedger 做高可用吗？ —— 不推荐。官方 5.x release notes 已把 Broker DLedger 模式标注为 legacy（deprecated，PR #10642），当前主线是 Proxy + gRPC + Controller 模式。存量 4.x 集群可继续维护，但新部署不应再选它。
  2. NameServer 无状态、不引入共识算法，那路由怎么保证不丢？ —— 靠的是最终的可用性而非强一致：两台 NameServer 互备，Broker 周期性注册，客户端周期性拉取并本地缓存。代价是路由是最终一致，切换窗口内客户端可能短暂持有旧路由。
  3. Kafka 和 RocketMQ 的协调层最大的差别是什么？ —— Kafka 用内置 RAFT 共识日志（Controller Quorum）达成元数据强一致；RocketMQ 的 NameServer 无状态、无共识、只最终一致。由此 Kafka 的控制面失效表现为「动态能力失效但数据面存活」，RocketMQ 的 NameServer 失效表现为「路由发现受影响」。
  4. 为什么 NameServer 不引入共识算法是合理的设计？ —— 代价换来的是极简的部署与极低的资源开销，路由信息的可容忍延迟窗口通常远大于业务对元数据一致性的要求。前提是 Broker 与客户端都必须能容忍一段时间的路由滞后，并且客户端有本地缓存兜底。这是基于官方架构文档口径的解读，官方未直接给出该取舍的理由，展开这一层建议标注为「需实操验证」。

七、三种高可用方案对比

这是本篇的收口表。 三个方案的差别不在「能不能用」，而在把一致性成本放在哪一层。

维度传统主从（无 Controller）Broker DLedger 模式（4.x）Controller 模式（5.x 主线）
谁决定谁是主人工或外部脚本Broker 之间的多数派投票独立的 Controller
RPO 特征取决于复制与刷盘方式，异步转发时滞后窗口明显多数派写入，滞后窗口被收窄；进程崩溃仍受刷盘方式约束取决于复制与刷盘方式；切换由协调者驱动，不因选主不确定而放大
RTO 特征切换耗时取决于人的响应，最不可控无外部协调者，切换自动完成；但需等多数派形成检测、选主、新主就绪、路由更新、客户端感知五段之和，可逐段优化
运维复杂度简单，但要人工兜底切换与配置修正较高，Broker 进程内嵌共识协议，排查链路长需额外维护 Controller 实例，但切换路径统一

基线对照：单主无副本。它是所有方案的起点：RPO 等于故障瞬间丢失的量（没有第二份数据），RTO 取决于重启或重建的速度，成本最低但没有任何冗余。任何高可用方案都是在单主基线上，用写入延迟、硬件成本与运维复杂度换 RPO 与 RTO。

与 Kafka 4.x 的对照必须单列一句，因为它决定了两套系统的故障面貌： Kafka 4.x 靠 KRaft 内置的 RAFT 共识日志（Controller Quorum）拿到元数据强一致，Broker 各自持有完整元数据日志副本，所以 Controller 全挂时集群退化为「按最后一次已知元数据继续服务数据面」——动态能力（新建、扩分区、副本重分配、Leader 变更）失效，但已有数据的读写与位点提交存活。RocketMQ 的 NameServer 无状态、不引入共识算法、路由最终一致，所以 NameServer 不可用时受影响的是路由发现——客户端已缓存的路由仍可继续用，依赖新路由的操作（新建主题、队列扩容、路由变更下发）拿不到结果，缓存为空的新客户端则无法取到路由。一句话记法：Kafka 的控制面缺失伤在「变更」，RocketMQ 的 NameServer 缺失伤在「发现」。

面试追问

  1. 三种方案该怎么选？ —— 只在 5.x 上新建就用 Controller 模式，没有选择余地。真正的问题是在 Controller 模式内把 RPO 与 RTO 调到多少，以及为此接受多少写入延迟。
  2. DLedger 看起来更强，为什么还是被弃用？ —— 它的多数派写入确实收窄了滞后窗口，代价是把共识协议塞进数据面进程，Broker 更重、排查链路更长、运维成本更高。5.x 选择了把协调职责外置到独立的 Controller。
  3. 说清 Kafka 与 RocketMQ 协调层的不对称。 —— Kafka 4.x 用内置 RAFT 共识日志实现元数据强一致，Controller 中断时数据面存活、动态能力失效；RocketMQ 的 NameServer 无状态、无共识、路由最终一致，中断时影响的是路由发现，存量路由可用但拿不到新路由。
  4. 传统主从真的不能用于 5.x 吗？ —— 本文只写语义不给阈值：默认阈值随版本变化，以你所用版本的官方文档为准。 架构上 5.x 的高可用设计以 Controller 模式为前提，传统主从属于存量形态，仅在维护存量集群时对照使用。

八、面试高频追问

面试追问

  1. RocketMQ 和 Kafka 的高可用，核心差别用一句话怎么说？ —— RocketMQ 把一致性留在数据面（主从复制与刷盘），元数据交给无状态、无共识、最终一致的 NameServer；Kafka 把一致性做进元数据面（KRaft 内置 RAFT 共识日志），数据面只认分区 Leader。
  2. NameServer 挂了 RocketMQ 集群还能用吗？ —— 能，但退化。要区分两层：客户端已缓存的路由继续支撑存量读写；依赖新路由的操作（新建主题、队列扩容、路由变更）拿不到结果，缓存为空的新客户端无法取路由。受影响的是路由发现，不是数据本身。
  3. 说清 RPO 与 RTO 各由什么决定。 —— RPO 由刷盘方式（主节点进程崩溃）与复制方式（主节点整机故障）分别决定；RTO 由故障检测、选主、新主就绪、路由更新、客户端感知五段之和决定，其中客户端路由拉取周期经常是最大的一段。
  4. 开从读有什么代价？ —— 稳态下读到的是从节点数据，属弱一致读；切换窗口内客户端缓存滞后会让一部分读短暂失败。收益是分摊主节点读压力并提供一条不依赖主节点的读路径。
  5. 5.x 部署时最常见的配置坑是什么？ —— brokerIP1 在多网卡 / 容器 / NAT 环境下自报地址客户端不可达，症状是发送超时而非找不到路由。

答题骨架

  1. 先立对照：Kafka 4.x 元数据强一致（KRaft 内置 RAFT 共识日志 / Controller Quorum），RocketMQ NameServer 无状态、无共识、路由最终一致。
  2. 再拆两个开关：复制方式与刷盘方式正交，分别回答，不要合说。
  3. 再给能力边界：故障转移由 Controller 决策，NameServer 只提供路由；RTO 是五段之和，客户端感知常占最大头。
  4. 最后给代价：收紧复制与刷盘推高延迟并让从节点进入主链路；开启从读换稳态冗余、代价是弱一致与切换窗口抖动。
  5. 收尾提旧版：DLedger 与传统主从均为 legacy，FilterServer 已由 Proxy 过滤链替代，涉及存量集群时对照使用。
